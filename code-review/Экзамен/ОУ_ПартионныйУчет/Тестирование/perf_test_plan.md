# План тестирования производительности проведения расходной накладной

## Гипотеза

В `ВыполнитьПроведениеРасхода` для **каждой** строки ТЧ вызываются:
1. `ОбщегоНазначенияТипНоменклатуры` — отдельный запрос к справочнику;
2. `ПодобратьПартииКСписанию` → `ПолучитьОстаткиПартий` — отдельный запрос остатков РН.

При N строках ТЧ получается порядка **2N запросов** вместо 1–2 пакетных. Ожидание: время проведения растет почти линейно с N.

## Цели

1. Замерить время проведения РН при N = 50 / 100 / 200 / 500 (уникальная номенклатура в строке).
2. Переписать алгоритм: один запрос типов + один запрос остатков на документ, списание в памяти.
3. Повторить замеры на тех же N; целевое ускорение — **не менее 3–5x** на N ≥ 200.
4. Проверить корректность: FIFO/LIFO/средняя и недостача (короткий регресс после оптимизации).

## Сценарий замера

| Шаг | Действие | Учитывается в таймере |
|-----|----------|------------------------|
| 1 | Создать склад, контрагентов, N товаров | Нет |
| 2 | Учетная политика FIFO | Нет |
| 3 | Одна приходная накладная: N строк по 10 шт × 100 | Нет (подготовка остатков) |
| 4 | Одна расходная: N строк по 1 шт × 300 | **Да — только `Записать(Проведение)`** |
| 5 | Повторить шаг 4 три раза на свежих остатках (или среднее по 3 прогонам с переподготовкой) | Да |

Метрики: `duration_ms`, `ms_per_line`, `rows`, `version` (`before` / `after`).

## Критерии приемки

- Автозамер `before` и `after` сохранены в HTML/JSON.
- На N=500: `after` существенно быстрее `before` (ориентир ≥ 5x).
- Регресс сценариев FIFO/средняя/LIFO/недостача — без FAIL.
