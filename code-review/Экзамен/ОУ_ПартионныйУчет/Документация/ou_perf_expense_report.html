Замеры скорости: расходная накладная с большой ТЧ

Дата: 13.09.2026 · ИБ OU_Training · Admin · таймер только на Записать(Проведение) расходной

1. План и гипотеза

Гипотеза: в исходном коде на каждую строку ТЧ выполнялись отдельные запросы типа номенклатуры и остатков партий (~2N запросов). При росте N время проведения растет линейно.

План: baseline (before) → пакетный алгоритм (after) → повторный замер → регресс FIFO/LIFO/средняя/недостача.

Детали: файл perf_test_plan.md, скрипт test_ou_perf_expense.py.

2. Что изменено в коде

  • Один пакетный запрос типов номенклатуры на документ.
  • Один пакетный запрос остатков по всем товарам накладной.
  • Списание FIFO/LIFO/средняя в памяти с уменьшением локальных остатков между строками.
  • Предпроверка доступного количества до изменения остатков (корректная недостача).

3. Результаты замеров

N строк ТЧ Before, avg ms After, avg ms Before ms/строка After ms/строка Ускорение
50 65.45 22.88 1.309 0.458 ×2.9
100 132.50 45.51 1.325 0.455 ×2.9
200 277.44 75.52 1.387 0.378 ×3.7
500 779.90 177.90 1.560 0.356 ×4.4
На N=500 проведение ускорено примерно в 4.4 раза (780 ms → 178 ms). Линейный рост ms/строка снизился с ~1.5 до ~0.36.

4. Корректность

Регресс test_ou_batch_scenarios.py: 23 / 23 PASS (FIFO=500, средняя≈1000, LIFO=1000, недостача блокирует, услуги без склада).

5. Выводы

  1. Гипотеза подтверждена: время before почти пропорционально N.
  2. Пакетное чтение остатков и типов убирает доминирующую стоимость запросов в цикле.
  3. Ускорение растет с N (от ×2.9 на 50 строках до ×4.4 на 500).
  4. Функциональное поведение сохранено по эталонным сценариям.
  5. Дальнейший резерв: пакетное создание партий на приходе (сейчас каждая партия пишется отдельно) — вне текущего замера расхода.
Сырые отчеты: perf_expense_before_*.html/json, perf_expense_after_*.html/json в каталоге отчетов тестирования.
