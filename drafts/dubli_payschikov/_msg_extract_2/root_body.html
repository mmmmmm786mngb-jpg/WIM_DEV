Анастасия, коллеги, добрый день.

По дублям пайщиков после августовского релиза и двух недавних выплат инвестдохода сделали дедуктивный разбор возможных причин: смотрели логику обработки, состав августовских задач и то, как это стыкуется с описанием со стороны Finance. Это не заключение по конкретной сентябрьской выплате и не подтвержденный корневой дефект. Ниже - рабочие гипотезы, которые нужно проверить на 1-2 свежих примерах.

Система: Аванкор ПИФ (учет пайщиков ЗПИФ, списки номинальных держателей, начисление инвестдохода и НДФЛ).

1. Что наблюдаем (как описывает бизнес)

Один и тот же человек в справочнике пайщиков оказывается двумя разными карточками. Налог и выплата считаются по карточке, а не "по человеку". Поэтому доход и НДФЛ могут разъехаться, налог приходится считать вручную, в регуляторной отчетности возможны искажения.

По письмам Finance дубли, похоже, не только "лежат" в справочнике: они могут появляться снова при новой начитке списка от номинального держателя (перед выплатой), даже если предыдущие уже объединяли. Именно это мы пытаемся объяснить гипотезами ниже.

2. Где дубль потенциально может появиться

Перед выплатой BSS загружает файл списка конечных владельцев от номинального держателя (типовой файл НРД вида EntitledReceiveIncomeRersons+MainData.xls) обработкой "Заполнение списка владельцев номинального держателя". Дальше из этого списка заполняется документ списка владельцев и начисление дохода пайщикам.

По коду обработки для каждой строки файла система должна решить: это уже наш пайщик или новый. Потенциально новая карточка появляется, если поиск не нашел существующую. Схематично цепочка такая:

Шаг

Как система, судя по коду, может искать

1

Сначала по постоянному коду НРД (НРД id, вида 01_21612345678) - то, что добавляли в августе. Если кода нет на карточке или он не пришел из файла, этот шаг, скорее всего, ничего не даст.

2

Если по коду НРД не нашла - может искать по ФИО и дате рождения. Паспорт в этом запасном поиске, судя по коду, почти не участвует.

3

Если не нашла ни так, ни так - может создать новую карточку пайщика (создание при начитке, по коду, включено по умолчанию).

3. Почему склейка, гипотетически, может не спасать на следующей выплате

Рабочая гипотеза: августовский релиз помогает только если на старой карточке уже записан НРД id.

Если кода на старой карточке нет, а в файле НРД у человека уже другая фамилия, другой паспорт или "съехавшее" ФИО из-за лишнего пробела - система может счесть его новым и создать вторую карточку. После ручной склейки код НРД может остаться не на той карточке, которую оставляют "правильной". Тогда на следующей выплате картина, описанная Finance, воспроизводится снова. Это правдоподобное объяснение, не доказанный кейс конкретной выплаты.

Возможные ситуации, когда шаг 1 и шаг 2 могли бы не сработать:

·        у ранее созданной карточки так и не появился НРД id;

·        клиент сменил фамилию и/или паспорт, а запасной поиск узнает его только по точному ФИО;

·        в файле НРД лишний пробел в ФИО - система может собрать другое полное имя и не найти существующую карточку (исторический кейс "Усова": повторная начитка того же файла создавала еще одну карточку);

·        файл начитан не тем форматом: по коду обработки код НРД подхватывается только в форматах "Гарант Excel" и "ЦДФ". В XML и в "новом" Гарант Excel колонка с кодом НРД в поиск, похоже, не идет.

Какой из пунктов сработал на сентябрьских выплатах - по переписке и коду однозначно не видно. Нужны примеры.

Ниже - потенциальные точки отказа по текущей версии обработки и связанных объектов. Без свежей пары "карточки + строка файла + формат" это только карта гипотез для ТЗ.

Контур. Аванкор ПИФ, не ДУ и не Аванкор Фин. Наиболее вероятная точка создания дубля - доп. обработка заполнения списка номинального держателя (синоним "Заполнение списка владельцев номинального держателя", версия 1.12, в прод 19.08). Документ "Начисление дохода пайщикам", судя по коду, карточки не создает: забирает уже подобранных контрагентов и с августа протягивает НРДid в ТЧ, регистр "Начисленный доход пайщикам" и печатный акт.

Объекты. Обработка пишет в документ "Список владельцев номинального держателя и доверительного управляющего" (ТЧ "Владельцы", реквизит НРДid) и при проведении - в РС "Владельцы номинальных держателей паев". На карточке контрагента код, по коду, хранится не в реквизите справочника, а в РС "Значения свойств объектов", свойство ПВХ "НРД id клиента" (поиск по наименованию, точное соответствие). Если свойства в базе нет или имя другое - весь контур НРД-ключа потенциально мертвый.

Маршруты начитки (команда "Прочитать") - гипотеза по коду, какой формат реально жмут на выплатах, не проверяли:

·        ФорматГарант = 0 - ПрочитатьФайлГарантExcel, НРДid из колонки 19, в поиск и в создание передается;

·        = 2 - ПрочитатьФайлЦДФ, НРДid из колонки 3, передается;

·        = 1 - XML ПрочитатьФайл, НРДid не передается;

·        = 3 - ПрочитатьФайлГарантExcelNEW, колонка 19 занята "данными регистрации", в ПолучитьКонтрагент / СоздатьКонтрагента id не идет.

Поиск - ПолучитьКонтрагент (как написано в модуле, не как факт сентябрьской выплаты):

1.      ПолучитьКонтрагентаПоНРДid без отбора по пометке удаления;

2.      если пусто - запрос: точное равенство Наименование или НаименованиеПолное нормализованному ФИО плюс дата рождения (номер паспорта только если ДР пустая). INNER JOIN на ПаспортныеДанныеФизЛиц.СрезПервых. Регистр ФИОФизЛиц не используется. Поиск по серии+номеру паспорта закомментирован;

3.      если нашли и свойство НРД пустое - ЗаписатьНРДid (существующий id, по коду, не перезаписывают);

4.      если несколько по ФИО - разбор через лицевой счет номинала по фонду, иначе "РучнойВыбор";

5.      если пустая ссылка и флаг создания (по умолчанию Истина) - СоздатьКонтрагента с ОбменДанными.Загрузка = Истина (проверка дублей при записи справочника обходится).

Разбор ФИО - возможный дефект ВыделитьСлово: СокрЛ делается во временном буфере, а остаток строки режется от исходной. Лишний пробел в начале или несколько пробелов между словами может сдвинуть имя/отчество. Тогда нормализованное ФИО для поиска и НаименованиеПолное новой карточки станут другими, старая карточка не найдется. Исторический кейс IMDEV-8578 / IMAPPS-36530 ("Усова") этим правдоподобно объясняется; правка пробелов в серии/номере паспорта РФ (тип 21) на этот сдвиг ФИО не влияет. Сохраняется ли этот сдвиг в сентябрьских файлах - не проверяли.

·        чинить ВыделитьСлово: остаток брать из уже обрезанного буфера, ФИО нормализовать до поиска и до записи;

·        не вызывать поиск/создание по НРД, пока id из файла не заполнен; во всех форматах, где колонка id есть, передавать его в ПолучитьКонтрагент;

·        запасной ключ после НРД: серия+номер ДУЛ (раскомментировать и нормализовать пробелы), не только ФИО+ДР;

·        при склейке переносить свойство "НРД id клиента" на оставляемую карточку - иначе релиз 7579 на исторических дублях может не сработать;

·        отдельно решить, нужен ли массовый прогон: проставить НРД id на существующие карточки по последним спискам номинала, без создания новых.
