Ниже - как обработка сейчас ищет клиента при начитке (по коду, не "как кажется"), и почему по паре Гнездилова / Дорогокупец вторая карточка создалась. Пока только эти две карточки.

1. Порядок поиска - как в коде сейчас

На каждую строку файла обработка спрашивает: этого человека мы уже знаем? Адрес, паспорт и номер счета спецдепозитария в этом решении почти не участвуют (оговорки ниже). Желтым - путь этой пары.

Старт. Из файла Гарант Excel: ФИО, дата рождения, паспорт, адрес, код НРД. Номер лицевого счета в этом файле пустой у всех строк; обработка его из Excel не берет.
+-- Вопрос 1. Есть ли уже карточка с таким же кодом НРД, как в строке файла?
|-- Да -> это старый клиент. Подставляем карточку. Дальше не ищем. Паспорт и ФИО уже не смотрим.
+-- Нет -> идем дальше.
В этой паре: на старой карточке код НРД есть, но другой. Для системы это "не нашли".
+-- Вопрос 2. Есть ли карточка с точно таким же полным ФИО (фамилия + имя + отчество, буква в букву) и той же датой рождения?
Паспорт здесь не сравнивают, если дата рождения заполнена и в файле, и на карточке. Отдельный поиск по серии и номеру паспорта в коде закомментирован - он не работает.
|-- Да -> это старый клиент. Подставляем карточку. Конец.
+-- Нет -> идем дальше.
В этой паре: имя, отчество и дата рождения те же, фамилия уже другая. Полное ФИО не совпало.
+-- Вопрос 3. Включено "Создавать контрагентов при начитке"?
|-- Да -> это новый клиент. Создаем карточку, пишем на нее ФИО, паспорт, адрес и код НРД из файла.
Эта пара дошла сюда.
+-- Нет -> карточку не создаем, строка остается без контрагента (или ручной выбор).

2. Почему обработка не узнала Дорогокупец как Гнездилову

В файле начитки фамилии Гнездилова нет. Есть строка с новой фамилией, новым паспортом и новым кодом НРД. Старая карточка в этот момент уже живет в базе со старой фамилией, старым паспортом и другим кодом НРД.

  • Вопрос 1. Код НРД из файла на старой карточке не стоит. На старой - свой, на новой строке - другой. Поиск по коду пустой. Августовский релиз как раз на этот шаг и рассчитывал, но он спасает только если код НРД тот же.
  • Вопрос 2. Полное ФИО должно совпасть целиком. Имя, отчество и дата рождения те же, фамилия уже другая - для системы это другой человек. Паспорт тут не помогает: при заполненной дате рождения его не сравнивают. Даже если бы сравнивали - в файле паспорт уже новый, на старой карточке старый.
  • Вопрос 3. Создание включено -> заводится карточка Дорогокупец с данными из файла.

Коротко: система не "ошиблась в адресе" и не "не увидела паспорт". Она отработала ровно свой алгоритм. Человека после смены фамилии и смены кода НРД этот алгоритм не склеивает.

3. Адрес: файл и скрины карточек

Адрес совпал.

  • в Excel (и юридический, и почтовый - одна и та же строка): Пермь, ул. Николая Островского, тот же дом и квартира;
  • на карточке Дорогокупец (вкладка "Контакты"): тот же адрес, и как фактический, и как адрес регистрации;
  • на карточке Гнездилова: тот же адрес, буква в букву, включая индекс и формат строки.

То есть по адресу это выглядит как один человек. Но в поиске адрес сейчас не используется: его читают из файла и записывают на новую карточку, если ее создали. Старую по адресу не ищут.

Номер счета на вкладке "Лицевые счета пайщика в спец.регистраторе" на обеих карточках тоже один. Это не личный номер из файла: в Excel колонка счета пустая, обработка копирует на технический счет код лицевого счета номинального держателя с шапки формы. Таким номером будут все пайщики этой начитки, по нему человека не отличить.

4. Что можно добавить, не ломая текущее дерево

Вопросы 1 и 2 оставляем как есть. После "полное ФИО не совпало" можно добавить запасную ветку:

Вопрос 2а (сейчас ее нет). Полное ФИО + дата рождения не сошлись, но совпали сразу четыре:
имя + отчество + дата рождения + адрес.
Фамилию здесь не требуем. Если нашли одну карточку - это старый клиент, новую не создаем, новый код НРД из файла дописываем, старый не затираем.

На этой паре ветка сработала бы: имя, отчество, дата рождения и адрес совпали, фамилия и паспорт - нет.

Оговорки, чтобы не склеить чужих:

  • если по четырем полям нашлось несколько карточек - не угадывать, а в ручной выбор / лог, как сейчас при нескольких полных ФИО;
  • адрес сравнивать не "на глаз", а после нормализации (пробелы, запятые, "г" / "г."), иначе при чуть другом написании из НРД ветка снова промахнется;
  • номер спецдепозитария из этого файла в ключ не ставить: его в строке нет, а номер на карточке общий на весь список номинала.

Задачу на доработку пока не открываем как закрытый диагноз по всем дублям. По этой паре цепочка уже собирается: новая анкета + новый код НРД, а запасного ключа без фамилии нет.

ПолучитьКонтрагент, формат Гарант Excel. Шаг 1: ПолучитьКонтрагентаПоНРДid по ПВХ "НРД id клиента". Шаг 2: запрос Наименование / НаименованиеПолное = нормализованное ФИО И дата рождения. Номер ДУЛ в этом запросе сравнивается только если ДР пустая в файле или на карточке. Серия в живой запрос не ставится. Поиск по серии+номеру закомментирован. INNER JOIN на ПаспортныеДанныеФизЛиц.СрезПервых - без записи паспорта карточка в выборку шага 2 не попадет, но это не сверка номера. Адрес в поиске нет.

Файл: фамилии Гнездилова нет. Строка новой фамилии, новый ДУЛ, новый НРД id. Старая карточка: другое ФИО, другой ДУЛ, другой НРД id, та же ДР. Адрес на обеих карточках и в col 5/8 Excel - одна строка. СоздатьЛицевойСчет копирует ЛицевойСчет.Код с шапки формы, не из файла.

Для ТЗ дерево не переписывать. После пустого ФИО+ДР: имя + отчество + ДР + представление адреса (после нормализации). Нашли одну - старый клиент, новый НРД id дописать. Нашли несколько - как сейчас, ручной выбор. Номер ЛС номинала и ДУЛ в ключ не ставить.
