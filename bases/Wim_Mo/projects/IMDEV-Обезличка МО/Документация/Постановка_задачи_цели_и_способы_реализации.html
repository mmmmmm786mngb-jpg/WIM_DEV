1. Контекст и бизнес-проблема

Для передачи копии базы МО внешнему разработчику требуется обезличить персональные и иные чувствительные данные: наименования контрагентов и фондов, идентификаторы (ИНН/ОГРН/КПП/TIN/ОКПО/ОКАТО), контактную информацию, номера счетов (банковские, депо, брокерские) и наименования мандатов. При этом нужно сохранить ссылочную целостность, чтобы подрядчик мог корректно работать с конфигурацией.

Ранее обезличивание делалось разными скриптами и доработками — без единой документированной точки запуска и формализованных правил. По переписке с бизнесом зафиксированы критические замечания (см. 1.1 ниже), которые повлияли на состав логики текущей реализации.

Главная боль: отсутствует повторяемый, проверяемый процесс обезличивания, привязанный к актуальной структуре данных, с прозрачным журналом действий и материалами для приемки бизнесом и ИБ.

1.1 История замечаний и доработок (по переписке)

  • Мандаты: вместо случайной нумерации требуется использовать префикс договора ДУ, если он заполнен.
  • Банковские счета: маскировать номер недостаточно — нужна замена всех цифровых групп в наименовании.
  • Фонды: требуется обезличивание наименований фондов в справочнике контрагентов.
  • Запуск: вместо нескольких ручных шагов в форме нужна одна кнопка Обезличить.
  • Регистр версий объектов: очищать после успешного обезличивания, иначе исходные значения остаются в истории.

Все пункты учтены в фактической реализации (см. раздел 8).

2. Цели и измеримые результаты

Бизнес-цель
Передать копию базы вендору без раскрытия персональных данных
ИБ-цель
Снизить риск утечки до уровня приемлемого для внешнего подряда
ИТ-цель
Один запуск без ручных под-этапов, фоновое выполнение, прогресс, журнал
Контроль
Снимок «до», карта мандатов, журнал Obezl, чек-листы

2.1 Что считается достижением цели

  1. После выполнения обработка возвращает структуру итога Успешно/ЧастичныйУспех/ТекстДиагностики/ДеталиЭтапов.
  2. В целевых полях не остается исходных значений (ИНН, телефоны, email, номера счетов, исходные наименования мандатов).
  3. Ссылочная целостность не нарушена (предопределенные элементы не меняются, ссылки между объектами сохраняются).
  4. Регистр ВерсииОбъектов очищен — нет «утечки» через историю версий.
  5. Бизнес-валидатор по выборочной проверке подтверждает корректность.

3.2 Что не входит в область

  • Документы (движения, табличные части) — не изменяются.
  • Предопределенные элементы любых справочников — не изменяются.
  • Регистры, кроме ВерсииОбъектов — не изменяются.
  • Пользователи ИБ, пароли, права — вне области (управляется отдельно при передаче копии).

3.3 Допущения

  • Обработка запускается только на копии базы. Запуск на продуктиве недопустим.
  • Процесс необратимый для копии: восстановление исходных значений требует бэкапа.
  • Подразумевается актуальная конфигурация Wim_Mo. Часть полей читается с защитой через Попытка.
  • Решение работает в управляемом приложении (тонкий/толстый клиент, толстый клиент обычное приложение, внешнее соединение).

4. Международные практики и стандарты (обоснование подхода)

Применяемые в обработке приемы соответствуют общепринятым техникам анонимизации/псевдонимизации, которые описаны в международных и отраслевых стандартах. Ниже — какие именно техники где применены и почему.

Техника Описание Где применяется в Obezl Источник/практика
Masking (маскирование) Замена символов «значимыми константами» с сохранением длины и структуры (digit-preserving). МаскаЦифр: ИНН/ОГРН/КПП/TIN/ОКПО/ОКАТО → нули; номер брокерского счета; номер банковского счета. NIST SP 800-188, ISO/IEC 20889 («data masking»)
Pseudonymisation Замена идентификаторов псевдонимами, сохраняющими ссылочную целостность. Наименования контрагентов: Контрагент {UUID32}, Фонд {UUID32}; мандаты: Мандат {префикс} / Мандат NNNNN. GDPR Art. 4(5), ENISA «Pseudonymisation techniques and best practices»
Generalization / Suppression Замена точного значения на обобщенное либо удаление поля. Контактная информация: Страна/Регион/Город → Обезличено; ЗначенияПолей → пусто; Комментарий банковского счета → пусто. ISO/IEC 20889, HIPAA Safe Harbor (подход к идентифицирующим атрибутам)
Tokenization (deterministic per-record) Уникальный детерминированный токен, привязанный к объекту. UUID ссылки без дефисов как суффикс псевдонима; стабильно при повторных запусках для одной и той же ссылки. PCI DSS Tokenization Guidelines (как иллюстрация подхода)
Format-preserving substitution Сохранение длины и структуры строки при замене. Банковский счет: замена групп цифр в наименовании фрагментом той же длины из кода/UUID. ISO/IEC 20889 («format-preserving»), NIST SP 800-38G (FPE — концептуально)
Synthetic identifiers (safe domains) Использование заведомо «недостижимых» доменов и номеров. Email → example.invalid (RFC 2606 reserved); телефон → префикс +7999. RFC 2606 (.invalid, .example), GDPR-friendly synthetic data
Snapshot & audit trail Снимок «до» и журнал действий для аудита. Таблица СформироватьСнимокДоОбезличивания + журнал Obezl по UUID запуска. ISO/IEC 27001 A.12.4 (Logging), NIST SP 800-188 §6
Data minimization Не хранить и не передавать чувствительные данные сверх необходимого. После успеха — ОчиститьВерсииОбъектов и ОчиститьСлужебныеДанные (карта мандатов). GDPR Art. 5(1)(c), ISO/IEC 27701
Separation of duties (Test/Prod) Обезличивание только на копии; продуктив не затрагивается. Запуск выполняется на копии базы; путь к продуктивной базе не используется. ISO/IEC 27002 §8.31 (Separation of development, test and production)

4.1 Что специально не используется (и почему)

  • k-anonymity / l-diversity / t-closeness: для копии 1С с сохранением ссылочной целостности это избыточно и не покрывается стандартным языком запросов.
  • Differential privacy: не применима для функционального тестирования (искажает значения, которые подрядчик ожидает увидеть как реалистичные).
  • Шифрование/реверсивный токен: не предусмотрено — обезличивание необратимо для копии (data minimization).

5. Требования

5.1 Функциональные требования

  1. Один запуск. Обезличивание выполняется одной кнопкой Обезличить в форме обработки.
  2. Полный набор объектов. Обработаны контрагенты-клиенты и контрагенты-фонды, мандаты, счета мандатов, счета ДЕПО, брокерские и банковские счета.
  3. Мандаты по префиксу ДУ. При заполненном ПрефиксДоговораДУ наименование = Мандат + префикс (приоритет над картой).
  4. Карта мандатов. Если префикса нет, имя берется из заранее сформированной карты в формате Мандат NNNNN (5 цифр).
  5. Согласованность счетов мандатов. В одной фоновой пачке обрабатываются мандаты и их счета (старое имя мандата заменяется новым в наименовании счета).
  6. Банковские счета. Маска номера + очистка комментария + замена всех цифровых групп в наименовании фрагментом той же длины.
  7. Снимок «до». Перед обезличиванием формируется таблица значений с исходными полями и сохраняется во временное хранилище.
  8. Очистка регистра версий. После успешного завершения этапов 1–5 регистр ВерсииОбъектов полностью очищается.
  9. Журнал. Все этапы и ошибки пишутся в журнал регистрации с событием Obezl и идентификатором запуска (UUID).

5.2 Нефункциональные требования

  • Производительность: параллельные фоновые пачки (до 8 потоков, ориентир ~1000 элементов на пачку).
  • UX: прогресс по этапам и пачкам через ДлительныеОперации.СообщитьПрогресс.
  • Отмена: отмена родительского задания корректно отменяет активные фоновые пачки.
  • Отказоустойчивость: ошибка одной пачки помечает результат как ЧастичныйУспех, остальные пачки продолжают работать.
  • Совместимость: модули работают в директивах #Если Сервер Или ТолстыйКлиентОбычноеПриложение Или ВнешнееСоединение Тогда.
  • Идемпотентность: повторный запуск не восстанавливает исходные значения, но и не делает данные «хуже» (повторное обезличивание уже обезличенного объекта дает тот же результат для контрагентов/мандатов; банковские счета — с учетом маски).
  • Защита от падений: чтение «опциональных» полей через Попытка при несовпадении конфигурации.

6.1 Состав расширения

  • Расширение: Obezl.
  • Обработка: DataProcessor.Obezl_Запуск, синоним: «Obezl Запуск обезличивания».
  • Форма: единственная форма обработки с кнопкой Обезличить.

7. Оркестратор и этапы обезличивания

7.1 Последовательность работы оркестратора

  1. Генерируется ИдентификаторЗапуска = UUID и запись в журнал [UUID][Старт].
  2. Создается экземпляр Обработки.Obezl_Запуск.Создать().
  3. Формируется снимок «до»: СформироватьСнимокДоОбезличивания → ПоместитьВоВременноеХранилище.
  4. Формируется карта мандатов: СформироватьКартуМандатов (детально см. раздел 9).
  5. Последовательно выполняются 5 этапов: Контрагенты, МандатыИСчета, СчетаДЕПО, БрокерскиеСчета, БанковскиеСчета.
  6. При успехе — ОчиститьВерсииОбъектов, затем ОчиститьСлужебныеДанные.
  7. В АдресРезультата помещается структура итога; журнал [UUID][Финиш].

7.2 Этапы (5 шагов прогресса)

8. Правила обезличивания по объектам

8.1 Справочник.Контрагенты

Отбор: клиенты (Клиент = Истина) + фонды (Фонд = Истина И Не Клиент), кроме предопределенных.

Идентификаторы (МаскаЦифр): ИНН, ОГРН, КПП, TIN, ОКПО, ОКАТО — каждая цифра 0-9 заменяется на «0», длина сохраняется.

Наименование: {Префикс} {UUID32}, где {Префикс} = Фонд (для фондов-не-клиентов) или Контрагент, {UUID32} = GUID ссылки без дефисов (32 шестнадцатеричных символа).

Английские наименования: Counterparty {UUID32}.

Контактная информация: обход всех реквизитов ТЧ КонтактнаяИнформация по метаданным; обрабатываются только типы Строка и Число. Правила:

8.2 Справочник.Мандаты

  1. Если ПрефиксДоговораДУ заполнен → Наименование = "Мандат " + Префикс.
  2. Иначе — из КартаМандатов по ключу Строка(Ссылка.УникальныйИдентификатор()) берется НовоеНаименование формата Мандат NNNNN (5 цифр).
  3. Если префикса нет и ключ в карте отсутствует — мандат не записывается (защита от случайных изменений).
  4. Синхронизируются также НаименованиеПолное и ПолноеНаименование (через Попытка).

8.3 Справочник.СчетаМандатов

Обрабатывается в той же фоновой пачке, что и мандаты-владельцы.

  1. Основной алгоритм: в наименовании ищется подстрока — старое краткое имя мандата из карты — и заменяется на новое.
  2. Fallback: если замена не сработала, но в наименовании есть пара (…), текст в первой паре скобок заменяется на Обезличено_{UUID32}; закрывающая скобка сохраняется.
  3. Если нет ни замены, ни скобок — наименование оставляется как есть, запись не выполняется.

8.4 Справочник.СчетаДЕПО

В наименовании текст в первой паре (…) заменяется на Обезличено_{UUID32}. Префикс и хвост строки не меняются. Если скобок нет — наименование не меняется.

8.5 Справочник.БрокерскиеСчета

Маска номера: НомерБанковскогоСчета → МаскаЦифр (каждая цифра — 0). Запись выполняется при успехе присвоения.

8.6 Справочник.БанковскиеСчета

  1. НомерСчета → МаскаЦифр.
  2. Комментарий → пустая строка, если он был заполнен.
  3. В Наименовании каждая группа подряд идущих цифр заменяется фрагментом той же длины из подстановки:
    • База подстановки = СокрЛП(Код) элемента.
    • Если код пуст — используются цифры из GUID ссылки (символы a-f приводятся к 0-5, остальные нецифры — к 0).
    • Фрагмент строится циклическим повторением базы до нужной длины.
  4. Защита: если после маски НомерСчета состоит только из нулей, подставляется фрагмент подстановки той же длины (чтобы не получить «000…0»).

8.7 РегистрСведений.ВерсииОбъектов

НаборЗаписей.Прочитать() → Очистить() → Записать(). При ошибке (например, нехватка памяти на больших базах) запись в журнал Obezl с уровнем «Ошибка» и проброс исключения наверх.

9. Карта мандатов и снимок «до»

9.1 Карта мандатов

Соответствие в памяти модуля объекта КартаМандатов:

  • Ключ: Строка(Ссылка.УникальныйИдентификатор()) мандата.
  • Значение: структура СтароеНаименование + НовоеНаименование (Мандат NNNNN, 5 цифр).
  • Карта строится один раз в основном потоке до запуска параллельных этапов.
  • Передается в каждую фоновую пачку (сериализация структуры параметров через ЗначениеВСтрокуВнутр).
  • В пачке восстанавливается как локальная карта и присваивается переменной модуля.

11. Параллельность, прогресс, отмена

11.1 Разбиение на пачки

  • Функция РазбитьНаПачки в модуле менеджера.
  • Макс. число пачек — 8; целевой размер — ~1000 ссылок.
  • Фактическое число пачек = min(8, ceil(N / 1000)); остаток равномерно распределяется по первым пачкам.

11.2 Фоновое выполнение

  • Каждая пачка запускается через ДлительныеОперации.ЗапуститьВыполнениеВФоне.
  • Метод во фоне: ДлительныеОперации.ВыполнитьПроцедуруМодуляОбъектаОбработки с именем процедуры Obezl_ВыполнитьПачку.
  • Параметры пачки сериализуются в ПараметрыXML через ЗначениеВСтрокуВнутр и десериализуются в фоне.

11.3 Прогресс и отмена

  • Прогресс этапа = (НомерЭтапа - 1 + ДоляЗавершенныхПачек) * 100 / ВсегоЭтапов.
  • Сообщения прогресса: «Этап 2/5: МандатыИСчета. Пачек завершено: 3 из 8».
  • Отмена родительского задания обнаруживается через ПолучитьТекущийСеансИнформационнойБазы().ПолучитьФоновоеЗадание() и приводит к вызову ОтменитьАктивныеПачки.
  • В заголовке фоновой задачи указывается "Obezl ИмяЭтапа пачка N" — удобно для журнала и менеджера задач.
Гарантия согласованности: один и тот же элемент не обрабатывается в двух пачках одновременно — внутри этапа пачки не пересекаются по ссылкам. Для этапа МандатыИСчета счета мандата формируются по списку владельцев именно этой пачки.

12. Логирование, диагностика, идемпотентность

12.1 Журнал регистрации

  • Событие: Obezl.
  • Формат: [UUID-запуска][ИмяЭтапа] сообщение.
  • Уровни: Информация для прогресса и завершения; Ошибка для исключений в пачках и при очистке регистра.

12.2 Структура итога

Итог:
  Успешно                    : Булево
  ЧастичныйУспех             : Булево  // одна или несколько пачек завершились с ошибкой
  ТекстДиагностики           : Строка  // подробный текст ошибки оркестратора, если есть
  ДеталиЭтапов               : Соответствие { ИмяЭтапа -> ОбработаноЭлементов }
  АдресСнимкаДоОбезличивания : Строка  // адрес во временном хранилище

12.3 Принципы обработки ошибок

  • Попытка используется только там, где результат может быть «неизвестен» (доступ к опциональным полям, запись объекта, очистка регистра версий).
  • Ошибка одной пачки не останавливает остальные — оркестратор помечает результат как ЧастичныйУспех и продолжает.
  • При ЧастичныйУспех финальные шаги очистки (ОчиститьВерсииОбъектов, ОчиститьСлужебныеДанные) не выполняются.

12.4 Идемпотентность

Повторный запуск на уже обезличенной базе не восстанавливает исходные данные и не «портит» их дополнительно (наименования контрагентов и мандатов формируются от UUID/префикса и при повторе будут такими же; банковские счета — обновление при необходимости с сохранением длины групп цифр).

14. Критерии приемки и контроль

14.1 Критерии приемки

  1. Обработаны контрагенты-клиенты и контрагенты-фонды (отбор п. 8.1).
  2. Мандаты с ПрефиксДоговораДУ — Мандат {префикс}; остальные — Мандат NNNNN.
  3. Наименования счетов мандатов синхронизированы с новыми именами мандатов (в пределах одной пачки).
  4. Банковские счета: маска номера + пустой комментарий + в наименовании нет исходных длинных цифровых групп.
  5. Регистр ВерсииОбъектов пуст.
  6. Запуск с формы одной кнопкой Обезличить без ручных под-этапов.
  7. Предопределенные элементы справочников не изменены.
  8. Журнал Obezl по UUID запуска содержит запись Финиш с уровнем «Информация».

14.2 Чек-лист контрольных запросов

1) Контрагенты-клиенты и фонды:
   нет исходных ИНН/ОГРН/телефонов/email в согласованных полях и ТЧ КИ.

2) Мандаты с заполненным ПрефиксДоговораДУ:
   Наименование = "Мандат <префикс>".

3) Остальные мандаты:
   Наименование вида "Мандат NNNNN" (5 цифр, по карте).

4) Счета мандатов:
   В наименовании нет старого краткого имени мандата
   (или присутствует подстрока "Обезличено_" в первой паре скобок).

5) Банковские счета:
   - Номер замаскирован (только "0") либо синтетический по подстановке.
   - Комментарий пуст.
   - В наименовании нет исходных длинных цифровых групп.

6) Регистр ВерсииОбъектов:
   Количество записей = 0.

7) Журнал Obezl по UUID запуска:
   Есть записи "Старт" и "Финиш"; при ЧастичныйУспех — есть строки уровня "Ошибка".

14.3 Что делает бизнес при приемке

  • Открывает 10–20 случайных контрагентов (клиентов и фондов): проверяет наименования, ИНН, ТЧ КИ.
  • Открывает 10–20 мандатов: проверяет, что имена соответствуют правилу префикса или карте.
  • Открывает 5–10 счетов мандатов и счетов ДЕПО: убеждается, что в наименовании нет исходных «человекочитаемых» данных.
  • Открывает 5–10 банковских счетов: проверяет номер, комментарий и наименование.
  • Подтверждает приемку в переписке или в трекере задач.

15. Порядок выполнения работ

  1. Подготовка копии. Сделать резервную копию рабочей базы; восстановить как копию Wim_Mo для обезличивания.
  2. Загрузка расширения. Загрузить актуальную версию расширения Obezl в копию и обновить конфигурацию базы данных.
  3. Запуск. Открыть обработку Obezl Запуск обезличивания, нажать Обезличить. Дождаться завершения длительной операции.
  4. Контроль. Получить из временного хранилища снимок «до» (по адресу из результата), пройти чек-лист п. 14.2.
  5. Приемка. Бизнес проверяет выборку (п. 14.3), фиксирует подтверждение в проекте.
  6. Передача. Свернуть/выгрузить обезличенную копию и передать вендору.

15.1 Откат

Откат отдельных полей не предусмотрен. Если контроль выявил критическое несоответствие, восстановите копию из резервной копии и повторите запуск после исправления расширения.
