IMDEV-Обезличка МО: постановка задачи и техническое задание

Документ подготовлен как внутреннее ТЗ для бизнеса и разработчиков по процессу обезличивания базы МО для вендора.

Проект: bases/Wim_Mo/projects/IMDEV-Обезличка МО
Расширение: Obezl
Объект: DataProcessor Obezl_Запуск
Основание: переписка по приемке и замечаниям к качеству обезличивания.

1. Постановка задачи

1.1 Бизнес-цель

Обеспечить подготовку обезличенной копии базы МО для внешнего разработчика без раскрытия персональных и чувствительных данных, с возможностью контролируемого подтверждения результатов для бизнеса и ИТ-команды.

1.2 Проблема

Для повторяемого процесса обезличивания требуется единое формализованное ТЗ, которое фиксирует: происхождение решения, описание логики работы, правила обработки данных, критерии готовности и приемки.

1.3 Область покрытия обезличивания

  • Справочник Контрагенты (клиенты и фонды).
  • Справочник Мандаты.
  • Справочник СчетаМандатов.
  • Справочник СчетаДЕПО.
  • Справочник БрокерскиеСчета.
  • Справочник БанковскиеСчета.

1.4 Базовый сценарий использования

  1. Оператор запускает основной оркестратор обезличивания в обработке Obezl_Запуск.
  2. Система строит снимок исходных значений (до изменений).
  3. Система выполняет 5 этапов обезличивания в фоновых пачках с прогрессом.
  4. После завершения очищаются служебные данные и формируется результат выполнения.
  5. Результаты запуска подтверждаются бизнесом и фиксируются в рабочей документации проекта.

3. История происхождения и приемки

3.1 Контекст

Для внешней разработки была подготовлена обезличенная копия базы МО. По результатам первичной проверки бизнесом зафиксированы замечания к качеству обезличивания, после чего выполнены доработки.

3.2 Ключевые замечания и доработки

  • Мандаты: вместо случайной нумерации требуется формирование по префиксу договора ДУ (если заполнен).
  • Банковские счета: маскирование требуется не только в номере счета, но и в наименовании.
  • Фонды: добавлено обезличивание наименований фондов в контрагентах.

3.3 Итог приемки

По переписке с бизнесом подтверждено, что доработанный вариант можно принимать. Данный документ фиксирует итоговую постановку и ТЗ для последующих запусков и доработок.

4. Описание логики работы

4.1 Точка входа

Основной запуск выполняется процедурой Obezl_ОркестраторОбезличивания(Параметры, АдресРезультата) в Ext/ManagerModule.bsl. Процедура формирует идентификатор запуска, пишет события в журнал регистрации (Obezl), собирает сводный результат и управляет этапами обработки.

4.2 Общая последовательность

  1. Сформировать снимок значений до обезличивания.
  2. Сформировать карту мандатов (для согласованной замены наименований).
  3. Выполнить этапы обезличивания:
    1. Контрагенты (клиенты и фонды).
    2. Мандаты и связанные счета мандатов (в одной пачке на владельца).
    3. Счета ДЕПО.
    4. Брокерские счета.
    5. Банковские счета.
  4. Очистить служебные данные и регистр версий объектов.
  5. Записать итог выполнения в адрес временного хранилища.

4.3 Параллельное выполнение

Каждый этап делится на пачки (ограничение по числу потоков и размеру пачки) и запускается в фоне через механизм длительных операций. Поддерживается прогресс и отмена родительским заданием.

4.4 Правила обезличивания по объектам

Объект Основные правила
Контрагенты Маскирование ИНН/ОГРН/КПП/TIN/ОКПО/ОКАТО; замена наименований на псевдонимы с префиксом Контрагент или Фонд; обезличивание контактной информации и дополнительных реквизитов.
Мандаты Наименование формируется как Мандат + ПрефиксДоговораДУ при наличии префикса; иначе используется предрассчитанная карта наименований.
Счета мандатов Замена в наименовании по соответствию старого и нового имени мандата; fallback: обезличивание фрагмента в скобках с уникальным суффиксом.
Счета ДЕПО Обезличивание фрагмента в круглых скобках с уникальным токеном.
Брокерские счета Маскирование поля НомерБанковскогоСчета заменой цифр.
Банковские счета Маскирование НомерСчета; очистка комментария; замена всех групп цифр в наименовании на вычисляемую подстановку; защита от строки из одних нулей.

4.5 Ошибки и диагностика

  • Логирование выполняется через ЗаписьЖурналаРегистрации по событию Obezl.
  • По каждой пачке и этапу фиксируется результат, включая частичный успех и текст ошибки.
  • Исключения возвращаются в результирующей структуре для анализа в форме и в журналах.

5. Техническое задание на реализацию

5.1 Функциональные требования

  1. Обезличивание выполняется одним запуском основного оркестратора без ручного запуска отдельных шагов.
  2. Обязательна обработка клиентов и фондов в контрагентах.
  3. Для мандатов обязателен приоритет префикса договора ДУ.
  4. Для банковских счетов обязательна маскировка номера и всех цифровых групп в наименовании.
  5. Перед началом обезличивания формируется снимок исходных значений.
  6. Результат запуска содержит флаги успеха, детализацию этапов и диагностику.

5.2 Нефункциональные требования

  • Обработка должна поддерживать фоновые пачки и отображение прогресса.
  • При отмене родительского задания активные пачки должны отменяться корректно.
  • Изменения должны быть идемпотентными в части повторного запуска (без восстановления исходных данных).
  • Все критичные операции должны иметь запись в журнале регистрации.

5.3 Ограничения и допущения

  • Решение работает в рамках существующей конфигурации и структуры метаданных.
  • Часть полей обрабатывается через безопасный доступ, если поле отсутствует в конкретной конфигурации.
  • Подтверждение успешности обезличивания включает бизнес-валидацию, а не только технический запуск.

5.4 Критерии готовности

  1. Запуск завершен без критической ошибки и с заполненной структурой результата.
  2. Проверочные выборки показывают отсутствие исходных чувствительных значений в целевых объектах.
  3. Получено явное подтверждение от бизнеса о корректности результата.
  4. Актуализирована документация по запуску и изменениям в логике обезличивания.
