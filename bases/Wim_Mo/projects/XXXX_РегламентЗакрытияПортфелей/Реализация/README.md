# Параллельный запуск формирования регламентных операций

Файл `СформироватьРегламентныеОперацииПараллельно.bsl` содержит два блока кода,
готовых к копированию в разные места конфигурации `Wim_Mo`.

## Идея

Вместо последовательной обработки мандатов пачками по 5 (MID-153) — разбить
весь список мандатов на **K партиций**, где `K = Константы.МаксимальноеКоличествоПараллельныхПотоков`,
и запустить **K фоновых заданий параллельно**. Каждое задание последовательно
обрабатывает свою партицию через существующий диспетчер
`Справочники.РегламентныеПериоды.СформироватьДокументыЗакрытияПериода()`.

```
Мандаты:  [M1 M2 M3 M4 M5 M6 M7 M8 M9 M10 M11 M12]    K = 4

Round-robin:
  Партиция 0 → [M1 M5 M9]    → ФЗ #1
  Партиция 1 → [M2 M6 M10]   → ФЗ #2
  Партиция 2 → [M3 M7 M11]   → ФЗ #3
  Партиция 3 → [M4 M8 M12]   → ФЗ #4

ФоновыеЗадания.ОжидатьЗавершения(…) — общий барьер
```

## Структура файла

| Блок | Куда копировать |
|---|---|
| **[Блок 1]** — модуль формы | `SRC/CF/Catalogs/РегламентныеПериоды/Forms/РегламентныйПериод/Ext/Form/Module.bsl` |
| **[Блок 2]** — общий модуль | `SRC/CF/CommonModules/ФоновыеЗаданияСервер/Ext/Module.bsl` |

## Пошаговое внедрение

### 1. Завести константу `МаксимальноеКоличествоПараллельныхПотоков`

- Тип значения: `Число`, длина **3**, неотрицательное.
- Синоним: «Максимальное количество параллельных потоков».
- Подсистема: та же, где настройки закрытия периода.
- Рекомендуемое значение в промышленной эксплуатации: равно числу ядер сервера минус 1
  (обычно 4–8). Для режима совместимости / тонкого сервера — 2.

Без константы код корректно деградирует до синхронного режима
(`ПолучитьМаксимальноеКоличествоПараллельныхПотоков()` вернёт 0 и сработает fallback).

### 2. Добавить команду формы

В форме `РегламентныйПериод` справочника `РегламентныеПериоды` создать команду:

- **Имя**: `СформироватьРеглОперацииПараллельно`
- **Заголовок**: `Сформировать регл. операции (параллельно)`
- **Действие**: обработчик `СформироватьРеглОперацииПараллельно` из модуля формы
  (первая процедура из [Блока 1]).
- **Размещение**: командная панель формы рядом с существующей кнопкой
  «Сформировать регл. операции».

### 3. Скопировать [Блок 1] в модуль формы

В модуль `РегламентныйПериод/Ext/Form/Module.bsl` добавить в конце (перед
последним `КонецЕсли`/концом модуля) блок из файла. Ничего существующего
не удаляется — код полностью параллелен старому маршруту.

### 4. Скопировать [Блок 2] в общий модуль

В `CommonModules/ФоновыеЗаданияСервер/Ext/Module.bsl` добавить экспортную
процедуру `СформироватьПартициюМандатов` в конец файла.

Флаги общего модуля (уже установлены в текущей конфигурации):
- **Сервер** — да
- **Вызов сервера** — опционально (процедура вызывается только через `ФоновыеЗадания.Выполнить`)

### 5. Тест

1. Открыть форму `РегламентныйПериод`, выбрать дату и мандаты в динамическом списке.
2. Нажать новую кнопку «Сформировать регл. операции (параллельно)».
3. Проверить:
   - В журнале регистрации / консоли фоновых заданий видно **K** одновременных
     заданий с именем `ФоновоеЗадание:<УИД формы>`.
   - Сообщения пользователя появляются в форме после завершения всех партиций.
   - Аварийные задания (если есть) отдельно перечисляются с причиной ошибки.

## Ключевые проектные решения

### Защита от «фона внутри фона»

Диспетчер `Справочники.РегламентныеПериоды.СформироватьДокументыЗакрытияПериода`
умеет сам запускать фоновые задания, если `КоличествоПотоков > 0`. Чтобы внутри
нашего нового фонового задания он этого не делал, перед запуском K заданий
вызывается `ПерезаписатьКоличествоПотоковВХранилище(..., 0, УИД)` — поле
`КоличествоПотоков` в общем временном хранилище явно выставляется в `0`.
После этого внутри каждой партиции диспетчер уходит в синхронную ветку
`Иначе` и последовательно вызывает `ФоновыеЗаданияСервер.СоздатьПланРегламентныхОпераций`.

### Round-robin вместо блоков

Мандаты раздаются по партициям через `Индекс % K`. Это даёт более равномерную
загрузку, чем «блоки по N/K», если мандаты сильно отличаются по объёму работы
(например, один мандат с 100 бумагами и девять мандатов с 5 бумагами).

### Синхронный fallback

Код падает в синхронный путь, если:
- константа `МаксимальноеКоличествоПараллельныхПотоков` не определена;
- значение константы `<= 1`;
- `ФоновыеЗаданияСервер.ФоновыеЗаданияРазрешены() = Ложь`;
- мандат всего один.

В этом случае всё отрабатывается в текущем серверном вызове без фоновых заданий.

### Хранилище и конкурентный доступ

Все K заданий **читают одно и то же** временное хранилище (по УИД формы-инициатора).
В синхронной ветке диспетчера запись в хранилище не производится — значит,
конкуренции по записи нет, чтение потокобезопасно.

### Сбор сообщений и ошибок

После `ОжидатьЗавершения` сервер:
1. Для каждого задания снимает пользовательские сообщения через
   `ТекЗадание.ПолучитьСообщенияПользователю(Истина)` и ретранслирует в сеанс формы.
2. Отдельно ищет задания со статусом `СостояниеФоновогоЗадания.ЗавершеноАварийно`
   и выводит текст ошибки с указанием УИД партиции.

## Что НЕ меняется

- Существующий маршрут `СформироватьРегламентныеОперации()` и пачки по 5 мандатов
  остаются рабочими. Новый код — дополнительная кнопка, не затрагивающая старую.
- Документ `ПланРегламентныхОпераций`, его `ОбработкаПроведения`,
  `ВыполнитьРегламентныеПроцедуры`, регистр `ИсполнениеОпераций` — без изменений.
- Общий модуль `ИсполняемыеПроцедурыЗакрытияПериода` — без изменений.
- Менеджерные модули `РегламентныеПериоды`, `ВидыОперацийЗакрытияПериода` — без
  изменений (мы только вызываем существующую процедуру, но под новым управлением).
