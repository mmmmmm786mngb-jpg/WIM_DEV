Клиентская процедура: &НаКлиенте Процедура СформироватьРегламентныеОперации() (строки 650–695)

Процедура вызывается из двух команд формы:

  • СформироватьРеглОперации(Команда) — строка 642 (кнопка «Сформировать регл. операции»)

КонецПроцедуры // СформироватьРегламентныеОперации()

Что важно в этой процедуре

  • Имя фонового задания — "ФоновоеЗадание:" + УникальныйИдентификатор формы. По этому имени потом отбираются задания сессии (в том числе аварийно завершённые).
  • Один вызов на сервер для подготовки — ПолучитьМандатыПоДинамическомуСписку(). Он делает тяжёлую работу: формирует список мандатов, распроводит ранее созданные документы, кладёт всё во временное хранилище с УИД = ЭтаФорма.УникальныйИдентификатор.
  • Пачки по 5 мандатов (MID-153). Между пачками клиент может вывести прогресс через Состояние(...) и картинку БиблиотекаКартинок.ЗапуститьОтдельныйСеансДляВыполненияРегламентныхЗаданий. Это НЕ фоновые задания — это обычные синхронные серверные вызовы по частям, чтобы не держать соединение на весь список и давать обратную связь.
  • После цикла — ОбновитьРеглОперацииНаСервере() перечитывает дерево «План / Факт», и дерево разворачивается.

Что делает Справочники.РегламентныеПериоды.ПолучитьАдресВременногоХранилища:

  1. Получает план регл. операций из регистра РегистрСведений.НастройкиЗакрытияПериода.ПланРеглОпераций(ДатаПериода, СписокМандатов, ГруппаРегламентныхОпераций).
  2. Проходит по ДеревоРеглОпераций формы и формирует СписокОпераций (Мандат, ВидОперации, Выполнять, ВремяРеглОпераций, ГруппаОперацийПользователя) — только то, что выбрано в дереве (поле Факт).
  3. Запросом находит уже существующие документы ПланРегламентныхОпераций по мандатам/дате/группе и распроводит их (Записать(РежимЗаписиДокумента.ОтменаПроведения)).
  4. Создаёт МассивФоновыхЗаданий = Новый Массив и жёстко задаёт КоличествоПотоков = 0; // Заглушка RMC-52 // Константы.МаксимальноеКоличествоПараллельныхПотоков.Получить(); — именно этот параметр определяет, будет ли использоваться многопоточность на этапе диспетчера.
  5. Формирует МассивРодителей = уникальные ГруппаОперацийПользователя из СписокОпераций.
  6. Кладёт всё во временное хранилище с УИД формы: 
    ПараметрыСохранения = Новый Структура(
    "СписокОпераций, ДокументыПоДоговорам, МассивФоновыхЗаданий, КоличествоПотоков, МассивРодителей",
    СписокОпераций, ДокументыПоДоговорам, МассивФоновыхЗаданий, КоличествоПотоков, МассивРодителей);

АдресВременногоХранилища = ПоместитьВоВременноеХранилище(ПараметрыСохранения, УИД);
Важно: АдресВременногоХранилища — это реквизит формы (см. Form.xml, Attribute id=10). Серверная функция записывает адрес прямо в реквизит, а после серверного вызова значение возвращается на клиент. Благодаря УИД формы данные «живут» между серверными вызовами пачек и доступны в СформироватьДокументыЗакрытияПериода.

Как устроено разделение на фоновые задания

Ключевая идея

  1. Единица работы — это комбинация (Мандат × ГруппаОперацийПользователя). Для каждой такой пары создаётся или перезаполняется один ПланРегламентныхОпераций, после записи которого автоматически запускается цепочка ВыполнитьРегламентныеПроцедуры(Отказ).
  2. Тело задания — всегда одно и то же: экспортная функция общего модуля ФоновыеЗаданияСервер.СоздатьПланРегламентныхОпераций(ДатаПериода, Мандат, ТаблицаОпераций, ТекущийПлан, ГруппаОперацийПользователя).
  3. Решение «в фон или синхронно» принимается на каждой итерации по одному критерию:

Места, где разделение «ломается»

  1. Заглушка RMC-52 — КоличествоПотоков = 0 в ManagerModule.bsl:493. Весь ветку с ФоновыеЗадания.Выполнить сейчас обойти невозможно — всегда идёт в Иначе. Для включения параллелизма нужно вернуть чтение Константы.МаксимальноеКоличествоПараллельныхПотоков.Получить() и убедиться, что константа определена в конфигурации.
  2. Проверка адреса хранилища в клиенте (Module.bsl:660): 
    АдресВременногоХранилища = Неопределено;
СписокМандатов           = ПолучитьМандатыПоДинамическомуСписку();
Если НЕ ЭтоАдресВременногоХранилища(АдресВременногоХранилища) Тогда
    ОбщегоНазначения.СообщитьОбОшибке("...");
    Возврат;
КонецЕсли;

    Локальное присваивание АдресВременногоХранилища = Неопределено обнуляет реквизит формы. После серверного вызова реквизит на сервере перезаписан, но клиент читает его уже после присваивания: значение приходит с сервера вместе с другими реквизитами формы и проверка проходит. Важный нюанс: если по какой-то причине сервер не выставил адрес (например, ошибка в ПолучитьАдресВременногоХранилища), проверка корректно заблокирует выполнение.

  3. Единица параллелизма — не мандат, а (мандат × группа операций пользователя). При большом числе групп операций вложенный цикл может быстро наполнить массив фоновых заданий до лимита, и следующая пачка ждёт. Барьер ставится внутри пачки из 5 мандатов, не между пачками.
  4. Сообщения из фоновых заданий видны только после ОжидатьЗавершения. Если упасть в таймаут или закрыть форму — сообщения теряются. Аварийные задания отбираются по имени, но только на последней итерации (ТекЗначение = МаксимальноеЗначение).

Мини-сценарии

Сценарий А — параллельно (КоличествоПотоков = 4, 17 мандатов × 1 группа)

  1. Клиент разбивает 17 на пачки: 5 + 5 + 5 + 2.
  2. В каждой пачке менеджер запускает по 1 фоновому заданию на мандат × группу. После 4-го — барьер ОжидатьЗавершения, сообщения выводятся, массив очищается.
  3. На последнем (17-м) мандате: ещё один барьер (массив может быть не полон), затем отбор аварийных заданий по имени.
  4. Клиент показывает прогресс между пачками.

Сценарий Б — синхронно (текущее состояние, КоличествоПотоков = 0, 17 мандатов)

  1. Клиент разбивает на пачки по 5 мандатов.
  2. Каждый мандат внутри пачки обрабатывается последовательно в том же серверном вызове.
  3. Барьеры фоновых заданий не используются — всё идёт синхронно.
  4. Пользователь видит прогресс только между пачками (по 5 мандатов за «тик»).
