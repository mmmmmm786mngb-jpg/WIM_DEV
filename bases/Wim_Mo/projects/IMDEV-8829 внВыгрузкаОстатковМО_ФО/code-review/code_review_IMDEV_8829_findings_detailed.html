C1. HIGH Сброс флага ЕстьОшибка перед итоговой рассылкой

ОбъектВнешняя обработка внВыгрузкаОстатковМО_ФО
МодульМодуль объекта (Ext/ObjectModule.bsl)
ПроцедураФоноваяВыгрузкаПачками
Строки529-536 (установка флага), 566 (сброс), 580-581 (использование)
В чём проблема
После барьера код корректно выставляет ЕстьОшибка = Истина, если хотя бы одно фоновое задание завершилось аварийно. Перед агрегацией результатов и письмом флаг снова обнуляется: 
ЕстьОшибка = Ложь;  // строка 566 - сбрасывает результат проверки выше
Дальше текст оповещения строится так: 
ТекстОповещения = ?(ЕстьОшибка, "Одна или несколько пачек завершились аварийно...", "");
Из-за сброса условие всегда ложно: даже при упавших пачках письмо не содержит предупреждения об аварии (остаётся только признак по КоличествоОшибок из агрегата, который тоже может быть пустым - см. C2).
Вариант решения
Не перезаписывать флаг. Удалить строку 566 или переименовать переменные: 
// После барьера (оставить как есть):
ЕстьАварияПачки = Ложь;
Для Каждого Задание Из МассивЗаданий Цикл
    Если Задание.Состояние = СостояниеФоновогоЗадания.ЗавершеноАварийно Тогда
        ЕстьАварияПачки = Истина;
        ...
    КонецЕсли;
КонецЦикла;

// При рассылке - НЕ сбрасывать:
ТекстОповещения = ?(ЕстьАварияПачки,
    "Одна или несколько пачек завершились аварийно. Подробности в логе.",
    "");
РассылкаСообщения(
    "Выгрузка остатков МО -> ФО (пачки)",
    ТекстОповещения,
    (ЕстьАварияПачки Или ДанныеДляРассылки.КоличествоОшибок > 0),
    Ложь);

C2. HIGH Временное хранилище между сеансами фоновых заданий

ОбъектВнешняя обработка внВыгрузкаОстатковМО_ФО
МодульМодуль объекта (Ext/ObjectModule.bsl)
Места 1) ФоноваяВыгрузкаПачками - создание адреса (стр. 491-494) и чтение (стр. 567-578)
2) ВыполнитьКоманду - запись результата воркером (стр. 132-139)

Фрагмент координатора (создание + чтение)

// ФоноваяВыгрузкаПачками, ~492
Адрес = ПоместитьВоВременноеХранилище(Новый Структура, Новый УникальныйИдентификатор);
НастройкиПачки.Вставить("АдресРезультата", Адрес);
...
// после барьера, ~567
ДанныеПачки = ПолучитьИзВременногоХранилища(Адрес);

Фрагмент воркера (запись)

// ВыполнитьКоманду, ~136-137
Если ПараметрыПачки.Свойство("АдресРезультата") Тогда
    ПоместитьВоВременноеХранилище(ДанныеДляРассылки, ПараметрыПачки.АдресРезультата);
КонецЕсли;
В чём проблема
Временное хранилище платформы привязано к сеансу. Координатор и каждое фоновое задание - разные сеансы. Паттерн "координатор создал адрес - воркер положил - координатор прочитал" часто даёт пустую структуру или исходную заглушку без полей КоличествоПортфелей. Тогда:
  • сводная статистика в письме не набирается;
  • ошибки позиций из пачек теряются;
  • создаётся ложное ощущение, что агрегация работает.
Вариант решения (рекомендуемый): файлы рядом с логами
Уже есть каталог сессии для логов - использовать его же для JSON/структуры результата пачки. 
// В координаторе при создании пачки:
ИмяФайлаРезультата = КаталогРезультатов + "\результат_пачка_" + (НомерПачки + 1) + ".txt";
НастройкиПачки.Вставить("ФайлРезультата", ИмяФайлаРезультата);

// В воркере (ВыполнитьКоманду) вместо ПоместитьВоВременноеХранилище:
Если ПараметрыПачки.Свойство("ФайлРезультата") Тогда
    ЗначениеВФайл(ПараметрыПачки.ФайлРезультата, ДанныеДляРассылки);
    // или ЗаписьJSON / сериализация структуры
КонецЕсли;

// В координаторе после барьера:
ДанныеПачки = ЗначениеИзФайла(ИмяФайлаРезультата);
Альтернативы: регистр сведений "служебный буфер пачек", механизм длительных операций БСП с адресом результата в параметрах задания. После внедрения - обязательный тест: 2 потока, ошибки в одной пачке, проверка что они попали в сводное письмо.

C3. HIGH Логи воркеров зависят от вклОтладка в чужом сеансе

ОбъектВнешняя обработка внВыгрузкаОстатковМО_ФО
МодульМодуль объекта (Ext/ObjectModule.bsl)
Места 1) ФоноваяВыгрузкаПачками - создание каталога при вклОтладка (стр. 455-466, 487-489)
2) ВыполнитьКоманду - запись файла лога тоже при вклОтладка (стр. 152-165)
3) Инициализация модуля: вклОтладка = Ложь (стр. 5711)
4) Форма: Forms/Форма/Ext/Form/Module.bsl, процедура ВыполнитьКомандуНаСервере - выставляет вклОтладка только у объекта координатора 
// Координатор:
Если вклОтладка Тогда
    КаталогЛогов = ...;
    НастройкиПачки.Вставить("КаталогЛогов", КаталогЛогов);
КонецЕсли;

// Воркер (новый сеанс обработки):
Если вклОтладка  // <-- здесь почти всегда Ложь
    И ...Свойство("КаталогЛогов") Тогда
    ТекстовыйЛог.Записать(КаталогЛогов + "\пачка_" + НомерПачки + ".txt");
КонецЕсли;
В чём проблема
Координатор может создать каталог и передать путь, но воркер стартует как новый экземпляр обработки: модульная переменная вклОтладка инициализируется в Ложь и через настройки узла/пачки не читается. Условие записи лога не выполняется - файлов пачка_N.txt нет, блок сбора логов в координаторе ловит ошибки чтения.
Вариант решения A (предпочтительный): писать лог по факту наличия каталога 
// ВыполнитьКоманду - убрать зависимость от вклОтладка:
Если ПараметрыВыполненияКоманды.Свойство("ПараметрыДополнительнойОбработки")
    И ПараметрыВыполненияКоманды.ПараметрыДополнительнойОбработки.Свойство("КаталогЛогов") Тогда
    КаталогЛогов = ПараметрыВыполненияКоманды.ПараметрыДополнительнойОбработки.КаталогЛогов;
    НомерПачки = ПараметрыВыполненияКоманды.ПараметрыДополнительнойОбработки.НомерПачки;
    ТекстовыйЛог.Записать(КаталогЛогов + "\пачка_" + НомерПачки + ".txt");
КонецЕсли;
Вариант решения B: явно прокинуть флаг в настройки пачки 
// В координаторе:
НастройкиПачки.Значения.Вставить("вклОтладка", вклОтладка);

// В УстановитьПользовательскиеНастройки:
Если Настройки.Значения.Свойство("вклОтладка") Тогда
    вклОтладка = Настройки.Значения.вклОтладка;
КонецЕсли;
Аналогично при необходимости прокидывать РежимОтладкиСервиса.

M1. MEDIUM Идентификатор команды воркера = ФоноваяВыгрузкаПачками

ОбъектВнешняя обработка внВыгрузкаОстатковМО_ФО
МодульМодуль объекта (Ext/ObjectModule.bsl)
Процедуры СведенияОВнешнейОбработке (стр. 56-59) - список команд
ВыполнитьКоманду (стр. 112-124) - ветвление координатор / обмен; защита ПРОДа закомментирована
ФоноваяВыгрузкаПачками (стр. 499-500) - с каким ID стартуют воркеры
Что здесь НЕ ошибка (задумка Федора - хорошая)
Регламент/узел по-прежнему вызывает только команду ФоноваяВыгрузка (как на ПРОДе). Дальше обработка сама выбирает режим: 
Если ИдентификаторКоманды = "ФоноваяВыгрузка" И КоличествоПотоков > 1 Тогда
    // параллель: координатор пачек
Иначе
    // обычная одиночная выгрузка (когда потоков = 1)
КонецЕсли;
Это удобно: не нужна отдельная команда в расписании. К этой идее претензий нет.

Где тогда претензия?

Претензия не к единому входу, а к тому, с каким ID координатор запускает фоновые задания-воркеры и к снятию прод-защиты в ВыполнитьКоманду. 

// Координатор (ФоноваяВыгрузкаПачками), стр. 499-500:
//ПараметрыКоманды.Вставить("ИдентификаторКоманды", "ФоноваяВыгрузка");  // было бы штатно
ПараметрыКоманды.Вставить("ИдентификаторКоманды", "ФоноваяВыгрузкаПачками"); // так сейчас

// Воркер снова входит в ВыполнитьКоманду уже с ID = "ФоноваяВыгрузкаПачками"
// Условие координатора не срабатывает (нужен именно "ФоноваяВыгрузка")
// и код падает в общий путь:
ОписаниеОбменов.ВыполнитьКомандуПоОбменам(ЭтотОбъект, ИдентификаторКоманды, ...);
//                                                ^^^^^^^^^^^^^^^^^^^^
//                        сюда уходит "ФоноваяВыгрузкаПачками", а не "ФоноваяВыгрузка"
1) Зачем Федор подменил ID воркера
Анти-рекурсия. Если бы воркер шёл как ФоноваяВыгрузка и в настройках пачки осталось КоличествоПотоков > 1, он снова вызвал бы координатор (пачки внутри пачек). Подмена ID на ФоноваяВыгрузкаПачками это обходит.

2) Что такое "в ОписаниеОбменов уходит нештатный ID"
ОписаниеОбменов.ВыполнитьКомандуПоОбменам - общий механизм обменов конфигурации (протокол, БП, вызов ПодготовитьДанные/ЗаписатьДанные). На ПРОДе и у Алексея туда всегда передавался ID рабочей выгрузки ФоноваяВыгрузка. У Федора воркер передаёт ФоноваяВыгрузкаПачками - это ID другой зарегистрированной команды (в UI даже подписана "не использовать!"). Если модуль обменов использует идентификатор только для записи в лог - может работать. Если есть ветвление/привязка к команде узла по ID - возможны сюрпризы. Это риск, который нужно проверить на стенде, а не доказанный стоп-баг.

3) Связанная регрессия: снята защита с ПРОДа
Оригинал и Алексей: 
Если ИдентификаторКоманды <> "ФоноваяВыгрузка" Тогда Возврат; КонецЕсли;
У Федора строка закомментирована (стр. 124). Почему: если оставить старый гард, воркер с ID ФоноваяВыгрузкаПачками сразу сделал бы Возврат и пачка не выгрузилась бы. Но без любого фильтра ВыполнитьКоманду теперь может отправить в обмен любой ID, в том числе прямой вызов команды "не использовать!" (это уже не координатор, а обычный путь обмена).
Рекомендуемое решение (сохраняет единый вход для регламента)
Регламент по-прежнему зовёт только ФоноваяВыгрузка. Воркерам тоже давать ФоноваяВыгрузка, но в настройках пачки принудительно КоличествоПотоков = 1 (анти-рекурсия без подмены ID): 
// В ФоноваяВыгрузкаПачками при подготовке НастройкиПачки:
НастройкиПачки.Значения.Вставить("КоличествоПотоков", 1);
НастройкиПачки.Значения.Вставить("МандатыПачки", Пачки[НомерПачки]);
НастройкиПачки.Значения.Вставить("ИдентификаторСеансаОбмена", СессияОбмена);

ПараметрыКоманды.Вставить("ИдентификаторКоманды", "ФоноваяВыгрузка");
Тогда можно вернуть прод-защиту: 
Если ИдентификаторКоманды <> "ФоноваяВыгрузка" Тогда
    Возврат;
КонецЕсли;

Если КоличествоПотоков > 1 Тогда
    ФоноваяВыгрузкаПачками(ПараметрыВыполненияКоманды);
    Возврат;
КонецЕсли;

ОписаниеОбменов.ВыполнитьКомандуПоОбменам(...);
Команду ФоноваяВыгрузкаПачками лучше убрать из регистрации БСП либо сделать явным alias на координатор (если нужна обратная совместимость), но не использовать её как "тихий" ID воркера.

        ТекстАварии = ТекстАварии + Описание + Символы.ПС;
    КонецЕсли;

// Сначала добить финальные действия (РСА/почта), затем:
Если ЕстьАварияПачки Тогда
    ВызватьИсключение СокрЛП(ТекстАварии);
КонецЕсли;
Если исключение до почты нежелательно - слать письмо, затем всё равно ВызватьИсключение, чтобы БП узла зафиксировал FAIL.
