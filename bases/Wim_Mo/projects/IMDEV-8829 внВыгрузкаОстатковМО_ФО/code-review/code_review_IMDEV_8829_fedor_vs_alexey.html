Параллельная выгрузка (КоличествоПотоков > 1) Частично Координатор/пачки/барьер/финальный РСА - да. Агрегация почты и логи воркеров - с дефектами.

Команда "ФоноваяВыгрузкаПачками" из БСП напрямую Сломана Помечена "не использовать!", но при вызове не становится координатором.

3. Критические и важные замечания по коду Федора

C1. HIGH - Сброс флага ЕстьОшибка перед итоговой рассылкой
В ФоноваяВыгрузкаПачками после проверки аварийных заданий флаг ЕстьОшибка выставляется в Истина, затем перед агрегацией результатов снова присваивается ЕстьОшибка = Ложь. Текст "Одна или несколько пачек завершились аварийно" фактически никогда не попадёт в письмо. 
// сначала ЕстьОшибка = Истина при аварии
ЕстьОшибка = Ложь; // сброс
...
ТекстОповещения = ?(ЕстьОшибка, "...аварийно...", "");
C2. HIGH - Временное хранилище между сеансами фоновых заданий
Координатор создаёт адреса через ПоместитьВоВременноеХранилище(..., Новый УникальныйИдентификатор), воркеры пишут туда ДанныеДляРассылки, координатор читает после барьера. Временное хранилище привязано к сеансу; фоновые задания - отдельные сеансы. Высокий риск, что агрегация статистики по пачкам в письме будет пустой/неполной. Надёжнее: файлы (как для логов), регистр, или возврат результата через механизм длительных операций.
C3. HIGH - Логи воркеров зависят от вклОтладка в чужом сеансе
Каталог логов создаётся в координаторе при вклОтладка, но запись файла в воркере тоже требует вклОтладка. Воркер стартует как новый экземпляр обработки: модульная переменная вклОтладка = Ложь по умолчанию и через настройки узла не передаётся. Итог: файлы пачек часто не создаются, сбор логов бесполезен. Нужно передавать флаг в НастройкиПачки.Значения и читать его в УстановитьПользовательскиеНастройки, либо писать лог воркера всегда при наличии КаталогЛогов.
M1. MEDIUM - ID воркера = ФоноваяВыгрузкаПачками (+ снятие прод-защиты)
Не ошибка: единый вход регламента через ФоноваяВыгрузка + КоличествоПотоков > 1 (сам выбор параллели/одиночки) - удачная задумка.
Проблема: воркеры стартуют с ID ФоноваяВыгрузкаПачками (анти-рекурсия), из-за этого:
  • в ОписаниеОбменов.ВыполнитьКомандуПоОбменам уходит не штатный ID обмена;
  • пришлось убрать прод-гард Если ИдентификаторКоманды <> "ФоноваяВыгрузка" Тогда Возврат - иначе воркер сразу выходил бы;
  • без фильтра любой ID снова может уйти в обмен.
Чище: воркерам ID ФоноваяВыгрузка + принудительно КоличествоПотоков = 1, вернуть защиту. Подробно: code_review_IMDEV_8829_findings_detailed.html, блок M1.
M2. MEDIUM - Барьер больше не пробрасывает исключение
У Алексея при аварии воркера: лог + ВызватьИсключение. У Федора: только запись в лог, выполнение идёт дальше (РСА + почта). Для мониторинга узла обмена это регрессия: бизнес-процесс может считаться успешным при частично упавших пачках.
M3. MEDIUM - Мёртвое поле формы КоличествоПачекМандатов
В Form.xml остался InputField name="КоличествоПачекМандатов" без DataPath рядом с рабочим КоличествоПотоков. Лишний/битый элемент UI.
L1. LOW - Дубль присваивания: Объект.КоличествоПотоков = 1; два раза подряд в НастройкиПоУмолчанию.
L2. LOW - ВесКоличествоМандатов в ПолучитьМассивВсехМандатовДляВыгрузки считается до Свернуть("Мандат") (строки счетов, не уникальные мандаты).
L3. LOW - Отступы в конце ОпубликоватьИсполнениеСделок (замер с лишним отступом) - косметика, на выполнение не влияет.
L4. LOW - Закомментированный код и смешение меток IMDEV-8829 / IMDEV-8972 усложняют сопровождение.

Хорошо - чистое разделение. Замечания: нет UI/настройки; не все прямые вызовы Прокси в модуле обязательно покрыты (основные пути в Опубликовать* - да).
10 Замеры ОценкаПроизводительности в ВыполнитьКоманду / Заполнить / Опубликовать* (IMDEV-8972) Измерить выигрыш от параллелизма и узкие места. Хорошо - осмысленные ключи с узлом/пачкой/потоками. Зависит от наличия подсистемы; вес мандатов чуть неточен (L2).

12 Переменная модуля ВесКоличествоМандатов Передать вес из Заполнить в замер ВыполнитьКоманду. Средне - работает в одном сеансе; в координаторе вес может быть от полного списка, в воркере - от пачки (это даже полезно).

14 Default КоличествоПотоков = 1 (было 3 пачки) Безопасный default: без явного включения параллель не стартует. Хорошо - правильнее для продакшена.
15 Мелкие правки в функциях выборок (ДенежныеСредстваНаДату, БлокировкиНаДату, и т.д.) В основном добавление замеров / обёрток вызовов сервиса в связанных процедурах публикации. Хорошо - диффы ratio > 0.88, логика выборок по сути не менялась.

7. Рекомендации перед продом

  1. Обязательно: убрать повторный сброс ЕстьОшибка = Ложь; использовать отдельную переменную или не перезаписывать.
  2. Обязательно: заменить обмен через временное хранилище на файлы/другой межсеансовый механизм; проверить на стенде чтение агрегатов.
  3. Обязательно: прокинуть вклОтладка (и при необходимости РежимОтладкиСервиса) в настройки пачки; писать лог при наличии КаталогЛогов.
  4. Желательно: воркерам передавать КоличествоПотоков = 1 и ID ФоноваяВыгрузка; убрать хрупкую подмену ID.
  5. Желательно: при аварии пачки поднимать исключение (или явно помечать ошибку обмена), как у Алексея.
  6. Желательно: удалить поле формы без DataPath; добавить чтение старого ключа настроек для совместимости.
  7. Тест-план минимум: потоки=1; потоки=2/3 на малом отборе; падение одного воркера; проверка одного письма; проверка ЖР/замеров; РежимОтладкиСервиса=Истина.
Общий вывод: доработки Федора двигают решение в правильную сторону (один вход, безопасный default, сводная почта, замеры, dry-run), но текущая сборка не готова к проду без исправления C1-C3. После правок - повторный короткий ревью этих трёх точек.
