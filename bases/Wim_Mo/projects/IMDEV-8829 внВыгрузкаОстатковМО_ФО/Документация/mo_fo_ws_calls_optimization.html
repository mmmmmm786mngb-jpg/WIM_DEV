2. Как ФО понимает, что вызовы разные

Важно: на ФО нет отдельных методов WS и нет поля «тип вызова». Все три обращения идут в WebServices.Avancore.DownloadPosition → ОбменДаннымиБэкОфис.ЗагрузитьПакет. Тип обработки определяется составом XDTO после разбора пакета.

3. Цепочки вызовов по каждому блоку

754 Предварительные флаги «позиция НЕ выгружена»

МО (СформироватьПакетФлагПозицияНеВыгружена, строка ~1246):

MO: для каждого из 45 мандатов -> Портфель.ВнешнийКод + ДопСведения[1]
MO: Прокси.DownloadPosition(ПакетХДТОФлагПозицииНеВыгружена) // строка 751

ФО:

Avancore.DownloadPosition
-> ОбменДаннымиБэкОфис.ЗагрузитьПакет
-> для каждого Портфель XDTO:
ОбработатьДанные_Портфель (НеполноеОбновление)
ОбработатьДополнительныеСведения:
НаборЗаписей.ДополнительныеСведения.Прочитать()
НайтиПоНаименованию("Лимиты позиция_выгружена")
НаборЗаписей.Записать() // x45 портфелей
-> внОперацииПослеОбмена: Комментарий пуст -> return
Назначение: заблокировать на ФО операции, зависящие от флага «позиция выгружена», пока идет загрузка пакета (лимиты, проверки ордеров).

768 Основная позиция

МО (накопление в ПакетХДТО в цикле по мандатам, отправка строка 765):

MO: ДС + ЦБ -> РегистрыСведений.ФактическаяПозиция
MO: СЧА/РСА -> РегистрыСведений.СтоимостьЧистыхАктивов
MO: Прокси.DownloadPosition(ПакетХДТО) // строка 765

ФО:

Avancore.DownloadPosition
-> ЗагрузитьДанные
-> ОбработатьДанные_ФактическаяПозиция:
НаборЗаписей.ФактическаяПозиция (полная замена по Портфель+Дата)
-> ОбработатьДанные_СтоимостьЧистыхАктивов:
РегистрРСА_СЧА + ДатаАктуальностиФактическойПозиции
-> внОперацииПослеОбмена: return (нет Комментария)
Назначение: загрузить фактическую позицию и переданные СЧА/РСА с МО. Самый «тяжелый» по объему данных, но быстрее 872 из-за оптимизированной записи регистров.

872 Пост-флаги «выгружена / ошибка»

МО (строки 856-870):

MO: СформироватьПакетФлагПозицияВыгружена (успех: 3 свойства для ДУ)
MO: СформироватьПакетФлагПозицияВыгруженаСОшибкой (ошибка: 3 свойства)
MO: Прокси.DownloadPosition(ПакетХДТОФлагПозиции) // строка 870
MO: ВыполнитьПерерасчетРСА(...) // строка 877 -> отдельный 4-й WS, не входит в 872

ФО:

Avancore.DownloadPosition
-> для каждого Портфель XDTO (успех + ошибка):
ОбработатьДанные_Портфель
ОбработатьДополнительныеСведения (до 3 ключей):
"Лимиты позиция_выгружена"
"Лимиты требуется_перерасчет_РСА"
"Лимиты есть_ошибки_выгрузки_позиции"
-> внОперацииПослеОбмена: return
Ложный след: флаг требуется_перерасчет_РСА в пакете 872 не запускает перерасчет синхронно. Перерасчет стартует только из 4-го вызова (JSON ТребуетсяПерерасчетРСА в Заголовок.Комментарий) через внОперацииПослеОбмена → внПерерасчетСтоимостиФактическойПозицииИ_РСА_СЧА в фоне. Медленность 872 — это запись доп. сведений + нагрузка СУБД после 768.

5. Рекомендации по оптимизации

5.1. ФО (максимальный эффект)

  • 872 / 754: переписать ОбработатьДополнительныеСведения — кешировать ссылки ПВХ «Лимиты …», не читать полный набор на каждое свойство, рассмотреть пакетную запись по массиву портфелей.
  • 872: убрать дублирование флагов или сократить число свойств (если бизнес-логика лимитов это допускает).
  • 768: профилировать запись ФактическаяПозиция на 45 портфелей; проверить блокировки и индексы СУБД.

5.2. МО (архитектура обмена)

  • Объединить 754 и 872 в один WS-вызов (если ФО согласует семантику).
  • Увеличить размер пакета (например 50–100) при стабильном IIS — меньше циклов, но больше риск 413; всегда задавать КоличествоПакет > 0.
  • Батчить ВыполнитьПерерасчетРСА реже (не 470 раз), чтобы снизить фоновую нагрузку на ФО во время 872.

5.3. Что не трогать в первую очередь

  • 4-й вызов (1526) — ~1 с/пакет, перерасчет уже в фоне.
  • Локальные проверки МО (строка 683) — < 1% времени.
