# ТЗ: трассировка полного маршрута расчета котировки (внешняя обработка Атомфонд)

## 1. Назначение и область

**Цель:** при каждом вызове `ТекущиеКотировкиПоПравилу` фиксировать **полный линейный маршрут** принятия решений по каждому активу из `СписокЦБ`: все значимые проверки, исходы «успех / пропуск / ноль / ранний выход» и итоговое разрешение. Результат сериализуется в **JSON (текст)** и при включенной настройке **показывается пользователю** через **`Сообщить`** (глобальный метод платформы; у вызова `СообщитьПользователю` из БСП нет ссылки во внешней обработке), чтобы JSON можно было **скопировать** из окна сообщений. В **журнал регистрации** (уровень **Информация**) попадает **только короткая сводка** без полного JSON; **разбиение JSON на несколько записей ЖР запрещено**.

**Контекст запуска:** обработку вызывает другая внешняя обработка, сценарий **интерактивный** (пользователь инициирует с клиента). **Не добавлять** реквизиты и элементы на формы `Форма` / `ФормаНастроек` данной обработки для вывода трассировки.

**Файл реализации:** `Разработка_Epf/внОпределениеССНПФАтомфонд/Ext/ObjectModule.bsl`.

**Вне области:** изменение бизнес-логики расчета цены (только добавление наблюдаемости и вызовов логирования); изменение контракта `ТекущиеКотировкиПоПравилу` для вызывающего кода **не обязательно** (см. п. 8); отдельные регистры конфигурации (в т.ч. «Замеры»).

## 2. Термины

- **Шаг маршрута** — одна атомарная запись в массиве трассировки с порядковым номером, кодом события и исходом.
- **Полный маршрут** — упорядоченный список шагов от входа в расчет по активу до фиксации итога `FOUND` или `NOT_FOUND`.
- **Код события** — стабильная латинская строка в формате `L{уровень}_{блок}_{деталь}` (см. каталог п. 5).

## 3. Требования к поведению

1. Для **каждого** элемента `СписокЦБ` создается отдельная трассировка (массив шагов).
2. Шаги добавляются **в порядке фактического выполнения** кода (включая ранние `Возврат` из процедур/функций — перед выходом должен быть зафиксирован исход).
3. Каждый шаг содержит минимум: `seq`, `lvl`, `code`, `outcome` (п. 4).
4. После завершения обхода всех активов формируется **одна** строка JSON по схеме п. 4.2 (один сеанс расчета — один документ).
5. Перед оператором `Возврат Новый Структура(...)` в `ТекущиеКотировкиПоПравилу` (в конце функции), если флаг включен:
   - **Полный JSON** передать в `Сообщить(<строка JSON>)` (одно или несколько сообщений **только** через `Сообщить`, без форм и без реквизитов обработки). При риске превышения лимита длины одного сообщения платформы — допускается **последовательно** несколько вызовов `Сообщить` с частями одного JSON, явно помеченными в тексте как `Часть 1/2`, `Часть 2/2` (это **не** чанки ЖР).
   - **Журнал регистрации:** одна запись `ЗаписьЖурналаРегистрации` с **коротким** комментарием фиксированного шаблона, например: имя события `Атомфонд.ОпределениеСС.МаршрутКотировки`, в комментарии — дата, мандат (строка), число активов, число шагов по всем строкам при необходимости, фраза «полный JSON выведен пользователю». **Не** помещать полный JSON в комментарий ЖР.
6. Заполнение трассировки **не должно менять числовые результаты** расчета; при ошибках внутри блока трассировки желательно поглощать их (не ломать основной расчет), при необходимости один шаг `TRACE_ERROR` с `outcome = error`.

## 4. Модель данных

### 4.1. Контекст трассировки на один актив

Рекомендуемая структура `КонтекстТрассыАктива` (имена полей — на усмотрение, смысл фиксирован):

| Поле | Тип | Описание |
|------|-----|----------|
| `Шаги` | `Массив` | Элементы — структуры шага (см. ниже). |
| `СледующийНомер` | `Число` | Счетчик для `seq`. |
| `Актив` | ссылка | Текущий актив (для hint в JSON). |
| `ISIN` | `Строка` | Кэш ISIN при наличии. |

**Структура одного шага** (для `ЗаписатьJSON` удобно сериализуемая):

| Поле | Тип | Обяз. | Описание |
|------|-----|-------|----------|
| `seq` | `Число` | да | Порядковый номер с 1. |
| `lvl` | `Число` | да | 0 = общий; 1/2/3 = уровень алгоритма. |
| `code` | `Строка` | да | Код из каталога п. 5. |
| `outcome` | `Строка` | да | Одно из: `ok`, `skip`, `zero`, `hit`, `miss`, `exit`. |
| `hint` | `Строка` | нет | Краткая подсказка (даты, ключевые числа округленные, код ветви НРД). Без огромных таблиц и без персональных данных. |

**Финальный блок по активу** (можно добавлять последним шагом или отдельным объектом в JSON-строке по активу):

- `resolution`: `FOUND` | `NOT_FOUND`
- `finalLevel`: число (0 если не найдено)
- `finalCode`: код последней успешной ветви или пустая строка
- `quote`: число или `null` (после основного расчета, опционально; учесть что номинальный пересчет идет позже цикла)

### 4.2. Корень JSON сессии

Рекомендуемые поля:

```json
{
  "event": "AtomFond.Quotation.RouteTrace.v1",
  "mandate": "<строка>",
  "date": "YYYY-MM-DD",
  "settingsDigest": "<кратко: наличие НРД2, оценщика, фрагмент идентификатора правила>",
  "rows": [ { "assetRef": "<UUID или строка>", "isin": "", "steps": [], "resolution": {} } ]
}
```

Имена полей в JSON — **латиница** (стабильный контракт для парсинга вне 1С).

## 5. Каталог кодов (обязательный минимум)

Ниже — коды, которые **должны** появиться при прохождении соответствующих веток. Расширение каталога допускается отдельными кодами при добавлении новых веток.

### 5.1. Точка входа (`ТекущиеКотировкиПоПравилу`)

| code | outcome | Когда |
|------|---------|--------|
| `SESSION_START` | ok | После подготовки периода/таблиц, перед циклом по ЦБ (один шаг на всю сессию, опционально вне `rows`) |
| `ASSET_ENTER` | ok | Сразу после `ТаблицаКотировок.Добавить()` для актива |
| `ASSET_RESOLUTION` | hit / miss | После L1/L2/L3: цена <> 0 или окончательный ноль |

### 5.2. Уровень 1 — `ЦенаАктиваУровень1`

| code | outcome | Когда |
|------|---------|--------|
| `L1_ENTER` | ok | Вход в функцию |
| `L1_SKIP_ALREADY_PRICED` | skip | Уже заполнена котировка (ранний `Возврат` в начале) |
| `L1_MMVB_QUOTES_EMPTY` | miss | `ТаблицаКотировокПоАктиву.Количество() = 0` |
| `L1_IPO_PRICE` | hit | Ветка первичного размещения, цена получена |
| `L1_IPO_PRICE_ZERO` | zero | Ветка первички, цена 0 (если возможно) |
| `L1_MARKET_ACTIVE_CHECK` | ok | После `ОсновнойРынокАктивен`, в `hint` — Истина/Ложь |
| `L1_KOTIROVKA_BY_FIELD` | hit / miss | Вызов `КотировкаПоВыбПолю`: итог с ненулевой котировкой или нет |

### 5.3. `КотировкаПоВыбПолю`

| code | outcome | Когда |
|------|---------|--------|
| `L1_FIELD_NO_ROW_FOR_DATE` | miss | Нет строки на `КонецПериода` |
| `L1_FIELD_ALL_ZEROS` | miss | Ветка `СредневзвешеннаяЦена = 0 и МинимальнаяЦена = 0 и МаксимальнаяЦена = 0` |
| `L1_FIELD_BID` | hit | Выбрана цена по ветке BID |
| `L1_FIELD_WAP` | hit | Средневзвешенная |
| `L1_FIELD_BID_MID` | hit | BID между WAP и OFFER |
| `L1_FIELD_CLOSE` | hit | Цена закрытия |
| `L1_FIELD_NO_MATCH` | miss | Иначе, ранний выход без цены |

### 5.4. Завершение уровня 1 (в `ЦенаАктиваУровень1` после ветвлений)

| code | outcome | Когда |
|------|---------|--------|
| `L1_LEVEL_SET` | ok | `УровеньЦены = 1` при ненулевой котировке |
| `L1_RESET_ZERO` | zero | Сброс уровня 1 при нуле |

### 5.5. Уровень 2 — `ЦенаАктиваУровень2`

| code | outcome | Когда |
|------|---------|--------|
| `L2_ENTER` | ok | Вход (если вызывается) |
| `L2_NRD2_SKIP_METHOD3_RUB` | ok | Рублёвая облигация: при обходе НРД2 отброшены строки с `НомерМетодаРасчета = 3` (политика IMDEV-8611 от 07.05.2026); в `hint` число таких строк (`ignoredRows=`) |
| `L2_NRD1_SKIP_METHOD3_RUB` | ok | То же для НРД1 при дозапросе котировки |
| `L2_NRD2_SEARCH` | hit / miss | Заполнен НРД2 и найдена ненулевая / нет |
| `L2_NRD1_SEARCH` | hit / miss | Аналогично НРД1 |
| `L2_NRD_QUOTE_APPLIED` | hit | Установлена котировка НРД, процедура завершена по `Возврат` |
| `L2_BOND_SPREAD_CALC` | ok / miss | Облигации: вызов `ЦенаОблигацииПоКредитномуСпредуРейтинговойГруппы`, `ДанныеРасчета.Количество() > 0` или нет |
| `L2_DCF_ROW_MISSING` | miss | `ТаблицаКотировокПоАктиву.Найти` вернул `Неопределено` |
| `L2_DCF_CLAMP_BID` | hit | PV < BID, взята цена спроса |
| `L2_DCF_CLAMP_OFFER` | hit | PV > OFFER |
| `L2_DCF_PV` | hit | PV в коридоре |
| `L2_EXIT_NO_PRICE` | exit | Завершение без цены |

### 5.6. Уровень 3 — `ЦенаАктиваУровень3`

| code | outcome | Когда |
|------|---------|--------|
| `L3_ENTER` | ok | Вход |
| `L3_NRD_METHOD3_V2` | hit / miss | Поиск по НРД2 с `НомерМетодаРасчета = 3` |
| `L3_NRD_QUOTE_APPLIED` | hit | Ненулевая цена НРД, выход |
| `L3_DCF_BLOCK_ENTER` | ok | Условие IMAPPS-11191 выполнено, блок DCF |
| `L3_DCF_RATING_EMPTY` | ok | `ПолучитьКредитныйРейтинг` вернул `""` |
| `L3_DCF_RATING_MIN` | ok | МинСпред |
| `L3_DCF_RATING_MED` | ok | Медиана |
| `L3_DCF_RATING_OTHER` | ok | Прочий уровень рейтинга |
| `L3_DCF_CHOICE_OFFER` | hit | PV > OFFER, OFFER <> 0 |
| `L3_DCF_CHOICE_BID` | hit | PV < BID |
| `L3_DCF_CHOICE_PV` | hit | Иначе PV |
| `L3_APPRAISER_SEARCH` | hit / miss | Поиск котировки оценщика |
| `L3_APPRAISER_APPLIED` | hit | Цена оценщика записана |
| `L3_EXIT_NO_PRICE` | exit | `ЦенаОценщик = 0` и выход |

### 5.7. Вспомогательные

| code | outcome | Когда |
|------|---------|--------|
| `TRACE_ERROR` | error | Исключение внутри блока логирования / JSON |

## 6. Техническая реализация (требования к коду)

### 6.1. Служебные процедуры в модуле объекта

Реализовать (имена на усмотрение, поведение фиксировано):

1. `Трасса_СоздатьКонтекст(Актив, ISIN)` — новый контекст с пустым массивом шагов.
2. `Трасса_ДобавитьШаг(Контекст, Уровень, Код, Исход, Подсказка = "")` — инкремент `seq`, добавление структуры шага.
3. `Трасса_СериализоватьСессиюВJSON(МассивКонтекстовПоАктивам, ПараметрыСессии)` — сборка корня п. 4.2, `ЗаписьJSON` + `ЗаписатьJSON`, возврат строки.
4. `Трасса_ПоказатьJSONПользователю(СтрокаJSON)` — вывод полного JSON через `Сообщить`; при необходимости дробление на несколько сообщений с пометкой частей (см. раздел 3, абзац о нескольких `Сообщить`).
5. `Трасса_ЗаписатьСводкуВЖурнал(ПараметрыСводки)` — одна запись `ЗаписьЖурналаРегистрации` (Информация), комментарий **короткий**, без тела JSON; имя события, например `Атомфонд.ОпределениеСС.МаршрутКотировки`.

### 6.2. Протягивание контекста

- В цикле `Для Каждого СтрокаСпискаЦБ` создавать `КонтекстТрассы`.
- Добавить **последний параметр** (необязательный) `КонтекстТрассы` в сигнатуры:
  - `ЦенаАктиваУровень1`
  - `КотировкаПоВыбПолю`
  - `ЦенаАктиваУровень2`
  - `ЦенаАктиваУровень3`
- Либо альтернатива: одна переменная модуля `ТекущийКонтекстТрассы`, устанавливаемая на время расчета актива (хуже для параллельности, проще внедрение). В ТЗ предпочтителен **явный параметр**.

Опционально: обернуть `ОсновнойРынокАктивен` так, чтобы в `hint` попадали агрегаты `NUMTRADES`, `ОбъемТоргов`, `ОбъемТорговВпоследнийДень` (без изменения самой функции — вызывающий код логирует после вызова).

### 6.3. Настройка включения

- Ввести флаг в `СтруктураНастроек` / `НастройкиАлгоритма`, например `ЛогироватьМаршрутКотировки` (Булево), по умолчанию `Ложь`, читается из хранилища настроек при наличии ключа.
- Если ключа нет — поведение как сейчас (без трассировки: нет сообщений пользователю и нет дополнительной записи ЖР по маршруту).
- При `Истина`: строится JSON, **показывается пользователю**, в ЖР пишется **только сводка**.

### 6.4. Журнал и длина текста

- **Не** использовать журнал регистрации для хранения полного JSON и **не** дробить JSON на несколько записей ЖР.
- Комментарий сводки уложить в разумную длину (одна строка или несколько коротких предложений), без вложения `rows`.

### 6.5. Вызывающая обработка и клиент

- Не менять формы текущей обработки под трассировку. Если в будущем вызов выполняется без клиентской сессии, сообщения пользователю могут быть не видны — вне текущего ТЗ; сейчас сценарий только интерактивный клиент.

## 7. Критерии приемки

1. При `ЛогироватьМаршрутКотировки = Истина` после расчета пользователю показано минимум одно сообщение, содержащее сериализованный JSON (или несколько сообщений — части одного JSON с явными пометками).
2. В журнале регистрации есть **ровно одна** (на сеанс) информационная запись о факте вывода трассировки со **кратким** комментарием; в комментарии **нет** полного JSON.
3. На формах обработки не появились новые реквизиты и элементы для трассировки.
4. Для тестового набора из 3 бумаг (ММВБ успех; только НРД; нерассчитанная) в показанном JSON видны **разные** последовательности `code`, отражающие фактический путь.
5. При `Ложь` — нет сообщений трассировки и нет дополнительной записи ЖР по маршруту (кроме уже существующих логов почты/ошибок).
6. Регрессия: числовые поля `ТаблицаКотировок` совпадают с эталоном до внедрения.
7. Коды из п. 5 документированы в комментарии в начале области `СлужебныеПроцедурыИФункции` или в отдельной функции `КаталогКодовМаршрута()`.

## 8. Опциональные расширения

- Колонка `ТаблицаКотировок.МаршрутJSON` или `МаршрутКодов` — только если понадобится без копирования из сообщения; в текущем ТЗ не требуется.
- Передача JSON вызывающей обработке через расширение возвращаемой структуры — только по согласованию с её кодом.

**Не использовать** регистр «Замеры» базовой конфигурации для хранения данного JSON: семантика замеров другая; при необходимости хранения в базе проектируется отдельный объект конфигурации вне этого ТЗ.

## 9. Ориентиры по текущему файлу (для исполнителя)

- Цикл по активам и вызовы уровней: `ТекущиеКотировкиПоПравилу`, строки ~93-118.
- Уровень 1: `ЦенаАктиваУровень1` ~505-556; `КотировкаПоВыбПолю` ~728-785.
- Уровень 2: `ЦенаАктиваУровень2` ~559-726.
- Уровень 3: `ЦенаАктиваУровень3` ~788-1015.
- `Возврат` результата: ~256-257.
