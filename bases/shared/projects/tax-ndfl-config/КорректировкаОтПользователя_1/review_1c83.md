## 1. Соответствие модели данных рекомендациям БСП / стандартам 1С

### 1.1 Регистры сведений vs регистры накопления — оценка

| Объект из ТЗ | Тип в ТЗ | Тип по рекомендациям | Оценка |
|---|---|---|---|

| `МатрицаСтавокИКБК` | РегистрСведений | Периодический РегистрСведений | OK, см. выше |
| `МатрицаСальдирования` | РегистрСведений | Периодический РегистрСведений | OK |
| `СрокиПеречисленияНалога` | РегистрСведений | Независимый РегистрСведений | OK |
| `ОперацииКлиентовДляНДФЛ` | РегистрНакопления «Остатки и обороты» | **Регистр накопления «Обороты»** | ⚠ Спорно — см. ниже |
| `ИсчисленныйНДФЛ` | РегистрНакопления «Обороты» | OK | OK |
| `УдержанныйИВозвращённыйНДФЛ` | РегистрНакопления «Обороты» | OK | OK |
| `ИзлишнеУдержанныйИНеудержанныйНДФЛ` | РегистрНакопления «Обороты» | OK | OK |
| `ЖурналРасчётаНДФЛ` | РегистрСведений | Независимый РегистрСведений | OK |
| `ЖурналКонтрольныхСверок` (новый, раздел 14) | РегистрСведений | Независимый, подчинённый регистратору | **OK** |

**Замечание 1 (важно).** Регистр `ОперацииКлиентовДляНДФЛ` объявлен как «Остатки и обороты»,
но в ТЗ нигде не используется концепция «остатков» (нет натурального актива/обязательства,
которое нужно сальдировать накопительно). Правильный тип — **«Обороты»**: операции — это
факт совершения, а не «остаток к моменту». Замена на «Обороты» уменьшит время записи и
объём таблицы итогов в БД примерно вдвое.

**Замечание 2.** Для версионирования нормативов лучше использовать **стандартный механизм
«Периодического регистра сведений»** (периодичность «День» или «Год») вместо отдельного
измерения `ВерсияНормативов`. Это даст:
- встроенный метод `Срез последних на ДатуПериода` без явных фильтров по версии;
- автоматическую блокировку перекрытия периодов;
- стандартный паттерн БСП для нормативно-справочной информации (НСИ);
- меньше кода в общих модулях.

С учётом ответа на открытый вопрос №1 (несколько редакций в одном периоде не нужны)
**периодичность «Год»** достаточна.

### 1.2 Справочники vs планы видов характеристик

Все нормативные справочники (`КодыДоходовНДФЛ`, `КодыВычетовНДФЛ`, `КодыКБК_НДФЛ`,
`КодыУбытковДляОтчётности`) — справочники с фиксированной структурой реквизитов. Это правильный
выбор: **план видов характеристик не нужен**, потому что нет «дополнительных свойств»,
определяемых пользователем.

Для нового **справочника «КодыКонтрольныхСверок»** (раздел 14) рекомендую сделать его
**предопределённым**: 67 элементов КС-01 … КС-67 описываются в конфигураторе как
«ПредопределённыеЭлементы». Это даёт:
- надёжную ссылку из кода (`Справочники.КодыКонтрольныхСверок.КС_30`);
- защиту от случайного удаления;
- сохранность ссылок при обновлении.

## 2. Управляемые формы: разделение клиент / сервер

### 2.1 Что хорошо

- В ТЗ не описано бизнес-логики «на клиенте», что соответствует правильному паттерну
  (вся логика — на сервере).
- Документ «РасчётНДФЛЗаПериод» как единый регистратор соответствует стандарту 1С.
- Пользовательская загрузка (FR-02, правка №2) предполагается «в одной форме» — это разумно.

### 2.2 Риски / на что обратить внимание

**R-1. Циклы по физлицам на клиенте — недопустимо.**
В алгоритме ALG-01 пайплайн расчёта явно итерирует по физлицам (шаг 1). В реализации
**весь цикл должен быть на сервере** в общем модуле `СерверныйВызов.МодульРасчётаНДФЛ`.
Серверный вызов на каждой итерации цикла («1 клиент = 1 серверный вызов») недопустим
при объёме ≈ 100 000 физлиц.

**R-2. Загрузка операций — пакетами, не по одной.**
HTTP API `POST /api/v1/operations/upload` принимает массив `operations`. На стороне 1С
обработка должна:
1. Получить весь массив за один HTTP-вызов.
2. Открыть транзакцию.
3. В цикле создавать `НаборЗаписей.Добавить()` без записи.
4. Один `НаборЗаписей.Записать()` в конце транзакции.

Иначе при пакете 10 000 операций будет 10 000 транзакций — нагрузочный сценарий не пройдёт.

**R-3. Пользовательская массовая загрузка (правка №2).**
Если пользователь загружает Excel-файл с 50 000 строк, нельзя делать модальный «прогресс»
на клиенте с серверным вызовом на каждую строку. Решение:
- запуск через **фоновое задание** (`ФоновыеЗадания.Запустить()`);
- состояние прогресса в регистре сведений `ФоновыеЗадачиЗагрузки`;
- форма опрашивает прогресс через `ОбработкаОжидания` (не серверный вызов!) с интервалом 5 сек.

**R-4. Форма документа «РасчётНДФЛЗаПериод».**
В реквизитах формы не должно быть выгруженных в память больших таблиц значений
(результат расчёта по 100 000 физлиц). Реализация:
- хранить только идентификатор документа и сводку (количество, статус, ошибки КС);
- детализация — в регистрах, читается по требованию через `Расшифровка`.

## 3. СКД для отчётности (6-НДФЛ, Приложение 1, Справка, Журнал КС, Реестры)

### 3.1 Рекомендации

**6-НДФЛ Раздел 2** — отчёт на СКД с обязательными параметрами:
- `НалоговыйПериод` (Год);
- `КварталОтчёта` (1 / Полугодие / 9 мес. / 12 мес.);
- `Контур` (Обычный / ИИС);
- `Ставка` (множественный выбор);
- `КБК` (множественный выбор).

Структура отчёта — наборы данных:
1. Запрос «Итоги по ставкам и КБК» (источник: `РегистрНакопления.ИсчисленныйНДФЛ.Обороты`).
2. Запрос «Удержанный и возвращённый» (источник: `РегистрНакопления.УдержанныйИВозвращённыйНДФЛ.Обороты`).
3. Связь по `(Ставка, КБК)`.

**Приложение 1 (по физлицу)** — отдельный отчёт СКД с параметром `Физлицо` (обязательный)
и группировками: Раздел 2 → Раздел 3 → Сведения о доходах и вычетах по месяцам → Раздел 4.

**Реестры Приложений №1 / Справок (правка №8)** — два отчёта СКД с одинаковым набором
показателей (см. таблицу в 10.4) и фильтрами:
- `НалоговыйПериод`, `Контур`, `Источник`, `СтатусНалогоплательщика`, `Ставка / КБК`.

**Журнал КС (раздел 14)** — отчёт СКД на регистре `ЖурналКонтрольныхСверок`:
- группировки: «Уровень» → «Группа КС» → «Код КС» → «Физлицо»;
- расшифровка двойным кликом на строку — открытие физлица или операции (через
  `ПолеТабличногоДокумента.ОбработкаРасшифровки`).

### 3.2 Что не сделать на СКД

**Раздел 1 6-НДФЛ** — табличный документ + СКД-набор данных, но **печать через
макет ФНС**. Свободная вёрстка СКД здесь приведёт к неприёмлемой ФНС форме.
Принцип: СКД формирует структурированный набор данных, шаблон макета — табличный документ
с областями, заполняемыми через `ПолучитьОбласть(...).Параметры.КБК = Данные.КБК`.

## 4. Производительность

### 4.1 Целевая нагрузка (после правки №10)

- 100 000 физлиц за период.
- ≤ 30 минут на расчёт (NFR-01, подтверждён ответом на ОВ №5).
- Параллелизация ≥ 8 потоков (NFR-02).

### 4.2 Что под угрозой

**Гросс-ап 1010 + ЗНП**. После правки №3 алгоритм гросс-апа в 1С НП **не выполняется
автоматически**: данные приходят уже разнесёнными по ставкам. Это **сильно упрощает**
производительность, потому что не нужно делать рассчётный шаг с округлением для каждого
физлица. **Эффект: положительный, режим 30 минут реалистичнее.**

**Сальдирование (ALG-02)**. Это самая «дорогая» операция, потому что:
- требует группировки по физлицу;
- РЕПО (1537 → 1530 + 1531) требует пропорционального распределения;
- очерёдность (1532 → 1535 → 1530) требует последовательных шагов.

Реализация **обязательно**:
- запрос с временной таблицей «ТЗ_ГруппыПоФизлицам» (1 запрос на весь портфель);
- цикл по физлицам в одном потоке выполняет шаги сальдирования над `ТаблицаЗначений`
  в памяти (без обращения к БД на каждой итерации);
- одна транзакция на физлицо при записи результатов.

**Параллелизация (NFR-02)**. Реализация через `БиблиотекаСтандартныхПодсистем.ФоновыеЗадания`:
1. Разбиение портфеля на N батчей (по 12 500 физлиц при N=8).
2. Запуск N фоновых заданий, каждое со своим параметром «отбор по физлицам».
3. Менеджер ожидает завершения всех, агрегирует ошибки.

⚠ **Важно**: каждое фоновое задание создаёт **собственное соединение с БД**. Контроль
сериализации — через **блокировку** регистра `ИсчисленныйНДФЛ` по диапазону физлиц,
иначе возможен deadlock при пересечении.

### 4.3 КС — отдельный риск производительности

В разделе 14 описано 67 КС. **Если выполнять КС последовательно на каждом физлице после
расчёта** — это +67 запросов на физлицо × 100 000 физлиц = 6,7 млн запросов. **Недопустимо.**

**Правильно**:
1. КС-25 … КС-33 (внутри Приложения №1 по физлицу) — один общий запрос с
   агрегатными вычислениями и `ВЫБОР КОГДА ... ТОГДА Ошибка КОНЕЦ`, возвращающий все КС
   разом по одному физлицу. Ожидаемая стоимость: 1 запрос на физлицо.
2. КС-34 … КС-44 (между Разделом 2 и Приложениями №1) — **глобальные**, 1 запрос на весь
   период, выполняется один раз после сборки 6-НДФЛ.
3. КС-01 … КС-24 (между Разделом 1 и Разделом 2) — **глобальные**, выполняются на готовых
   итогах отчётов, 1 запрос на пару (Период, КБК).
4. КС-55 … КС-63 (поля физлица) — реализуются как **проверки при загрузке операций**,
   а не на этапе формирования отчёта. Это разово при FR-02.

**Рекомендация**: вынести КС в **общий модуль «МодульКонтрольныхСверок»** с тремя точками:
`ВыполнитьКСПриЗагрузке`, `ВыполнитьКСПоФизлицу(...)`, `ВыполнитьГлобальныеКС(...)`.

### 4.4 Индексация регистров

Для нагрузочного сценария **обязательно**:
- Все измерения регистров оборотов индексировать.
- Регистр `ЖурналКонтрольныхСверок` должен иметь индексы по `(Расчёт)` и `(КодКС)` —
  иначе фильтрация по коду КС в отчёте будет полным сканом.
- Регистр `ОперацииКлиентовДляНДФЛ`: дополнительный индекс по `(Клиент, КодДохода, Период)`.

## 6. Интеграции (HTTP-сервисы, JSON / XDTO, CFE)

### 6.1 HTTP-сервисы 1С

Контракт `POST /api/v1/operations/upload` в 10.2 описан в JSON. **На стороне 1С**:
- HTTP-сервис с шаблоном URL `/api/v1/operations/upload`;
- метод POST;
- обработчик возвращает JSON-ответ `{ "status": "OK", "batchId": "...", "loaded": N, "errors": [...] }`;
- разбор тела запроса через `ПрочитатьJSON()` в общем модуле «ОбменОперациями».

### 6.2 XDTO vs JSON

> **Уточнено в раунде 2.** Аргумент «источники не на 1С» снят как ошибочный
> (см. 6.3 и правку R2-1 в HTML — все источники на 1С). Текущая рекомендация остаётся,
> но мотивация другая.

Для **простых пакетов операций** (правка №2) — **JSON предпочтительнее**, потому что:
- ~~источники не на 1С (`Аванкор FIN`, `Аванкор PIF`);~~ *(снято)*
- JSON-контракт проще отлаживать и логировать (читаемый формат);
- XDTO избыточен для плоского массива операций;
- унифицированный контракт легче переиспользовать (например, для будущего ручного импорта).

Для **выгрузки в EnterpriseData** между 1С НП и источниковыми конфигурациями (все на 1С) —
XDTO / планы обмена остаются валидным вариантом, особенно для синхронизации общих НСИ
(см. R2-1, раздел 10.5).

### 6.3 CFE-расширения источников

> **Исправлено в раунде 2.** Прежняя формулировка этого пункта была ошибочной (см.
> зачёркнутый текст ниже). По уточнению пользователя и `bases/BASES_GLOSSARY.md`,
> **«Аванкор FIN» и «Аванкор PIF» — это конфигурации линейки «1С Аванкор»**
> (вендор ООО «Аванкор», платформа 1С:Предприятие 8.3). См. правку R2-1 в HTML.

После правки №2 источники — `1С ИЦ`, `Аванкор FIN`, `Аванкор PIF` — **все на платформе
1С:Предприятие**:

- `1С ИЦ` — конфигурация «ИнвестиционныйЦентр», вендор ООО «СБ-Брокер».
- `Аванкор FIN` — конфигурация «ДУ» / «ДУ ред. 2» линейки «1С Аванкор», вендор ООО «Аванкор».
- `Аванкор PIF` — конфигурация для ПИФ линейки «1С Аванкор», вендор ООО «Аванкор»
  (в перспективе разделяется на ЗПИФ и ОПИФ).

**Следствие.** **CFE-расширения 1С применимы ко всем трём источникам** единообразно
(тонкие расширения для выгрузки операций без модификации основной поставки вендора).
Помимо HTTP-сервисов 1С, допустимы план обмена / EnterpriseData для синхронизации НСИ
(справочник «Физлица»).

  через план обмена).

### 9.3 Что разумно вынести в `СерверныйВызов`-модули

- `СерверныйВызов.МодульРасчётаНДФЛ` — главный движок (вызывается из документа-регистратора).

(он не нужен).

### 9.4 «Опасные» места после правок

**Правка №3 (дивиденды без гросс-апа)** — теряем гросс-ап как локальную операцию, но
теперь обязаны:
- проверять КС-32 (исчисленный = удержанный + ...) с учётом ЗНП из источника;
- доверять разбивке источника. Если источник передаст «дивиденды 1010, ставка 13 %» с
  ошибкой (например, превышение 2,4 млн ушло в 13 %, а не в 15 %), 1С НП не сможет это
  поймать. **Добавить контрольную сверку «согласованность сумм 1010 по двум ставкам
  с прогрессивной шкалой»** — это новая КС, не из Excel.

**Правка №2 (массовое удаление)** — высокий риск ошибки оператора. **Обязательно**:
- двойное подтверждение;
- логирование операции в журнал регистрации с уровнем «Предупреждение»;
- возможность отката за последние 24 часа (резервный регистр «УдалённыеОперации»).
