# IMDEV-9749. Перенос доработки исполнения сделок из расширения в cf - задание

Промт на будущее. Запускать, когда пользователь предоставит актуальную cf вендора (выгрузку или файл .cf).
До этого момента доработка живет в расширении `FO_DealExecutionParallel`, cf не трогать.

## Промт

> IMDEV-9749: перенеси доработку параллельного исполнения сделок из расширения `FO_DealExecutionParallel`
> в предоставленную cf ФО `<путь к cf или выгрузке, версия>`. Исходник доработки - сборка расширения
> `Расширения/1.4.10.2/FO_DealExecutionParallel` (если версия cf новее 1.4.10.2 - сначала сверь перехват,
> см. шаг 1). Задание и состав переноса - файл `Перенос в cf - задание.md` в папке задачи. Сначала покажи
> план и результат сверки версий, переноси после согласования.

## Что переносится

### 1. Обработка «Групповое исполнение сделок», модуль объекта

Источник: `Расширения/1.4.10.2/FO_DealExecutionParallel/DataProcessors/ГрупповоеИсполнениеСделок/Ext/ObjectModule.bsl`.

- Процедура `СоздатьДокументыИсполнения`: цикл `Для Каждого Стр Из Сделки ... КонецЦикла` (блок `#Удаление`
  перехвата) заменяется строкой `ТекстОшибкиИсполнения = ИсполнитьСтрокиСделок(ДатаДокумента, СозданныеДокументы);`;
  в конце процедуры, после замеров и `АдресРезультата`, - вызов исключения, если `ТекстОшибкиИсполнения`
  заполнен (блоки `#Вставка`). Замеры производительности вендора сохраняются как есть.
- Экспортная процедура `ПровестиПорциюИсполнения(Параметры, АдресХранилища)` - тело фонового потока, в область
  `ПрограммныйИнтерфейс`.
- Служебные методы области `ПараллельноеИсполнениеСделок` - переносятся целиком, с шапками:
  `ИсполнитьСтрокиСделок`, `ПровестиСтрокиИсполнения`, `РазложитьПоПотокам`, `ПровестиПорцииВФоне`,
  `ОшибкаЗавершенияПотока`, `ИтогиПотоков`, `ПересчитатьПоручения`, `ЗаписатьОшибкиИсполнения`,
  `СтрокиСделокДляПроведения`, `ПорученияСделок`, `КоличествоПотоковИсполнения`, `ЭтоКоллизияНомера`,
  `ИмяСобытияИсполнения`.
- В cf перехватчика нет: `&ИзменениеИКонтроль`, `#Вставка`/`#Удаление` и имя `FO_DealExecutionParallel_...`
  не переносятся, правка вносится прямо в процедуру вендора.

### 2. Константа `КоличествоПотоковИсполненияСделок`

- Тип «Число (2,0)», синоним «Количество потоков исполнения сделок», по образцу `ПотоковНаСеансПроверкиЛимитов`
  (источник описания: `Расширения/1.4.10.2/FO_DealExecutionParallel/Constants/КоличествоПотоковИсполненияСделок.xml`,
  uuid в cf - новый).
- Смысл: пусто, 0 и 1 - проведение в одном сеансе (с одним пересчетом поручений в конце); 2 и больше - число
  фоновых потоков. Рекомендуемое значение 6.
- Права: роль «Полные права» конфигурации получает константу флажком «Устанавливать права для новых объектов»;
  другим ролям права не нужны (код читает константу в привилегированном режиме). Проверить, что флажок у роли
  в новой cf по-прежнему включен.

### 3. Поле на панели «Общие настройки учета» (в расширении его нет, добавляется только в cf)

Форма `Обработка.ПанельАдминистрированияАванкор.Форма.ОбщиеНастройкиУчета`.

- Поле ввода `КоличествоПотоковИсполненияСделок`, путь к данным `НаборКонстант.КоличествоПотоковИсполненияСделок`,
  сразу после поля `КоличествоПотоковДляПроверкиЛимитов` (группа `ГруппаОбщиеНастройкиПодсистемыЛимитов`).
- Заголовок «Количество потоков исполнения сделок», высота заголовка 2 (как у соседнего поля).
- Подсказка: «Сколько фоновых потоков проводят документы ночного исполнения сделок. Пусто, 0 или 1 - проведение
  в одном сеансе; рекомендуется 6.»
- Обработчик `ПриИзменении` - `КоличествоПотоковИсполненияСделокПриИзменении(Элемент)` в модуле формы, тело:
  `КонстантаПриИзменении(Элемент);` - как у остальных констант панели.

### 4. Что НЕ переносится

- Заимствованные объекты расширения (справочники, документ «Сделка», перечисления, определяемый тип, реквизиты
  табличной части `Сделки`) - нужны были только расширению.
- Само расширение после установки cf с доработкой с базы снимается, иначе перехват наложится на уже измененную
  процедуру.

## Порядок работы при переносе

1. **Сверка версий.** Если cf новее 1.4.10.2 - `/cfe-patch-method -Check` расширения 1.4.10.2 против выгрузки
   новой cf: процедура `СоздатьДокументыИсполнения` не должна измениться. Если изменилась - показать разницу
   пользователю до переноса. Сверить и зависимости: флаг `ДополнительныеСвойства.ОбновитьДанныеИсполнения`
   в модуле документа «Исполнение по сделке», `РегистрыСведений.РасширенияПоручений.ОбновитьДанныеИсполнения(Поручения, ...)`,
   `ДлительныеОперации.ВыполнитьПроцедуруМодуляОбъектаОбработки`, панель «Общие настройки учета».
2. **Нет ли уже константы у вендора.** Если в новой cf есть своя константа числа потоков исполнения - взять ее,
   свою не добавлять.
3. **Маркеры правок.** Стиль маркеров в правке кода вендора согласовать с пользователем до переноса
   (в своих обработках - `//++ IMDEV-9749` / `//-- IMDEV-9749` без закомментированных старых строк).
4. **Перенос** в выгрузку cf в папке задачи (`TestProject`), не в `WORK` и не в `WIM_DEV`.
5. **Проверка:** валидация выгрузки (`/cf-validate`, `/form-validate`), загрузка в тестовую базу, синтаксический
   контроль, затем на DEV ФО (с той же версией cf, расширение `FO_DealExecutionParallel` снято):
   - малый набор стенда `Скрипты/run_bench_parallel.py` (`prepare smoke`, `run A`) при константе 0, 1 и 6:
     в журнале регистрации «потоков 1 / 1 / 6», снимки совпадают со снимком старого кода
     (`Тестирование/reports/bench_parallel_snapA_20261101_072841.txt`; номера сделок старого снимка
     `TPAR-00005-` и `TPAR--` приводить к `TPAR-00005-0000` и `TPAR-00000-0000`);
   - поле на панели видно пользователю с «Полными правами», значение записывается и читается после повторного
     открытия;
   - сценарии РЕПО, заполнения по сумме и двух портфелей - `Скрипты/run_bench_risks.py`
     (`Тестирование/regression-risk-scenarios.md`).
6. **Итог:** cf (или пакет изменений для Конфигуратора, `/1c-change-package`) и короткое описание правок для
   вендора; приложить результаты проверки.

## Факты, которые не нужно переисследовать

- Логика и результаты: `README.md` (раздел «Расширение FO_DealExecutionParallel»), отчеты в `Документация/`.
- Перехват одинаков по логике для 1.4.9.5, 1.4.10.0 и 1.4.10.2; в 1.4.10.0 и новее в процедуре есть замеры
  производительности вендора.
- Автонумерация документа «Исполнение по сделке» при параллельной записи изредка дает «Номер не уникально» -
  повтор записи новым объектом до 5 раз обязателен (на Т-1 в рознице было 2 повтора).
- Ожидание потоков - без ограничения времени (решение пользователя 01.11.2026).
