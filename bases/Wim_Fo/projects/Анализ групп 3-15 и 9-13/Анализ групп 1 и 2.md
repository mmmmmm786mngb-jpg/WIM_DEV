## Группа 1

### Строка 3. Установка лимитов: распространение правил на новых клиентов

**Как работает.** `внОперацииПослеОбмена.ВыполнитьОбработку` после обмена (признак `ТребуетсяРаспространениеПравил`)
вызывает `ВыполнитьРаспространениеПравилПослеОбмена`. Для каждого класса лимитов (в рознице два: комплаенс и
риски, в обычном ФО - один):

1. `НайтиНовыхКлиентовРозничногоДУ` / `НайтиНовыхКлиентов` - запрос по всем портфелям нужных типов клиентов без
   даты автоустановки, с эталонным портфелем по внешнему коду и его действующей `УстановкаЛимитов`.
2. Для каждого найденного портфеля: 2-3 записи `ДополнительныеСведения` (дата автоустановки, эталонный портфель,
   внешний код), затем `СоздатьУстановкиЛимитов`:
   - два запроса к срезу `ДействующиеЛимитыПоПортфелю` и `ПолучитьПорогиЛимитовЭталонногоПортфеля`;
   - запись `ПорогиЛимитов` по каждому лимиту без действующего порога (в рознице с `ОбменДанными.Загрузка`);
   - создание и проведение документа `УстановкаЛимитов` (проведение вендорское);
   - признак стратегии, дата распространения, "лимиты заведены" - еще 2-3 записи `ДополнительныеСведения`;
   - **отдельное письмо с вложением XLS на каждую пару портфель+класс** (`РассылкаСообщения` внутри
     `СоздатьУстановкиЛимитов`, стр. 1145).
3. Итоговое письмо по классу.
4. В рознице после метода - фоновое задание `ВыполнитьЗаписьВерсийЛимитов`.

**Замеры ПРОД (розница 19.10).** 42 запуска, 349 с за день, 10.1-24.2 с на запуск, 4-10 пар портфель+класс за
запуск (2-5 новых клиентов). Шаги: `СозданиеУстановок` 266.5 с на 172 пары (~1.55 с на пару),
`ПоискНовыхКлиентов` 46.6 с на 84 поиска (~0.55 с), итоговая `Рассылка` 31.6 с на 84 письма (~0.38 с).
Обычный ФО 19.10: 16 запусков, из них 3 с клиентом, каждый ~24 с на **одного** клиента одного класса
(`СозданиеУстановок` 23.5 с) - в 15 раз медленнее розницы на пару, причину надо смотреть отдельно
(число лимитов эталона, проведение, письмо `РассылкаОбУспешномАвтораспространении`).

**Оценка.** Узким местом не является: запуск укладывается в 10-25 с между обменами. Риск - массовое заведение
клиентов: 1000 новых клиентов в рознице = 2000 пар x 1.55 с = ~52 мин в сеансе обмена.

**Резервы.**

### Строка 15. Исполнение сделок, 23:55

**Как работает.** Регламентное задание `АванкорИсполнениеСделок` -> `АванкорВыполнениеРегламентныхЗаданий.ИсполнениеСделок`
-> `ГрупповоеИсполнениеСделок.СоздатьДокументыИсполнения(Истина)`:

1. `ЗаполнитьТаблицуСделок`: `ПлановаяПозиция.Остатки(КонецДня, ИСТИНА)` - остатки плановой позиции по ВСЕМ
   портфелям во временную таблицу, затем соединение с `Документ.Сделка` по `ДатаПоставки = &Дата`
   (реквизит `ДатаПоставки` не индексирован) и разыменование `Сделки.Поручение.Биржа.Внебиржевая`.
2. Цикл по строкам (строка = остаток плановой позиции по сделке: бумага или деньги, на сделку минимум 2 строки):
   создание и проведение `ИсполнениеПоСделке`. Проведение каждого документа:
   - очистка движений `ПлановаяПозиция` и запрос остатка по сделке;
   - движения `ПлановаяПозиция`, `ЗадолженностьПоБумаге`/`ЗадолженностьПоВалюте`, `СделкиДляОбмена` (с текстом XDTO);
   - `ОбновитьДанныеИсполнения`: `Движения.Записать()` + `РасширенияПоручений.ОбновитьДанныеИсполнения(поручение)`
     с `СтатусыПоручений.ОбработатьРасчетныеСтатусыРасш` - **на каждый документ**, то есть по одному поручению
     2 и более раз за ночь.
3. Один поток, без `Попытка` вокруг проведения.

**Замеры.** На ПРОД данных нет. В 1.4.9.5 замера нет, FO_KeyOpsPerf на ПРОД не установлен (ключей
FO_KeyOpsPerf нет в выгрузках 16-20.10). В 1.4.10.0 вендор включил замеры в базовый код (см. сводку, п. 2).

**Резервы (все - на стороне вендора, Аванкор).**

| # | Что | Эффект |
|---|---|---|
| 15.1 | Пересчет расширений и статусов поручений один раз в конце: в цикле передавать `ДополнительныеСвойства.ОбновитьДанныеИсполнения = Ложь` (точка уже есть в `ПередЗаписью`), после цикла один вызов `РасширенияПоручений.ОбновитьДанныеИсполнения(<все поручения>)` | Убирает 2+ пересчета на поручение; вероятно самый крупный резерв проведения |
| 15.2 | Отбор сделок по дате поставки - в параметры виртуальной таблицы (`Сделка В (ВЫБРАТЬ ... ГДЕ ДатаПоставки = &Дата)`), индекс по `Сделка.ДатаПоставки` | Не читать остатки по всем портфелям |
| 15.3 | Параллельное проведение по портфелям в фоновых заданиях (как в постконтроле) | Строки разных портфелей независимы |

**Дефект надежности.** Исключение при проведении одного `ИсполнениеПоСделке` (например, конфликт блокировок с
ночными заданиями) прерывает цикл: остальные сделки дня остаются неисполненными до ручного запуска.
Предложение вендору: `Попытка` на документ, запись в ЖР, продолжение цикла.

**Что сделать сейчас.** До 1.4.10.0 длительность можно оценить по ЖР ПРОД: событие "Аванкор. Исполнение сделок"
(старт) и последнее проведение `ИсполнениеПоСделке` в ту же ночь; объем - число документов за дату.

### Строка 9. Загрузка депозитов, 05:00

**Как работает.** Команда `ФоновоеВыполнение`:

1. `ЗаполнитьДепозиты` (шаг 98-99% времени):
   - ДУ: `Новый WSОпределения` + `getDeposits(ДатаЗапроса)` веб-сервиса `deposits` базы ДУ;
   - ПИФ: то же для базы ПИФ;
   - Calipso: SQL-запрос через ADODB к `AMDBRATES\DBMVTBAM01` (тайм-аут команды 30 с);
   - на каждый депозит: `Валюты.НайтиПоНаименованию`, для ДУ `НайтиПортфель` (`КодПортфеля ПОДОБНО "%..%"` по
     всем портфелям), `НайтиМестоХранения` (`ДополнительныеСведения` по `Свойство` + `Значение`, `Значение` не
     индексировано), `НайтиСубПортфель`; для Calipso `НайтиСубПортфельПоМаске` (`КодСчета ПОДОБНО "%..%"`).
2. `ОбновитьФактическуюПозицию`: ставка в `БанковскиеСчета` и запись `ВТБ_ФактическаяПозицияДепозитов` по одному
   депозиту, удаление депозитов, которых нет в источниках, постановка пересчета РСА в фон, `Пауза(10)`, постановка
   рассылки по пересчету.
3. Письмо.

**Где время.** Шаг `ЗаполнитьДепозиты` замеряется целиком, поэтому разделение - вывод, а не измерение:

- Длительность почти одинакова в рознице (сопоставление ничего не находит) и в обычном ФО (находит 108),

- Calipso ограничен тайм-аутами 15 + 30 с.
- `getDeposits` ДУ (`WebServices/deposits`, `ЗаполнитьНачальныйНоминал`): выборка из ТАБЛИЦЫ движений
  `РегистрНакопления.ДенежныеСредстваУправленческий` с `Период < &ДатаЗапроса` без начальной даты и с отбором через
  разыменование `ВЫРАЗИТЬ(АналитическийСчет.МестоХранения КАК Справочник.БанковскиеСчета) В (&СписокСчетов)` -
  проход по всей истории движений денег ДУ. Плюс остатки с условием через разыменование в параметрах.

**Дефекты и риски.**

- **В рознице каждый день ставится пересчет РСА по всем портфелям с признаком пересчета.** Портфелей с депозитами
  0, `МассивПортфелей` пустой, `ПоВсемПортфелям = Ложь`; обработка пересчета
  (`внПерерасчетСтоимостиФактическойПозицииИ_РСА_СЧА` 1.18, `ВыполнитьПерерасчет`) при пустом массиве берет
  `ПолучитьСписокПортфелей()` - все портфели с `ПризнакДляПерерасчетаПортфеля = Истина`. То, что пауза 10 с в
  рознице есть (шаг 11.4 с), значит обработка пересчета в настройках розницы указана. Надо проверить на ПРОД,
  сколько портфелей пересчитывается в 05:12 и сколько это длится (лог пересчета в регистре).
- Сбой одного источника удаляет его депозиты из ФО за дату: `ПолучитьДепозитыФО_КУдалению` удаляет все записи
  `ВТБ_ФактическаяПозицияДепозитов`, которых нет в ответе. Если ДУ не ответил, удаляются все депозиты ДУ; если
  не ответил никто - все депозиты за дату (отмечено и в IMDEV-9530).
- Calipso: найденный депозит с ненулевыми процентами будет удален сразу после записи. В регистр пишется
  `Стоимость = Qty`, а сравнение для удаления идет по `РыночнаяСтоимость` (MV), соединение по
  `Субпортфель И Стоимость`. Сейчас не проявляется: все 12 депозитов Calipso не сопоставляются ни в одной базе.
- Учетные данные SQL Server и веб-сервисов ДУ/ПИФ заданы в коде (отмечено в IMDEV-9530).

### Строка 13. Загрузка неторговых поручений РОСТ, каждые 10 минут

**Как работает.** Команда `ФоновоеВыполнение` в рабочий день биржи:

1. `ПроверитьОбновитьСтатусДСВыведены` - статусы портфелей "подано поручение на вывод" старше 30 мин переводит в
   "ДС выведены".
2. `ПолучитьСуммуДСБрокер` - позиция по брокерскому счету через адаптер FIX (внешний вызов).
3. `ПолучитьСуммуКупоны`, `ПолучитьСуммуСделкиПродажи`, `ПолучитьСуммуСделкиПодПокупки` - запросы для расчета
   свободного остатка.
4. `ПолучитьПортфелиДляСозданияПоручений` - портфели в статусах "ожидание ДС" и "ДС отправлены брокеру".
5. По каждому такому портфелю - вызов `GetAgreementAmount` сервиса 1С:ДО; при сумме > 0, деньгах на брокерском
   счете и достаточном остатке - в транзакции поручение `Ввод` (проведение), `РегистрРСА_СЧА`,
   `ДатаАктуальностиФактическойПозиции`, статус и признаки в `ДополнительныеСведения`.
6. Письмо, если есть поручения или ошибки.

**Замеры ПРОД (розница 19.10).** 52 запуска, 260.6 с за день, в среднем 5 с, максимум 35.6 с.
`СозданиеПоручений` 193.5 с на 121 поручение; пустой запуск 5-7 с; 42 поручения - 27.8 с (~0.55 с на поручение).
`Рассылка` обычно 0.5-6 с, один раз 30.1 с (почтовый сервер).

**Оценка.** Узким местом не является: 5 с работы на 10-минутное окно.

**Резервы.**

| # | Что | Эффект |
|---|---|---|
| 13.1 | Удалить вызов `ПолучитьСуммуКупоны` (стр. 595): результат `СуммаПогашенногоКупона` нигде не используется, а запрос группирует `ФактическаяПозиция` за день по всем портфелям и читает купонное расписание | Часть постоянных 5-7 с каждые 10 мин; без изменения результата |
