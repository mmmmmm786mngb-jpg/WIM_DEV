Блокировки занижают стоимость портфеля в воркбенче — причина и исправление

IMAPPS-37889 ФО Дата: 03.07.2026 | База: ФО | Инструмент: Воркбенч | Автор анализа: разбор исходников + арифметика из обращения

Вывод в одну строку: одна и та же блокировка учитывается в итоговой стоимости дважды (и в «количестве», и в «стоимости брокерского учёта»), поэтому из портфеля вычитается 2×20 млн = 40 млн вместо 20 млн — отсюда отрицательная «Стоимость, общая по владельцу».
Важное уточнение (задваивается НЕ у всех клиентов): двойной счёт возникает только тогда, когда специальная корректировка ВТ_Корректировка не срабатывает и не «снимает» денежное количество прогнозной позиции. Для части клиентов она срабатывает — и тогда блокировка учитывается корректно (один раз). Условия, при которых возникает ошибка, разобраны в разделе 7.

2. Доказательство причины на цифрах бизнеса

Возьмём только два числа, которые пользователь видит в одной строке (профиль RUB, с блокировкой):

Сумма факт. = 30 512 322,63
Стоимость, общая по владельцу = -9 489 323,91
Разница = 30 512 322,63 − (−9 489 323,91) = 40 001 646,54 руб.

А блокировка = 20 000 000, значит 40 001 646,54 ≈ 2 × 20 000 000.

То есть между «фактом» и «общей по владельцу» разница ровно в две блокировки, а не в одну. Остаток 1 646,54 руб. — это прочие составляющие портфеля (НКД, задолженность, округления), которые в норме и так дают небольшую разницу между этими колонками.

Как должно быть

Ожидаемо: общая по владельцу = Сумма факт. − одна блокировка − прочее
= 30 512 322,63 − 20 000 000 − 1 646,54 = ≈ 10 510 676 руб.
Либо от «без блокировки»: 30 359 550,15 − 20 000 000 = ≈ 10 359 550 руб.

Правильное значение должно быть ≈ 10,4–10,5 млн руб. (положительное), а не −9,49 млн.

ДЛЯ РАЗРАБОТЧИКА

5. Точный механизм в коде

5.1. Формула ОбщаяСтоимость (то, что показывается как «общая по владельцу»)

Модуль CommonModule.ВоркбенчПолныеПрава, функция расчёта стоимостей портфелей (КэшСеансовПортфели.ОбщаяСтоимость), строки ~2350–2386:

// Количество: из позиции вычитаются "брокерские" части *_бр (стр. 2351-2353)
Количество = (КоличествоФактическаяПозиция  - КоличествоФактическаяПозиция_бр)
           + (КоличествоПлановаяПозиция      - КоличествоПлановаяПозиция_бр)
           + (КоличествоПрогнознаяПозиция     - КоличествоПрогнознаяПозиция_бр)

// Стоимость_бр: денежные "брокерские" суммы (стр. 2354-2355)
Стоимость_бр = ФактическаяПозиция_бр + ПлановаяПозиция_бр + ПрогнознаяПозиция_бр + СуммаРЕПО

// Итог для денег (ПризнакЭтоВалюта, Цена = 1), стр. 2382-2386:
ОбщаяСтоимость = СУММА( Цена * Количество + Стоимость_бр )   // = Количество + Стоимость_бр

Инвариант архитектуры _бр: если сумма попала в Стоимость_бр (как деньги), то соответствующее количество обязано быть вычтено из Количество через поле Количество…_бр. Иначе одна и та же величина попадёт в итог дважды.

5.2. Где инвариант нарушается для блокировок

Модуль CommonModule.РасчетПозицииПортфелей, процедура МодифицироватьПрогнозВоркбенч(), строки 1484–1517. Для блокировки (СуммаБлокировкаОстаток <> 0):

// стр. 1506-1515: СУММА блокировки кладётся в ПрогнознаяПозиция_бр  -> попадает в Стоимость_бр
"0 КАК ПрогнознаяПозиция_бр"  ->  ВЫБОР ... КОГДА Т.СуммаБлокировкаОстаток <> 0
                                        ТОГДА Т.СуммаБлокировкаОстаток   // = -20 000 000
                                  КОНЕЦ КАК ПрогнознаяПозиция_бр

// А вот КоличествоПрогнознаяПозиция_бр для блокировки НЕ заполняется — остаётся 0!
// При этом КоличествоПрогнознаяПозиция = КоличествоОстаток (движение блокировки) = -20 000 000

Корень проблемы: блокировка попадает в ПрогнознаяПозиция_бр (сумма, −20 млн), но КоличествоПрогнознаяПозиция_бр для неё остаётся 0. Поэтому:

  • в Количество блокировка входит через КоличествоПрогнознаяПозиция = −20 млн (не скомпенсирована);
  • в Стоимость_бр та же блокировка входит ещё раз через ПрогнознаяПозиция_бр = −20 млн.

Для денег (Цена = 1): ОбщаяСтоимость = Количество + Стоимость_бр получает −20 − 20 = −40 млн.

5.3. Сопутствующее наблюдение (не главная причина)

В МодифицироватьПрогнозВоркбенч два подряд СтрЗаменить по одной и той же подстроке "0 КАК КоличествоПрогнознаяПозицияОтправленные" (стр. 1486 и 1495). СтрЗаменить заменяет все вхождения, поэтому вторая замена (с веткой блокировки СуммаБлокировкаОстаток <> 0 → КоличествоБлокировкаОстаток) фактически не срабатывает — мёртвый код. На денежный итог это не влияет (поле «Отправленные» не участвует в формуле Количество), но стоит поправить заодно, чтобы не путало.

КЛЮЧЕВОЕ УТОЧНЕНИЕ

7. Почему задваивается только у части клиентов

Ошибка не универсальна — и это подтверждается кодом. Сумма блокировки всегда попадает в ПрогнознаяПозиция_бр (→ Стоимость_бр). А вот количество блокировки остаётся в Количество не всегда: есть отдельный запрос-корректировка ВТ_Корректировка, который в определённых случаях обнуляет денежную прогнозную позицию.

  • Корректировка сработала → количество блокировки убрано из Количество → блокировка учтена один раз (через Стоимость_бр) → цифры верные.
  • Корректировка не сработала → количество осталось в Количество И сумма в Стоимость_бр → блокировка учтена дважды → минус в портфеле.

7.1. Когда корректировка «снимает» количество (тогда всё правильно)

ВоркбенчПолныеПрава, формирование ВТ_Корректировка (стр. 199–213). Итог применяется в стр. 425/488: КоличествоПрогнознаяПозиция + Корректировка.Количество, где Корректировка.Количество = −КоличествоПрогнознаяПозиция (обнуляет). Корректировка формируется только при выполнении ВСЕХ условий:

ГДЕ
    Т.КоличествоПрогнознаяПозиция <> 0
    И Т.КоличествоПрогнознаяПозицияОтправленные = 0            // поручение НЕ отправлено на биржу
    И Т.Актив.ВидАктива = ЗНАЧЕНИЕ(...ВидыАктивов.Валюты)       // строка — это ДЕНЬГИ
    И Т.Поручение.Актив.ВидАктива <> ЗНАЧЕНИЕ(...Валюты)      // базовый актив поручения — ЦБ, не валюта
    И Т.Поручение.ВидОперации <> ЗНАЧЕНИЕ(...ВалютныйРынок)   // не валютный рынок

То есть корректировка задумана для «денежной ноги» покупки/продажи ЦБ: когда покупка бумаги резервирует деньги, денежная прогнозная позиция обнуляется, чтобы не считать её отдельно. Побочный полезный эффект — блокировка в таких строках не задваивается.

7.2. Когда корректировка НЕ срабатывает (тогда задвоение)

Достаточно, чтобы хотя бы одно из условий не выполнилось. Типичные случаи «задваивающих» клиентов:

СитуацияКакое условие не выполненоРезультат
Блокировка выгружена напрямую на деньги (RUB), без поручения по ЦБ Поручение.Актив — валюта (или поручения нет)задвоение
Блокировка по валютному ордеру ВидОперации = ВалютныйРынокзадвоение

Вывод раздела: причина задвоения — несогласованность двух механизмов: сумма блокировки уходит в Стоимость_бр всегда, а её количество снимается из Количество только узкой корректировкой ВТ_Корректировка (для «денежной ноги» покупки ЦБ, не отправленной на биржу). Клиенты, у которых блокировка не подпадает под эту корректировку (прямая денежная блокировка, валютный рынок, отправленные поручения), получают двойной счёт.

8. Варианты исправления с примерами «до/после»

Важно при выборе фикса: из-за корректировки ВТ_Корректировка у части клиентов количество блокировки уже обнулено. Поэтому «слепой» фикс (безусловно снять количество ещё раз или безусловно убрать сумму из Стоимость_бр) сломает тех клиентов, у кого сейчас всё правильно. Правка должна снимать количество блокировки из Количество ровно один раз и для всех блокировочных строк — согласованно с уже существующей корректировкой.

Вариант B1 — заполнить КоличествоПрогнознаяПозиция_бр для блокировки РЕКОМЕНДУЕТСЯ

Файл: CommonModule.РасчетПозицииПортфелей, процедура МодифицироватьПрогнозВоркбенч().

Идея: раз сумма блокировки уходит в ПрогнознаяПозиция_бр, то количество блокировки надо симметрично положить в КоличествоПрогнознаяПозиция_бр — тогда в Количество оно скомпенсируется, и блокировка учтётся ровно один раз (через Стоимость_бр). Это соответствует инварианту архитектуры _бр.

Было (в тексте запроса присутствует 0 КАК КоличествоПрогнознаяПозиция_бр, замена не делается):

ТекстЗапроса = СтрЗаменить(ТекстЗапроса, "0 КАК ПрогнознаяПозиция_бр",
        "ВЫБОР
        |  КОГДА ...РЕПО ИЛИ ...ОткрытиеДепозита ИЛИ НЕ ПорученияОтправленные.Поручение ЕСТЬ NULL
        |    ТОГДА Т.СуммаОстаток
        |  КОГДА Т.СуммаБлокировкаОстаток <> 0
        |    ТОГДА Т.СуммаБлокировкаОстаток
        |  ИНАЧЕ 0
        |КОНЕЦ КАК ПрогнознаяПозиция_бр");

Стало (добавляем симметричную замену для количества):

ТекстЗапроса = СтрЗаменить(ТекстЗапроса, "0 КАК ПрогнознаяПозиция_бр",
        "ВЫБОР
        |  КОГДА ...РЕПО ИЛИ ...ОткрытиеДепозита ИЛИ НЕ ПорученияОтправленные.Поручение ЕСТЬ NULL
        |    ТОГДА Т.СуммаОстаток
        |  КОГДА Т.СуммаБлокировкаОстаток <> 0
        |    ТОГДА Т.СуммаБлокировкаОстаток
        |  ИНАЧЕ 0
        |КОНЕЦ КАК ПрогнознаяПозиция_бр");

// НОВОЕ: симметрично снимаем количество блокировки из Количество
ТекстЗапроса = СтрЗаменить(ТекстЗапроса, "0 КАК КоличествоПрогнознаяПозиция_бр",
        "ВЫБОР
        |  КОГДА Т.СуммаБлокировкаОстаток <> 0
        |    ТОГДА Т.КоличествоБлокировкаОстаток
        |  ИНАЧЕ 0
        |КОНЕЦ КАК КоличествоПрогнознаяПозиция_бр");

Правильная (безопасная) форма B1: снимать количество блокировки только там, где корректировка не сработала — то есть привязать замену к тем же условиям, что и ВТ_Корректировка, либо расширить саму ВТ_Корректировка, чтобы она покрывала все блокировочные денежные строки. Тогда количество блокировки снимается ровно один раз для всех клиентов:

// Снимаем количество блокировки ТОЛЬКО если корректировка ВТ_Корректировка не применилась
// (условия зеркальны условиям формирования ВТ_Корректировка):
ВЫБОР
  КОГДА Т.СуммаБлокировкаОстаток <> 0
    И НЕ ( Т.Актив.ВидАктива = ЗНАЧЕНИЕ(...Валюты)
           И Т.КоличествоПрогнознаяПозицияОтправленные = 0
           И Т.Поручение.Актив.ВидАктива <> ЗНАЧЕНИЕ(...Валюты)
           И Т.Поручение.ВидОперации <> ЗНАЧЕНИЕ(...ВалютныйРынок) )
    ТОГДА Т.КоличествоБлокировкаОстаток
  ИНАЧЕ 0
КОНЕЦ КАК КоличествоПрогнознаяПозиция_бр

Проверить обязательно: (1) регрессия по обеим группам клиентов — и с прямой денежной блокировкой, и с блокировкой-«ногой» покупки ЦБ; (2) чтобы поле КоличествоПрогнознаяПозиция_бр переносилось в кэш КэшСеансов; (3) поведение по ЦБ-блокировкам и по отправленным поручениям. Предпочтительнее по чистоте — вариант B3 ниже.

Вариант B3 — унифицировать снятие количества в ВТ_Корректировка ЧИЩЕ ВСЕГО

Файл: ВоркбенчПолныеПрава, формирование ВТ_КорректировкаВсп (стр. 199–213).

Идея: причина «часть клиентов — да, часть — нет» в том, что снятие денежного количества делает только узкая корректировка. Достаточно, чтобы эта корректировка (или её аналог) срабатывала для всех блокировочных денежных строк, чей объём уже отражён в Стоимость_бр. Тогда сумма блокировки в Стоимость_бр всегда компенсируется снятием количества — единообразно и один раз.

Плюс: одно место правки, симметрия сохраняется для всех сценариев (прямые денежные блокировки, валютный рынок, отправленные поручения, «нога» покупки ЦБ).

Проверить: не задеть уже корректно обрабатываемую «ногу покупки ЦБ» (не снять количество дважды).

Вариант B2 — не дублировать блокировку в Стоимость_бр АЛЬТЕРНАТИВА

Файл: тот же, МодифицироватьПрогнозВоркбенч().

Идея: раз количество блокировки уже входит в КоличествоПрогнознаяПозиция (и, значит, в Количество), не класть сумму блокировки в ПрогнознаяПозиция_бр — тогда для денег ОбщаяСтоимость = Количество учтёт блокировку один раз.

Стало — убрать блокировочную ветку из замены ПрогнознаяПозиция_бр:

ТекстЗапроса = СтрЗаменить(ТекстЗапроса, "0 КАК ПрогнознаяПозиция_бр",
        "ВЫБОР
        |  КОГДА ...РЕПО ИЛИ ...ОткрытиеДепозита ИЛИ НЕ ПорученияОтправленные.Поручение ЕСТЬ NULL
        |    ТОГДА Т.СуммаОстаток
        |  КОГДА Т.СуммаБлокировкаОстаток <> 0        // УБРАТЬ
        |    ТОГДА Т.СуммаБлокировкаОстаток            // УБРАТЬ
        |  ИНАЧЕ 0
        |КОНЕЦ КАК ПрогнознаяПозиция_бр");

Риск (тот же капкан, что и у B1): у «здоровых» клиентов количество блокировки уже снято корректировкой ВТ_Корректировка (КоличествоПрогнознаяПозиция=0). Если ещё и убрать сумму из Стоимость_бр, блокировка у них потеряется полностью (учтётся 0 раз вместо 1). Плюс для валютных активов сумма считается как Цена × Количество — при отсутствии/некорректной цене в кэше значение «поедет». Поэтому безусловный B2 не рекомендуется; предпочтительны B1(с условием) или B3.

Вариант A — исправить ОбщаяСтоимостьБезБлокировок (обязательно вместе с B1/B2)

Файл: ВоркбенчПолныеПрава.ТекстЗапросаСтоимостиПортфелей, стр. 2387–2391.

Сейчас: ОбщаяСтоимостьБезБлокировок = Цена * (Количество − КоличествоБлокировка) + Стоимость_бр. После B1 Количество уже не содержит блокировку (она в Стоимость_бр), поэтому дополнительное вычитание − КоличествоБлокировка даст новую ошибку в этой метрике. Её надо пересчитать согласованно (эта метрика используется в долях ДоляПозиции в макете СКД).

Проверить формулу «без блокировок» на кейсе: она должна равняться полной стоимости портфеля так, как будто блокировки нет (≈ 30,36 млн для примера).

Вариант C — временный workaround в отображении НЕ РЕКОМЕНДУЕТСЯ как основной

Файлы: макет DataProcessor.Воркбенч.Макет / запрос ОбъединённыеДанные.

Для колонки «Стоимость, общая по владельцу» использовать метрику, где блокировка учтена один раз (например, по аналогии с CommonModule.РаботаСЛимитами: ОбщаяСтоимость + СуммаБлокировка).

Минус: чинит только экран. Кэш КэшСеансовПортфели.ОбщаяСтоимость останется неверным, а он используется для долей, лимитов и распределения — рассогласование сохранится. Годится лишь как быстрый обходной путь.

9. Критерии приёмки и проверочный запрос

Критерии приёмки

Обязательна регрессия по ОБЕИМ группам клиентов: и по «задваивающим» (прямая денежная блокировка, валютный рынок, отправленные поручения), и по «здоровым» (блокировка-«нога» покупки ЦБ, где сейчас всё правильно). Фикс не должен изменить цифры второй группы.

Как отличить группу клиента: если при блокировке ПрогнознаяПозиция_бр = -20 000 000 И КоличествоПрогнознаяПозиция <> 0 — это «задваивающий» клиент (дефект). Если КоличествоПрогнознаяПозиция = 0 при той же ПрогнознаяПозиция_бр — корректировка уже сработала, клиент «здоровый». Признаки, по которым корректировка НЕ срабатывает (значит, будет задвоение): Поручение.Актив.ВидАктива = Валюты, либо ВидОперации = ВалютныйРынок, либо КоличествоПрогнознаяПозицияОтправленные <> 0.
