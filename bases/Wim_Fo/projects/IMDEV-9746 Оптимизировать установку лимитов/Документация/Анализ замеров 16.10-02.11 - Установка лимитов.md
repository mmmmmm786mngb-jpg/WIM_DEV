## 2. Обычный ФО: почему 25 с на одного клиента (пункт 3.4 анализа)

Причина найдена в коде, это не конкуренция и не проведение документа.

Обработка пишет пороги нового портфеля в регистр `ПорогиЛимитов` по одному набору записей на лимит. В
обычном ФО набор пишется **без** `ОбменДанными.Загрузка`, поэтому на каждый набор отрабатывают
обработчики модуля набора записей регистра:

- `ПередЗаписью`: проверка "нельзя изменять пороги подтвержденного лимита", доступ по классу лимита,
  пометки удаления настроек порогов; `ЗафиксироватьПорогиВПоследнейВерсииЛимита` (чтение последней версии
  лимита, при необходимости перезапись с таблицей порогов лимита по всем портфелям); запись новой версии
  элемента справочника `Лимиты` (`ВерсионированиеОбъектов.ЗаписатьВерсиюОбъекта` с сериализацией объекта);
- `ПриЗаписи`: `Справочники.Лимиты.СохранитьНастройкиЛимита` - пересчет настроек лимита и запись
  `КэшНастроекЛимитов`, в том числе таблица всех порогов этого лимита по всем портфелям.

Объем: в обычном ФО у нового клиента около 25 порогов (диагностика Т-1: 22-28 на портфель, в документе
`УстановкаЛимитов` в среднем 31 лимит), в рознице 4 порога на портфель, то есть около 2 на пару, и они
пишутся с `ОбменДанными.Загрузка = Истина`, обработчики не выполняются.

Подтверждение по данным Т-1: число версий справочника `Лимиты` за день в обычном ФО совпадает с числом
записанных порогов - одна версия на каждый набор.

| День | Порогов записано | Версий лимитов |
|---|---|---|
| 16.10.2026 | 104 | 106 |
| 21.10.2026 | 88 | 93 |
| 23.10.2026 | 52 | 64 |
| 27.10.2026 | 44 | 68 |

**Механизм, подтвержденный на стенде.** Подсистема версионирования БСП пишет текущую версию объекта без
данных, с одной контрольной суммой; данные версии дописываются при создании следующей версии. Поэтому при
каждой записи набора порогов:

1. `ЗафиксироватьПорогиВПоследнейВерсииЛимита` находит последнюю версию лимита без данных и записывает в нее
   сериализованный объект лимита и таблицу порогов лимита по всем портфелям (сжатие уровня 9);
2. `ЗаписатьВерсииПорогов` создает новую версию: БСП дважды считает контрольную сумму по данным версии, куда
   входит та же таблица порогов в виде XML-строки (`ДанныеДляХранения`, `КонтрольнаяСумма`);
3. `СохранитьНастройкиЛимита` пересчитывает настройки лимита и записывает в `КэшНастроекЛимитов` таблицу всех
   порогов лимита (`ДополнитьКэшНастроекЛимитаПорогами`).

Все три действия читают и сериализуют пороги лимита по всем портфелям, поэтому стоимость набора растет с их
числом. Стенд, медиана полной записи одного набора: 255 мс при 2000 портфелей с порогом по лимиту, 417 мс при
3000, 684 мс при 6000 (около 41 мс плюс 0.107 мс на портфель). Сумма раздельно измеренных действий
обработчиков совпадает с полной записью набора (424 против 417 мс при 3000).

## 3. Почему в рознице и обычном ФО по-разному работает `ОбменДанными.Загрузка`

Код один и тот же, различие задает настройка обработки **"Это база розничного ДУ"** (`ЭтоБазаРозничногоДУ`,
флажок на форме настроек, хранится в настройках регистрации обработки в каждой базе). Ветка в
`СоздатьУстановкиЛимитов`:

```bsl
НаборЗаписей = РегистрыСведений.ПорогиЛимитов.СоздатьНаборЗаписей();
Если ЭтоБазаРозничногоДУ = Истина Тогда
	НаборЗаписей.ОбменДанными.Загрузка = Истина;
КонецЕсли;
```

Тем же флажком включаются еще две вещи, которых нет в обычном ФО:

1. фоновое задание "Запись версий лимитов" (`ВыполнитьЗаписьВерсийЛимитов`): после паузы 2 с на пару
   записывает одну версию на каждый лимит созданных установок (в рознице 5 версий на запуск вместо
   версии на каждый набор порогов);
2. полное отключение обновления ключей доступа в сеансе (`ОтключениеОбновленияКлючейДоступа`) перед
   постановкой задания.

Ручное распространение из формы (`ПерезаполнитьУстановкиЛимитов`) пишет пороги без `Загрузка` в обеих
базах. Комментариев и истории изменений, объясняющих решение, в обработке нет.

**Вывод:** это осознанная схема для розницы "пороги записать быстро, версии лимитов записать потом в фоне".
Наиболее вероятная причина - объем (в рознице около 160 пар в день против 1-3 в обычном ФО). Вторая
возможная причина - обход запрета "Нельзя изменять пороги подтвержденного лимита" (`ПроверитьВозможностьЗаписиНабора`),
который действует для классов лимитов с расширенным подтверждением; по коду это не определить, нужны
настройки розничной базы.

**Что схема розницы не восполняет** (обработчики пропущены, а фоновое задание делает только версии):

| Пропущено при `Загрузка` | Последствие |
|---|---|
| `СохранитьНастройкиЛимита` (обновление `КэшНастроекЛимитов`) | Для лимитов класса с расширенным подтверждением проверка лимитов берет пороги **только из кэша** (`РегистрыСведений.ПорогиЛимитов.СведенияОПорогах`, регистр для них исключен условием `НЕ Лимит В (&ЛимитыРасширеннаяПроверка)`). Пороги нового портфеля попадут в кэш только при следующей записи элемента лимита; до этого портфель проверяется по порогу "для всех портфелей" из кэша либо без порога. Для классов без расширенного подтверждения пороги читаются из регистра, последствий нет |
| `ЗафиксироватьПорогиВПоследнейВерсииЛимита` | В версиях лимитов, записанных фоновым заданием, может не быть таблицы порогов |
| Проверки записи набора (подтвержденный лимит, доступ по классу, пометки удаления) | Пороги пишутся без этих проверок |

Первая строка - функциональный риск, а не производительность. Его надо проверить на Т-1 до любых изменений
(раздел 6).

в сеансе обмена: 1000 новых клиентов в рознице = 2000 пар x 1.48 с = около 49 минут; 100 новых клиентов в
обычном ФО = около 42 минут.

**Где главный резерв.** В обычном ФО - обработчики регистра `ПорогиЛимитов` (пункты 3 и 3а), это 82% времени
операции. В рознице время распределено: письма 30% (пункты 5 и 1), записи `ДополнительныеСведения` 25% (пункт 4),
проведение `УстановкаЛимитов` 22% (пункт 4а), поиск 14%. Пункт 4 пересекается с IMDEV-8829 и IMDEV-9532:
стоимость записи `ДополнительныеСведения` в ФО определяется теми же обработчиками и для флагов обмена МО -> ФО.

## 5. Что не подтверждено и остается оценкой

- Перевод стенда на ПРОД предполагает, что ПРОД медленнее стенда одинаково для всех действий режима (один k).
  Для записи `ДополнительныеСведения` это согласуется с независимым замером на тестовой копии; для проведения
  документа и обработчиков порогов отдельной проверки нет.
- Стоимость письма по паре принята равной стоимости итогового письма на ПРОД (то же почтовое API, вложение XLS
  до 35 КБ). Письмо об успешном автораспространении в обычном ФО учтено как отправляемое (сеанс веб-сервиса в
  списке сервисных пользователей); если на ПРОД оно не отправляется, доля писем обычного ФО меньше на 1.4%.
- Число портфелей с порогами по лимитам на Т-1 не измерялось: значение 3000 выбрано по совпадению k с
  розницей. Выводы по обычному ФО от него почти не зависят (обработчики 80-84% при 2000-6000).
- Причина `Загрузка` в рознице - вывод по коду, документального подтверждения нет.
- Пункт 3а - вывод по коду, требует проверки всех потребителей `КэшНастроекЛимитов`.
