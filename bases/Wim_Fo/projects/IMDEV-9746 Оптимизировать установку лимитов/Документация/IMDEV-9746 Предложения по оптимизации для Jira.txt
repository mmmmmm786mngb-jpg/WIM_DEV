h3. Ускорение установки лимитов новым клиентам

Когда после обмена с МО в ФО появляются новые клиенты, обработка "Распространение правил с одного клиента на список клиентов" автоматически назначает им лимиты по образцу эталонного клиента и рассылает уведомления. Предлагаем пять доработок этой обработки, после которых:
* в ФО лимиты новым клиентам назначаются в 7,7 раза быстрее;
* в ФО розница назначение лимитов проходит в 1,3 раза быстрее, ответственные получают одно письмо по классу лимитов вместо отдельного письма по каждому клиенту - около 160 писем в день меньше;
* на сервере перестают накапливаться временные файлы вложений писем.

Все изменения вносятся только в обработку распространения правил, базовая конфигурация остается без изменений. Расчет основан на замерах времени ПРОД за 16.10-02.11.2026, проверке на тестовом стенде и проверке настроек на копии ПРОД.

h4. 1. Удалять временные файлы вложений (ФО и ФО розница)

*Сейчас:* файл с порогами для письма по каждому клиенту остается на сервере после отправки, в рознице около 160 файлов в день.
*Предлагаем:* удалять файл сразу после отправки письма.
*Выигрыш:* файлы не накапливаются в каталоге временных файлов сервера.
*Риск:* низкий. *Сложность:* низкая.

h4. 2. Ускорить запись порогов лимитов (ФО)

*Сейчас:* каждый из 25 порогов нового клиента записывается со всеми проверками, обновлением истории лимита и кэша настроек лимита; каждый раз перебираются пороги лимита по всем клиентам. На это уходит около 80% времени операции.
*Предлагаем:* записывать пороги быстро, как в рознице; проверку подтвержденного лимита выполнять в обработке; историю лимита и кэш настроек обновлять один раз на лимит в фоновом задании после распространения. Дополнительно (2а): кэш настроек обновлять только для классов лимитов с расширенным подтверждением - только для них проверка лимитов берет пороги из кэша; на копии ПРОД таких классов нет.
*Выигрыш:* назначение лимитов новому клиенту в 6,9 раза быстрее; с пунктом 2а фоновая работа в 2 раза меньше.
*Риск:* средний - история лимита пишется один раз за запуск, кэш обновляется чуть позже. *Сложность:* средняя.

h4. 3. Одно письмо на класс вместо письма на каждого клиента (ФО и ФО розница)

*Сейчас:* по каждой паре клиент + класс уходит отдельное письмо с файлом порогов, плюс итоговое письмо по классу.
*Предлагаем:* собирать пороги всех клиентов запуска в один файл и прикладывать его к итоговому письму класса.
*Выигрыш:* в рознице запуск в 1,2 раза быстрее и около 160 писем в день меньше; в ФО дополняет пункт 2.
*Риск:* низкий, меняется формат писем. *Сложность:* низкая.

h4. 4. Не ждать запуска фонового задания записи версий (ФО розница)

*Сейчас:* поставив фоновое задание, обработка ждет его окончания, хотя результат не использует.
*Предлагаем:* запускать задание без ожидания.
*Выигрыш:* запуск в 1,1 раза быстрее.
*Риск:* низкий. *Сложность:* очень низкая.

h4. 5. Не ждать впустую в фоновом задании записи версий (ФО розница)

*Сейчас:* задание перед записью версий всегда делает паузу на каждую пару клиент + класс, ожидая создания установок лимитов, хотя к этому моменту они уже созданы.
*Предлагаем:* сначала проверять, созданы ли установки, и делать паузу, только если их еще нет.
*Выигрыш:* фоновое задание в 4,6 раза быстрее; на время обмена не влияет.
*Риск:* низкий - если установки еще создаются, задание ждет, как сейчас. *Сложность:* низкая.
