# IMDEV-9746. Сравнение версий 1.16 и 1.17 на стенде разработческой ФО (03.11.2026)

Версии: 1.16 - рабочая версия ПРОД (`ОРИГИНАЛ_1_16`, совпадает с выгрузкой ПРОД от 29.10.2026), 1.17 - доработки
1, 2, 2а, 3, 4, 5 (`УСКОРЕНО_1_17`). Обе версии по очереди загружались в рабочий элемент справочника дополнительных
обработок (его находят подписки расширения ВТБ_Прод), вызов - как из обработки "Операции после обмена". Данные стенда как
на Т-1: пороги 3000 портфелей на лимит, обычный ФО - 31 лимит в установке эталона и 25 порогов, розница - 2 класса по
7 лимитов. Константа `ИспользоватьКлассыЛимитов` и версионирование лимитов включены, подписки ВТБ_Прод на запись сведений
срабатывают (рабочие имена свойств), сервисный пользователь в списке - как на Т-1. Почта - локальная заглушка.

## Проверка подтвержденного лимита (обычный ФО)

Временно классу Compliance включено расширенное подтверждение, первому лимиту с порогом эталона - "Подтвержден"; по
одному запуску каждой версии, затем признаки возвращены. Обе версии: порог этого лимита не записан (24 из 25),
установка лимитов не проведена, по паре отказ, письмо с флагом FAIL. 1.16 отправляет письмо по паре и итоговое, 1.17 -
одно итоговое.

## Правки 1.17 по внешнему ревью (03.11.2026, вечер)

1. Признак отказа сбрасывается в начале каждого класса. Раньше отказ последней пары комплаенса попадал в письмо рисков,
   если по рискам не было ни одной пары (письмо отправлялось из-за сообщений по клиентам без эталона). Дефект был и в
   1.16.
2. В обычном ФО после обмена пороги пишутся без обработчиков регистра, поэтому обработка сама повторяет все проверки
   обработчика `ПередЗаписью`: подтвержденный лимит с расширенным подтверждением (было), доступ к классу лимита
   (`НастройкаДоступаКЛимитам.ДоступРазрешен`), пометка удаления настройки порогов. Тексты ошибок - как у обработчика.

Прогон на стенде после пересборки (`Стенд/grok_fixes_test.py`, результаты `results/grok_fixes.jsonl`):

| Проверка | 1.16 | 1.17 |
|---|---|---|
| Обычные запуски 1.17: обычный ФО 2, розница 2 | - | данные как у 1.16 (31 лимит и 25 порогов; оба класса розницы), версий 25 и 4, запуск ФО 1.3-1.9 с, ошибок журнала и повторных установок нет |
| Настройка порогов эталона помечена на удаление (обычный ФО) | порогов 0 из 25, установка проведена, письма FAIL; в логе общий текст "Ошибка при вызове метода контекста (Записать)" | то же; в логе по каждому порогу текст обработчика "... с установленной пометкой на удаление" |
| Розница: отказ в комплаенсе (подтвержденный лимит), у рисков клиенты без пар | 4 письма, все FAIL, включая письмо рисков | 2 письма: комплаенс FAIL, риски WARN |

Не проверено на стенде: запрет по классу лимита. Стенд работает под полноправным пользователем, для него
`ДоступРазрешен` всегда возвращает Истина. Вызов тот же, что в обработчике регистра.

Письма 1.17 (текст и вложения) - `Тестирование/Письма 1.17/Письма 1.17.html`.

## Ограничение версии (п. 3 внешнего ревью)

Версии лимитов и кэш настроек лимита обновляет фоновое задание после возврата из обмена. До его завершения (на стенде
2-8 с) в последней версии лимита нет новых порогов, а кэш настроек не учитывает новые пороги. Проверка лимитов берет
пороги из кэша только для классов с расширенным подтверждением, на Т-1 таких классов нет. Если задание завершится с
ошибкой, версии и кэш обновятся при следующей записи порогов этого лимита; ошибка задания - в журнале регистрации.

## Отличия 1.17 от 1.16, ожидаемые по доработкам

- Письма: одно итоговое письмо на класс с порогами всех клиентов запуска вместо письма по каждой паре (пункт 3).
- Версии лимитов в обычном ФО пишет фоновое задание: одна версия на лимит за запуск, только по лимитам, по которым у
  клиентов запуска есть пороги. Первая сборка 1.17 писала версии по всем лимитам установки с порогами у любых портфелей
  (31 в обычном ФО, 14 в рознице - так было и в 1.16 розницы); по решению 03.11.2026 отбор ограничен порогами клиентов
  запуска в обеих базах. Повторный прогон 1.17 после правки: обычный ФО 2 запуска - 25 версий, запуск 0.94-1.57 с;
  розница 2 запуска - 4 версии; данные клиентов совпадают с 1.16, ошибок журнала и повторных установок нет.
- Кэш настроек лимита обновляется только для классов с расширенным подтверждением (пункт 2а); на Т-1 таких классов нет.
- Временные xls удаляются после отправки (пункт 1).
