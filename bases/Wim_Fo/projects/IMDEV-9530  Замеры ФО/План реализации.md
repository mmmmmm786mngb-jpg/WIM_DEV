# IMDEV-9530. План реализации замеров ключевых операций ФО

Состояние: план согласован по вопросам В1-В6, редакция 5 от 02.10.2026 (вес и комментарий замеров).
Основа: `Ключевые операции ФО_объекты замеров.xlsx`, `Документация/measurement_points.html`.

## 1. Оценка сложности

Средняя. Три носителя изменений: новое расширение FO_KeyOpsPerf (замеры конфигурации), копия
расширения FO_PositionLoadOpt задачи IMDEV-9532 (один замер, пересекающийся с ее кодом) и 7
внешних обработок. 12 точек вставки, без изменения бизнес-логики. Риски: два расширения
заимствуют одну обработку обмена; вендор переносит IMDEV-9532 в базовую конфигурацию; безопасный
режим.

## 2. Требования

- Добавить замеры производительности по списку ключевых операций ФО (Розница).
- Строки 1, 2, 4, 14 уже замеряются (константа `ВыполнятьЗамерыПроизводительности` включена на
  PROD и тестовых базах). Для строки 2 добавляется отдельный ключ постконтроля.
- Загрузки из МО (строки 6-8) - в разрезе каждого регистра, справочника, документа.
- Депозиты (строка 9) - с количеством депозитов.
- Загрузки 10-13 - без влияния на производительность.

## 3. Найденные факты, влияющие на решение

| Факт | Следствие |
|---|---|
| БСП 3.1.2.252. `ЗакончитьЗамерВремени` пишет запись в `РегистрСведений.ЗамерыВремени` сразу, одним `Записать()` | Каждая запись замера - одна запись в БД. Нельзя писать замер на каждый элемент |
| В безопасном режиме БСП не пишет замер, только событие в журнал регистрации | Оба расширения подключаются без безопасного режима; внешние обработки уже зарегистрированы с `БезопасныйРежим = Ложь` |
| Перехват модуля обработки в безопасном режиме платформа молча не применяет (опыт IMDEV-9532) | Второй довод за подключение без безопасного режима |
| Строковый ключ замера БСП сама создает в справочнике `КлючевыеОперации` (поиск по хешу имени, кэш сеанса) | Справочник заранее не заполняем; имя до 1000 символов |
| `ОбработатьДанные_РегистрыСведений` вызывает все 27 процедур на каждый пакет, в том числе с пустым списком | Замер раздела писать только при непустом списке |
| Процедуры справочников и документов вызываются в цикле по одному элементу | Замер ставить вокруг цикла в диспетчере, не внутри процедуры |
| FO_PositionLoadOpt (IMDEV-9532) перехватывает `ОбработатьДанные_ДополнительныеСведения` и модуль набора записей `ДополнительныеСведения`; вендор переносит эту доработку в базовую конфигурацию по копии расширения из этой задачи | Замер регистра `ДополнительныеСведения` - в копии FO_PositionLoadOpt, внутри ее перехвата; остальные замеры - в новом расширении (Р1, Р6) |
| В базовой конфигурации замеры пишутся прямыми вызовами `ОценкаПроизводительности` (`Распорядители`, `Воркбенч`, `Адаптеры`); в `Распорядители` есть локальная обертка `ЗакончитьЗамерВремени` | Тот же стиль: прямые вызовы БСП, локальный метод в том же модуле, без собственных общих модулей |
| У длительных замеров БСП время шага считается от предыдущего шага, а в регистр пишется удельное время | Для диспетчеров с пропуском пустых разделов это смешивает время; выбран простой API (Р2) |
| В `ЗакончитьЗамерДлительнойОперации` БСП заменяет вес 0 на 1 | То же соглашение для операций без данных |

## 4. Ответы на вопросы

| № | Вопрос | Ответ |
|---|---|---|
| В1 | Отдельный ключ постконтроля (строка 2) | Да |
| В2 | API замера | Простой: `НачатьЗамерВремени` / `ЗакончитьЗамерВремени` |
| В3 | Имя расширения | `FO_KeyOpsPerf` для замеров конфигурации; замер, пересекающийся с IMDEV-9532, - в копии FO_PositionLoadOpt. Собственных общих модулей нет |
| В4 | Исходники | Внешние обработки (актуальные оригиналы) и расширение FO_PositionLoadOpt 1.0.0.4 скопированы в `ОРИГИНАЛЫ` (не меняются) и `ЗАМЕРЫ` (правятся). Версии сверены |
| В5 | Стенд | Строки 6-8: dev-стенд МО-ФО IMDEV-9532. Остальные: тестовая копия |
| В6 | Замер загрузки неторговых поручений РОСТ при нуле поручений | Да: вес 1, фактическое число в комментарии |

## 5. Решения

- **Р1. Носители изменений.**

| Носитель | Где | Что | Строки |
|---|---|---|---|
| Новое расширение FO_KeyOpsPerf (префикс `FO_KeyOpsPerf_`) | `ЗАМЕРЫ/FO_KeyOpsPerf` | Замеры пакета обмена и разделов, кроме `ДополнительныеСведения`; исполнение сделок; упаковка данных; постконтроль | 2, 6-8, 15, 17 |
| Копия FO_PositionLoadOpt, версия 1.0.0.4 -> 1.0.0.5 | `ЗАМЕРЫ/FO_PositionLoadOpt` | Замер регистра `ДополнительныеСведения` внутри перехвата `ОбработатьДанные_ДополнительныеСведения` | 6 (часть) |
| Внешние обработки, новые версии | `ЗАМЕРЫ/<обработка>_epf` | Замеры операций и шагов | 3, 5, 9-13 |

- **Р2. API.** Везде простой замер БСП: `Начало = ОценкаПроизводительности.НачатьЗамерВремени()`
  перед участком, `ЗакончитьЗамерВремени(Ключ, Начало, Вес, Комментарий)` после. Время шага
  точное, в регистр пишется полная длительность и вес. Один стиль с существующими замерами
  `Распорядители`.
- **Р3. Вес и комментарий.**
  - Вес по возможности - число портфелей (договоров): каждый элемент справочника `Портфели` -
    договор с `НомерДоговора`. Где портфеля в операции нет - число обработанных объектов
    (котировки, записи индексов, контрагенты). Если 0 - вес 1, в комментарий `Количество: 0`
    (соглашение БСП).
  - Разные портфели в разделе пакета считаются по `Портфель.ВнешнийКод` строк XDTO, без
    обращения к базе. Портфель есть в 20 разделах пакета (по XDTO-пакету Avancore): регистры
    `ФактическаяПозиция`, `ФактическаяПозицияIntraDay`, `ФактическаяПозицияПоПартиям`,
    `СтоимостьЧистыхАктивов`, `АктивыВРЕПО`, `ГарантийноеОбеспечение`,
    `ВеличинаЧистогоОттокаПаев`, `ЗафиксированныеКотировки`, `ПорогиЛимитовПоТипамАктивов`,
    `ПоступленияДенежныхСредств`, `ПроцентыПоСделкамМНО`, `РезервыПодОбесценение`,
    `ФинансовыеПоказателиОблигацийПоПортфелю`, `ФактическиеПоказателиДляПрогнозирования`,
    `ДополнительныеСведения` (`Объект.Портфель`); справочники `Субпортфели`, `МестаХранения`,
    `МодельныеПортфели`; документы `СделкаРЕПО`, `СделкаСЦеннымиБумагами`,
    `РаскрытиеСтруктурыАктивов`, `ИсполненияПоСделке`, `РегистрацияПлановойПозиции`.
    Справочник `Портфели`: вес = число элементов.
  - Комментарий - строка `Показатель: значение; ...`; БСП кладет ее в поле `ДопИнф`
    стандартного комментария замера. Состав по строкам - таблица Р4 и колонки "Вес замера",
    "Комментарий замера" в Excel и `measurement_points.html`.
  - Потоки: где число потоков известно в коде ФО (постконтроль - параметр сеанса
    `ПотоковНаСеансПроверкиЛимитов` и признак фоновых заданий) - в комментарий. Для приема
    пакетов из МО число потоков МО на стороне ФО неизвестно (на PROD 5); параллельность
    считается по пересечению интервалов замеров разных сеансов: номер сеанса БСП пишет в каждую
    запись замера, УИД пакета в комментарии связывает разделы с пакетом.
- **Р4. Схема ключей.** `<Операция>` для всей операции и `<Операция>.<Шаг>` для шагов.

| 17 | `УпаковкаДанных` | `.КэшВмОписания`, `.ОчиститьСлужебныеКэши`, `.ОчиститьДанныеНеактивныхСеансов`, `.Сократить.<Регистр>` (5) | 1 | `Активных торговых дат` | FO_KeyOpsPerf |

Существующие замеры не меняются: строка 1 - вес поручения (вес распорядителя), строка 4 -
поручения, строка 14 - сообщения пакета адаптера; комментарий стандартный.

- **Р5. Объем записей.** Около 500 пакетов остатков x 3-6 непустых разделов, мандаты каждый час,
  остальное единицы в день: 3-10 тысяч записей в сутки. Хранение и очистка штатные:
  регламентное задание `ОчисткаЗамеровВремени`, константа `ПериодХраненияЗамеров`.
- **Р6. Код в стиле базовой конфигурации и раздельная судьба двух расширений.**
  - Собственных общих модулей и других новых объектов нет ни в одном расширении: только
    заимствованные объекты и перехваты их методов.
  - Перехваты - `&ИзменениеИКонтроль` с блоками `#Вставка`, как в IMDEV-9532: место и фрагмент
    вставки видны точно.
  - Вызовы БСП прямые. Повторяющаяся запись замера раздела пакета - один локальный метод в модуле
    обработки `ОбменДаннымиБэкОфис` расширения FO_KeyOpsPerf, `#Область ЗамерыРазделовПакета`.
  - Оба расширения заимствуют `ОбменДаннымиБэкОфис`, но перехватывают разные методы: FO_KeyOpsPerf
    - диспетчеры и `ЗагрузитьПакет`, FO_PositionLoadOpt - только
    `ОбработатьДанные_ДополнительныеСведения`. Порядок применения расширений не важен.
  - Имена новых методов FO_KeyOpsPerf проверяются на совпадение с методами базового модуля и с
    новыми методами FO_PositionLoadOpt (`СвойствоПоНаименованию`, `ПреобразованноеЗначениеСведения`,
    `ФлагУжеИмеетЗначение`, `ТекущиеЗначенияСведенийОбъекта`, `ЗапомнитьЗаписанноеЗначение`):
    совпадение имен в двух расширениях одного модуля мешает применению.
  - Замер `ДополнительныеСведения` в копии FO_PositionLoadOpt уходит вендору вместе с кодом
    IMDEV-9532. После выхода релиза вендора FO_PositionLoadOpt снимается, FO_KeyOpsPerf остается:
    его диспетчеры доработка IMDEV-9532 не меняет, а замер `ДополнительныеСведения` будет писать
    уже базовая конфигурация.
  - Комментарий `Записано: N` при весе = строкам пакета показывает, сколько флагов IMDEV-9532
    пропустила без записи: фактическое подтверждение эффекта оптимизации на PROD.
  - Без установленного FO_PositionLoadOpt регистр `ДополнительныеСведения` не замеряется; так
    задумано, чтобы не было двойного замера после переноса вендором.

## 6. Архитектурные инварианты

1. Базовая конфигурация не меняется. Код конфигурации - только через расширения FO_KeyOpsPerf и
   FO_PositionLoadOpt.
2. Замеры пишутся только через подсистему БСП `ОценкаПроизводительности`; своих регистров,
   справочников и общих модулей не создаем.
3. Код замера не меняет бизнес-результат: не меняет данные, порядок вызовов, параметры и
   возвращаемые значения перехваченных методов.
4. Точки замеров не находятся внутри явных транзакций (проверяется для каждой точки): запись
   замера не попадает в откат и не удлиняет транзакцию. Вызовы БСП без `Попытка`, как в
   существующем коде конфигурации.
5. Не более одной записи на раздел пакета; пустые разделы не пишутся; внутри процедур, которые
   вызываются по одному элементу, замеров нет.
6. Каждый раздел пакета замеряется ровно в одном расширении: `ДополнительныеСведения` - в
   FO_PositionLoadOpt, остальные - в FO_KeyOpsPerf. FO_KeyOpsPerf не перехватывает методы,
   которые перехватывает FO_PositionLoadOpt.
7. В копии FO_PositionLoadOpt логика IMDEV-9532 не меняется: diff с
   `ОРИГИНАЛЫ/FO_PositionLoadOpt` содержит только блоки `#Вставка` замера в
   `ОбработатьДанные_ДополнительныеСведения` и номер версии.
8. Оба расширения подключаются без безопасного режима.
9. Стиль кода расширений: префикс только у перехватчиков; у перехвата экспортного метода
   сохраняется `Экспорт`; новые методы без префикса внутри именованной `#Область`; имена не
   совпадают с методами базовых модулей и другого расширения.
10. Внешние обработки: правки только в `ЗАМЕРЫ`; меняются номер версии и тело рабочих процедур;
    наименование, команды, `БезопасныйРежим`, блоки DevOps без изменений. `ОРИГИНАЛЫ` не меняются.
11. Ключи замеров - строго по таблице Р4.

- [ ] **Этап 1. Каркас FO_KeyOpsPerf.**
  Создать расширение `ЗАМЕРЫ/FO_KeyOpsPerf`, режим совместимости 8.3.27. Заимствовать:
  обработку `ОбменДаннымиБэкОфис` (модуль объекта), обработку `ГрупповоеИсполнениеСделок`
