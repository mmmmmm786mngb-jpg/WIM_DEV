Предконтроль и постконтроль лимитов

Две операции нулевого приоритета: проверка поручения с блоттера и проверка всех портфелей по расписанию. В коде это один серверный конвейер. Различаются только вход (поручения или портфели) и то, что делают с результатом.

Главное в трех абзацах

Один двигатель

И предконтроль, и постконтроль вызывают серверную функцию Распорядители.ПроверкаИОтправка. Она строит план проверки «портфель x лимит», читает позиции и настройки, раздает проверку исполнителям (фоновым заданиям) и пишет результат в служебные регистры КэшВм*.

Вход разный

Предконтроль: человек выделяет поручения на блоттере или в карточке, план строится из портфелей этих поручений, позиция дополняется прогнозом по поручению. Постконтроль: регламентное задание берет портфели из настроек рассылки, поручений нет, проверяется текущая позиция.

Выход разный

Предконтроль ставит поручению статус «Проверено» или «Проверка не пройдена», при команде «Проверить и отправить» уходит через адаптер на биржу. Постконтроль складывает результат в очередь рассылки, письма отправляет другое регламентное задание.

Легенда диаграмм

Один цвет на всех схемах. Внешние системы всегда оранжевые.

Клиент: формы, действия пользователя Сервер 1С: модули, фоновые задания Хранилище: регистры, документы, справочники базы Настройки: константы, параметры сеанса Внешняя система: биржа, торговый терминал, почта
Схемы строятся скриптом при открытии страницы. Если схема не отрисовалась, под каждой есть полное текстовое описание блоков: содержание не теряется.

Назначение блоков

1 Точки входа на клиенте клиент

Крупно. Пользователь нажимает «Проверить» или «Проверить и отправить». Кнопки есть на обработке Блоттер (таблица «Поручения» - динамический список по документу Поручение) и на трех формах поручения: ФормаСделки, ФормаРЕПО, ФормаНеторговогоПоручения.

Мелко. Обработчик команды вызывает КоПорученияКлиент.Проверить(Форма). Тот запрашивает у сервера флаг контроля отклонения цены от рынка (ТорговаяЧастьВызовСервера.КонтрольОтклоненияЦеныОтРынка) и передает управление в РаботаСПоручениямиКлиент.Проверить. Там формируется структура указаний: профиль настроек блоттера, флаг «открывать справку-расчет при нарушениях», признак «отправить после проверки» и имя клиентского метода-входа РаспорядителиКлиент.Вход.

Сбор поручений. ОбработатьПорученияФормы берет все выделенные строки таблицы «Список» на блоттере (строки группировок пропускаются) или ссылку текущего поручения в карточке. Если поручений нет - выход без действий.

2 Диалоги перед запуском клиент

Крупно. РаспорядителиКлиент.ПроверкаИОтправка_Вход решает, что спросить у пользователя до старта.

Мелко. Сначала серверный вопрос: есть ли среди выбранных пуловые поручения, которые нужно разделить (РаботаСПоручениямиВызовСервера.ПорученияНеобходимоРазделить). Если есть - вопрос «Продолжить?», при согласии выполняется распорядитель Разделение синхронно и список поручений заменяется на новые. Дальше: если включено расширенное подтверждение сделок и это отправка - открывается форма ПодтверждениеОтправки, групповая отправка запрещена. Иначе вопрос «Проверить выбранные (N) поручения?». Из карточки поручения вопрос не задается.

3 Переход на сервер сервер настройки

Крупно. РаспорядителиВызовСервера.ВыполнитьРаспоряжение запускает серверный метод либо синхронно, либо фоновым заданием через ДлительныеОперации.ВыполнитьВФоне.

Мелко. Режим определяет константа ИспользоватьФоновыеЗадания (в файловой базе всегда синхронно). В фоновом режиме на клиенте открывается общая форма ДлительнаяОперация с прогрессом, отмена запрещена. По завершении Распоряжение_Завершение читает результат из временного хранилища, оповещает формы об изменении поручений и открывает форму результата Обработка.Блоттер.Форма.ОбработкаПоручений.

Параметры проверки собирает РаспорядителиВызовСервера.ПараметрыПроверки: дата проверки, возможен ли запуск (Справочники.Лимиты.ЗапускПроверкиЛимитовВозможен), общие настройки лимитов из документа УстановкаДополнительныхНастроекЛимитов (выводить предупреждения при претрейде, использовать дату актуальности, состав позиции, рассылать результаты претрейда), ключевая операция замера Проверка, метод Распорядители.ПроверкаИОтправка.

4 Конвейер проверки сервер

Общий для обеих задач. Разобран отдельно в разделе Конвейер проверки. Для предконтроля включены дополнительные этапы: предварительное чтение поручений, снятие акцепта, чтение наборов данных по поручениям (позиция плюс прогноз по поручению), запись статусов поручений.

5 Итог по поручению хранилище

Крупно. По каждому поручению собираются строки результата «поручение - лимит - зона - отказ». Зона красная - нарушение, желтая - предупреждение, отказ - лимит не удалось проверить.

Мелко. ИсполнителиПолныеПрава.ЗаписатьСтатусыПоручений: есть красная зона - статус «Проверка не пройдена»; иначе «Проверено» и, если не включен режим «отправлять только вручную», сразу «Ожидает отправки». Текст итога берется из шаблонов: «Нарушений не обнаружено», «только предупреждения», «Есть нарушения», «Есть нарушения и ошибки», «Нет назначенных лимитов». Дополнительно при включенном контроле отклонения цены - проверка превышений по документу УстановкаОтклоненийЦенПоручений. Все записывается в регистр СобытияПоручений.

6 Отправка на биржу сервер внешние системы

Крупно. Только для «Проверить и отправить». Поручения без нарушений передаются в Распорядители.Отправка, затем через адаптер в торговую систему.

Мелко. Перед отправкой: разблокировка поручений, повторная проверка отклонения цены, переопределение адаптеров по расширениям поручений. В Отправка для каждого поручения: проверка «можно отправить» по статусам, при включенном контроле целостности - сверка хеша полей, готовность адаптера, валидация адаптера. Поручения группируются по адаптеру, каждая группа уходит отдельным фоновым заданием Исполнители.Отправка_ОтправкаПоручений, которое вызывает Менеджер.ПорученияОтправить конкретной обработки-адаптера. Внебиржевые поручения на биржу не идут: по ним создается документ Сделка или СделкаРЕПО и ставится статус «Исполнена».

Выход наружу: QUIK - COM компонента T2Q (только Windows x64, путь к терминалу в настройках адаптера); FIX - HTTP запросы к WebSocket прокси; WINVESTOR - HTTPS на адрес подключения. Ответ биржи приходит асинхронно, статус меняется на «Отправлено, ожидается подтверждение».

Этапы конвейера подробно

0 Старт

УстановитьПривилегированныйРежим, затем ОбработатьЗапуск: дообработка поручений, сменивших статус (ТорговаяЧасть.ОбработатьПорученияСменившиеСтатус), сброс повторно используемых значений сеанса (ОбновитьПовторноИспользуемыеЗначения), отключение обновления ключей доступа на время работы. Параметры копируются рекурсивно, план проверки распаковывается из хранилища значения. Признак претрейда = есть поручения. Дата проверки приводится к концу дня, вычисляется дата фактической позиции со смещением. Создается запись КэшВмОписания с идентификатором «вместилища» - это ключ, под которым лежат все результаты одной проверки.

Число потоков на этап задается в коде: предварительное чтение 4, пороги 2, наборы данных 3, наборы по поручениям 4, расширения 1, обработка проверки - из константы ПотоковНаСеансПроверкиЛимитов, запись результатов 1. При выключенных фоновых заданиях все этапы идут в одном сеансе.

1 ЧтениеПредварительное замер только претрейд

Исполнитель Исполнители.ПроверкаИОтправка_ЧтениеПредварительное, минимум 30 поручений на задание. Читает таблицу данных поручений, блокирует поручения под идентификатор распорядителя, для каждого решает судьбу: пуловое, требующее разделения - игнор; помечено на удаление - отказ; проверка прав доступа УправлениеДоступомАванкор.ПередЗаписью; черновик - проводится через контроллер поручения с профилем блоттера; уже акцептовано и это отправка - сразу в список на отправку без проверки; иначе МожноПроверить по статусам и в список на проверку. В конце читаются реквизиты поручений (ПроверкаЛимитов.РеквизитыПоручений) и базовые активы депозитарных расписок.

2 ОбновлениеРасширений

Для каждого объекта фокуса (поручение, портфель, группа) обновляются записи регистров РасширенияПоручений, РасширенияПортфелей, РасширенияГруппПортфелей под текущее вместилище. Можно отключить параметром ОбновлятьРасширения. Для постконтроля фокус - только портфели и пуловые группы, непуловая группа в параметрах дает ошибку валидации.

3 ВалидацияОкружения

Три проверки, любая останавливает конвейер с исключением «Ошибка валидации окружения»: не загружена фактическая позиция на дату проверки (если не используется дата актуальности); не указаны настройки УКР; запуск проверки запрещен (ЗапускПроверкиЛимитовВозможен). Тексты ошибок возвращаются пользователю сообщениями.

4 СнятиеАкцепта только претрейд

Если это отправка - у поручений, требующих снятия акцепта, ставится статус «Автоматическое снятие акцепта» через распорядитель Акцептование. Если это просто проверка и не используется согласование акцептов - акцепт снимается у поручений со статусом «Акцептовано» и у связанных с ними.

5 ДействующиеЛимиты замер

План проверки. РаботаСЛимитами.ПланПроверки. Для претрейда: портфели берутся из табличной части Поручение.РаспределениеПоПортфелям, к ним подбираются действующие лимиты с учетом режима проверки поручений (не использовать на претрейде, только покупки, только продажи, открытие депозита проверяется всегда). Для постконтроля: действующие лимиты по портфелям и по группам портфелей из регистров установок лимитов. Строка плана = поручение (или пусто), лимит, класс лимита, набор данных, группа, портфель, документ установки.

Нарезка. ПланОбработкиПроверки нумерует строки и раздает их исполнителям: на одно задание не меньше 10 проверок, число заданий - по константе потоков. План пишется в регистр КэшВмПланПроверки. Лимиты, проверяемые пакетно («внешние»), выносятся в КэшВмПланПроверкиВнешние. Вес распорядителя = число строк плана; он же идет в замер и в прогресс.

Дополнительно: портфели групп на дату, портфели наборов данных, реквизиты наборов данных (Справочники.НаборыДанныхДляПроверкиЛимитов) с подменой состава позиции из общих настроек.

6 ЧтениеНаборовДанных замер

По наборам данных (ЧтениеНаборовДанных): для каждого набора строится описание набора и через РасчетПозицииПортфелей.ТекущаяПозицияДляПроверкиЛимитов_МВТ собирается позиция портфелей во временных таблицах, затем ПроверкаЛимитов_ОписаниеИсточников.ДанныеНабора разворачивает ее в объединенную таблицу. Котировки, попавшие в набор, складываются в КэшВмКотировки. Данные набора сжимаются в хранилище значения и передаются главному сеансу.

По поручениям (ЧтениеНаборовДанныхПоручений, только претрейд): план чтения из КэшВмПланПроверки, по каждой строке вызывается ПроверкаЛимитовСлужебный.РезультатИсточникаДанныхПоПоручению - позиция «как будет после исполнения поручения», при необходимости дополненная остатками позиции.

Настройки лимитов (ЧтениеЛимитов, без потоков): для лимитов не «по алгоритму» читаются настройки внутренней проверки из кэша справочника Лимиты или рассчитываются заново. Некорректные настройки откладываются с описанием, структурные лимиты отмечаются отдельно, собираются поля условий отбора.

7 ПорогиБазисыПростые замер

ЧтениеСведенийОПорогах для структурных лимитов: РегистрыСведений.ПорогиЛимитов.СведенияОПорогах на дату фактической позиции по портфелям, результат пишется в регистр КэшВмПороги, в журнал уходит информационная запись с количествами. Параллельно в главном сеансе по каждому набору данных читаются ИсполнителиПолныеПрава.СтоимостиАктивовПортфелей - основа базисов (СЧА, РСА и другие).

8 ОбработкаПроверки замер

Крупно. Самый тяжелый этап. Каждый исполнитель получает номер и читает свою часть плана из КэшВмПланПроверки. Дальше цикл по лимитам, внутри - по группам портфелей плана, вызов ПроверкаЛимитов.Проверить.

Мелко. Перед циклом: план дополняется, отделяются внешние лимиты, читаются виды базисов, величины оттока паев, гарантийные обеспечения. При смене набора данных: старые временные таблицы удаляются, данные набора распаковываются; для источника «Поручение» объединенная таблица кладется во временную таблицу запросом; для источника «Текущая позиция» строится ВТ_ТаблицаНабораДанных плюс деноминации, капитализации, объемы облигаций. Для структурных лимитов из КэшВмПороги читаются пороги, собирается базис: стоимость активов, рыночная стоимость, объем облигаций в обращении, деноминатор, капитализация, отток, ГО.

ПроверкаЛимитов.Проверить по виду лимита: Состав - дерево значений по составу с квалификаторами; Структура - Справочники.ВариантыПроверкиПороговЛимитов.ПроверитьЛимиты; Поручение - дерево по поручению. Результат порции пишется сразу: ЗаписатьПорциюРезультатов в КэшВмКратко, КэшВмКраткоЭмитенты, КэшВмДетально. Ошибка проверки лимита не останавливает исполнителя: строка получает признак «Отказ» с описанием. По каждому лимиту фиксируется отдельный замер ПроверкаЛимита. Прогресс главному сеансу передается сообщениями пользователю с префиксом «[И]», главный опрашивает задания раз в секунду.

9 ПроверкаВнешних

Лимиты типа «пакетно» проверяются одним исполнителем без потоков: план из КэшВмПланПроверкиВнешние, метод РаботаСЛимитами.ОбработатьПланПоВнешнимЛимитам, запись в те же регистры результатов.

10 ЗаписьРезультатов замер

ЗаписьРезультатовПервогоЭшелона: для претрейда пишет НарушенияКлассовЛимитовПоПоручениям; если включена рассылка ведомостей (постконтроль) или рассылка результатов претрейда - ставит отложенный вызов ИсполнителиПолныеПрава.ДополнитьОчередьНаРассылку через ДлительныеОперации.ВыполнитьПроцедуру. Сам этап короткий: тяжелая запись результатов уже прошла внутри этапа 8.

11 РезультатОбработкиПоручений только претрейд

Статусы поручений по зонам (см. задачу 1, блок 5), проверка отклонения цены, формирование текста итога по каждому поручению, добавление в список на отправку тех, у кого нет красной зоны и отказа. Дописываются результаты акцептования связанных поручений.

12 Отправка внешние системы

Только при флаге «отправить после проверки». Описано в задаче 1, блок 6.

13 ПроектВместилище и завершение

В описание вместилища добавляется «Проверок: N». В КэшВмНакопитель сжато пишется накопитель: реквизиты наборов, краткие реквизиты поручений, базисы (в рабочем режиме сокращенные до СЧА и РСА). Котировки - в КэшВмКотировки. Для постконтроля - связи фокусов в КэшВмСвязи. При включенном логе отладки результат отладки возвращается клиенту. При исключении регистры вместилища очищаются (ОчиститьРегистрыПриАварии), все непроверенные поручения получают «Не удалось проверить». В любом случае: запись КэшВмОписания, события поручений, разблокировка, замер ключевой операции Проверка с весом = число проверок.

Назначение блоков

1 Запуск по расписанию сервер

Регламентное задание ПроверкаПоЛимитам вызывает АванкорВыполнениеРегламентныхЗаданий.ПроверкаПоЛимитам, тот - Обработки.ПроверкаЛимитовПоПортфелям.ПроверкаПоЛимитамПоРасписанию с размером порции 500 по умолчанию. Свойства задания: 3 перезапуска при сбое с интервалом 60 секунд. Расписание задается в базе, в метаданных задания нет.

2 Настройки настройки

Все берется из константы НастройкиРассылкиПоЛимитам (хранилище значения со структурой, см. ПроверкаЛимитов.НовыеНастройкиРассылки): список портфелей и групп портфелей, смещение даты, использовать дату актуальности, изменить состав позиции и сам состав, настройки рассылки писем отдельно для претрейда и посттрейда, вид выбираемых лимитов. Если список портфелей пуст - в журнал пишется ошибка и задание выходит.

Дата проверки: начало текущего дня; при отрицательном смещении - предыдущая рабочая дата по календарю смещения фактической позиции (ПолныеПрава.ПолучитьКалендарьСмещениеФактическойПозиции), без календаря - минус N календарных дней. В параметры уходит конец этого дня.

3 Список портфелей хранилище

Каждый элемент списка раскрывается: портфель - как есть; группа с признаком «Все портфели» - состав пула на текущую дату (СоставПулаПоГруппеПортфелей); пуловая группа - как единый объект проверки; обычная группа - перечень портфелей из ее списка. Затем РегистрыСведений.НеактивныеПортфели.ИсключитьНеактивныеИзСписка. Пустой список - тихий выход без ошибки.

4 Вызов конвейера сервер

Формируются стандартные параметры проверки, в них подставляются портфели, состав позиции и флаг даты актуальности из настроек. Поручений нет, поэтому в конвейере пропускаются этапы 1, 4, 11, 12 и чтение наборов по поручениям. Признак «претрейд» ложь: пороги поручений не используются, дата проверки записывается в описание вместилища. Отказ конвейера превращается в исключение регламентного задания.

5 Очередь рассылки хранилище

После успешной проверки ИсполнителиПолныеПрава.ДополнитьОчередьНаРассылку(Вместилище): читает краткий результат из КэшВмКратко, исключает неактивные портфели, ждет паузу (10 секунд по умолчанию, при клиент-серверном вызове 1 секунда), затем по режиму настройки рассылки раскладывает записи в КэшВмРассылка либо по адресам, либо по получателям с фильтром по виду лимитов.

6 Отправка писем внешние системы

Отдельное регламентное задание АванкорРассылкаВедомостей вызывает РегистрыСведений.КэшВмРассылка.РассылкаВедомостей: подготовка вместилищ во временных таблицах, рассылка претрейд, рассылка посттрейд, сохранение ведомостей в файлы по настройкам. Письмо формируется с телом по списку поручений или портфелей и навигационными ссылками на объекты базы, отправляется через РаботаСПочтовымиСообщениями.ОтправитьПочтовоеСообщение с учетной записью из настроек.

Выход наружу: почтовый сервер по учетной записи электронной почты. Это единственная внешняя связь постконтроля. Сама проверка внешних систем не трогает.
7 Просмотр результата клиент

Результаты вместилища доступны через отчет СправкаРасчет и форму обработки ПроверкаЛимитовПоПортфелям (ручной запуск той же проверки с выбором портфелей, ограничением плановой позиции и своими лимитами). Табличная сводка результата: ТаблицаРезультатовПроверки по КэшВмКратко - зона, лимит, вид, «проверка успешна» = зона не красная, «лимит проверен» = не отказ.

Сброс кэша на каждом старте

ОбработатьЗапуск вызывает ОбновитьПовторноИспользуемыеЗначения() при каждом распоряжении. Значит, каждая проверка поручения обнуляет все повторно используемые значения сеанса, включая настройки лимитов из кэша, которые потом читаются заново.

Запросы внутри цикла по лимитам

В ОбработкаПроверки для каждого лимита и каждой порции портфелей выполняются запросы (помечены query-in-loop), собирается базис, пишется порция результатов в три регистра. Число итераций = строк плана в доле исполнителя.

Передача данных через сериализацию

Данные наборов, описания наборов и результаты исполнителей упаковываются в хранилище значения со сжатием и передаются через временное хранилище, затем распаковываются в каждом исполнителе проверки. Объем пропорционален числу портфелей и активов.

Ожидание фоновых заданий

Главный сеанс опрашивает задания с таймаутом 1 секунда и читает сообщения пользователю для прогресса. Порождение заданий идет последовательно, на каждое - отдельный замер ПорождениеИсполнителя. Минимум 10 проверок на задание, поэтому при малом плане потоки не задействуются.

Нарезка плана без учета веса

ПланОбработкиПроверки делит строки поровну по количеству, не по сложности лимита или размеру портфеля. Исполнитель с тяжелыми структурными лимитами держит весь этап, пока остальные простаивают.

Пауза перед рассылкой

ДополнитьОчередьНаРассылку ждет 10 секунд (1 секунду при клиент-серверном вызове) перед чтением результатов. Для постконтроля это фиксированная задержка после каждой проверки.

Замер записи не там, где запись

Замер «ЗаписьРезультатов» накрывает только первый эшелон. Основная запись в КэшВмКратко, КэшВмДетально происходит внутри исполнителей этапа 8 и попадает в «ОбработкаПроверки». Разделить расчет и запись в текущих замерах нельзя.

Дообработка поручений на входе и выходе
