Код: конфигурация "Аванкор: Фронт-офис" 1.4.9.5, расширение FO_LimitCheckOpt

Почему сведения о порогах можно строить только для пар из плана
Ни одна проверка не теряется: пары вне плана строились, но никогда не читались

Штатный код строит сведения о порогах для каждого портфеля с каждым лимитом. Расширение строит их только для пар "лимит - портфель" из плана проверки плюс пустой портфель каждого лимита. Ниже показано, откуда берется план, кто и по какому ключу читает сведения о порогах и почему множество читаемых ключей совпадает с тем, что строит расширение.

Словесное обоснование

Что делает штатный код. При проверке лимитов по портфелям задание "Чтение сведений о порогах" для каждого структурного лимита готовит соответствие "портфель - сведения о порогах" и кладет его в регистр КэшВмПороги. Список пар для этого соответствия задает первый запрос пакета: он берет все портфели проверки и соединяет каждый с каждым лимитом задания, плюс пустой портфель на каждый лимит. На обычном ФО это 551 лимит на 3 857 портфелей, то есть 2,1 млн структур, которые затем сериализуются и записываются.

Откуда берутся портфели и лимиты. Портфели, которые передаются в чтение порогов, - это не весь справочник, а портфели плана проверки текущего запуска. План строится раньше, на шаге "Действующие лимиты", по установкам лимитов (для поручения - по портфелям поручения) и записывается в регистр КэшВмПланПроверки с ключом Вместилище - идентификатором этого запуска. В плане каждая строка - конкретная пара "лимит - портфель" или "лимит - группа портфелей". Штатный запрос из этих же портфелей и лимитов собирает все сочетания, в том числе такие, где лимит на портфель не установлен и в плане не стоит.

Кто читает сведения о порогах. Читатель один - задание "Обработка проверки", процедура ПроверкаЛимитов.КэшВмКратко. Задание берет свои строки плана из того же регистра КэшВмПланПроверки по тому же Вместилищу и для каждой строки обращается к соответствию порогов по ключу. Ключ - это фокус строки плана: портфель, если строка по портфелю, или пустой портфель, если строка по группе портфелей. Других обращений к сведениям о порогах в конфигурации нет.

Отсюда вывод. Все ключи, по которым сведения о порогах когда-либо читаются, - это пары "лимит - портфель" из плана и пара "лимит - пустой портфель". Пары, которых нет в плане, штатный код строил, сериализовал и записывал, но ни одна проверка к ним не обращалась. Поэтому их можно не строить: ни одна проверка не выпадает, потому что каждая проверка - это строка плана, а ключ каждой строки плана в новом наборе есть.

Почему значения не меняются. Порог для пары вычисляется дальше по пакету, и этот код не менялся: к паре подтягивается порог, заданный на сам портфель, и порог, заданный на лимит (пустой портфель), затем выбирается приоритет портфеля над лимитом. Все соединения идут по самой паре или по лимиту, поэтому результат по паре не зависит от того, какие еще пары есть в наборе. Портфель без собственного порога по-прежнему получает порог лимита.

Порядок и ключ совпадают. План записывается до запуска чтения порогов, а чтение порогов и обработка проверки получают одно и то же Вместилище от распорядителя запуска. Поэтому расширение читает из КэшВмПланПроверки ровно те строки, по которым потом пойдет обработка проверки.

Защита. Расширение меняет только первый запрос пакета. Если плана по Вместилищу нет или штатный текст первого запроса изменился (например, после обновления конфигурации), выполняется штатный запрос без изменений. Проверка на данных подтверждает рассуждение: 0 расхождений в кратком итоге на базе разработчика, совпадение всех строк на уровне запроса, успешный регламент на Т-1 при сокращении структур с 2,1 млн до 175 тыс.

Раздел 1

Что такое Вместилище

Вместилище - уникальный идентификатор одного запуска проверки (Распорядитель.Идентификатор). Его создает Распорядители.ПроверкаИОтправка в начале проверки, и дальше им помечаются все промежуточные данные этого запуска.

Все кэш-регистры проверки имеют измерение Вместилище: план, описания наборов, сведения о порогах, результаты. Поэтому данные одного запуска не смешиваются с другими - ни с параллельным предконтролем, ни с предыдущим регламентом.

Раздел 2

Поток данных одного запуска

Три шага идут строго по порядку. План записывается раньше, чем начинается чтение порогов, и оба последующих шага берут его из одного регистра по одному Вместилищу.

Раздел 3

Какие ключи вообще читаются

Ключевое утверждение

Потребитель сведений о порогах один - ПроверкаЛимитов.КэшВмКратко в задании обработки проверки. Он обращается к соответствию только по фокусу строки плана своего лимита:

Кратко.Сведения = Параметры.СведенияОПорогах[Гр_Фокус.Фокус];
Если ТипЗнч(Гр_Фокус.Фокус) = Тип("СправочникСсылка.ГруппыПортфелей") Тогда
    Кратко.Сведения = Параметры.СведенияОПорогах[Справочники.Портфели.ПустаяСсылка()];
КонецЕсли;

Фокус берется из КэшВмПланПроверки по тому же Вместилищу. Значит, каждый ключ, который читается, - это либо пара "лимит - портфель" из плана, либо "лимит - пустой портфель". Расширение строит ровно эти ключи. Остальные пары штатный код строил, сериализовал и записывал, но к ним никто не обращался.

Раздел 4

Обоснование по шагам

Утв.
1

Портфели в чтении порогов - это уже портфели плана

&Портфели = Кэш.Массивы.Портфели = ПланПроверки.Портфели (заполняется в ПланОбработкиПроверки по строкам плана). Штатный запрос не добавлял новых портфелей - он только пересекал каждый портфель плана с каждым лимитом. Лишние пары - это "портфель, для которого лимит в плане не стоит".

Утв.
2

План записан раньше и тем же ключом

В Распорядители.ПроверкаИОтправка область "ПортфелиИГруппы" вызывает ПланОбработкиПроверки(ПланПроверки, Вместилище, ...), которая пишет КэшВмПланПроверки с этим Вместилищем. Только потом, в области "ПорогиБазисыПростые", запускается чтение сведений о порогах. Задание чтения порогов и задание обработки проверки берут Вместилище из одного и того же Распорядитель.Идентификатор; задание обработки читает план по нему же (ПланПроверкиИсполнителя(Вместилище, НомерИсполнителя)).

Утв.
3

Значение по каждой паре не зависит от других пар

Дальше по пакету к каждой паре левыми соединениями подтягиваются порог самого портфеля и порог пустого портфеля того же лимита, выбирается приоритет, затем группировка по паре. Все соединения - по паре или по лимиту. Удаление других пар не меняет значение оставшихся: порог портфеля без своей записи по-прежнему наследуется от пустого портфеля лимита.

Утв.
4

Потребитель читает только ключи плана и пустой портфель

Раздел 3: фокус строки плана или пустой портфель для группы. Пустой портфель расширение оставляет для каждого лимита задания, как в штатном тексте. Других обращений к СведенияОПорогах[...] и к КэшВмПороги в конфигурации нет.

Вывод
=

Каждая проверка получает те же пороги, что и раньше

Множество читаемых ключей (утв. 4) целиком входит в множество построенных (утв. 1-2), и значения по этим ключам те же (утв. 3). Значит, ни одна проверка лимита не пропадает и ни одна не получает другой порог. Меняется только объем промежуточных данных, которые никто не читал.

Раздел 5

Особые случаи

СлучайЧто происходит
Строка плана по группе портфелейПотребитель берет пустой портфель лимита. Пустой портфель строится на каждый лимит всегда - вторая часть первого запроса не менялась.
Портфель без собственной записи пороговПара есть в плане - значит, есть и в новом наборе; порог наследуется от пустого портфеля лимита теми же соединениями.
Портфель с собственным порогомПриоритет портфеля над лимитом выбирается дальше по пакету, код не менялся. Проверено на синтетическом пороге портфеля: результат совпал со штатным.
Предконтроль порученияПлан поручения пишется тем же путем до чтения порогов, в строке - портфель поручения. Работает по новому запросу.
Внешние лимиты и лимиты другого типаВ КэшВмПланПроверки попадают только стандартные лимиты. Внешние обрабатываются отдельно и сведения о порогах не читают.
Плана по Вместилищу нет или изменился штатный текстРасширение выполняет штатный запрос без изменений: проверяет наличие плана и совпадение первого запроса пакета.
Раздел 6

Проверка на данных

Полный прогон, база разработчика

Три набора до 3 100 портфелей x 89 лимитов, прогон с расширением и без. Краткий итог по каждой паре "лимит - фокус" (зона, базис, отказ, описание, зона порогов, все примененные пороги): 0 расхождений на 177 000, 275 900 и 75 020 строках.

Уровень запроса

Штатный и новый текст пакета на одних параметрах, плюс синтетический порог портфеля: каждая строка нового результата совпала со строкой штатного, пары нового результата - ровно пары плана и пустой портфель. Т-1 обычного ФО: регламент завершился без ошибок, 175 тыс. структур вместо 2,1 млн.
