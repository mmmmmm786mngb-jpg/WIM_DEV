Коротко. Почти всё время ночного постконтроля розницы уходит не на расчёт лимитов, а на одну строку служебного кода. Почему это квадратичная сложность

В Исполнители.ПроверкаИОтправка_ОбработкаПроверки для каждой строки порции вызывается

Для Каждого Строка Из ПорцияДанных Цикл
    ...
    ДополнитьМассив(ПортфелиПорции, ПортфелиГруппы, Истина);   // Исполнители:2486

БСП-версия с флагом уникальности при каждом вызове заново строит соответствие по всему приёмнику (строки 505–507). Приёмник растёт до размера порции, поэтому на порцию из n портфелей работа ≈ n²/2.

В рознице у лимита шаблона одна порция на ~25 тыс. портфелей: 176 063 строки / 7 порций ≈ 25 150. Получается 7 × 25 150² / 2 ≈ 2,2·10⁹ итераций, а замер показывает 1,97·10⁹. Цифры сходятся.

То же объясняет и обычный фронт-офис

Проверим на обычном ФО: ~25 лимитов × 3 100² / 2 ≈ 1,2·10⁸ итераций. При скорости из розничного замера (≈ 5,6 мкс на итерацию) это ≈ 670 с. Фактическая медиана «Обработки проверки» регламента обычного ФО — 625 с (fo_non_rdu_gap.txt). Разные объёмы, один механизм. Он же объясняет, почему розница «толще» обычного ФО не в 8 раз по портфелям, а в ~18 раз по времени.

4. Риски быстрого пути FO_LimitShare

«0 расхождений» получено на синтетике FO_SHAPE / FO_REP. Её строили под возможности быстрого пути: портфели без групп, вариант «по общему итогу», без минимальных порогов. Ниже случаи, которые эти тесты не покрывают. По коду в них результат может разойтись со штатным.

  1. Фокус-группа (ПоГруппе = Истина, пулы). Суммы Факты собираются по Портфель, а ищутся по Фокус. Для группы факт не находится, считается 0, и лимит получает «Позиция 0» с пустой зоной вместо суммы по портфелям группы.
  2. Нулевая позиция при заданном минимуме. Штатно «ниже минимума» ловит пустой портфель и даёт красную или жёлтую зону. Быстрый путь при Факт = 0 всегда ставит пустую зону.
  3. Функция порога не проверяется. Если сравнение идёт «по каждому эмитенту» или «по каждому активу», быстрый путь всё равно сравнивает общий итог фокуса.
  4. Претрейд. Путь не отключается при ЭтоПретрейд, если источник набора не «Поручение». Проверяется флаг Сведения.ИспользоватьПорогиПоручения, а не параметр прогона. Понижение красной до жёлтой на продаже не выполняется.
  5. Разбор текста отбора. Разбор идёт по " И ". Фрагменты без #Т. молча пропускаются, префикс НЕ и скобки не учитываются. Условие может «потеряться» без отказа от быстрого пути.
  6. Ошибки репрайсинга (ЕстьОшибкиРепрайсинга) в быстром пути не учитываются.
  7. Клонирование результата (ПроверитьИлиПодставить). В ключ не входят тексты квалификаторов, модификатор данных и режим лимита. Два лимита состава с одинаковым основным отбором, но разными квалификаторами могут получить чужой результат.
  8. Нет КэшВмДетально и КэшВмКраткоЭмитенты для лимитов быстрого пути, поэтому расшифровка на экране будет пустой.

Кроме того, задание fo-limit-share-prompt-v2.html (состав и поручение в пачке, операторы «в списке», «в группе» и т.д.) реализовано частично. В коде есть только «процент от РСА» по полям ВидАктива и ВалютаНоминала.

5. Два технических вопроса, которые нужно закрыть

5.1. Три расширения перехватывают одну и ту же функцию

FO_LimitShare, FO_CheckProc и FO_PortionIndex — каждое делает &ИзменениеИКонтроль("ПроверкаИОтправка_ОбработкаПроверки"), у каждого своя полная копия тела. Эти правки не складываются: одновременно включённые, они не дадут суммы эффектов. Для замеров включайте по одному. Для переноса в типовую нужна одна сведённая версия процедуры.

5.2. Параметры.Данные[0]: весь ли план считается

Штатная функция читает план только по первому номеру исполнителя. Распорядители.ИсполнитьРаспоряжение режет номера как Макс(Окр(N / потоки + 0.5), …), и при 6 номерах и 6 потоках в задание уходит по 2 номера. Тогда второй номер не считается (это есть в limit-check-map.html, FO_CheckProc это исправляет).

Косвенно на это указывает сам замер: в .pff обработано 176 063 строки порций, это около трети плана в ~551 тыс. строк. Возможно, профилировщик поймал одно задание из трёх. Возможно, часть плана не проверяется вообще.

Проверка: по одному вместилищу регламента сравнить число строк КэшВмКратко с весом плана. Если строк меньше, это ошибка полноты, её нужно отдельно сообщить Аванкор. И учтите: после исправления работы станет больше, чем сейчас.

Исходников базовой конфигурации в папке нет, так что по коду типовой это не сверено. Вывод опирается на документацию и тела перехватов.

7. Предконтроль

Для одного поручения порция маленькая (медиана 36 строк плана), квадратичная склейка там незаметна. 11 с на вызов складываются из «Обработки проверки» (~4 с), чтения наборов (~1,6 с), порогов и действующих лимитов (~1,4 с) и накладных расходов на фоновые задания. FO_PortionIndex предконтроль заметно не ускорит. Это отдельная задача, и её стоит разбирать по хвосту (p95 21 с, максимум 83 с), а не по медиане, которая уже близка к ориентиру 10 с.
