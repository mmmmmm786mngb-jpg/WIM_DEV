Раздел 3

Почему чтение сведений о порогах такое тяжелое

Функция РегистрСведений.ПорогиЛимитов.СведенияОПорогах, вызывается из фонового задания Исполнители.ПроверкаИОтправка_ЧтениеСведенийОПорогах для структурных лимитов.

Как устроено

  • Первый запрос пакета (ВТ_ПортфелиЛимиты) соединяет все портфели проверки со всеми лимитами без условия - каждый с каждым.
  • На каждую пару создается структура сведений о порогах: около 30 полей и вложенная структура реквизитов настроек.
  • По каждому лимиту соответствие "портфель - сведения" сериализуется в ХранилищеЗначения и пишется в регистр КэшВмПороги.
  • Потребитель, функция ПроверкаЛимитов.КэшВмКратко, берет сведения только по фокусу строки плана; для группы портфелей - по пустому портфелю лимита.

Приложение 1

Постановка на расширение: сведения о порогах только для нужных пар

Текст постановки для разработки. Обе доработки - индекс портфелей порции и сведения о порогах - собираются в одном расширении.

ЗАДАЧА
Доработать расширение конфигурации "Аванкор: Фронт-офис" 1.4.9.5 так, чтобы регламент "Проверка по лимитам" (постконтроль по портфелям) строил сведения о порогах только для пар "лимит - портфель" из плана проверки и для пустого портфеля каждого лимита. Результат проверки лимитов меняться не должен.

КОНТЕКСТ И ЗАМЕРЫ
- Обычный ФО, тестовая база (ночная копия ПРОД): 551 структурный лимит, 3 857 портфелей, 374 284 строки плана (все виды лимитов).
- РегистрСведений.ПорогиЛимитов.СведенияОПорогах(Параметры, Вместилище, Исполнитель) строит 2 117 338 структур сведений о порогах (551 x 3 857); плану нужно не больше 18% из них.
- На ПРОД блок занимает около 10 минут из 29 и стоит на критическом пути; на тестовом сервере два фоновых задания чтения порогов падают с ошибкой "На сервере недостаточно памяти для выполнения задания".
- Замер одного задания (чистое время 514 с): цикл по парам около 336 с, сериализация в ХранилищеЗначения и освобождение соответствия около 103 с, запрос ВыполнитьПакет около 49 с, запись КэшВмПороги около 26 с. Ожидание после доработки - 110-135 с на задание, память под структуры примерно на 80% меньше.
- Розница: 7 лимитов x 23 056 портфелей = 161 392 структуры, около 45 секунд. Доработка не должна ухудшить розницу.

ОДНО РАСШИРЕНИЕ
- Сейчас в работе расширение FO_PortionIndex ("Индекс портфелей порции"): один перехват &ИзменениеИКонтроль("ПроверкаИОтправка_ОбработкаПроверки") в общем модуле Исполнители (индекс ИндексПортфелейПорции вместо ДополнитьМассив(ПортфелиПорции, ПортфелиГруппы, Истина)).
- Новая доработка - другой метод того же контура проверки лимитов (модуль менеджера регистра ПорогиЛимитов); с перехватом индекса они не пересекаются, но должны жить в одном расширении. Поэтому: создать расширение FO_LimitCheckOpt, перенести в него перехват из FO_PortionIndex без изменений (те же маркеры #Вставка / #Удаление) и добавить новый перехват. После проверки FO_PortionIndex отключить и удалить из баз.
- Расширение пакетной проверки FO_LimitShare перехватывает ту же процедуру ОбработкаПроверки; одновременно с новым расширением его не включать.

ЧТО СДЕЛАТЬ
1. Один перехват модуля менеджера РегистрСведений.ПорогиЛимитов: функция ТекстЗапросаПолученияПорогов и функция СведенияОПорогах.
   - Сейчас первый запрос пакета ВТ_ПортфелиЛимиты - соединение всех портфелей (&Портфели) со всеми лимитами (&Лимиты) по условию ИСТИНА, плюс пустой портфель на каждый лимит. &Портфели - это уже портфели плана (Кэш.Массивы.Портфели = ПланПроверки.Портфели), поэтому сужение только списка портфелей ничего не даст: лишние пары возникают из-за пересечения каждого портфеля с каждым лимитом.
   - Заменить только этот первый запрос: пары "Лимит, Портфель" брать из строк плана РегистрСведений.КэшВмПланПроверки с отбором Вместилище = &Вместилище и Лимит В (&Лимиты) - только лимиты текущего задания. Плюс пустой портфель на каждый лимит из &Лимиты, как сейчас: строки плана с фокусом "группа портфелей" читают именно его.
   - В СведенияОПорогах передать в запрос параметр Вместилище (он уже есть среди параметров функции). План записывается в РаботаСЛимитами.ПланОбработкиПроверки с тем же Вместилищем до запуска чтения порогов (Распорядители.ПроверкаИОтправка, область ПортфелиИГруппы, затем ПорогиБазисыПростые) - при реализации подтвердить, что Распорядитель.Идентификатор в задании равен этому Вместилищу.
   - Основа пар - план, а не записи регистра ПорогиЛимитов. Не ограничивать пары портфелями, у которых есть своя запись порогов: сейчас портфель без своей записи получает порог пустого портфеля лимита (Приоритет 2), и этот порог кладется в ключ самого портфеля. Если такие пары выбросить, портфели получат "Не заданы пороги" и красную зону.
   - Остальные запросы пакета и цикл функции (приоритет портфеля над лимитом, таблица порогов, структуры "пороги не найдены") не менять. Текст запроса в перехвате переносится целиком, меняется только первый запрос пакета.
   - Запасной вариант: если плана по Вместилищу нет, выполнять штатный первый запрос.
2. Потребителя ПроверкаЛимитов.КэшВмКратко не менять. Это единственное место чтения соответствия по портфелю: фокус-портфель читается по портфелю, фокус-группа - по пустой ссылке. При реализации подтвердить, что других обращений нет.
3. Предконтроль поручения тоже пойдет по новому запросу: план поручения записывается до чтения порогов, в строке плана - портфель поручения. Проверить отдельно (см. приемку).
4. Розница: в чтении порогов 7 лимитов, блок около 45 секунд; если эти лимиты стоят в плане почти у всех портфелей, блок почти не сократится. Требование - результат совпадает, время не хуже.

ОГРАНИЧЕНИЯ
- Базовую конфигурацию не менять. Только перехваты расширения: &ИзменениеИКонтроль с маркерами #Вставка / #Удаление, либо &Перед / &После, где хватает.
- Вызовы API платформы и БСП сверять со справочником, прикладные объекты - с выгрузкой конфигурации.
- Каждое место правки - с комментарием о причине. Без буквы е с точками, без длинных тире.
- Не менять расчет зон, базисов, порогов и запись результатов.

ПРИЕМКА
- Сверка результата: на одной базе прогон без расширения и с расширением; регистр КэшВмКратко по паре "лимит - фокус": совпадают Зона, Базис, Отказ, Описание, ЕстьНарушение, ОшибкаСбораДанных, Сведения.ПорогиНайдены. Критерий - 0 расхождений; порядок строк не сравнивается.
- Обычный ФО, тестовая база: регламент "Проверка по лимитам" проходит без ошибки памяти и доходит до шага "Обработка проверки"; записать время шагов по регистру "Замеры времени", длительность заданий чтения порогов и число структур в сведениях о порогах (ожидается не больше 374 тысяч вместо 2,1 миллиона).
- Розница: время проверки не хуже прогона с FO_PortionIndex (около 0 ч 18 мин на тестовом сервере), результат совпадает.
- Предконтроль одного поручения: результат и время совпадают со штатными (новый запрос работает и здесь).
- Отдельно проверить в сверке портфели без собственной записи порогов: зона и ПорогиНайдены как в штатном прогоне, без "Не заданы пороги".
- Отчет: что перенесено из FO_PortionIndex, список перехватов с маркерами, таблица замеров до и после, результат сверки.
