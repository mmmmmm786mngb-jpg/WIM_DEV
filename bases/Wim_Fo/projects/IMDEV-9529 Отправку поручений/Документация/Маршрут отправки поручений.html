ФО · Блоттер · кнопка "Проверить и отправить"

Куда уходит поручение после нажатия "Проверить и отправить"

Трасса вызовов от команды формы блоттера до сетевого вызова в адаптере торговой системы. Собрано по исходникам основной конфигурации ФО; расширения (VTB, ВТБ_Прод) эту цепочку не перехватывают.

Короткий ответ

Сначала на сервере выполняется pre-trade проверка лимитов (Распорядители.ПроверкаИОтправка). Поручения, прошедшие проверку, передаются в Распорядители.Отправка, где группируются по адаптеру. Адаптер берется из регистра сведений РасширенияПоручений (поле Адаптер), его вид - из Справочник.Адаптеры.Вид. Дальше заявка уходит во внешнюю торговую систему: в терминал QUIK через COM-компоненту T2Q, либо HTTP POST в шлюз FIX / FIX-Ray / WINVESTOR. Внебиржевые поручения никуда не отправляются: по ним сразу создается документ Сделка или СделкаРЕПО.

В этой базе один адаптер вида FIX: биржевые поручения уходят HTTP-запросом на WebSocket-прокси, а прокси пересылает FIX-сообщение в сессию с ВТБ (FORDU_PROD → FORDU_VTB24).

Адаптер этой базы: (UID 1189634) QUIK FIX Банк ВТБ (ПАО)

В справочнике Адаптеры одна запись, ее Вид = FIX. Слово QUIK в наименовании на маршрут не влияет: менеджер выбирается по реквизиту Вид, поэтому работает Обработка.АдаптерFIX, а COM-компонента T2Q не используется.

Поле формы адаптераКак используется при отправке
Вид = FIXКлюч в Справочники.Адаптеры.Менеджеры(): выбирается Обработки.АдаптерFIX.
Адрес подключенияАдрес FIX-сервера брокера вида x.x.x.x:port. 1С сама к нему не подключается: адрес передается прокси в команде connect?params={ip, port, guid, message=Logon} (ВыполнитьСоединение). Хранится в безопасном хранилище, поэтому на форме отображается маской.
Отправитель / ПолучательSenderCompID (49) и TargetCompID (56) в заголовке каждого FIX-сообщения.
OutMsgSeqNoСчетчик исходящих номеров MsgSeqNum (34), регистр СообщенияАдаптеровСчетчики. Перед отправкой номера захватываются на все поручения пакета, после успешной отправки сохраняется последний.
InMsgSeqNoНомер последнего входящего сообщения. Ответы (ExecutionReport) забираются у прокси отдельно командой get?params={guid} и подтверждаются командой confirm.
СердцебиениеИнтервал Heartbeat (35=0) для FIX-сессии.
Идентификатор адаптераПоле guid в запросах к прокси: по нему прокси определяет, в какую FIX-сессию переслать сообщение.

Адрес самого прокси (АдресHTTPСервиса) задается не в карточке адаптера, а в общих настройках: объект ВебСокетПрокси, ключ НастройкиВебСокетПрокси. Поручение уходит только при состоянии адаптера "готов к работе" в регистре СостоянияАдаптеров. Это состояние обновляет КонтроллерСинхронизации через АдаптерFIX.СоединениеДоступно: он опрашивает прокси и, если сессия не в состоянии Connected, выполняет connect с Logon. Таймаут HTTP-вызова /send - 2 секунды.

ИсполнитьРаспоряжение: диспетчер исполнителей

Распорядители.ИсполнитьРаспоряжение (стр. 2791) сама ничего не отправляет. Это общий механизм для всех этапов распорядителей: чтение, проверка лимитов, запись результатов, отправка, отмена, изменение цен. Она получает массив данных и метод исполнителя и запускает этот метод либо синхронно, либо фоновыми заданиями по частям. Отправкой вызов становится, только когда ему передан исполнитель Исполнители.Отправка_ОтправкаПоручений.

План отправки - один элемент {Адаптер, все поручения}: потоков 1, одно фоновое задание. В нем все поручения собираются в один пакет FIX и уходят одним HTTP POST на /send. Параллельно работают только два участка: внебиржевые поручения, которые родительский сеанс обрабатывает, пока идет задание, и этап ОбработкаПроверки в проверке лимитов. Даже при нескольких заданиях на один адаптер они бы выстроились в очередь: ЗахватитьНомераИсходящие ставит исключительную блокировку на СообщенияАдаптеровСчетчики по адаптеру, и транзакция держит ее до ответа прокси.

Как распараллелить отправку поручений

Ограничение FIX. В одной FIX-сессии MsgSeqNum (34) обязан строго возрастать. Сообщение с номером ниже ожидаемого приводит к разрыву сессии контрагентом, с номером выше - к ResendRequest. Поэтому параллельные POST в одну сессию с разными блоками номеров недопустимы: блоки могут прийти не по порядку. Параллелить можно либо подготовку при одном последовательном вызове, либо сами FIX-сессии.

Сначала замер. Время отправки складывается из трех частей: цикл проверок в Распорядители.Отправка (статусы, хеш, валидация), сборка сообщений и запись статусов в задании, сам HTTP-вызов. Если основное время занимает HTTP, вариант A не даст выигрыша и нужен вариант B. Если время уходит на запись в регистры - выигрыш даст вариант A. Ключевая операция КлючевыеОперации.Отправка уже есть, ее достаточно разбить на подзамеры.

  1. Новые исполнители в модуле расширения, например Отправка_ПодготовкаПоручений и Отправка_ФиксацияОтправки. Запуск через тот же ИсполнитьРаспоряжение, число потоков - новая константа, например ПотоковОтправкиПоручений, минимум 20-50 поручений на задание.
  2. Перехват Распорядители.Отправка: цикл проверок по поручениям заменяется распоряжением подготовки, затем последовательный блок отправки (номера, сборка, POST, счетчик), затем распоряжение фиксации с ожиданием через РезультатИсполненияРаспоряжений.
  3. Исходящие номера назначаются только в родителе, по порядку сортировки поручений. Порядок MsgSeqNum сохраняется.

Риск: сейчас статусы "Отправлено" пишутся в той же транзакции, что и отправка, и откатываются при ошибке POST. В варианте A они пишутся после успешного ответа прокси, отдельными заданиями. Если задание фиксации упадет, поручение уже на бирже, но в 1С без статуса. Нужен повтор фиксации по журналу отправленного пакета, и надо проверить, что ExecutionReport из get корректно обрабатывается для поручения в статусе "Проверено".

Вариант B. Несколько FIX-сессий у брокера

Распределениепоручения по кругу между адаптерами FIX_1..FIX_K
→
ИсполнитьРаспоряжениекак сейчас: K адаптеров = K фоновых заданий
→
K параллельных POST /sendу каждой сессии свои SenderCompID и счетчик номеров
  1. У ВТБ запрашиваются дополнительные FIX-сессии (свои SenderCompID). На каждую в справочнике Адаптеры создается адаптер вида FIX с собственным идентификатором для прокси.
  2. В расширении перехватывается РасширенияПоручений.ПереопределитьАдаптеры (или формирование ТаблицаДанныхПоручений): поручения распределяются между готовыми адаптерами по кругу или по нагрузке.
  3. Механизм распараллеливания уже есть: Распорядители.Отправка строит план по адаптерам, и ИсполнитьРаспоряжение запускает по заданию на адаптер. Блокировки счетчиков независимы, MsgSeqNum в каждой сессии остается последовательным.

Риск: отмена и изменение поручения должны уходить через ту же сессию, через которую оно было отправлено. Адаптер поручения нужно закрепить в РасширенияПоручений в момент отправки и не переопределять его при последующих операциях. Также нужна проверка, что прокси держит несколько сессий одновременно.

Рекомендация: начать с замера. При одной FIX-сессии выигрыш возможен только на подготовке и записи статусов (вариант A). Реальная параллельная отправка в биржу - только через несколько сессий (вариант B), и он почти не требует нового кода. Обе доработки делаются в расширении, без изменения основной конфигурации.

Веб-клиент

Динамический вызов распорядителя в РаботаСПоручениямиКлиент.ВыполнитьМетодОбработкиПоручений отключен директивой #Если Не ВебКлиент. В веб-клиенте кнопка не выдает ни ошибки, ни отправки.

Два уровня фоновых заданий

Проверка лимитов идет в фоновом задании БСП (ДлительныеОперации), если база клиент-серверная и фоновые задания включены настройкой. Внутри него отправка порождает собственные фоновые задания через ФоновыеЗадания.Выполнить, по адаптерам.

Адаптер определяется поручением

Адаптер не выбирается на форме: он берется из записи РС РасширенияПоручений поручения. Перед отправкой его может подменить ПереопределитьАдаптеры, если в настройках включено переопределение адаптера.

Источник: код конфигурации Аванкор Фронт-офис; расширения VTB и ВТБ_Прод проверены на перехват методов цепочки - перехватов нет. Номера строк актуальны для текущей выгрузки.
