ТЗ-промпт: разработка обработки «внАвтоНачислениеВУК_РДУ»

Роль исполнителя. Ты — разработчик 1С:Enterprise (BSL, управляемое приложение, платформа не ниже 8.3.21), знакомый с конфигурацией «Аванкор: Доверительное управление» (база Wim_Du). Твоя задача — по этому ТЗ реализовать новую внешнюю дополнительную обработку с командой фонового выполнения и регламентным заданием. Соблюдай стандарты кодирования 1С проекта: PascalCase, корректный регистр ключевых слов, документирующие комментарии к экспортным процедурам, параметры запросов (без конкатенации), обработку ошибок через Попытка только там, где ошибка непредсказуема, логирование в ЖурналРегистрации.
Статус: черновик для разработки. Часть поведения (выходные дни, режим пересчёта, письмо об ошибках, состав отбора) уточняется у заказчика (см. письмо-запрос и раздел «Открытые вопросы»). До получения ответов реализуются значения по умолчанию, вынесенные в настройки обработки.

1. Задача (IMDEV-9153)

Автоматизировать начисление вознаграждения управляющей компании (ВУК, management fee) по договорам розничного ДУ (пул «Розничное ДУ») в регламентные даты — без ручного открытия монитора.

Требования заказчика:

  1. Начисление ВУК договоров РДУ в регламентные даты — многопоточным способом.
  2. Фоновое исполнение по расписанию: 1 апреля / 1 июля / 1 октября / 1 января в 00:15.
Важно (уже выяснено при анализе). Многопоточность уже реализована в базовом контуре монитора (экспортная процедура Справочники.РегламентныеПериоды.СформироватьРегламентныеОперации), на ПРОД константа МаксимальноеКоличествоПараллельныхПотоков = 12. Поэтому новую обработку НЕ надо снабжать собственным движком потоков — она должна лишь корректно подготовить параметры и вызвать существующий метод. Основная новизна задачи — автозапуск по расписанию.

2. Что делает сейчас пользователь (воспроизводим программно)

1-го числа квартала (например, 1 апреля) сотрудник вручную открывает Монитор регламентных операций и задаёт:

  • дата периода = конец предыдущего квартала (31.03);
  • отбор договоров: Договор ДУ.Пул = «Розничное ДУ»;
  • группа регламентных операций: «3.1 Вознаграждение за управление»;
  • операция: «Вознаграждение управляющей компании (БУ)»;
  • кнопка «Создать».

Далее по каждому договору формируется ПланРегламентныхОперацийДУ и подчинённый НачислениеВознаграждения (УК, ЗаУспех = Ложь); сумма считается внешним алгоритмом MF. Расчет вознаграждения за управление: Розничное ДУ при проведении документа.

6. Основной сценарий (алгоритм фонового выполнения)

  1. Установить дату запуска = ТекущаяДатаСеанса().
  2. Проверить, что день запуска — регламентная дата (1 января / 1 апреля / 1 июля / 1 октября). Если нет — записать в ЖР предупреждение и выйти (защита от случайного запуска). Поведение при выходном дне — по ответу заказчика; по умолчанию запуск по календарю без переноса.
  3. Вычислить ДатаПериода = КонецДня(НачалоМесяца(ДатаЗапуска) - 1) (конец предыдущего квартала).
  4. Получить группу «3.1 ...», прочитать её ВремяРеглОпераций; получить вид операции ВознаграждениеУК_БУ.
  5. Проверить РегламентныеПериоды на ДатаПериода:
    • нет и СоздаватьПериодЕслиНет = Истина -> создать элемент (ДатаПериода, Записать);
    • нет и создавать нельзя -> ошибка, выход;
    • есть, но закрыт по договорам -> поведение по BA (по умолчанию: зафиксировать ошибку и не запускать массово).
  6. Сформировать СписокДоговоровДУ (пул «Розничное ДУ», действующие на дату; отборы уточняются BA).
  7. Если список пуст — записать в ЖР и завершить (метод не вызывать).
  8. Собрать параметры (раздел 7) и вызвать Справочники.РегламентныеПериоды.СформироватьРегламентныеОперации(ПараметрыПроцедуры, Адрес).
  9. Прочитать результат {Успешно, Сообщение}; собрать итоги по договорам (успешно / ошибки / списки); записать в ЖР; при ОтправлятьПисьмоОбИтогах — сформировать и отправить HTML-письмо (раздел 8).
Детальный контракт параметров вынесен в отдельный документ: TZ_params_SformirovatReglamentnyeOperacii.html. Здесь — сводка, чтобы обработка была самодостаточной.

8. Письмо об итогах (ОтправлятьПисьмоОбИтогах)

Если в настройках обработки ОтправлятьПисьмоОбИтогах = Истина, после завершения СформироватьРегламентныеОперации (успех или ошибка) сформировать и отправить HTML-письмо по образцу соседних обработок РДУ (внРасчетВознагражденияРозничногоДУ, внОплатаКЗПоКлиентамРДУ): через РаботаСПочтовымиСообщениями.ОтправитьСообщение.

8.1. Когда отправлять

  • Всегда при включённой опции — и при полном успехе, и при частичных/критических ошибках.
  • Не отправлять, если запуск отменён на ранней проверке (не регламентная дата) — только запись в ЖР.
  • Если список договоров пуст — письмо с итогом «обработано: 0» (чтобы было видно, что РЗ отработало).
  • Если СписокРассылки пуст — не падать: записать предупреждение в ЖР и не слать письмо.

8.2. Тема письма

{OK} Авто-начисление ВУК РДУ за 31.03.2026 {r9153, ib: <имяИБ>}
{ERR} Авто-начисление ВУК РДУ за 31.03.2026 {r9153, ib: <имяИБ>}
  • Префикс {OK} / {ERR} — по итоговому признаку Результат.Успешно и наличию ошибок по договорам.
  • Дата в теме — ДатаПериода (конец квартала), не дата запуска РЗ.
  • Прописка рассылки (номер + имя ИБ) — по аналогии с ПропискаРассылки в соседних EPF.

8.3. Тело письма (HTML) — обязательные блоки

БлокСодержание
Шапка / сводка
  • Дата запуска РЗ
  • Дата периода (начисления)
  • Пул, группа операций, вид операции
  • Число потоков
  • Всего договоров в отборе
  • Успешно обработано (есть проведённый план / начисление без отказа)
  • С ошибками
  • Пропущено (если режим «с учётом выполненных»)
  • Признак итога: Успешно / Ошибка + текст Результат.Сообщение
Список успешно обработанных Таблица: ДоговорДУ | Код/наименование | Ссылка на ПланРегламентныхОперацийДУ | Ссылка на НачислениеВознаграждения | Сумма вознаграждения (если доступна).
Если список длинный (> N, напр. 200) — в тело первые N строк + фраза «и ещё X договоров (полный список в ЖР / вложении)».
Список ошибок Таблица: ДоговорДУ | Текст ошибки / отказ регламентной операции.
Источник: сообщения пользователей фоновых заданий + отказы проведения планов / начислений за ДатаПериода по группе 3.1.
Если ошибок нет — блок «Ошибок нет».
Базовый метод СформироватьРегламентныеОперации возвращает только {Успешно, Сообщение}. Детальный список «обработано / ошибки по договорам» нужно собрать после вызова отдельным запросом (планы и начисления за дату периода) и/или накоплением сообщений фоновых заданий. Это отдельный шаг после вызова метода, не часть контракта параметров.

8.4. Получатели и отправка

  • ТЧ СписокРассылки (колонки: ПочтовыйЯщик, Представление) — как в внРасчетВознагражденияРозничногоДУ.
  • Реквизит ПочтовыйЛогин — учётная запись почты для РаботаСПочтовымиСообщениями.ОтправитьСообщение(ПочтовыйЛогин, ПараметрыПисьма).
  • ТипТекста = HTML; Важность = Обычная (или Высокая при {ERR}).
  • Отправку обернуть в Попытка...Исключение: сбой почты не должен «ломать» уже выполненное начисление; ошибку почты писать в ЖР.

8.6. Критерии приёмки по письму

  • При успешном прогоне тема с {OK}, в теле сводка + список обработанных.
  • При ошибках тема с {ERR}, в теле блок ошибок с договорами и текстами.
  • Пустой СписокРассылки не приводит к исключению регламента.
  • Сбой SMTP не откатывает созданные документы начисления.

10. Обработка ошибок и логирование

  • Все ключевые этапы (старт, дата периода, число договоров, вызов метода, итог) — в ЖурналРегистрации с событием вида "IMDEV-9153.АвтоВУК_РДУ".
  • Попытка...Исключение — вокруг: вызова метода, создания периода, отправки письма (непредсказуемые ошибки). Валидации (пустой список, нет группы/операции) — обычными проверками, без Попытки.
  • Ошибки по отдельным договорам метод возвращает через сообщения фоновых заданий — собрать и залогировать/включить в письмо.
  • Итоговая запись: сколько договоров в списке, сколько успешно, сколько с отказом, признак Успешно.

11. Тестирование

  • Тестовый ручной запуск команды ФоновоеВыполнение / кнопки формы «Выполнить сейчас (тест)» на дату периода 31.03 (тест-база).
  • Сверка с ручным запуском монитора на том же наборе договоров: состав и суммы НачислениеВознаграждения, даты/время документов, число проведённых планов.
  • Проверка автосоздания периода (когда его нет) и поведения при закрытом периоде.
  • Проверка пустого списка договоров (корректный выход без ошибок).
  • Проверка многопоточности (до 12) — время выполнения и отсутствие блокировок.
  • Проверка расписания (тестово сдвинуть дату/эмуляция).
  • Проверка письма: успех ({OK} + список), ошибки ({ERR} + список), пустой СписокРассылки, сбой SMTP.

12. Критерии приёмки

  1. РЗ запускается 1 января / 1 апреля / 1 июля / 1 октября в 00:15 без участия пользователя.
  2. Документы НачислениеВознаграждения (УК, БУ) создаются на дату конца предыдущего квартала.
  3. Результат идентичен ручному запуску монитора (группа 3.1, операция УК БУ, пул РДУ).
  4. Расчёт идёт многопоточно (константа = 12), без деградации/блокировок.
  5. Все итоги и ошибки фиксируются в ЖР; при включённой опции — приходит письмо со сводкой (обработано / ошибки / списки) по разделу 8.
  6. Базовая конфигурация не изменена; всё в внешней обработке + регистрация + РЗ.

13. Открытые вопросы (до финализации — значения по умолчанию из настроек)

  • Поведение, если 1-е число или конец квартала — выходной (перенос/без переноса).
  • УчитыватьВыполненные: Ложь / Истина / «с учётом выполненных».
  • Нужна ли операция НУ дополнительно к БУ.
  • Автосоздание периода и поведение при закрытом периоде.
  • Нужно ли письмо об итогах и кому (адреса СписокРассылки).
  • Нужен ли полный список успешных договоров в теле или достаточно сводки + только ошибки (при большом числе договоров РДУ письмо может быть огромным).
  • Точный состав отбора договоров РДУ (действующие/расторгнутые/стратегии).
