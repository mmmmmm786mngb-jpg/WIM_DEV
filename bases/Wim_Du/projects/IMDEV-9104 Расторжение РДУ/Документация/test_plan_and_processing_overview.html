IMDEV-9104: план тестирования и описание тестовой обработки

Обработка: внТестРасторжениеДоговоровРДУ.epf
Боевая обработка: внРасторжениеДоговоровРозничногоДУ (контур РЗ «ФоновоеДоговорыИзДОКРасторжению»)
База: Wim_Du | Задача: оптимизация расторжения РДУ

1. Введение

Документ описывает план тестирования производительности процесса расторжения договоров розничного ДУ и то, как тестовая обработка относится к боевому коду: какие шаги она имитирует, какие выполняет в точности (те же типы операций / вызовы API базы ДУ), а какие намеренно не запускает.

Цель прогона: на N существующих договоров пула «Розничное ДУ» получить замеры времени основных блоков и понять, что является узким местом, без вызовов внешних систем (1С:ДО, Finance, FO, почта).

Важно
Тест не является полной копией боевой EPF «один в один». Это управляемый прогон горячих участков контура с подменой входа из ДО и отключением внешних интеграций. Запись в ДУ по умолчанию выполняется и затем откатывается транзакцией.

2. Боевые контуры (для справки)

2.1. Регламентное задание (целевой контур IMDEV-9104 / замер №14)

ВыполнитьКоманду("ФоновоеДоговорыИзДОКРасторжению")
  |- ДОДоговорыДУКРасторжению()          <-- APDEX / ключевая операция
  |    |- GetClosingRetailAgreements()  (чтение WS 1С:ДО)
  |    |- цикл: ДоговорПоНомеру, аналитика, счет, дата, поручение на вывод
  |- СформироватьИОтправитьПисьмо("Перевод"|"Вывод"|"Ввод"|"МатВыгода")
       (после замера; может вызвать FO при рассылке «Перевод»)

2.2. Интерактив / кнопка «Выполнить расторжение» (не РЗ)

ВыполнитьРасторжениеНаСервере()
  |- ДОДоговорыДУКРасторжению()
  |- ОбработкаДоговоровКРасторжению()
       |- ДанныеНДФЛИзФИН()              (Finance)
       |- ДанныеПоРасторжению()
       |- цикл: СЧА, платежки, вознаграждение...
       |- ЗакрытьДоговор() -> SetRetailAgreementClosed()  (запись в ДО, письмо r287)
Фокус тестовой обработки
Основной измеряемый контур — тело РЗ (ДОДоговорыДУКРасторжению). Дополнительно (флаги по умолчанию включены) меряются два тяжёлых read-only куска из контура полного закрытия: укороченный ДанныеПоРасторжению и ПолучитьСуммыРСА_СЧА. Это помогает заранее оценить стоимость шагов кнопки, но не является полным ОбработкаДоговоровКРасторжению.

5. План тестирования

5.1. Подготовка

  1. Использовать тестовую / копию базы ДУ (не PROD).
  2. Убедиться, что в пуле «Розничное ДУ» есть достаточное число действующих договоров.
  3. Открыть файл внТестРасторжениеДоговоровРДУ.epf в 1С:Предприятие.
  4. Проверить значения флажков по умолчанию (см. раздел 4).

5.2. Сценарии

Сценарий Параметры Ожидаемый результат
S1. Базовый (50 договоров) N=50, флаги по умолчанию Успех; заполнены блоки 1–4 и ИТОГО; данные в ДУ не изменились (откат)
S2. Нагрузка (100 / 200 / 500) N увеличивать ступенчато Рост времени; выявить блок с максимальной долей %
S3. Только чтение ТолькоЧтение = Да Нет блоков 2.5/2.6; нет записи/создания документов
S4. Без СЧА / без ДанныеПоРасторжению Снять соответствующий флаг В отчёте нет блока 3 и/или 4; время ИТОГО меньше

5.3. Чек-лист после прогона

  • В шапке отчёта: Успех = Да, количество договоров = N (или меньше, если в пуле мало).
  • Внешние вызовы: в отчёте указано «НЕТ (ДО / ФИН / FO / почта)».
  • Откат транзакции = Да — договоры не остались с тестовой датой расторжения / тестовыми поручениями.
  • Зафиксировать топ-3 самых долгих блока (время мс и доля %).
  • При ошибке — текст в отчёте и событие в журнале IMDEV-9104.Замер.

5.4. Критерии успеха тестирования (для задачи оптимизации)

  • Получен воспроизводимый отчёт замеров на выбранном N.
  • Понятны кандидаты на оптимизацию (блоки с наибольшей долей %).
  • Подтверждено отсутствие побочных эффектов во внешних системах и (при откате) в данных ДУ.

6. Что сделать после открытия обработки

  1. Проверить Пул = «Розничное ДУ».
  2. Задать Количество договоров.
  3. Оставить флажки по умолчанию (все блоки включены, откат включён).
  4. Нажать «Запустить тест (замеры)».
  5. Проанализировать табличный документ и при необходимости журнал регистрации.

7. Ограничения и риски

  • Не запускать на PROD без крайней необходимости; даже с откатом создаётся нагрузка на СУБД.
  • Имитация входа из ДО не воспроизводит сетевую задержку и объём реального ответа WS.
  • Боевое проведение поручения и создание отсутствующего банковского счёта упрощены.
  • Полный путь кнопки (НДФЛ из ФИН, закрытие в ДО, рассылки) тестом не покрыт.
  • Если снять «Откатывать транзакцию» при ТолькоЧтение = Нет — возможна порча тестовых данных (в коде защитный откат всё равно выполняется; полагаться на это не стоит при будущих правках).
