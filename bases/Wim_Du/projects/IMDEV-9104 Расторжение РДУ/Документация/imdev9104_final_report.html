1. Введение и вердикт

По результатам разработки и ИТ-тестирования закрыты два основных узких места контура расторжения РДУ: P2 (подбор счёта УК по платёжной позиции) и P3 (MF расчёт вознаграждения). На выборке 10 договоров ускорение каждого алгоритма порядка x20. P1 (проверка достаточности ДС) осознанно не дорабатывался.

Baseline N=50 (протокол v2.2): весь прогон ~1291 с; P2 ~515 с (40%), P3 ~205 с (16%), P1 ~329 с (25%). ИТ-сравнение «было/стало» выполнялось на 10 договорах по изолированным алгоритмам (не полный контур).

2. Технология тестирования

ИТ-проверки выполнялись вручную в 1С на тестовом разработческом контуре: открывались специальные внешние обработки сравнения (EPF), подготовленные для IMDEV-9104. Автоматизация через COM/Python в этом прогоне не использовалась.

2.1. Контур и способ запуска

  • База: тестовый разработческий контур ДУ
  • Способ: Файл → Открыть → внешняя обработка .epf
  • Параметры на форме: пул «Розничное ДУ», количество договоров (лимит / все), дата расчёта
  • Результат: табличный документ на форме + (для P3) HTML-файл на клиентской машине

2.2. Специальные обработки сравнения

Обработка Что сравнивает Что измеряет
внТестСравнениеПлатежнойПозиции.epf P2: подбор счёта УК без кэша vs с пакетным кэшем регресс полей ПП + скорость
внТестСравнениеMFВознаграждения.epf P3: РазмерВознагражденияПриРасторжении «было» (MAX+сумма) vs «стало» (только сумма) регресс сумм Договор/Сумма + скорость

2.3. Как устроен прогон «было / стало»

  1. На форме задаётся пул и лимит договоров (например, 10; 0 = все договоры пула).
  2. Обработка последовательно считает алгоритм по-старому и по-новому на одном и том же наборе.
  3. Сверяются результаты (поля ПП или суммы вознаграждения) и суммарное время обоих путей.
  4. Для P3 запись HTML выполняется на клиенте по выбранному пути (расчёт — на сервере ИБ).

2.4. Baseline полного контура (для контекста долей %)

Доли P1/P2/P3 (~25% / ~40% / ~16%) взяты из более раннего замера полного контура внТестРасторжениеРДУ_ПолныйКонтур v2.2 (N=50) — это исходный протокол hotspots, а не способ ИТ-приёмки P2/P3. Приёмка улучшений — через сравнения выше.

4. Что сделано в разработке

P2 Пакетный кэш платёжных позиций

Обработка внРасторжениеДоговоровРозничногоДУ v1.19 ((IMDEV-9104-P2): перед циклом один вызов ПлатежныеПозицииПоСчетамДС(СписокДоговоров, Валюта), результат в КэшПлатежныхПозицийПакет; БанковскийСчетПоПлатежнойПозиции читает кэш вместо N запросов. 
// Было: на каждый договор
ТЗ = Документы.ПлатежноеПоручение.ПлатежныеПозицииПоСчетамДС(ДоговорДУ, Валюта);

// Стало: один пакет + кэш
КэшПлатежныхПозицийПакет = ПодготовитьКэшПлатежныхПозицийПоСчетамДС(Список, Валюта);
// далее БанковскийСчетПоПлатежнойПозиции берёт строки из кэша

P3 MF вознаграждение без лишнего MAX

Обработка MF_РасчетВознаграждения_РозничноеДУ v1.01 (IMDEV-9104-3): в РазмерВознагражденияПриРасторжении отключён запрос МАКСИМУМ(Период) — дата не использовалась, запрос всегда возвращал одну строку и всегда вёл к РазмерВознаграждения. 
// Было: тяжёлый MAX + РазмерВознаграждения
// Стало (IMDEV-9104-3):
СуммаВознаграждения = РазмерВознаграждения(ДоговорДУ, ДатаРасчета, ПоказателиСправки);
Возврат СуммаВознаграждения;

P1 Не дорабатывался

Пакетный API ПервыйЭтапПроверкиДостаточностиДСПоСпискуСчетов семантически расходится с одиночным (дата и состав запроса). Доработка менеджера ПП не входила в задачу. Решение: оставить как есть; при необходимости — отдельный этап (свой пакет-клон в EPF или memo-кэш).

6. Детали тестов и артефакты

6.1. Регресс и скорость P2

  • Обработка: Тестирование/внТестСравнениеПлатежнойПозиции.epf
  • Регресс: поля ПП (СчетДоговораДУ, ТекстПлательщика и др.) было/стало
  • Скорость: заполнение с кэшем vs без кэша
параметры: Пул="Розничное ДУ", КоличествоДоговоров=N
режим было: КэшПлатежныхПозицийПакет = Неопределено
режим стало: ПодготовитьКэшПлатежныхПозицийПоСчетамДС(Список, Валюта)

6.2. Регресс и скорость P3

  • Обработка: Тестирование/внТестСравнениеMFВознаграждения.epf (v1.3)
  • Регресс: таблица ДоговорДУ — СуммаВознаграждения (старая/новая)
  • Скорость: MAX+сумма vs только сумма; лимит 0 = все договоры пула
  • Без УдалитьОбязательствоДС (только чтение)
параметры: Пул="Розничное ДУ", КоличествоДоговоров=10 (или 0=все)
было: Запрос МАКСИМУМ(Период) + СуммаВознагражденияПоОстатку
стало: СуммаВознагражденияПоОстатку
HTML: сохраняется на клиенте по выбранному пути

7. Выводы

  1. P2 и P3 выполнены и подтверждены ИТ-тестом: на 10 РДУ ускорение порядка x20 по каждому алгоритму (P2: 112→6 с; P3: 43→2 с).
  2. P1 не входил в доработку из-за рисков расхождения пакетного API ПП и нежелания менять менеджер документа; hotspot ~25% baseline сохраняется.
  3. Поставка: обновлённые EPF внРасторжениеДоговоровРозничногоДУ (v1.19) и MF_РасчетВознаграждения_РозничноеДУ (v1.01), плюс тестовые сравнения в каталоге Тестирование/.
  4. Рекомендация: принять P2+P3; при необходимости продолжения — отдельная задача на P1 и контрольный полный замер N=50 после выкладки.
