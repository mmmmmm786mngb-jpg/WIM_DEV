5. Три проблемы: откуда вызываются и где происходит

P1 Проверка достаточности ДС перед ПП на вывод — 328.6 с (25.5%)

Суть

Перед созданием платежного поручения на вывод клиенту вызывается проверка платёжной позиции. Почти всё время — один тяжёлый SELECT в модуле менеджера ПП.

Откуда вызывается (обработка расторжения)

ОбработкаДоговоровКРасторжению (блок EPF 2 / корзина 2.6) цикл по ДанныеПоРасторжению если СтатусПорученияНаВывод = Новый ДостаточноДенегНаСчету(ПоручениеПоДСНаВывод) // вызовы: ObjectModule стр. 894 (18 раз), 913 (38 раз) = 56 Документы.ПлатежноеПоручение.ПервыйЭтапПроверкиДостаточностиДС(...) // стр. 2010 Запрос.Выполнить() // ManagerModule стр. 1835 <-- ПРОБЛЕМА

Где происходит проблема

  • Файл: CF/Documents/ПлатежноеПоручение/Ext/ManagerModule.bsl
  • Функция: ПервыйЭтапПроверкиДостаточностиДС
  • Строка: 1835 — РезультатЗапроса = Запрос.Выполнить();
  • Содержимое запроса: остатки/обороты Хозрасчетный, статусы ПП, депозиты, обязательства — на один договор/счёт за вызов.

Суть

При создании ПП по НДФЛ / вознаграждению / комиссии для нового документа подбирается банковский счёт УК с достаточной позицией. Самый тяжёлый self-time в прогоне.

  • Функция: ПлатежныеПозицииПоСчетамДС (API уже принимает СписокДоговоровДУ)
  • Строка: 1388 — РезультатЗапроса = Запрос.Выполнить();

Приложение А. Варианты исправления

По каждой проблеме: формулировка и описание решения. Решения не реализованы в рамках данного протокола. Порядок по доле времени: P2 → P1 → P3.

P2 ~40% — ПлатежныеПозицииПоСчетамДС (L1388)

Проблема. При создании ПП по НДФЛ / вознаграждению / комиссии обработка для каждого договора вызывает ПлатежныеПозицииПоСчетамДС(одинДоговор, Валюта). За прогон — 104 полных пересчёта платёжной позиции (~515 с). При этом API функции уже принимает список договоров, но контур расторжения использует его поштучно.
Решение. Перед циклом создания ПП собрать список договоров, которым нужны ПП по начислениям, и один раз вызвать ПлатежныеПозицииПоСчетамДС(СписокДоговоровДУ, Валюта). Результат разложить в соответствие ДоговорДУ → счета/позиции в памяти; при создании документов брать данные из кэша, без повторного SELECT. Дополнительно: снять план запроса L1388 и при необходимости поправить индексы / отборы (ДоговорДУ, банковский счёт, периоды остатков), чтобы пакетный вызов не деградировал на большом списке.

P1 ~25% — ПервыйЭтапПроверкиДостаточностиДС (L1835)

Проблема. Перед ПП на вывод для каждого договора вызывается ДостаточноДенегНаСчету → ПервыйЭтапПроверкиДостаточностиДС (56 раз, ~329 с). Каждый вызов заново считает позицию по остаткам/оборотам Хозрасчетный, статусам ПП и депозитам для одного договора/счёта.
Решение. Перейти на пакетную проверку: собрать таблицу кандидатов (ДоговорДУ, АналитическийСчет, БанковскийСчет) и использовать ПервыйЭтапПроверкиДостаточностиДСПоСпискуСчетов (или эквивалентный один запрос на набор). Если пакет сразу недоступен — кэш позиции по ключу (ДоговорДУ, Счёт, Дата) на время одного прогона расторжения, чтобы не считать одно и то же повторно. Параллельно: анализ плана запроса L1835 и индексы под используемые отборы.

P3 ~16% — MF_РасчетВознаграждения_РозничноеДУ (L197)

Проблема. При проведении НачислениеВознаграждения алгоритм MF_РасчетВознаграждения_РозничноеДУ в ветке расторжения выполняет запрос к ОбязательстваПоДС (МАКСИМУМ(Период) с условием Основание.Ссылка ЕСТЬ NULL). 43 вызова дают ~205 с. Разыменование составного типа в ГДЕ мешает эффективному использованию индекса и удорожает каждый вызов.
Решение. 1) Переписать условие без Основание.Ссылка (явная проверка пустого основания / тип через ВТ регистраторов), чтобы запрос шёл по индексу ДоговорДУ + ВидДвижения + Период. 2) При необходимости добавить/уточнить индекс регистра под этот отбор. 3) Для массового расторжения — предзагрузка дат/сумм по списку договоров одним запросом (или пакетный режим в MF) до цикла начислений, либо кэш результата алгоритма по ДоговорДУ+ДатаРасчета внутри прогона.

Записи документов (Записать / проведение) как цель оптимизации в IMDEV-9104 не рассматриваются: фокус — SELECT и повторные расчёты.
