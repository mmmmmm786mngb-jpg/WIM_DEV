Ключевое наблюдение по PFF

Узкое место: повторный запрос к БД на каждое проведение, хотя МоментВремени = Новый МоментВремени(Дата, Ссылка) меняется (ссылка регистратора — текущий документ).

П.3 — анализ вариантов кеширования

Вариант Суть Ожидаемый эффект Сложность Риск
1. Общий кеш (eager) Один запрос в начале «Создать всё» — все остатки по ДоговорДУ и счетам переоценки на дату Высокий при массовой загрузке Средняя Средний
2. Ленивый кеш Запрос только при промахе; ключ (ДоговорДУ, Счет, Валюта, Субконто1..3) Средний (зависит от повторов) Средняя Средний
3. Бегущий кеш (рекомендуемый) Снимок на старт + корректировка дельтой после каждого проведения в сессии EPF Высокий для 754 документов Высокая Контролируемый

Вариант 1 — общий кеш (запрос сразу)

Идея: перед циклом EPF выполнить один пакетный запрос остатков по всем счетам из ПолучитьСчетаПодлежащиеПереоценке() для ДоговорДУ на дату операций. Результат — таблица в памяти или ВТ сеанса.

    Остатки.Валюта, Остатки.ВалютнаяСуммаОстаток, Остатки.СуммаОстаток, ...

    РегистрБухгалтерии.Хозрасчетный.Остатки(
        &МоментНачала,

В ПодготовитьТаблицуВалютныхОстатковПоДокументу вместо цикла с Запрос.Выполнить() — отбор строк из предзагруженной таблицы по ключу.

Плюсы:

  • 1 тяжелый запрос вместо 795 легких — меньше round-trip к СУБД.
  • Простая модель чтения: «все остатки уже в памяти».

Минусы и риски:

  • МоментВремени в оригинале уникален для каждого документа — eager-снимок на «начало дня» не учитывает проводки уже проведенных в этой же сессии (документы 2..754).
  • ДЛЯ ИЗМЕНЕНИЯ в оригинале блокирует конкретные записи регистра; при eager-загрузке блокировки нужно проектировать отдельно.
  • Загрузка «всех» остатков по договору может быть избыточной по объему, если нужны 1-2 комбинации на документ.

Вердикт: применим только вместе с механизмом обновления кеша после каждого проведения (фактически переходит в вариант 3). Без этого — риск расхождения остатков.

Вариант 2 — ленивый кеш

Идея: кеш сеанса Соответствие или индексированная ТЗ. Ключ: ДоговорДУ + Счет + Валюта + Субконто1 + Субконто2 + Субконто3 (без ссылки документа). При обращении — если ключ есть, взять из кеша; иначе — запрос к БД и сохранить.

Ключ = СтрШаблон("%1|%2|%3|%4|%5|%6",
    ДоговорДУ, Счет, Валюта, Субконто1, Субконто2, Субконто3);

Если КешОстатков.Получить(Ключ) = Неопределено Тогда
    // текущий запрос с ДЛЯ ИЗМЕНЕНИЯ
    КешОстатков.Вставить(Ключ, Результат.Выгрузить());
КонецЕсли;

Плюсы:

  • Загружается только то, что реально запрашивалось.
  • Меньше памяти, чем полный снимок по договору.
  • Проще внедрить, чем бегущий кеш: обертка вокруг строки 1219.

Минусы и риски:

  • Для НКД по облигациям субконто (ЦБ, купон) уникальны почти в каждом документе — низкий процент попаданий в кеш, выигрыш может быть минимальным (~0-20% от 95 с).
  • Без инвалидации после проведения кеш отдает устаревшие остатки (игнорирует изменение МоментВремени).
  • Нужна политика сброса: после Записать(Проведение) удалять или корректировать затронутые ключи.

Вердикт: имеет смысл как промежуточный шаг с обязательной инвалидацией по движениям документа. Сам по себе «чистый» lazy-кеш без инвалидации — некорректен для последовательного проведения.

Вариант 3 — бегущий кеш остатков (рекомендуемый для проработки)

Идея: комбинация eager-старта и lazy-дозагрузки с корректировкой дельтой после каждого проведения в сессии EPF. Сохраняет семантику последовательного МоментВремени без 795 обращений к СУБД.

Алгоритм:

  1. Старт «Создать всё»: один запрос остатков по ДоговорДУ на момент до первого документа (или пустой кеш + lazy).
  2. При проведении документа N: ПодготовитьТаблицуВалютныхОстатковПоДокументу читает остатки из кеша по ключу (без Запрос.Выполнить()).
  3. После Записать(Проведение): по движениям Хозрасчетный документа N обновить затронутые строки кеша (дельта Дт/Кт).
  4. Промах lazy: если комбинации нет в кеше — точечный запрос (как сейчас) + добавление в кеш.
// Псевдокод уровня EPF / общего модуля сеанса
КешОстатковНКД = Новый Соответствие; // или ТЗ с индексом

// после проведения каждого ОбОперация:
ОбновитьКешОстатковПоДвижениям(КешОстатковНКД, ОбОперация.Движения.Хозрасчетный);

// в ПодготовитьТаблицуВалютныхОстатковПоДокументу (доработка):
Если КешПередан И ОстатокЕстьВКеше(Ключ) Тогда
    СтрокаОстатка = КешОстатковНКД[Ключ]; // без запроса
Иначе
    // fallback: текущий запрос стр. 1219
КонецЕсли;

Плюсы:

  • Корректность при последовательном проведении 754 документов — остаток на документ N учитывает документы 1..N-1.
  • Потенциально 0 запросов на строке 1219 при полном покрытии кеша (цель: с 95 с до единичных секунд + один стартовый запрос).
  • EPF может передавать кеш через параметр сеанса / реквизит обработки без смены модели проведения (п.2).

Минусы и риски:

  • Доработка УчетДоходовРасходовСервер (новый параметр кеша) + логика дельт в EPF.
  • Нужно воспроизвести логику ДЛЯ ИЗМЕНЕНИЯ — при параллельных сеансах возможны конфликты (для «Создать всё» в одном сеансе — приемлемо).
  • Обязательны регрессионные тесты: сравнение проводок и сумм переоценки до/после на выборке документов.

Вердикт: наиболее перспективный для сценария 9095. Требует отдельной оценки трудозатрат и прототипа на 10-20 документах с PFF-замером.

Дополнительно: пакетный запрос внутри одного документа

Замена цикла (стр. 1176-1235) одним запросом через ВТ со списком ключей из ТаблицаДляПереоценки убирает лишние round-trip, если в документе несколько строк после Свернуть. По PFF при НКД это редкость (~1 строка на документ) — эффект на 95 с будет незначительным. Имеет смысл как доработка конфигурации «в целом», но не как основной рычаг 9095.

Рекомендуемый порядок проработки п.3

  1. Замерить среднее число строк в ТаблицаДляПереоценки после Свернуть (лог / временный счетчик).
  2. Оценить повторяемость ключей (Счет+Субконто) между 754 документами — от этого зависит ценность варианта 2.
  3. Спроектировать прототип варианта 3 (бегущий кеш) с передачей из EPF.
  4. PFF-замер: baseline 95,16 с на строке 1219 vs после внедрения.
