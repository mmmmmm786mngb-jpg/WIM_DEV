1. Введение

Задача IMDEV-9095 формулируется как «оптимизация загрузки отчетов брокера». В рамках РДУ целевая EPF — «Распределение доходов по ценным бумагам». Это второй этап контура «отчет брокера за T-1»: после того как движения по брокерскому счету и начисления доходов уже попали в учет, обработка сопоставляет начисления с операциями по счету брокера и при необходимости создает недостающие документы ОперацияПоСчетуБрокера.

Да, два основных блока — верно: «Заполнение» (чтение и сопоставление данных) и «Создание» (запись документов с проведением). Каждый блок разбит на три вкладки: НКД (Купон), Погашение, Дивиденды.

Регламентного задания нет — только ручной запуск формы.

3. Откуда идет заполнение (источники данных)

Важно: заполнение в этой EPF не читает файл/SQL отчета брокера напрямую. Данные берутся из уже проведенного учета в базе ДУ.

3.1. Цепочка данных (полный контур «отчет брокера»)

3.2. Что именно читает блок «Заполнение»

Вкладка Основной источник начислений Счета / регистр Сопоставление с брокером
НКД (Купон) Обороты по начислению НКД за период Хозрасчетный.Обороты:
Счет = РасчетыПоОблигациям, КорСчет = НачислениеНКД
+ Хозрасчетный.Остатки (ОблигацииТело) 		LEFT JOIN Документ.ОперацияПоСчетуБрокера
по (ДоговорДУ, Актив, КупонныйПериод, Валюта, Дата)
Погашение Обороты по погашению тела облигации Хозрасчетный.Обороты:
ОблигацииТело / Себестоимость,
РасчетыПоОблигациям_ПогашениеТела / Выручка
+ остатки 		Аналогично — поиск существующей операции брокера
Дивиденды Обороты по начислению дивидендов Хозрасчетный.Обороты:
РасчетыПоДивидендам / Дивиденды
+ Хозрасчетный.Остатки (АкцииТело) 		LEFT JOIN Документ.ОперацияПоСчетуБрокера

Общие параметры отбора во всех трех запросах:

  • &Пул — фильтр договоров ДУ через Справочник.ДоговорДУ (ВТ_ДУ);
  • &Дата1, &Дата2 — период (Период формы);
  • Регистратор в оборотах — документ-основание начисления (попадает в колонку «Документ» ТЧ).

7. Рекомендуемый порядок работ (9095)

В проекте EPF v1.03 с универсальным блоком замеров (паттерн IMDEV-9096): проверка наличия ОценкаПроизводительности в метаданных, вызовы через ТекОбъект.НачатьЗамерОперации() / ЗакончитьЗамерОперации(). На PROD без релиза IMDEV-8927 обработка не падает — замеры просто не записываются.

  1. Замеры — реализованы оба блока (v1.03).
    • Заполнить всё: ключ ...Заполнение..., вес = число строк в ТЧ.
    • Создать всё: ключ ...СозданиеОпераций..., вес = строки с Отм = Истина.
    • Загрузить EPF v1.03 в тест; на PROD до релиза конфигурации — проверить отсутствие ошибок.
    • После релиза IMDEV-8927 на PROD — собрать baseline «до оптимизации» по обоим ключам.
  2. Блок 2 (быстрый win): кэш справочников и курсов валют до цикла. Сравнивать по ключу «СозданиеОпераций».
  3. Блок 1: профилирование запросов; оптимизация JOIN; общая ВТ_ДУ. Сравнивать по ключу «Заполнение».
  4. Блок 2 (структурно): пакетное проведение или фоновое выполнение при N > порога.
  5. Интеграция: согласовать с владельцами внПакетныйОтчетБрокераДУ_ДВО, если узкое место раньше по цепочке.
  6. Финал: синхронизировать v1.03 с WORK после проверки на тесте.

8. Выводы

  • Два блока — «Заполнение» (3 запроса к Хозрасчетному + сопоставление) и «Создание» (3 цикла проведения документов).
  • Заполнение идет не из файла брокера, а из регистра бухгалтерии Хозрасчетный (обороты/остатки начислений за период по пулу) плюс поиск уже существующих ОперацияПоСчетуБрокера.
  • Источник начислений в учете — документы-регистраторы, созданные на предыдущих этапах контура (пакетный отчет брокера, выписки, ручные начисления).
  • Наиболее вероятные узкие места: тяжелые запросы с виртуальными таблицами оборотов (блок 1) и построчное проведение с повторными обращениями к справочникам и курсам (блок 2).
  • Для 9095 в EPF v1.03 реализованы универсальные замеры обоих блоков (паттерн 9096); далее — baseline и оптимизация с сравнением по ключам ОценкиПроизводительности.
