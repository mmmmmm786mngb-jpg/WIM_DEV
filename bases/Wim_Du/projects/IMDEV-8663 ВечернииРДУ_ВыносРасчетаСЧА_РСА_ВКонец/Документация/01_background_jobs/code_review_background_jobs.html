1. Вердикт

Механизм оставлять можно. Полная переработка не нужна. Обязательны две точечные правки. Архитектура «родительское длительное задание + дочерние фоновые» для этой задачи нормальна. Подтверждены два дефекта: незакрытый хвост заданий, если у последнего договора нет операций, и разбор аварийного завершения по устаревшему снимку объекта ФоновоеЗадание. Остальное из первой редакции — либо неверно разобранный цикл, либо рекомендации по производительности и наблюдаемости без доказанной ошибки расчёта.
Что снято из первой редакции Утверждение, что окно потоков «проскакивает» равенство и запускает 22 000 заданий сразу, неверно: задание добавляется по одному, проверка идёт сразу после добавления. Утверждение, что предподготовка следующей пачки читает остатки тех же договоров без ещё не записанных движений, не подтверждено: в запрос уходит список договоров следующей пачки. Цикл Пока вокруг ОжидатьЗавершенияВыполнения не вырожденный — это штатная реакция на досрочный возврат платформы (в том числе после первого аварийного завершения).
Связь с доработкой 2 (IMDEV-8663): группа 3. Расчет СЧА/РСА Безусловное ожидание хвоста в конце пачки — удобная точка синхронизации перед отдельным этапом 3. "Расчет СЧА/РСА". Документы доработки 2 — в ../02_scha_rsa_group3/. Это аргумент «сделать барьер заранее», а не доказательство, что текущий диспетчер уже портит вечерние остатки.

2. Как механизм работает

  1. Форма собирает СписокОпераций, ДокументыПоДоговорам, МассивРодителей, пустой СписокФоновыхЗаданий и число потоков из константы (модуль формы, 1312–1318).
  2. Через ДлительныеОперации.ВыполнитьВФоне стартует родитель Справочники.РегламентныеПериоды.СформироватьРегламентныеОперации.
  3. Родитель режет договоры на пачки по 3 000. Пакетная предподготовка утренних/вечерних данных включается только если МассивРодителей.Количество() = 1 (строки 120–133, 160–178).
  4. По каждому договору пачки вызывается СформироватьДокументыЗакрытияПериода. Для каждой группы из МассивРодителей при непустой таблице операций стартует дочернее задание ФоновыеЗаданияСервер.СоздатьПланРегламентныхОперацийДУ.
  5. После каждого запуска, если число накопленных заданий равно числу потоков или это последний договор всего отбора, родитель ждёт порцию, забирает сообщения и очищает список (1156–1191).

Для типового вечернего запуска пользователь выбирает одну группу, предподготовка работает, на договор обычно приходится одно дочернее задание. Команда «все операции» или пустой отбор группы даёт несколько родителей — предподготовка тогда выключена, но окно потоков по-прежнему закрывается после каждого добавления.

4. Подтверждённые дефекты

BG-02Хвост не закрывается, если последний договор без операций

Справочник.РегламентныеПериоды.МодульМенеджера, 1142 и 1158

Ожидание порции срабатывает в двух случаях: набор достиг числа потоков либо обрабатывается последний договор всего отбора (ТекЗначение = МаксимальноеЗначение). Оба случая стоят внутри ветки «по текущей группе есть операции». 

Если ТаблицаОпераций.Количество() > 0 Тогда
    ...
    Если СписокФоновыхЗаданий.Количество() = КоличествоПотоков
        Или ТекЗначение = МаксимальноеЗначение Тогда
        // ждать и очистить
    КонецЕсли;
КонецЕсли;

Если у последнего договора отбора нет строк в ТаблицаОпераций ни по одной группе, финального ожидания нет. Родитель доходит до СообщитьПрогресс(100, "завершено"), форма обновляет дерево, а в списке остаются задания предыдущих договоров — не больше КоличествоПотоков - 1, не весь отбор.

В типовом вечернем прогоне, где у последнего договора есть операции, ожидание срабатывает. Это краевой случай, не постоянный сбой 22 000 договоров. Чинить всё равно нужно: сообщение «готово» при живых заданиях вводит в заблуждение, сообщения хвоста теряются.

Исправление

Вынести ожидание и разбор результатов в отдельную процедуру и вызывать её безусловно: когда набор достиг числа потоков, в конце каждой пачки и в конце СформироватьРегламентныеОперации. Внутри СформироватьДокументыЗакрытияПериода оставить только запуск и проверку порога окна. 

// В конце цикла по договорам пачки и ещё раз после цикла по пачкам
ЗавершитьФоновыеЗаданияПорции(ПараметрыСохранения);

ОценкаПроизводительности.ЗафиксироватьЗамерДлительнойОперации(...);

BG-14Авария проверяется по устаревшему снимку задания

МодульМенеджера, 1160–1185 и 1214–1223

По документации платформы свойства объекта ФоновоеЗадание — снимок на момент получения. Актуальные объекты возвращает ФоновыеЗадания.ОжидатьЗавершенияВыполнения.

Сейчас вызывающий код сохраняет массив до ожидания и разбирает именно его. Функция ожидания переприсваивает свой локальный параметр и не возвращает обновлённый массив: 

МассивФоновыхЗаданий = ПараметрыСохранения.СписокФоновыхЗаданий.ВыгрузитьЗначения();
РезультатЗавершенияФоновых = ОжидатьЗавершенияТекущихФоновых(МассивФоновыхЗаданий);

Для Каждого ТекЗадание Из МассивФоновыхЗаданий Цикл
    Если ТекЗадание.Состояние = СостояниеФоновогоЗадания.ЗавершеноАварийно Тогда
        ...
    КонецЕсли;
КонецЦикла;
Функция ОжидатьЗавершенияТекущихФоновых(МассивЗаданийЗакрытияПериода)
    ...
    МассивЗаданийЗакрытияПериода = ФоновыеЗадания.ОжидатьЗавершенияВыполнения(МассивЗаданийЗакрытияПериода);
    ...
КонецФункции

Присвоение внутри функции не меняет массив снаружи. Проверка ЗавершеноАварийно и разбор ИнформацияОбОшибке могут не увидеть аварию. Сообщения через ПолучитьСообщенияПользователю часто всё же доходят — это вызов метода, а не чтение снимка, — но на это нельзя опираться как на замену проверки состояния.

Исправление

Функция ОжидатьЗавершенияТекущихФоновых(МассивЗаданий)

    Пока Истина Цикл
        МассивЗаданий = ФоновыеЗадания.ОжидатьЗавершенияВыполнения(МассивЗаданий);
        Если ВсеЗаданияЗавершены(МассивЗаданий) Тогда
            Прервать;
        КонецЕсли;

    Возврат МассивЗаданий;

КонецФункции

// Вызов:
МассивФоновыхЗаданий = ОжидатьЗавершенияТекущихФоновых(
    ПараметрыСохранения.СписокФоновыхЗаданий.ВыгрузитьЗначения());

Для сопоставления с договором лучше сразу обходить СписокФоновыхЗаданий (значение — исходный объект, представление — текст с договором) и состояние брать из обновлённого массива по УникальныйИдентификатор. Вложенный поиск при размере окна в единицы потоков на производительность не влияет — это вопрос ясности, не P2.

5. Рекомендации, не являющиеся ошибками

BG-10Дочерние задания не снимаются при ошибке родителя

МодульМенеджера, обработчик исключения 244–270

Дочерние задания, запущенные через ФоновыеЗадания.Выполнить, не принадлежат сеансу родителя. Отмена длительной операции или исключение в родителе сами по себе их не останавливают — так устроена платформа, это не баг прикладного кода. Имеет смысл в блоке Исключение пройти СписокФоновыхЗаданий и вызвать Отменить() у ещё активных. То же — если пользователь отменил длительную операцию и управление вернулось в родителя.

BG-11Диагностика бизнес-ошибок

ФоновыеЗаданияСервер, 286–315; МодульМенеджера, 1163–1185

Руководство разработчика прямо говорит: если методом фонового задания является функция, возвращаемое значение игнорируется. Поэтому Выполнено = Ложь из СоздатьПланРегламентныхОперацийДУ диспетчер не увидит. Внутренний Попытка...Исключение гасит исключение, состояние задания — «завершено», не «завершено аварийно». Сообщения пользователю при штатном ожидании доходят. Журнала регистрации и итоговой сводки (успешно / с ошибкой / список договоров) нет — при 22 000 договоров разбор инцидента неудобен. Это качество сопровождения, не ошибка расчёта.

BG-03Явный барьер на границе пачки

МодульМенеджера, 142–220

После цикла по договорам пачки хвост не ждётся, сразу фиксируется замер и начинается следующая пачка. Предподготовка пачки N+1 вызывается со списком следующих договоров. Запросы остатков фильтруются по ДоговорДУ В (&МассивДоговоровДУ). Движения хвоста пачки N в эту выборку не попадают. Утверждение первой редакции про «остатки без ещё не записанных движений» как подтверждённый дефект данных снято.

Теоретическая гонка возможна только по общим данным (котировки операции 0010), если бумага пачки N ещё пишется, а предподготовка N+1 её уже читает. По коду это не доказано, замеров нет.

Хвост на границе пачки появляется, если 3000 % КоличествоПотоков <> 0 или часть договоров пачки не создала задание. При 4, 5, 6 или 10 потоках 3000 делится нацело: если каждый договор стартует задание, хвоста нет и замер пачки не занижен.

Барьер в конце пачки всё равно стоит сделать вместе с BG-02: предсказуемое завершение, честный замер IMDEV-8927 и готовое место для хвостового СЧА/РСА.

BG-04Однократная проверка доступности заданий

МодульМенеджера, 1144; ФоновыеЗаданияСервер, 8–23

На клиент-серверной базе (продуктив ДУ) функция после проверки файлового варианта сразу возвращает Истина. Тысячи разборов строки соединения на прогон — копейки. Запуск тестового задания ТестФоновогоЗадания выполняется только в файловой ИБ; процедура пустая и завершается сразу. Для продакшена это не дефект. Кэш флага в ПараметрыСохранения — мелкая гигиена, не обязательный этап.

BG-05Ожидание без таймаута

МодульМенеджера, 1214–1227

Без второго параметра ОжидатьЗавершенияВыполнения ждёт завершения всех заданий или первого аварийного завершения. Зависшее на блокировке задание действительно держит весь регламент, прогресс в это время не обновляется. Это риск эксплуатации, не ошибка логики.

Чего не делать Не ставить произвольный предел (например, 1800 секунд) с Отменить() у ещё активных заданий. Пока нет замера самых тяжёлых договоров, автоотмена оборвёт проведение посреди документа и будет хуже, чем текущее бесконечное ожидание. Если таймаут когда-нибудь понадобится — сначала замер, потом согласованный предел, без автоотмены по умолчанию.

Цикл Пока Не ЗначениеЗаполнено(Результат) оставлять можно: при досрочном возврате платформы он продолжает ждать оставшиеся задания. Мёртвым кодом он не является. Строка "Успех" действительно нигде не читается — её можно убрать, вернув массив заданий (см. BG-14).

BG-06 / BG-07Чанкование и скользящее окно

Одно задание на договор стоит сеанса рабочего процесса, вызова УстановкаПараметровСеанса и сериализации параметров. Это цена платформы, не баг. Предподготовка IMAPPS-35037/35039 от этого не «обесценивается»: запросы по пачке по-прежнему один раз, сериализация — отдельная статья.

Барьерная синхронизация (набрали N — ждём всех) проще и предсказуемее скользящего окна. Оценка «утилизация падает примерно вдвое» в первой редакции ничем не подтверждена.

Если когда-нибудь переходить на «пачка договоров в одном задании», помнить лимит платформы: сериализованные параметры фонового задания не больше 1 Гбайт. Чанк 50–200 с таблицами предподготовки может этот лимит задеть. Без замера на копии базы этот шаг не делать.

ПрочееСтиль и наблюдаемость

  • BG-08. Вложенный поиск представления по идентификатору при окне в 4–10 заданий на скорость не влияет. Достаточно обходить сам список значений.
  • BG-09. У константы 3 знака, неотрицательное, верхней границы в метаданных нет. Риск только при ручной установке десятков потоков. Это настройка, не найденный баг.
  • BG-12. Массив параметров по позициям неудобен при расширении сигнатуры. Именованная структура — вкус, не дефект.
  • BG-13. Одинаковое наименование дочерних заданий мешает в консоли кластера. Ключ задания защитит только от второго такого же запуска (дата + группа + договор), не от всех гонок. Имя параметра ЗаданияОтложенныхПроводок — копипаста, на логику не влияет.

6. Снятые и завышенные пункты

BG-01Снято: окно «проскакивает» равенство

МодульМенеджера, 1156–1158

Первая редакция утверждала: при нескольких группах в МассивРодителей за один договор в список попадает два и больше заданий, счётчик перескакивает через КоличествоПотоков (например, с 4 на 6 при пяти потоках), равенство больше не срабатывает, и на последнем договоре стартуют все 22 000 заданий.

Это не соответствует коду. Добавить и проверка стоят внутри цикла по группам, после каждого запуска. Приращение всегда 1. Когда счётчик доходит до числа потоков, порция ждётся и список очищается — в том числе между двумя группами одного договора.

Замена = на >= безвредна и не обязательна. Как P1-дефект пункт снят.

Что было завышено, но не выдумано BG-03 (барьер пачек), BG-04 (вызов в цикле), BG-05 (нет таймаута) описывают реальные места в коде. Ошибочны были следствия: порча остатков, 22 000 тестовых заданий на серверной базе, «вырожденный» цикл ожидания, обязательный таймаут с отменой.
