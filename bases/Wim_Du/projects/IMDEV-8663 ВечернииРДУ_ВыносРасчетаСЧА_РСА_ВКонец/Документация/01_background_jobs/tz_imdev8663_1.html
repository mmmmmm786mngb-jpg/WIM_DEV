1. Цель, этапы, границы

Цель Одно расширение, сразу рабочий режим. Этап A — инфраструктура ожидания: хвост, актуальный снимок, барьер пачки, отмена детей, журнал и сводка. Этап B — диспетчер: чанк договоров на задание и скользящее окно. Старый параллельный режим «одно задание на один договор» не сохраняем и флагом не прикрываем. Последовательный путь остаётся только при КоличествоПотоков = 0 или если фоновые недоступны. Констант расширения нет. Размер чанка — переменная в коде (старт 50). Ускорение заранее не обещать: параллельность договоров равна числу потоков. Замер D-10 — после кода, на копии.

Входит

  • A: BG-02, BG-14, барьер пачки (BG-03), BG-10, BG-11, однократная проверка доступности (BG-04).
  • B: очередь чанков, срез предподготовки, обёртка чанка, скользящее окно. Размер чанка — переменная.

Не входит

  • BG-01 (снято), автоотмена по таймауту (BG-05 в редакции «1800 сек и Отменить»).
  • Изменение состава операций, методик СЧА/РСА, тела СоздатьПланРегламентныхОперацийДУ.
  • Обновление БСП, переход на ДлительныеОперации.ВыполнитьФункциюВНесколькоПотоков.
  • Доработка 2 (группа 3 СЧА/РСА). Диспетчер только оставляет барьер пачки как точку вставки.

2. Как работает сейчас

  1. Форма РегламентныйПериод собирает ПараметрыСохранения (операции, документы, пустой список заданий, число потоков, МассивРодителей).
  2. Родитель: длительная операция Справочники.РегламентныеПериоды.СформироватьРегламентныеОперации.
  3. Пачки по 3 000. Предподготовка утренних/вечерних только если МассивРодителей.Количество() = 1.
  4. По каждому договору: СформироватьДокументыЗакрытияПериода. При непустой таблице операций стартует ФоновыеЗаданияСервер.СоздатьПланРегламентныхОперацийДУ (один договор = одно задание).
  5. Ожидание порции спрятано внутри «есть операции» и срабатывает при наборе N потоков или на последнем договоре отбора.

Дефекты: если у последнего договора нет операций, хвост не ждут (BG-02); аварию разбирают по старому снимку ФоновоеЗадание (BG-14); на границе пачки нет явного барьера (BG-03); при исключении родителя дети не снимаются (BG-10).

3. Правила кода: области, маркеры, мало процедур

3.1. Маркеры

  • Каждая вставка в перехваченный метод: комментарий // IMDEV-8663.1.A или // IMDEV-8663.1.B на первой строке блока #Вставка.
  • Каждая новая процедура: тот же маркер сразу после заголовка (после документирующего комментария, перед телом).
  • В #Удаление маркер не обязателен: удаляемый код и так виден.

3.2. Области

Все новые процедуры модуля класть в область с номером задачи и подгруппы. Перехватчики &ИзменениеИКонтроль тоже в ту же область. 

#Область IMDEV_8663_1_A
    // перехват СформироватьРегламентныеОперации
    // перехват СформироватьДокументыЗакрытияПериода
    // IM8663_ЗавершитьФоновыеЗаданияПорции
    // IM8663_ОтменитьАктивныеЗадания
#КонецОбласти

#Область IMDEV_8663_1_B
    // IM8663_ОбработатьПачкуДиспетчером
    // IM8663_СоздатьПланыРегламентныхОперацийПоЧанку (модуль менеджера, экспорт)
#КонецОбласти

В общем модуле ФоновыеЗаданияСервер только область B: тонкая экспортная обёртка метода фонового задания.

3.3. Мало новых процедур

Не дробить диспетчер на «подготовить / очередь / запуск / окно / срез / разбор». Итого четыре новые прикладные процедуры плюс одна платформенная обёртка задания:

5. Этап A

Процедуры этапа A — общая инфраструктура диспетчера. Отдельного «режима только A» нет.

5.1. Инициализация в родителе

В СформироватьРегламентныеОперации после проверки ПараметрыСохранения, один раз на прогон (маркеры // IMDEV-8663.1.A и // IMDEV-8663.1.B): 

ФоновыеЗаданияДоступны = ПараметрыСохранения.КоличествоПотоков > 0
    И ФоновыеЗаданияСервер.ФоновыеЗаданияРазрешены();
ПараметрыСохранения.Вставить("ФоновыеЗаданияДоступны", ФоновыеЗаданияДоступны);
ПараметрыСохранения.Вставить("УспешныхЗаданий", 0);
ПараметрыСохранения.Вставить("ОшибокЗаданий", 0);
ПараметрыСохранения.Вставить("ПроблемныеДоговоры", Новый Массив);

// IMDEV-8663.1.B
РазмерЧанка = 50;
ПараметрыСохранения.Вставить("РазмерЧанка", РазмерЧанка);

Размер чанка не выносить в константу метаданных и не читать из настроек системы. Чтобы подобрать значение после D-11 — менять эту переменную в коде.

5.2. Запуск без ожидания внутри «есть операции»

В СформироватьДокументыЗакрытияПериода родительский цикл больше не стартует фоновые по одному договору (это делает диспетчер). Процедуру всё равно поправить: её вызывают последовательный путь и воркер чанка с КоличествоПотоков = 0. Если внутри всё же окажется параллельный запуск — ожидание должно идти через процедуру этапа A, а не через старый блок.

В СформироватьДокументыЗакрытияПериода:

  • Проверку ФоновыеЗаданияСервер.ФоновыеЗаданияРазрешены() заменить на ПараметрыСохранения.ФоновыеЗаданияДоступны (если ключа нет — вычислить один раз и вставить).
  • После СписокФоновыхЗаданий.Добавить вызывать завершение порции при Количество() >= КоличествоПотоков. Не привязывать ожидание к ТекЗначение = МаксимальноеЗначение.
  • Блок ожидания/разбора/очистки внутри этой процедуры удалить (#Удаление), вместо него вызов IM8663_ЗавершитьФоновыеЗаданияПорции(ПараметрыСохранения).
// IMDEV-8663.1.A
Если ПараметрыСохранения.СписокФоновыхЗаданий.Количество() >= КоличествоПотоков Тогда
    IM8663_ЗавершитьФоновыеЗаданияПорции(ПараметрыСохранения);
КонецЕсли;

5.6. Приёмка инфраструктуры A

Сценарии ниже выполняются уже на диспетчере (кроме T-07). Отдельного прогона «как раньше, одно задание на договор» нет.

ID Сценарий Критерий
T-01 Последний договор без операций, потоков 3–5 К «завершено» активных детей нет; документы на месте; сообщения хвоста доставлены
T-02 Обычный вечерний отбор, у последнего есть операции Результат как до правки, прогресс 100% после фактического конца
T-03 Инфраструктурная авария одного задания Видно ЗавершеноАварийно по обновлённому объекту; договор в тексте и в журнале
T-04 Пачка временно 5, отбор 12, потоков 3 К старту предподготовки пачки N+1 заданий пачки N нет
T-05 Исключение или отмена в середине Активные дети сняты; новых документов после отмены нет
T-06 Эталонный вечерний набор Документы и движения совпадают с прогоном без расширения. Приёмка A

6. Этап B

Диспетчер сразу основной Старый параллельный цикл «договор = задание» не оставляем рядом. Откат — отключить расширение. D-09 (состав документов) обязателен до продуктивного прогона. D-10 (время) снимаем после кода; порог «не хуже» в ТЗ не фиксируем.

6.3. IM8663_ОбработатьПачкуДиспетчером

Одна процедура, внутри по шагам (отдельные процедуры не создавать):

  1. Размер чанка взять из ПараметрыСохранения.РазмерЧанка (задано при старте прогона, 50). Если меньше 1 — считать 1; не больше размера текущей пачки.
  2. Построить очередь: для каждой группы из МассивРодителей отдельно. В чанк только договоры, у которых по группе есть строки операций (та же логика, что ТаблицаОпераций.Количество() > 0). Пустые чанки не создавать. Группы в одном чанке не смешивать.
  3. Скользящее окно: пока очередь не пуста или есть активные: пока активных меньше числа потоков и очередь не пуста — запустить чанк; иначе короткое ожидание (5 сек), разобрать завершённые через ту же IM8663_ЗавершитьФоновыеЗаданияПорции нельзя вслепую, если в списке ещё активные, которых ждать «всех» рано. Для окна: ждать шагом, из возвращённого массива убрать завершённые из СписокФоновыхЗаданий, разобрать их (сообщения/журнал/счётчики) и оставить активные. Разбор завершённых не дублировать вторым модулем: вынести внутренний цикл разбора внутрь IM8663_ЗавершитьФоновыеЗаданияПорции параметром «ждать всех» / «снять только уже завершённых». Это не пятая процедура, а необязательный параметр той же процедуры этапа A.
  4. Параметры задания — одна структура, не массив по позициям. В ФоновыеЗадания.Выполнить передаётся массив из одного элемента. Срез предподготовки только по договорам чанка (ключи как в ОчиститьПакетныеДанныеПараметрыСохранения). Весь кэш пачки 3 000 не передавать.
  5. Наименование: группа + номер чанка + число договоров. Ключ: дата периода + группа + номер чанка пачки (уникален в прогоне, иначе платформа сериализует второе задание с тем же ключом).
  6. Прогресс: «обработано X из Y, активных чанков Z» по завершённым договорам чанков. Не обещать «договор N», пока чанк живой.

Параметр завершения порции (этап A, используется и B):

Процедура IM8663_ЗавершитьФоновыеЗаданияПорции(ПараметрыСохранения, ЖдатьВсех = Истина)
  • ЖдатьВсех = Истина (барьер пачки/прогона, порог окна этапа A): ждать, пока активных не останется, затем разобрать все, очистить список.
  • ЖдатьВсех = Ложь (скользящее окно B): один шаг ожидания 5 сек, разобрать только уже завершённые, активные оставить в списке.

6.4. Срез предподготовки

Ключи соответствий «договор - таблица» те же, что чистит ОчиститьПакетныеДанныеПараметрыСохранения. Для каждого ключа-соответствия в срез попадают только договоры чанка. ТаблицаДефолтныеСобытияКотировокУУ и СоответствиеПропускРЕПОВетки можно передать как есть, если они общие на пачку и невелики; если запуск падает по лимиту 1 Гбайт — урезать. При падении по размеру параметров уменьшить РазмерЧанка в коде, не отключать срез.

6.5. Воркер чанка

Метод задания: ФоновыеЗаданияСервер.IM8663_СоздатьПланыРегламентныхОперацийПоЧанку. Обёртка общего модуля вызывает экспорт менеджера. Внутри менеджера: для каждого договора чанка вызвать существующую СформироватьДокументыЗакрытияПериода, подложив в копию ПараметрыСохранения КоличествоПотоков = 0 и ФоновыеЗаданияДоступны = Ложь, чтобы внутри договора шёл синхронный вызов СоздатьПланРегламентныхОперацийДУ без вложенных фоновых. Нарезку таблиц предподготовки не копировать.

Ошибка одного договора: Попытка вокруг вызова, сообщение + журнал с договором, переход к следующему. Исключение уровня сеанса может завершить задание аварийно — диспетчер увидит по состоянию (этап A / BG-14). В этом случае оставшиеся договоры чанка не обработаются — это осознанное отличие от схемы «один договор = одно задание». В сводке чанк должен быть виден.

Авария одного чанка не останавливает очередь: слот свободен, стартует следующий.

7. Что не менять

  • Схему «родитель длительная операция + дочерние задания».
  • Пачки 3 000 и пакетную предподготовку.
  • Тело СоздатьПланРегламентныхОперацийДУ.
  • Последовательный режим при 0 потоков.
  • Цикл ожидания вокруг API платформы (он нужен: платформа может вернуть управление после первого аварийного).
  • Автоотмену по произвольному таймауту.
  • Передачу в задание кэша всей пачки 3 000.
Запрещено Пять-девять мелких процедур диспетчера вместо двух толстых. Менять методику операций «чтобы лучше параллелилось». Обещать ускорение без D-10. Создавать константы расширения под флаг или размер чанка. Иероглифы и спецсимволы Unicode в коде (только кириллица, латиница, ASCII).

8. Приёмка сводно

  1. Этап A+B вместе: T-01, T-02, T-03, T-06, D-02, D-03, D-04, D-07.
  2. На копии: D-09, при необходимости D-11, затем D-10.
  3. Маркеры и области на месте, расширение проходит валидацию. Своих констант нет.

9. Порядок работ

  1. Создать расширение, заимствовать объекты. Константы не создавать.
  2. Реализовать этап A (перехваты + две процедуры ожидания/отмены).
  3. Реализовать этап B (диспетчер сразу в ветке «фоновые доступны», обёртка чанка, переменная РазмерЧанка = 50).
  4. Короткий отбор: T-01…T-07, D-02…D-08. На копии — D-09, затем D-10.

Оценка ориентировочно: A около 2,5 человеко-дня с тестами; B с проверкой на коротком отборе около 4 дней; нагрузка D-10 — отдельно, после появления кода.
