1. Цель

Два связанных дефекта после разделения групп «2. Вечерние операции» и «3. Расчет СЧА/РСА».

NПроблемаЧто сделать
1 Кнопка «Отмена» окна длительной операции гасит только родительское задание. Дочерние порции с ключом IM8663_… живут и продолжают проводить планы. Повторное «Создать» на части договоров падает с «Обнаружен существующий документ … Нельзя создавать два документа в один день». При отмене и перед новым «Создать» остановить активные ФЗ с ключом IM8663_ на эту дату и дождаться остановки. Снимок планов — только после этого. Штатное перепроведение найденного плана не переписывать.
2 Группа 3 стартует по всему отбору формы. Связи между планом СЧА/РСА и планом вечерних нет: РасчетСЧА_РСА.ДокументОснование указывает на план группы 3, а не на вечерний. Группа 3 (ручной «Создать» и автозапуск) — только договоры с проведенным планом группы 2 за дату. На плане группы 3 — реквизит ПланВечернихОпераций (ссылка на этот вечерний план).
Как уже работает «Создать», если план есть в снимке. Это штат CF, не переписывать. ПолучитьДоговораДУпоДинамическомуСписку один раз заполняет ДокументыПоДоговорам запросом по дате, группе и списку договоров с единственным условием ПометкаУдаления = ЛОЖЬ — то есть в снимок попадают все планы, и проведенные тоже. Для найденной строки диспетчер вызывает ПолучитьОбъект(), чистит ТЧ, записывает проведением, а ВыполнитьРегламентныеПроцедуры при НЕ УчитыватьВыполненные первым делом помечает на удаление подчиненные документы и создает их заново. Требование «документы при Создать должны удаляться» этим уже закрыто.
Диагноз подтвержден по коду и по протоколу теста 14.09.2026 (период 11.09.2026).
  • Проверка ПроверитьНаличиеСуществующегоДокумента срабатывает только на чужой проведенный план. Проведенный документ пометить на удаление нельзя, значит любой проведенный план на момент снимка в снимок попадает. Вывод: конфликтующий план физически создан после снимка — его записали выжившие порции прошлого запуска. Другого источника нет.
  • Тогда плана нет в снимке → СоздатьДокумент() вместо ПолучитьОбъект() → Записать(Проведение) падает, и в сеанс уходит пара сообщений: «Обнаружен существующий документ …» и «Не удалось провести документ по договору ДУ … Причина: Ошибка при вызове метода контекста (Записать)».
  • Сообщения дочерних порций видны пользователю: их переливает ЗавершитьФоновыеЗаданияПорции через ПолучитьСообщенияПользователю.
  • Наблюдалось на 12 потоках: второй проход на ~700-м договоре из 3 122 дошел до участка, который старые порции добивали уже после снимка. Ошибки шли по идущим подряд портфелям.
  • Ошибка уникальности ключа ФЗ в протоколе не зафиксирована. Это побочный риск-гонка: номера чанков между запусками совпадают, и если старая порция ещё держит тот же ключ, ФоновыеЗадания.Выполнить выбросит исключение. Гашение порций закрывает и это.
Честная граница проверки (в коде так и закладывать). Фильтр группы 3 смотрит на проведенный план группы 2, а не на каждый вид документа внутри плана (котировки, НКД, переоценка поштучно). Если план есть, а документ внутри не записался — группа 3 договор всё равно возьмёт. Пуловые / общие операции (План общих рег операций) в объём не входят.

2. Запрещено

  • Править базовую CF Wim_Du. Только расширение IM86632.
  • Вызывать cfe-init, пересоздавать расширение, откатывать UX этапа 2 и пакет этапов 3–4.
  • Переименовывать ключ порции IM8663_%1_%2_%3_%4 (дата yyyyMMdd + индекс пачки + номер чанка + XMLСтрока группы).
  • Объявлять Перем в модуле менеджера. Платформа это запрещает (модуль менеджера объекта метаданных не имеет переменных модуля). Не обходить это параметрами сеанса и не заводить «кэш» на переменных общего модуля.
  • Заимствовать ФоновыеЗаданияСервер ради отмены порций — отмена идёт через платформенный менеджер ФоновыеЗадания. Исключение: точечный &ИзменениеИКонтроль только на СоздатьПланРегламентныхОперацийДУ (выставить реквизит на объекте до Записать, см. п. 5.2).
  • Перехватывать целиком ПолучитьДоговораДУпоДинамическомуСписку (большой метод, дрейф). Фильтр — после её вызова, в уже существующем перехвате формы.
  • Раскомментировать массовую отмену/пометку планов в этой функции.
  • Писать в РасчетСЧА_РСА.ДокументОснование ссылку на вечерний план (критерий «Связанные документы» сломается). Связь — отдельный реквизит на плане группы 3.
  • Менять состав операций, флажок автозапуска, пакетный расчет 1000, константу, «Создать с учетом выполненных», обработку поддержки переноса в группу 3.
  • Добавлять новый флажок на форму периода. Отбор и связь — штатное правило запуска.
  • Схлопывать два проведенных плана в один. Уникальность CF не трогать.
  • Одновременно держать IM86632 и IM86632T1 на одной ИБ (одинаковый префикс). IM86632T1 в этой задаче не править, пока явно не попросили скопировать те же правки.

4. Задача 1. Отмена порций

4.1. Что именно делает «Отмена» в базовой CF

ЗвеноФакт
ОбщаяФорма.ДлительнаяОперация, ПередЗакрытием → Подключаемый_ОтменитьЗадание → ПриЗакрытии / ПроверитьЗаданиеВыполнено(Истина) Вызывает ДлительныеОперации.ОтменитьВыполнениеЗадания(ИдентификаторЗадания). Идентификатор один — родительского задания ДТО.
ДлительныеОперации.ОтменитьВыполнениеЗадания НайтиЗаданиеПоИдентификатору + Задание.Отменить(). Ровно одно задание. Каскада «родитель → дети» в платформе нет.
Дочерние порции Запущены изнутри родителя через ФоновыеЗадания.Выполнить("ОбщегоНазначения.ВыполнитьБПБезопасно", …) с ключом IM8663_…. Самостоятельные задания, живут дальше.
ОтменитьАктивныеЗадания(ПараметрыСохранения) в CF Есть, но вызывается только из ветки Исключение процедуры СформироватьРегламентныеОперации. При Отменить() родитель прерывается платформой, а не скриптовым исключением — до этой строки управление не доходит.
Форма периода Обработчика отмены нет: ОбработатьРезультатЗадания на Неопределено и на статус «Отменено» пишет только Состояние(...).

Поэтому типовой ОтменитьАктивныеЗадания нам не годится: он неэкспортный и обходит ПараметрыСохранения.СписокФоновыхЗаданий своего прогона, а после «Отмена» этой структуры на руках уже нет. Ключ родителя ДТО — Строка(Новый УникальныйИдентификатор), не IM8663_. Гасить нужно детей по префиксу ключа.

4.2. Алгоритм ОтменитьПорцииРегламентаЗаДату

  1. Префикс: "IM8663_" + Формат(ДатаПериода, "ДФ=yyyyMMdd"). Не трогать порции других дат.
  2. ФоновыеЗадания.ПолучитьФоновыеЗадания с отбором Состояние = Активно. Отбор по Ключ в платформе — точное равенство, не префикс; поэтому цикл по активным и СтрНачинаетсяС(Задание.Ключ, Префикс).
  3. Для совпавших: Задание.Отменить(), собрать массив.
  4. Ждать ФоновыеЗадания.ОжидатьЗавершенияВыполнения (как диспетчер CF, шаг 5 сек), не ОжидатьЗавершения: отменённое задание для второго метода — аварийное завершение, будет исключение.
  5. Цикл, пока среди отобранных есть СостояниеФоновогоЗадания.Активно.
  6. Не заимствовать ФоновыеЗаданияСервер. Платформенный менеджер ФоновыеЗадания из модуля менеджера справочника доступен.
Ключ порции не содержит пользователя. Два сеанса на одну дату и так конфликтуют по уникальности ключа. Отмена всех активных IM8663_ этой даты — то же правило, что у ключа. Не добавлять в ключ пользователя и не переименовывать шаблон.
