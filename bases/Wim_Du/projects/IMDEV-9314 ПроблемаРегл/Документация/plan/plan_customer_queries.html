IMDEV-9314. Как выполняю задачу и как доделываю запросы

Дорабатываю два запроса в документе «Установка котировок ц/б»: ЗафиксированныеКотировкиБУ (строка 404) и ЗафиксированныеКотировкиУУ (строка 562). Схема правок одна, регистры и набор полей разные. Причина тикета: IMAPPS-38656.

1. Как буду выполнять задачу Заказчика

В IMDEV-9314 три пункта. Параллельность уже проверена. Дальше правлю оба запроса (БУ и УУ) одной схемой: как просил Заказчик, плюс JOIN по активам.

Пункт тикета Статус Что делаю
2. Перепроверить многопоточность ИДУ в справочнике «Регламентные периоды» (IMDEV-8926, IMAPPS-35039) Сделано Прогон на 3 договорах ДУ. В отладчике: 1 тонкий клиент + 1 главное фоновое задание + 3 отдельных ФЗ по договорам. Параллельность живая.

2. Как доделать запросы так, как хочет Заказчик

Два требования Заказчика — про разные проблемы. Оба применяются и к БУ, и к УУ. Ниже — общая схема. Готовые тексты запросов с подсветкой строк: query_before_after_BU.html и query_before_after_UU.html.

2.1. Список значений -> таблица значений. Почему.

Конструкция Актив В (&СписокЦБ) для платформы — это не «одна таблица», а набор отдельных параметров: Актив В (&П1, &П2, … &ПN). На договоре с сотнями/тысячами ЦБ запрос раздувается и упирается в ограничение движка (как раз формулировка тикета: «чтобы не попасть на ограничения движка из-за большого кол-ва параметров»).

Сейчас в конфигурации (модуль объекта, заполнение втАктивы) — список всё ещё в IN:

ВЫБРАТЬ РАЗРЕШЕННЫЕ
    СпрАктивы.Ссылка КАК Актив
ПОМЕСТИТЬ втАктивы
ИЗ
    Справочник.Активы КАК СпрАктивы
ГДЕ
    СпрАктивы.Ссылка В (&СписокЦБ)   // каждый элемент списка = отдельный параметр
ИНДЕКСИРОВАТЬ ПО
    Актив

Как надо по Заказчику — один параметр-таблица (тот же приём уже есть в этом документе для приоритета бирж, &ПриоритетБирж):

// BSL, до текста запроса
ТаблицаАктивов = Новый ТаблицаЗначений;
ТаблицаАктивов.Колонки.Добавить("Актив", Новый ОписаниеТипов("СправочникСсылка.Активы"));
Для Каждого ТекАктив Из СписокЦБ Цикл
    СтрокаТЗ = ТаблицаАктивов.Добавить();
    СтрокаТЗ.Актив = ТекАктив;
КонецЦикла;
Запрос.УстановитьПараметр("ТаблицаАктивов", ТаблицаАктивов);

// в тексте запроса — ОДИН параметр, не N
ВЫБРАТЬ
    ТаблицаАктивов.Актив КАК Актив
ПОМЕСТИТЬ втАктивы
ИЗ
    &ТаблицаАктивов КАК ТаблицаАктивов
ИНДЕКСИРОВАТЬ ПО
    Актив

Почему так быстрее/надёжнее: во временную таблицу данные кладутся пакетом. Дальше соединения идут по индексу колонки Актив. SQL не разворачивает тысячу параметров в IN. Обход справочника Активы через Справочник.Активы ГДЕ Ссылка В (...) тоже не нужен — ссылки уже есть в таблице.

2.2. СрезПоследних во временную таблицу, потом JOIN с ВТ_КотировкиЦБ. Почему.

СрезПоследних — виртуальная таблица. Пока она стоит прямо в FROM рядом с JOIN, оптимизатор часто не может нормально использовать индекс: он сначала считает срез, потом на лету стыкует с мин/макс биржи. Заказчик просит: сначала положить срез в обычную временную таблицу, повесить индекс, и уже эту таблицу соединять с ВТ_КотировкиЦБ.

Сейчас (УУ, фрагмент) — срез и JOIN в одном шаге:

ПОМЕСТИТЬ АктуальныеКотировки
ИЗ
    РегистрСведений.ЗафиксированныеКотировкиЦБ.СрезПоследних(
            &Дата,
            Актив В (ВЫБРАТЬ Актив ИЗ втАктивы)
                И ДоговорДУ = &ДоговорДУ
                И Расчетная = ЛОЖЬ) КАК Котировки
        ЛЕВОЕ СОЕДИНЕНИЕ ВТ_КотировкиЦБ КАК ВТ_КотировкиЦБ
        ПО Котировки.Актив = ВТ_КотировкиЦБ.Актив
            И Котировки.Валюта = ВТ_КотировкиЦБ.Валюта

Как надо по Заказчику — два шага пакета:

// шаг 1: материализовать срез, индекс под будущий JOIN
ВЫБРАТЬ
    Котировки.Актив,
    Котировки.Валюта,
    Котировки.Котировка,
    Котировки.Расчетная,
    Котировки.МинимальнаяЦена,
    Котировки.МаксимальнаяЦена,
    Котировки.Биржа,
    ВЫБОР
        КОГДА Котировки.ДатаОпределения = &ПустаяДата
            ТОГДА Котировки.Период
        ИНАЧЕ Котировки.ДатаОпределения
    КОНЕЦ КАК ДатаОпределения
    // + поля УУ: СредневзвешеннаяЦена, ЦенаЗакрытия, ...
ПОМЕСТИТЬ втСрезЗафиксированных
ИЗ
    РегистрСведений.ЗафиксированныеКотировкиЦБ.СрезПоследних(
            &Дата,
            ДоговорДУ = &ДоговорДУ
                И Расчетная = ЛОЖЬ) КАК Котировки
ИНДЕКСИРОВАТЬ ПО
    Актив,
    Валюта
;

// шаг 2: уже обычные таблицы + индексное соединение с биржей
ВЫБРАТЬ
    Котировки.Актив,
    Котировки.Валюта,
    Котировки.Котировка,
    Котировки.Расчетная,
    ЕСТЬNULL(ВТ_КотировкиЦБ.МинимальнаяЦена, Котировки.МинимальнаяЦена) КАК МинимальнаяЦена,
    ЕСТЬNULL(ВТ_КотировкиЦБ.МаксимальнаяЦена, Котировки.МаксимальнаяЦена) КАК МаксимальнаяЦена,
    Котировки.Биржа,
    Котировки.ДатаОпределения
ПОМЕСТИТЬ АктуальныеКотировки
ИЗ
    втСрезЗафиксированных КАК Котировки
        ЛЕВОЕ СОЕДИНЕНИЕ ВТ_КотировкиЦБ КАК ВТ_КотировкиЦБ
        ПО Котировки.Актив = ВТ_КотировкиЦБ.Актив
            И Котировки.Валюта = ВТ_КотировкиЦБ.Валюта
ИНДЕКСИРОВАТЬ ПО
    Актив,
    ДатаОпределения

Почему так: после ПОМЕСТИТЬ+ИНДЕКСИРОВАТЬ оптимизатор видит обычную таблицу с индексом (Актив, Валюта). Соединение с ВТ_КотировкиЦБ становится hash/index join, а не «виртуальный срез на лету».

Разница двух запросов только в регистре и полях: БУ — ЗафиксированныеКотировкиЦБ_БУ; УУ — ЗафиксированныеКотировкиЦБ плюс средневзвешенная, закрытие, экспертная, спрос, объём, уровень листа. Обвязка BSL (таблица значений вместо &СписокЦБ) одинаковая в обеих функциях.
3. Свой вариант: INNER JOIN втАктивы — реально x2 на этом запросе

Пункты Заказчика убирают лимит параметров и делают JOIN с биржей по индексу. Но главный тормоз замера — не биржа, а отбор активов внутри виртуальной таблицы:

Актив В (ВЫБРАТЬ Актив ИЗ втАктивы) в параметрах СрезПоследних.

Почему это медленно. Условие виртуальной таблицы платформа часто не превращает в «сначала маленькая втАктивы, потом срез». Она либо разворачивает подзапрос обратно в набор параметров, либо считает срез с тяжёлым предикатом. В замере «1 поток, физики»: 2195 вызовов, две такие строки — 3652 с + 3134 с (~39% всего времени).

Что предлагаю добавить (уже проверено в консоли КОнсоль9314.q9, запросы «Котировки» vs «Котировки_олд», и на живых ФЗ 13.08):

  • убрать отбор по активу из параметров СрезПоследних;
  • оставить в срезе «дешёвые» условия: договор + не расчётная (и биржа — в срезе котировок на бирже);
  • отсечь активы JOIN-ом по индексированной втАктивы.

Фрагмент, который дал x2 (консоль, поверх схемы Заказчика из блока 2):

ПОМЕСТИТЬ АктуальныеКотировки
ИЗ
    втСрезЗафиксированных КАК Котировки
        ВНУТРЕННЕЕ СОЕДИНЕНИЕ втАктивы КАК втАктивы
        ПО Котировки.Актив = втАктивы.Актив
        ЛЕВОЕ СОЕДИНЕНИЕ ВТ_КотировкиЦБ КАК ВТ_КотировкиЦБ
        ПО Котировки.Актив = ВТ_КотировкиЦБ.Актив
            И Котировки.Валюта = ВТ_КотировкиЦБ.Валюта

Почему x2: втАктивы маленькая и с индексом. SQL не тащит условие IN внутрь виртуальной таблицы. На тесте Власова (45 ЦБ, 6 бирж): «внутреннее соединение втАктивы … работает в 2 раза быстрее». На скрине 13.08, строка 404 в разных ФЗ: ~1.30–1.46 с против ~0.32–0.47 с. Тот же приём ставим в УУ (строка 562) — там тот же тормоз, 21% замера.

Что Без JOIN (как сейчас в СрезПоследних) С INNER JOIN втАктивы
Строка 404, живые ФЗ 13.08 ~1.3–1.5 с на вызов ~0.3–0.5 с на вызов
Вывод протокола узкое место БУ/УУ, 18%+21% «работает в 2 раза быстрее»

Оговорка. Если убрать фильтр из среза и не отсечь JOIN-ом, срез по договору прочитает все зафиксированные котировки договора, не только нужные ЦБ. JOIN как раз это отсекает. На полном вечернем ИДУ всё равно нужен контрольный замер: на 45 активах выигрыш есть, на «толстом» срезе план может измениться. Если вдруг станет хуже — фильтр по договору в срезе оставляем, JOIN по активу оставляем, IN внутрь виртуальной таблицы не возвращаем.

Итоговая схема запроса (Заказчик + свой JOIN), коротко:

  1. втАктивы из &ТаблицаАктивов, индекс по Актив — пункт 1а.
  2. ВТ_КотировкиЦБ: срез биржи без IN-списка, отбор активов тем же JOIN к втАктивы, индекс (Актив, Валюта).
  3. втСрезЗафиксированных: СрезПоследних только по договору/признаку, индекс (Актив, Валюта) — пункт 1б.
  4. АктуальныеКотировки: срез JOIN втАктивы JOIN ВТ_КотировкиЦБ — пункт 1б + свой x2.
Прошу согласовать

1. Считать проверку параллельности закрытой.
Обоснование: на трёх договорах ДУ в отладчике видно тонкий клиент, общее фоновое задание и по одному заданию на каждый договор. Пул работает, отдельно этот пункт больше не крутим.

2. Править оба запроса — БУ и УУ — по схеме Заказчика.
Обоснование: узкое место замера — две функции, не одна (404 = 18%, 562 = 21%). Сейчас в обеих список активов уходит как длинный IN, срез и соединение с биржей идут в одном шаге. Таблица значений и «сначала временная таблица, потом JOIN» закрывают пункты 1а и 1б в каждой функции. Сравнение построчно: БУ и УУ.

3. В те же две правки добавить отбор активов через соединение, а не через условие внутри среза.
Обоснование: это не вместо пунктов Заказчика, а поверх них, в БУ и в УУ. На тесте запрос стал примерно в два раза быстрее (консоль и живые ФЗ: ~1.4 с на вызов против ~0.4 с). Без этого строки 404 и 562 почти не сдвинутся.

4. Вендору отдавать после замера «стало», не сейчас.
Обоснование: сначала нужна цифра, что на том же сценарии реально быстрее. Иначе в коробку уедет непроверенное.
