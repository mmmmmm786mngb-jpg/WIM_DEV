0. Что делает ваш код — коротко

Экспорт возвращает Соответствие: ключ = элемент ПВХ ПараметрыДоговораДУ, значение = ресурс регистра на дату (срез последних). Вход: договор, список параметров или один элемент, дата (пустая = ТекущаяДата()).

Контракт, на который завязаны документы: в соответствии есть все запрошенные ключи. Нет записи в регистре — значение Неопределено, а не отсутствие ключа. Поэтому вызывающий код пишет .Получить(ПВХ) = Истина и не проверяет наличие ключа.

Этот контракт вы обеспечивали левым соединением списка из ПВХ со срезом плюс ЕСТЬNULL(..., Неопределено). Решение корректное. На 136 443 вызовах вечернего регламента (стр. 73, Запрос.Выполнить()) пакет стал узким местом: 1 174 сек, 7,49%.

Зачем был ПВХ + LEFT JOIN. Первая часть пакета строит множество ключей ответа. Вторая читает срез (фильтр тот же: договор + Параметр В (&Параметры)) и гарантирует строку даже при отсутствии записи. Это и есть ваш контракт «ключ всегда есть».

ПВХ здесь не дает новых данных: вызывающий код уже передал ссылки предопределенных элементов. Запрос к плану видов характеристик на каждом из 136 тысяч вызовов — лишняя работа СУБД. Срез и так ограничен тем же В (&Параметры).

Приложение

A. Принципы тестирования

Цель проверки — не «провести документ и глазами сравнить проводки», а доказать, что новое тело функции отвечает тем же соответствием, что ваш пакет, на тех наборах ПВХ, которыми реально пользуются 0110 и 0400. Проводки меняться не должны, если не меняется ответ функции.

  1. Эталон — ваш код, не «ожидание с потолка». В обработке внСравнениеПараметровДоговораДУ функция ЗначенияПараметровДоговораДУ_Текущий — дословная копия вашего пакета (ПВХ + LEFT JOIN + ЕСТЬNULL + тот же лог). Новый вариант сравнивается с вами, а не с ручным списком значений.
  2. Сравниваем по запрошенным ключам, не по составу строк запроса. Для каждого элемента массива: Эталон.Получить(ПВХ) vs Новый.Получить(ПВХ). Так проверяется контракт вызывающего кода, а не формат выборки.
  3. Пустое из запроса и Неопределено — одно значение. ЗначенияПараметраРавны: если оба не заполнены, считаем равными. Это закрывает NULL / пустую характеристику / Неопределено без ложных расхождений.
  4. Наборы ПВХ — с ваших же вызовов регламента, не синтетика. Четыре списка: котировки (0110), РЕПО (0110), доп. параметры проведения (0110), алгоритм резервов (0400). Выборка договоров: пул «Розничное ДУ», без пометки удаления, первые N по коду.
  5. Корректность и скорость — разные этапы. Сначала полный проход сверки значений (без секундомера). Потом один прогрев (холодный кэш СУБД не в статистике). Потом три отдельных замера, чтобы кэш одного алгоритма не помогал другому.
  6. Третий алгоритм (полный срез без фильтра) — контроль, не кандидат в КФ. Его гоняли, чтобы увидеть: ответы могут совпасть, но читается лишнее. В базу он не идет. В КФ только вариант с вашим фильтром Параметр В (&Параметры).
  7. Ваш юнит-тест не выкидываем. ЮТ_ЗначенияПараметровДоговораДУ бьет другую ось: создание УП, срез есть, вход — один элемент ПВХ. Сравнительная обработка бьет массовый путь и отсутствие записи.
Обработка лежит в проекте IMDEV-8899: Скрипты/benchmark_params_du_epf/внСравнениеПараметровДоговораДУ. Форма: дата среза, число договоров (по умолчанию 100), прогрев, кнопка «Запустить сравнение». Зафиксированный прогон — 3000 договоров.

C.3. Как повторить регресс у себя

  1. Открыть внСравнениеПараметровДоговораДУ в базе с живыми договорами РДУ.
  2. Дата среза — рабочий день закрытия (как в регламенте). Договоров — 3000 (или меньше для дымового прогона).
  3. Прогрев включен. Запустить сравнение.
  4. Критерий приемки: 0 расхождений «Текущий vs Фильтр»; фильтр быстрее эталона.
  5. По желанию: прогнать ЮТ_ЗначенияПараметровДоговораДУ штатным механизмом юнит-тестов регистра.
Регресс для приемки в КФ: обработка сравнения зелёная (0 расхождений) и ваш ЮТ зелёный. Если появится хотя бы одно расхождение по ключу — в КФ не переносить, разбирать конкретный договор/набор из отчета (первые 20 деталей пишутся в текст).
