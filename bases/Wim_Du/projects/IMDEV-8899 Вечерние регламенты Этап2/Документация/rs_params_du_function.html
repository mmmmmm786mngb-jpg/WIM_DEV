1. Зачем эта функция

Регистр периодический, подчинен регистратору (обычно документ учетной политики). Измерения: ДоговорДУ и Параметр (план видов характеристик ПараметрыДоговораДУ). Ресурс: Значение — характеристика договора на конкретную дату.

Вызывающий код не читает срез сам. Он спрашивает: «по этому договору, на эту дату, дай мне вот эти параметры». Типичный вызов при проведении поступления: 

МассивПараметров.Добавить(ПВХ.ОбособленныйУчетЗадолженностиЭмитента_УУ);
МассивПараметров.Добавить(ПВХ.ОбособленныйУчетЗадолженностиПоДивидендам_УУ);
МассивПараметров.Добавить(ПВХ.ОценкаНезавершенныхСделокПоСС);
ЗначенияПараметров = РегистрыСведений.ЗначенияПараметровДоговораДУ.ЗначенияПараметровДоговораДУ(
    ДоговорДУ, МассивПараметров, Дата);

ОбособленныйУчет... = ЗначенияПараметров.Получить(ПВХ.ОбособленныйУчетЗадолженностиЭмитента_УУ) = Истина;

Контракт для вызывающего кода: в соответствии есть все запрошенные ключи. Если записи в регистре нет — значение Неопределено, а не «ключа нет». Проверка .Получить(...) = Истина тогда дает Ложь, как и задумано.

Тот же контракт используют десятки документов и отчетов: переоценка, сделки, расчет СЧА/РСА, регламентированные отчеты. Менять смысл ответа нельзя. Можно менять только способ его получить.

2. Что было

Старая версия (до IMDEV-8899) делала два шага в одном пакете запроса:

  1. Временная таблица из плана видов характеристик: «какие из переданных ссылок вообще существуют в ПВХ».
  2. Левое соединение этой таблицы со СрезПоследних регистра. Нет записи — ЕСТЬNULL(..., Неопределено).
ВЫБРАТЬ
    ПараметрыДоговораДУ.Ссылка
ПОМЕСТИТЬ Параметры
ИЗ
    ПланВидовХарактеристик.ПараметрыДоговораДУ КАК ПараметрыДоговораДУ
ГДЕ
    ПараметрыДоговораДУ.Ссылка В(&Параметры)
;

ВЫБРАТЬ
    Параметры.Ссылка КАК Параметр,
    ЕСТЬNULL(ПараметрыДУ.Значение, НЕОПРЕДЕЛЕНО) КАК Значение
ИЗ
    Параметры КАК Параметры
        ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.ЗначенияПараметровДоговораДУ.СрезПоследних(
            &Дата,
            ДоговорДУ = &ДоговорДУ
                И Параметр В (&Параметры)) КАК ПараметрыДУ
        ПО Параметры.Ссылка = ПараметрыДУ.Параметр

Дальше выборка обходила результат и складывала пары в соответствие. Логирование: ОбщегоНазначенияДУ.ДобавитьВЛогОтладки с тем же именем точки.

Зачем левое соединение? Только чтобы ключи без записи в регистре все равно попали в результат как Неопределено. Зачем временная таблица из ПВХ? Это лишний запрос к справочнику характеристик: вызывающий код и так передает готовые ссылки ПВХ. В вечернем регламенте это было 136 443 вызова и 7,49% времени (строка 73 модуля менеджера).

3. Что стало (текущая база)

Доработанная версия оставляет тот же контракт, но убирает ПВХ и левое соединение.

  1. В BSL заранее вставить в соответствие все запрошенные параметры со значением Неопределено.
  2. Одним запросом взять СрезПоследних только по договору и списку параметров.
  3. Найденные значения перезаписать в соответствие.
Для Каждого Параметр Из МассивПараметров Цикл
    ЗначенияПараметров.Вставить(Параметр, Неопределено);
КонецЦикла;

|            &Дата,

Убрали

  • Пакет с ПОМЕСТИТЬ.
  • Обращение к ПланВидовХарактеристик.ПараметрыДоговораДУ.
  • Левое соединение.
  • ЕСТЬNULL(..., Неопределено) в запросе.

Оставили без изменения

  • Имя, параметры, значение по умолчанию даты.
  • Пустой вход: Параметры = Неопределено -> пустое соответствие.
  • Один элемент вместо массива: оборачивается в массив.
  • Пустая дата '00010101' -> ТекущаяДата().
  • Фильтр среза: договор + Параметр В (&Параметры).
  • Точка логирования отладки.
  • Юнит-тест ЮТ_ЗначенияПараметровДоговораДУ.

4. Почему так быстрее

Виртуальная таблица СрезПоследних и раньше, и сейчас строится одинаково: последний срез по договору среди запрошенных параметров. Старый запрос заставлял СУБД дополнительно:

  • выбрать элементы ПВХ по списку ссылок;
  • положить их во временную таблицу;
  • соединить с уже отфильтрованным срезом.

Для вызывающего кода ПВХ не несет новой информации: он сам передал эти ссылки. Предзаполнение в BSL заменяет левое соединение за доли миллисекунды. Срез остается единственной работой СУБД.

5. Доказательство, что логика та же

Ниже — четыре независимых доказательства. Их достаточно вместе: контракт, подстановка шагов, живой прогон и вызывающий код.

1
Одинаковый публичный контракт. Сигнатура не менялась. Граничные ветки до запроса — те же. Возврат — Соответствие. Вызывающий код не переписывался. Кэш ОбщегоНазначенияДУПовтИсп.ЗначенияПараметровДоговораДУ по-прежнему просто вызывает эту функцию.
2
Пошаговая подстановка. Источник фактических значений — одна и та же виртуальная таблица СрезПоследних(&Дата, ДоговорДУ = &ДоговорДУ И Параметр В (&Параметры)). Левое соединение + ЕСТЬNULL в SQL = «сначала ключи с Неопределено, потом перезапись найденным» в BSL. Это не эвристика, а стандартная замена LEFT JOIN на предзаполнение.

Текущий модуль менеджера в КФ — это уже собранное тело вставки, без директив расширения. Комментарий в rev2: «бенчмарк 3000 договоров x 4 набора, 0 расхождений, -69% к текущему КФ».

Единственный формальный край, который не ломает вызывающий код

Старый запрос брал ключи из ПВХ (Ссылка В (&Параметры)). Новый предзаполняет ровно то, что передали в массиве. На реальных вызовах в массив кладут предопределенные элементы ПВХ — поэтому ключи те же. Если бы кто-то передал «мусорную» ссылку, которой нет в плане видов характеристик, старый запрос ее отбросил бы, новый оставил бы как Неопределено. Таких вызовов в конфигурации нет: массивы собираются из ПланыВидовХарактеристик.ПараметрыДоговораДУ.*.

Вывод: для всех существующих вызовов, включая проведение поступления РДУ, ответ функции тот же. Изменился только путь к ответу.
