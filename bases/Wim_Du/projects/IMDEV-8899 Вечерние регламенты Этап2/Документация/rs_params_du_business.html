Связь с поступлениями РДУIMDEV-9202: при проведении поступления программа один раз читает эти параметры. Это уже новая функция

1. Что это такое простыми словами

У каждого договора ДУ есть настройки учетной политики: как списывать партии, как учитывать задолженность, как переоценивать бумаги и т.д. Настройки живут в регистре и могут меняться со временем.

Когда проводится документ (поступление на счет, переоценка, расчет СЧА), программа спрашивает: «по этому договору, на дату документа, какие сейчас значения вот этих настроек?» Ответ — список пар «название настройки / значение». Если настройка для договора не задана, ответ: «пусто» (в коде это Неопределено).

Пример из поступления на расчетный счет: программа спрашивает три флага (обособленный учет задолженности эмитента, дивидендов и оценка незавершенных сделок). От этого зависит, как лягут проводки. Смысл вопроса и ответа не менялся.

2. Что изменилось и почему

Старый способ делал лишнюю работу. Сначала программа шла в справочник видов настроек (план видов характеристик) и спрашивала: «эти ссылки вообще существуют?». Потом соединяла ответ с фактическими значениями из регистра. Соединение было «левым»: даже если значения нет — строка все равно нужна, чтобы вернуть «пусто».

Это было дорого: в вечернем регламенте такую функцию вызывали 136 443 раза и тратили на нее 1 174 секунды (7,49% времени фонового задания).

Новый способ делает ровно то, что нужно бизнесу:

  1. Заранее помечает все запрошенные настройки как «пусто».
  2. Одним запросом берет из регистра последние значения на дату — только по этому договору и только по запрошенному списку.
  3. Найденное подставляет вместо «пусто».

Убрали

  • Лишний запрос в справочник видов настроек.
  • Временную таблицу и левое соединение.
  • Двойную работу СУБД на каждый вызов.

Не трогали

  • Какие настройки спрашивают документы.
  • Как считается «последнее значение на дату».
  • Что делать, если настройки нет (ответ «пусто»).
  • Форму, кнопки, печатные формы, проводки.
Это не новая учетная политика и не смена методики. Это более короткий путь к тем же цифрам. Проводки, СЧА, статусы поручений и выгрузка в Finance от этой правки не должны измениться.

4. Почему логика не изменилась

Бизнесу важен ответ, а не текст запроса. Ответ совпадает по четырем причинам.

1
Тот же вопрос. Функция по-прежнему принимает договор, список настроек и дату. Если список не передали — пустой ответ. Если передали одну настройку, а не список — программа сама кладет ее в список. Если дату не указали — берется текущая. Это не менялось.
2
Тот же источник правды. Фактические значения и раньше, и сейчас берутся из «последнего среза» регистра на дату по договору и списку настроек. Мы не читаем другой регистр и не подставляем значения «с потолка».
3
Тот же смысл «настройки нет». Раньше «пусто» давало левое соединение: нет строки в регистре — в ответ все равно попадала настройка со значением «не задано». Сейчас то же самое делается заранее: все запрошенные ключи помечаются как «пусто», затем найденное перезаписывается. Для документа это одно и то же: проверка «значение = Да» по-прежнему ложна, если настройки нет.
4
Это проверено на живых договорах, не только на бумаге. Отдельным тестом старый и новый алгоритмы гонялись на 3 000 договорах пула «Розничное ДУ» по четырем реальным наборам настроек вечернего регламента. Расхождений: 0. Подробности — в разделе 7.
Вывод для приемки: менять тест-кейсы по суммам, счетам и статусам не нужно. Регресс этой правки — «те же параметры на ту же дату». Это как раз то, что сравнивал тест.

5. Что стало: полный текущий код с назначением

Ниже — функция, которая сейчас в базовой конфигурации (РегистрСведений.ЗначенияПараметровДоговораДУ, модуль менеджера). Комментарии добавлены для этого отчета: в рабочей базе их нет, код тот же. 

// Назначение функции:
//   Вернуть настройки договора ДУ, действующие на дату.
//   Вход: договор, список нужных настроек (или одна настройка), дата.
//   Выход: соответствие «настройка -> значение».
//   Если записи в регистре нет, ключ все равно есть, значение пустое.

Функция ЗначенияПараметровДоговораДУ(ДоговорДУ, Параметры, Знач Дата = '00010101') Экспорт

    // Пустой ответ, в него будем складывать пары.
    ЗначенияПараметров = Новый Соответствие;

    // Защита: вызывающий код ничего не попросил — сразу выходим,
    // чтобы не ходить в базу.
    Если Параметры = Неопределено Тогда
        Возврат ЗначенияПараметров;
    КонецЕсли;

    // Удобство вызова: можно передать одну настройку, а не массив.
    // Дальше всегда работаем со списком — одинаковая логика.
    Если ТипЗнч(Параметры) <> Тип("Массив") Тогда
        МассивПараметров = Новый Массив;
        МассивПараметров.Добавить(Параметры);
    Иначе
        МассивПараметров = Параметры;
    КонецЕсли;

    // Если дату не указали (пустая '00010101') — берем сейчас.
    // Так было и в старой версии.
    Если Дата = '00010101' Тогда
        Дата = ТекущаяДата();
    КонецЕсли;

    // ЭТО ГЛАВНОЕ ИЗМЕНЕНИЕ ВМЕСТО ЛЕВОГО СОЕДИНЕНИЯ.
    // Сначала все запрошенные настройки помечаем как «не задано».
    // Тогда в ответе всегда полный список ключей, даже если в регистре пусто.
    Для Каждого Параметр Из МассивПараметров Цикл
        ЗначенияПараметров.Вставить(Параметр, Неопределено);
    КонецЦикла;

    // Готовим один запрос к регистру. Три параметра:
    //   Дата      — «на какой момент смотреть последнее значение»;
    //   ДоговорДУ — «чей договор»;
    //   Параметры — «какие именно настройки, не все подряд».
    Запрос = Новый Запрос;
    Запрос.УстановитьПараметр("Дата",      Дата);
    Запрос.УстановитьПараметр("ДоговорДУ", ДоговорДУ);
    Запрос.УстановитьПараметр("Параметры", МассивПараметров);

    // СрезПоследних = «последняя запись не позже даты».
    // Фильтр сразу в срезе: только этот договор и только запрошенный список.
    // Не читаем сотни чужих настроек учетной политики.
    Запрос.Текст =
    "ВЫБРАТЬ
    |    ЗначенияПараметров.Параметр КАК Параметр,
    |    ЗначенияПараметров.Значение КАК Значение
    |ИЗ
    |    РегистрСведений.ЗначенияПараметровДоговораДУ.СрезПоследних(
    |            &Дата,
    |            ДоговорДУ = &ДоговорДУ
    |                И Параметр В (&Параметры)) КАК ЗначенияПараметров";

    // Служебный лог отладки. Имя точки то же, что было в старой версии,
    // чтобы не ломать существующие журналы.
    ОбщегоНазначенияДУ.ДобавитьВЛогОтладки(Запрос,
        "РегистрСведений.ЗначенияПараметровДоговоровДУ.МодульМенеджера:ЗначенияПараметровДоговораДУ");

    // Выполняем запрос и найденные значения кладем поверх «пусто».
    // Что не нашлось — остается Неопределено из цикла выше.
    Выборка = Запрос.Выполнить().Выбрать();
    Пока Выборка.Следующий() Цикл
        ЗначенияПараметров.Вставить(Выборка.Параметр, Выборка.Значение);

    Возврат ЗначенияПараметров;

ОбособленныйУчет... = ЗначенияПараметров.Получить(ПВХ.ОбособленныйУчетЗадолженностиЭмитента_УУ) = Истина;

Если флага в регистре нет, Получить дает пусто, сравнение с «Да» дает «нет». Так было, так и осталось. Меняется только скорость получения соответствия.

Как устроен прогон внутри обработки (это и есть методика):

  1. Этап корректности. Для каждого договора и каждого набора настроек считаются три ответа: старый (эталон), полный срез без фильтра, новый с фильтром. По каждому запрошенному ключу значения сравниваются. Пустое из запроса и Неопределено считаются одним и тем же. Расхождение пишется в отчет (первые 20 деталей).
  2. Прогрев. Один договор, один набор, все три алгоритма — чтобы первый холодный запрос к СУБД не попал в замер.
  3. Замер времени. Три отдельных прохода по всей выборке, чтобы кэш одного алгоритма не помогал другому. Считается суммарное время и среднее на вызов.

Третий алгоритм в том же тесте — полный срез без фильтра — специально сравнивали и не взяли. Он читает все настройки договора (их у учетной политики сотни), а документы просят 1–10. Даже если ответы совпали, это лишние данные из базы. В конфигурацию пошел вариант с фильтром.

Повторить прогон можно той же обработкой: открыть в базе, поставить дату и 3000 договоров, нажать «Запустить сравнение». Ожидаемый текст: «Корректность: значения параметров совпадают (0 расхождений)» и «Быстрее всех: вариант 3 (фильтр)».

7.4. Юнит-тест конфигурации

В том же модуле менеджера остается ЮТ_ЗначенияПараметровДоговораДУ. Он не сравнивает старый и новый запрос. Он проверяет смысл для учета:

  1. Создает тестового контрагента-брокера и договор ДУ.
  2. Проводит учетную политику на 01.01.2013 с методом списания ЛИФО.
  3. Спрашивает функцию: «метод списания на 01.01.2013».
  4. Ожидает ЛИФО. Иначе — отказ теста.

Тест живет в макете юнит-тестов регистра. После переноса новой функции в базу его не удаляли: если бы срез начал врать, ЛИФО бы не прочитался.
