h2. IMDEV-8926: пакетная обработка при формировании регламентных операций

{panel:title=Кратко|borderStyle=solid|borderColor=#B8D4E8|titleBGColor=#D6E9F5|bgColor=#EBF5FB}
После релиза 1.5.28.4 и доработок IMAPPS-35037 / IMAPPS-35039 формирование регламентных операций на большом объеме договоров Retail ДУ приводит к нехватке памяти в рабочем процессе кластера.

Решение: расширение *revM* с перехватом {{СформироватьРегламентныеОперации}} - разбивка списка договоров на пачки по 3000 и пакетная предзагрузка данных только для текущей пачки.
{panel}

----

h3. Причина

{panel:title=Что происходит в типовой логике|borderStyle=solid|borderColor=#B8D4E8|titleBGColor=#D6E9F5|bgColor=#EBF5FB}
При выборе одной группы операций (Утренние / Вечерние) процедура {{СформироватьРегламентныеОперации}} один раз вызывает:

* {{ЗаполнитьПараметрыСохраненияПакетнымиДаннымиУтреннихОпераций}} или
* {{ЗаполнитьПараметрыСохраненияПакетнымиДаннымиВечернихОпераций}}

на *весь* {{СписокДоговоровДУ}}. В {{ПараметрыСохранения}} создаются крупные соответствия (взаиморасчеты, НКД, котировки, остатки и т.д.) по всем договорам сразу. Эти данные остаются в памяти на протяжении всего цикла обработки договоров.
{panel}

{panel:title=Связанные задачи|borderStyle=solid|borderColor=#D4CCE8|titleBGColor=#E8E2F3|bgColor=#F3F0FA}
* IMAPPS-35037 - пакетные запросы для утренних регламентов
* IMAPPS-35039 - пакетные запросы для вечерних регламентов
* Релиз 1.5.28.4
{panel}

----

h3. Решение

{panel:title=Расширение revM|borderStyle=solid|borderColor=#B8DDB8|titleBGColor=#D4EDD4|bgColor=#EBF7EB}
|| Параметр || Значение ||
| Имя | revM |
| Назначение | Patch |
| Префикс | revM_ |
| Объект | Справочник.РегламентныеПериоды |
| Перехват | {{&Вместо("СформироватьРегламентныеОперации")}} |
| Размер пачки | 3000 договоров |
{panel}

{panel:title=Алгоритм (без изменения бизнес-логики по договору)|borderStyle=solid|borderColor=#B8D8D4|titleBGColor=#D4EBE4|bgColor=#EBF7F2}
# Список договоров разбивается на пачки по 3000.
# Перед каждой пачкой очищаются пакетные ключи в {{ПараметрыСохранения}} (процедура {{ОчиститьПакетныеДанныеПараметрыСохранения}}).
# Пакетные процедуры (утренние / вечерние) вызываются только для договоров *текущей* пачки.
# Для каждого договора пачки вызывается типовой {{СформироватьДокументыЗакрытияПериода}} - без изменений.
# Прогресс, фоновые задания, {{ОжидатьЗавершения}} - работают по всему списку, как раньше.
{panel}

----

h3. Что изменено в коде

{code:title=Новые элементы модуля менеджера Справочник.РегламентныеПериоды (расширение revM)}
ОчиститьПакетныеДанныеПараметрыСохранения(ПараметрыСохранения)
  - удаляет 12 ключей пакетных данных из ПараметрыСохранения между пачками

revM_СформироватьРегламентныеОперации(...)
  - &Вместо("СформироватьРегламентныеОперации")
  - внешний цикл по пачкам
  - prefetch только для СписокПачки
{code}

{panel:title=Что НЕ менялось|borderStyle=solid|borderColor=#E8D4B8|titleBGColor=#F5E8D4|bgColor=#FBF5EB}
* {{СформироватьДокументыЗакрытияПериода}} и остальные процедуры модуля
* {{СписокОпераций}}, {{ДокументыПоДоговорам}} в {{ПараметрыСохранения}}
* Логика многопоточности и {{МассивФоновыхЗаданий}}
* Сценарий без пакетной предзагрузки (несколько групп операций / выключенные константы)
{panel}

{panel:title=Ограничение решения|borderStyle=solid|borderColor=#D4CCE8|titleBGColor=#E8E2F3|bgColor=#F3F0FA}
Снижается пик памяти от пакетной предзагрузки (IMAPPS-35037/35039). Память от {{СписокОпераций}}, {{ДокументыПоДоговорам}} и вложенных фоновых заданий ({{ОжидатьЗавершения}}) этим исправлением не оптимизируется. При повторных падениях РП - отдельный анализ потоков и фоновых заданий.
{panel}

----

h3. Замеры на стенде (prefetch)

{panel:title=До и после revM|borderStyle=solid|borderColor=#B8DDB8|titleBGColor=#D4EDD4|bgColor=#EBF7EB}
*До доработки (типовая логика):* prefetch на *весь* список - 17 000 договоров сразу в память (пик по пакетным соответствиям на весь {{СписокДоговоровДУ}}).

*После revM (пачка 3000):* на одну пачку prefetch - около *0,28 ГБ* (~280 МБ) дополнительно к базе процесса; между пачками ключи очищаются, рост не линейный (пример: ~200 МБ -> ~280 МБ -> ~238 МБ на 6000 договоров).

*Оценка пика prefetch (линейно, ориентир):*
|| Вариант || Договоров в prefetch || Оценка объема prefetch ||
| Было | 17 000 сразу | ~0,28 ГБ x (17 000 / 3 000) = *~1,6 ГБ* (если та же плотность данных) |
| Стало | 3 000 за пачку | *~0,28 ГБ* на пачку |

Снижение *пикового* объема пакетных данных в памяти примерно в *5,7 раза* (17 000 / 3 000) по отношению к prefetch. Фактический пик процесса rphost может быть выше за счет {{СписокОпераций}}, фоновых заданий и базы сеанса.

*Важно:* 0,28 ГБ - замер на стенде для конкретной группы операций (утро/вечер); на проде цифры могут отличаться, но порядок эффекта сохраняется.
{panel}
