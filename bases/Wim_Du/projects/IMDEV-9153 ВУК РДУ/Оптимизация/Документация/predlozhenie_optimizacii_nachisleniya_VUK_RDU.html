2. Текущее поведение (AS-IS)

Сейчас ручной сценарий состоит из двух шагов, оба серверные и полностью последовательные:

  1. Выбрать → ДоговорыКНачислению(): один пакетный запрос заполняет табличную часть ДоговорыДУКНачислению договорами к начислению.
  2. Начислить → СоздатьНачисления(): цикл Для каждого ДоговорДУ Из ДоговорыДУКНачислению, и для каждой строки выполняются три действия:
#ДействиеПроцедураЧто делает
1Создание начисленияНачислениеВознаграждения() Создаёт и проводит документ НачислениеВознаграждения (Неоперативный режим)
2Создание PDFФормироватьСправкуРасчет() → СохранитьНаДиск() Формирует табличный документ и пишет .pdf в каталог (в т.ч. сетевой) + каталог кабинета ДУ
3aУдаление движений регистраУдалитьОбязательствоДС() — часть 1 Записывает набор РегистрНакопления.ОбязательстваПоДС по отбору регистратора → движения сняты
3bУдаление самого регистратораУдалитьОбязательствоДС() — часть 2 Регистратор.ПолучитьОбъект().Удалить() — удаляет документ ОперацияБух (проверка ссылочной целостности → узкое место при параллели)

Проблема производительности: при большом числе договоров цикл выполняется в одном потоке, а самое дорогое (запись/проведение документа, генерация и сохранение PDF на сетевой ресурс) не распараллелено. Ветка расторжения (РежимРасторжения = Истина) вызывается отдельным фоновым методом и остаётся последовательной.

3. Ключевое ограничение: почему удаление регистратора нельзя параллелить

Главный вывод (уточнено): удаление состоит из двух подшагов, и параллелится только первый:
  • Удаление движений регистра ОбязательстваПоДС (запись набора по регистратору) — остаётся в пачке и параллелится вместе с начислением и PDF;
  • Удаление самого документа-регистратора ОперацияБух (.Удалить()) — выносится в конец и выполняется последовательно, после завершения всех фонов.
Именно удаление документа-регистратора (с проверкой ссылочной целостности) — узкое место, дающее взаимоблокировки при параллельном выполнении. Снятие движений по своему регистратору изолировано и параллелится штатно.

Технические факты по метаданным (подтверждены конфигурацией):

ФактСледствие
Документ.ОперацияБух: Posting = Deny, RegisterRecordsDeletion = AutoDeleteOff Удаление документа не снимает движения автоматически. Нужно отдельно записать пустой набор ОбязательстваПоДС по отбору регистратора, затем удалить сам документ. Это две операции записи на регистр.
У ОперацияБух один договор ДУ (основной реквизит) Фильтр строк набора по ДоговорДУ не нужен — очищается весь набор регистратора.
Удаление документа ОперацияБух проверяет ссылочную целостность и конкурирует за блокировки Несколько фонов, одновременно удаляющих документы-регистраторы, дают таймауты/взаимоблокировки. Снятие же движений по отдельному регистратору изолировано. Поэтому в пачке оставляем снятие движений, а .Удалить() документов — в финальную последовательную фазу. Ранее (черновой параллельный вариант, где удаление документа шло в фоне) это и стало источником сбоев.
Опыт предыдущего чернового прогона (ветка с пачками в ObjectModule.bsl) показал: когда удаление документа-регистратора выполняется внутри фоновых пачек, прогоны падают с ошибками транзакций и блокировок, а сводка получается неполной. Поэтому в текущем предложении в фоне остаётся только снятие движений, а удаление самих документов-регистраторов вынесено в отдельную последовательную фазу.

4. Целевая архитектура (TO-BE): три фазы

Команда Начислить (обычный режим, не расторжение) разбивается на три последовательные фазы. Внутри Фазы 2 работа идёт параллельно волнами пачек.

ФАЗА 0 Подготовка (главный сеанс). Выбрать уже заполнил ДоговорыДУКНачислению. Выгружаем ТЧ в таблицу, режем на пачки, фиксируем настройки шапки (Дата, Ставка, Счёт, Каталоги сохранения).
↓
ФАЗА 1 — ПАРАЛЛЕЛЬНО Начисление + PDF + снятие движений по пачкам. Каждая пачка договоров уходит в фоновое задание (ФоновыеЗадания.Выполнить("ДлительныеОперации.ВыполнитьПроцедуруМодуляОбъектаОбработки", ...)). В фоне по каждому договору пачки:
  1. создаётся и проводится документ НачислениеВознаграждения;
  2. формируется и сохраняется PDF-справка;
  3. снимаются движения регистра ОбязательстваПоДС по регистратору (запись набора).
Сам документ-регистратор ОперацияБух в фоне НЕ удаляется — его ссылка складывается в результат пачки для финальной фазы. Одновременно в памяти сервера крутится не более N = Константы.МаксимальноеКоличествоПараллельныхПотоков заданий (дирижёр запускает волнами и ждёт ФоновыеЗадания.ОжидатьЗавершенияВыполнения перед следующей волной). Каждая пачка возвращает результаты по договорам, признак успеха и список регистраторов к удалению.
↓ (дождались завершения ВСЕХ волн)
ФАЗА 2 — ПОСЛЕДОВАТЕЛЬНО Удаление документов-регистраторов ОперацияБух (главный сеанс). В одном потоке главного сеанса проходим по списку регистраторов, собранному из результатов пачек (движения по ним уже сняты в Фазе 1), и удаляем каждый документ: Регистратор.ПолучитьОбъект().Удалить(). Никакой конкуренции за блокировки — гонок больше нет.
Важно (корректность): в Фазе 2 нельзя повторно искать регистраторы запросом по регистру ОбязательстваПоДС — движения там уже сняты в Фазе 1, запрос вернёт пусто. Список регистраторов к удалению берётся только из результатов пачек, накопленных в Фазе 1.
↓
ФАЗА 3 Сводка. Собираем итоги всех пачек и фазы удаления, пишем в Журнал регистрации, показываем сообщение на форме (при ручном запуске) и опционально отправляем письмо (при регламентном запуске).
Режим расторжения (РежимРасторжения = Истина) не меняется: остаётся последовательным однопоточным вызовом с прежним УдалитьОбязательствоДС(..., Истина). Параллелизм включается только для обычного режима.

4.1. Почему такой раздел безопасен

  • Документы НачислениеВознаграждения по разным договорам независимы — их запись/проведение параллелится штатно (это же делает типовой механизм РегламентныеПериоды.СформироватьРегламентныеОперации).
  • PDF пишутся в разные файлы (имя файла зависит от договора) — конфликтов файловой системы нет.
  • Удаление документа-регистратора — единственная операция с общим «узким» ресурсом (проверка ссылочной целостности) — выполняется строго последовательно после завершения всех фонов; снятие же движений остаётся в фоне.

5.3. Сбор результатов пачек

Каждая фоновая пачка складывает результат (по каждому договору: создано ли начисление, сформирован ли PDF, сняты ли движения, ссылка на регистратор ОперацияБух к удалению, текст ошибки) во временное хранилище по своему адресу. Дирижёр после ОжидатьЗавершенияВыполнения читает результаты, объединяет их и формирует единый список регистраторов для Фазы 2 (удаление документов).

Надёжность передачи результата. Фон выполняется в отдельном сеансе, поэтому результат возвращается через временное хранилище. Чтобы он попадал туда всегда (в т.ч. при ошибке внутри пачки), всё тело фоновой процедуры оборачивается в Попытка…Исключение: в блоке Исключение ошибка фиксируется в структуру результата, и результат всё равно кладётся в хранилище. Дополнительно дирижёр после ОжидатьЗавершенияВыполнения проверяет Задание.Состояние и Задание.ИнформацияОбОшибке() — на случай, если фон упал «жёстко» и не успел записать результат; такие пачки помечаются в сводке как ошибочные. Отдельный дублирующий канал через Сообщить() не нужен.

6. Этап 2. Новая регламентная команда (4 раза в год)

Добавляется новая команда БСП с использованием ВызовСерверногоМетода (по образцу существующей команды «...ПриРасторжении...Фоновое»), которую можно назначить на регламентное задание.

6.1. Логика команды

  1. Проверка регламентной даты: запуск отрабатывает только если сегодня 1 января / 1 апреля / 1 июля / 1 октября (с флагом-настройкой «игнорировать проверку даты» для ручного тестового прогона).
  2. Определение периода и параметров начисления (пул «Розничное ДУ», ставка, счёт, каталоги сохранения) из настроек обработки.
  3. Вызов той же связки: ДоговорыКНачислению() → параллельное СоздатьНачисления() (Фаза 1) → последовательное удаление (Фаза 2).
  4. Итог: запись в Журнал регистрации и (опционально) письмо на адрес поддержки из настроек.
Расписание регламентного задания (настраивается администратором в конфигурации после регистрации обработки в справочнике «Дополнительные отчёты и обработки»): 4 отдельных срабатывания в год — 01.01, 01.04, 01.07, 01.10 в 00:15. Реализуется штатным механизмом расписания БСП для команд доп. обработок.

6.2. Реализация Этапа 2 — команда в той же обработке

Этап 2 реализуется командой внутри той же обработки внНачислениеВознаграждения_РозничноеДУ: добавляется новая команда "НачислениеВознагражденияРегламентноеФоновое", которая переиспользует фазовый движок Этапа 1 (параллельные пачки + финальное последовательное удаление документов-регистраторов).

Один объект, единая логика начисления/удаления, минимум дублирования кода. Никаких отдельных обработок-обёрток не создаётся — и ручной запуск с формы, и регламентный запуск идут через один и тот же движок.

        НачислитьПоследовательно();   // fallback
        Возврат "";
    КонецЕсли;

    ТаблицаДоговоров = ДоговорыДУКНачислению.Выгрузить();
    НастройкиШапки   = СобратьНастройкиШапки();  // Дата, Ставка, Счёт, Каталоги...

    ИтогиПачек = Новый Массив;
    Волна      = Новый Массив;

    // ФАЗА 1 — параллельно: начисление + PDF + снятие движений (без удаления документа-регистратора)
    Для Каждого Пачка Из РазбитьНаПачки(ТаблицаДоговоров, РазмерПачки) Цикл
        Задание = ЗапуститьПачкуВФоне(Пачка, НастройкиШапки);  // ДлительныеОперации...
        Волна.Добавить(Задание);
        Если Волна.Количество() >= N Тогда
            ФоновыеЗадания.ОжидатьЗавершенияВыполнения(МассивЗаданий(Волна));
            СобратьИтогиВолны(Волна, ИтогиПачек);
            Волна.Очистить();
        КонецЕсли;
    КонецЦикла;
    Если Волна.Количество() > 0 Тогда
        ФоновыеЗадания.ОжидатьЗавершенияВыполнения(МассивЗаданий(Волна));
        СобратьИтогиВолны(Волна, ИтогиПачек);
    КонецЕсли;

    // ФАЗА 2 — последовательно: удаляем ТОЛЬКО документы-регистраторы (движения уже сняты в фоне).
    // Список берём из результатов пачек, а не повторным запросом по регистру.
    СписокРегистраторов = РегистраторыИзИтоговПачек(ИтогиПачек);
    РезультатУдаления   = УдалитьРегистраторыПоследовательно(СписокРегистраторов);

    // ФАЗА 3 — сводка
    ТекстСводки = СформироватьСводку(ИтогиПачек, РезультатУдаления);
    ЗаписатьИОтправитьСводку(ТекстСводки);
    Возврат ТекстСводки;

9. Обработка ошибок, транзакции, отчётность

  • Изоляция ошибок: ошибка по одному договору не должна ронять всю пачку/прогон — ловим на уровне договора, фиксируем в сводке, продолжаем.
  • Транзакции в фоне: после исключения при записи/проведении сбрасывать возможную активную транзакцию (Пока ТранзакцияАктивна() Цикл ОтменитьТранзакцию() КонецЦикла;), иначе последующие операции пачки упадут.
  • Аварийное завершение фона: при сборке итогов проверять Состояние = ЗавершеноАварийно и ИнформацияОбОшибке; такую пачку помечать как ошибочную.
  • Правило удаления: движения снимаем и регистратор добавляем к удалению только по договорам с успешным начислением; в Фазу 2 попадают лишь такие регистраторы. Ошибка PDF не блокирует снятие движений/удаление (документ создан корректно).
  • Сводка: в Журнал регистрации (событие IMDEV-9153.НачислениеВознагражденияРозничноеДУ) — всего/успешно/с ошибками по начислениям, PDF, удалению; при ручном запуске — сообщение на форме; при регламенте — письмо.

10. Критерии приёмки

  1. В обычном режиме при N > 1 начисления и PDF по пачкам выполняются параллельно; одновременно активно не более N фоновых заданий.
  2. Снятие движений ОбязательстваПоДС выполняется в фоне (параллельно), а удаление документов-регистраторов ОперацияБух — после завершения всех фонов, в один поток, без ошибок блокировок.
  3. После прогона по каждому успешному договору: создан и проведён документ начисления, сформирован PDF, сняты движения ОбязательстваПоДС (Приход, пустое Основание) и удалён документ-регистратор ОперацияБух.
  4. Ошибка по одному договору не прерывает прогон и попадает в сводку.
  5. Режим расторжения работает как до доработки (регрессия).
  6. Новая регламентная команда запускается по расписанию (01.01/01.04/01.07/01.10, 00:15), в прочие даты — корректно завершается без начислений (кроме тестового флага).
  7. При N <= 1 или отключённых фонах отрабатывает последовательный fallback.
