IMDEV-9336 — Три ключевые операции сверки

Задача: IMDEV-9336 — «Проверить список ключевых операций на потребность в оптимизации».
База: Wim_Du (AvancoreDU). Эпик: IMDEV-8633. Оценка: 1 week. Статус на момент выгрузки: BA in progress.

Суть задачи: оценить три ежедневные сверки на предмет необходимости оптимизации производительности. Ниже — что это за объекты (внешние обработки), как работают и с чем взаимодействуют. Объекты 1–2: IMDEV-8927 / IMDEV-8471 (BSS). Объект 3: IMDEV-8274 (в списке 9336 назван «Сверка API сигнал vs Реестры платежей» — фактически это отчёт по отрицательным остаткам на аналитических счетах РДУ). Исходники и собранные EPF: ОРИГИНАЛЫ/.

1 Сверка с отчетом брокера

EPF В проде внСверкаCделокДУСОтчетомБрокера

Тип: дополнительная обработка (не отчёт ERF). Регистрация: «Сверка cделок ДУ с отчетом брокера». Вид БСП: ДополнительнаяОбработка.

ПолеЗначение
ФайлвнСверкаCделокДУСОтчетомБрокера.epf
Команда РЗФоновоеВыполнение — отчёт-рассылка сверки
Доп. командаФоновоеПроведение — проставление флага «подтверждена брокером» в документах
Расписание РЗежедневно 09:00, 10:00, 12:00:01 (svc_avancore)
Внешняя ИБSQL BrokerReports (AMDBRATES\DBMVTBAM01)

Что делает:

  • Берёт сделки ДУ за предыдущий рабочий день (календарь ММВБ).
  • Сравнивает их с данными брокерского отчёта, загруженными во внешнюю SQL-базу BrokerReports.
  • Формирует табличный документ с расхождениями (FAIL / WARN / OK).
  • Рассылает результат по списку e-mail (BSS, HNWI, AppSupport и др.).
  • Опционально (ФоновоеПроведение) проставляет в документах признак подтверждения отчётом брокера.
Поток: РЗ / форма → ВыполнитьКоманду → подключение SQL (ВнешниеИнформационныеБазы) → выборка сделок из ДУ + из BrokerReports → сверка → письмо + задача интеграции.

С чем взаимодействует:

  • Справочник ВнешниеИнформационныеБазы (BrokerReports)
  • Документы сделок ДУ (признак подтверждения брокером)
  • Справочник Календари (ММВБ) — дата сверки = пред. рабочий день
  • Учётные записи почты + список рассылки
  • Задачи ЗадачаИнтеграции (журнал выполнения)
  • Смежные EPF (не основной объект): внСверкаCделокДУСОтчетомБрокераРЕПОСберКИБ, внУстановитьПризнакПодтвержденаОтчетомБрокера

Тип: дополнительная обработка / отчёт-рассылка по ценным бумагам. Регистрация: «Сверка ценных бумаг». По ответу BSS: сверки только для индивидуального ДУ; для РДУ не применяются.

ПолеЗначение

Расписание РЗпн–пт 12:00 (в Excel ошибочно было 09:00)
Внешняя ИБпо умолчанию rates_view (AMDBRATES\DBMVTBAM01)

Что делает:

  • Собирает остатки ЦБ по договорам ДУ из регистров учёта (БУ / ВУ / УУ): РегистрБухгалтерии.Хозрасчетный, СтоимостьАктивовПоСделкамРЕПОУправленческий и др.
  • Сопоставляет с внешними данными по выпискам депозитария (через внешнюю ИБ).
  • Отмечает строки с расхождениями между контурами учёта и/или с выпиской.
  • Формирует табличный документ и рассылает отчёт («Аванкор ДУ: Отчет по сверке ценных бумаг», рассылка r240).
Поток: РЗ → ВыполнитьКоманду → запрос остатков по ЦБ в ДУ + данные выписок (внешняя ИБ) → сравнение → макет отчёта → e-mail.

С чем взаимодействует:

  • Регистры остатков ЦБ (хозрасчётный, управленческий, РЕПО)
  • Справочник ВнешниеИнформационныеБазы (данные депозитария / rates)
  • Справочник ДоговорДУ (фильтр по типу клиента — ИДУ)

Узкие (дополнительные) EPF — не заменяют внСверкаЦБ, но относятся к той же теме:

3 Сверка отрицательного остатка на р/с (пул РДУ)

EPF Код есть IMDEV-8274 внОтрицательныеОстаткиНаАналитическомСчете

Тип: дополнительная обработка (в UI — «Отчет отрицательные остатки по аналитическим счетам»). Раздел: Отчетность → Пользовательские обработки. Задача: IMDEV-8274 («Новая сверка для клиентов пула РД», статус Deploying to Prod; в UAT/GIT уже есть, на прод по комментариям +PROD 2026-07-14).

В списке IMDEV-9336 операция названа «Сверка API сигнал vs Реестры платежей» — устаревшая/ошибочная формулировка из старых материалов IMDEV-8471. Фактический объект — сверка минусов на аналитических счетах ДС по пулу «Розничное ДУ».

ПолеЗначение
ФайлвнОтрицательныеОстаткиНаАналитическомСчете.epf
Регистрация«Отчет отрицательные остатки по аналитическим счетам» (версия 1.1)
КомандаОткрытиеФормыОбработки — ручной запуск формы
ЭкспортСформироватьОтчет(ДатаОтчета)
Источник в WORKWim_Du/SRC/epf/внОтрицательныеОстаткиНаАналитическомСчете_epf
Связанная задачаповторные вводы в ДУ вынесены в IMDEV-9081 (отдельная обработка)

Что делает:

  • Ищет договоры пула «Розничное ДУ», у которых на счетах ДС сальдо Дт < 0 (минус на аналитическом р/с — типичный кейс: перевод на биржу без отражения ввода в ДУ).
  • Строит табличный документ: аналитический счёт, договор ДУ, конечный остаток (минус), валюта.
  • Данные — из РегистрБухгалтерии.Хозрасчетный.Остатки по счетам ДС, отбор ДоговорДУ.Пул = Розничное ДУ.
Поток: форма / СформироватьОтчет(Дата) → запрос остатков Хозрасчетный (счета ДС, пул РДУ, СуммаОстатокДт < 0) → вывод в макет «Макет» (шапка + строки).

С чем взаимодействует:

  • РегистрБухгалтерии.Хозрасчетный (остатки по ДС)
  • ПланСчетов.Хозрасчетный — счёт «ДС»
  • Справочник.Пул — «Розничное ДУ»
  • Справочник.ДоговорДУ (через отбор по пулу)
  • Макет табличного документа «Макет»

Анализ продовых замеров (июль–август 2026)

Источник: Замеры_СверкаСделокСОтчетомБрокера.xlsx (281 запись), Замеры_СверкаЦБ.xlsx (59 записей). Плановый порог из IMDEV-8927: 1800 с (0,5 ч) на ключевую операцию.

Методика с весом: абсолютное время само по себе некорректно сравнивать при разном объёме. Для сверки с брокером вес = число сделок из SQL (СделокИзSQL). Нормировка: с/сделку = время / вес, сделок/с = вес / время. Итоговая оценка — по абсолютному времени и по удельным показателям.

Сравнение команд при похожем медианном весе (~8,4 тыс. сделок): ФоновоеВыполнение ~100 с (~70 сделок/с), ФоновоеПроведение ~851 с (~9 сделок/с) — ~8× медленнее на сделку из-за цикла ПолучитьОбъект + Записать(Проведение). Выброс 46 мин при весе 10 210: 0,27 с/сделку (в ~18× хуже типичной сверки без записи). Дни с малым весом (134 сделки) дают «плохую» удельную скорость из-за фиксированных накладных (SQL, запрос, рассылка) — это не признак деградации алгоритма.

Вывод по п.1 (ФоновоеВыполнение): оптимизация не требуется. При типичном весе ~8 тыс. сделок медиана ~100 с (0,01 с/сделку, ~70 сделок/с). Даже при max весе 18 509 время 345 с — далеко от порога 30 мин. Рост времени объясняется объёмом, а не деградацией.
Замечание (вне основного РЗ 9336): ФоновоеПроведение при том же весе работает ~8× медленнее на сделку (медиана 0,11 с/сделку vs 0,01). Узкое место — массовая запись/перепроведение документов, а не сама сверка SQL. Кандидат на оптимизацию только если включать эту команду в scope.

2. Сверка остатков ЦБ с депозитарием

РЗ: ДУ.СверкаЦБ.Сверка.ФоновоеВыполнение.
Вес в коде всегда = 1 (замер не масштабируется по числу договоров/ЦБ). Поэтому «с/единицу» = абсолютное время; сравнивать throughput по весу нельзя — это ограничение качества замера, не показатель нагрузки.

Вывод по п.2: по абсолютному времени оптимизация не требуется (РЗ стабильно 2,8–4,8 мин, намного меньше 30 мин). Но вес=1 не даёт понять, растёт ли время с объёмом портфеля. Рекомендация на будущее: в замер ставить вес = число строк сверки / договоров — тогда можно будет оценивать удельную производительность.

3. Отрицательные остатки на р/с (IMDEV-8274)

Замеры с прода пока не предоставлены. В EPF нет блока ОценкаПроизводительности. После деплоя: вставить замер с весом = число найденных минусовых строк (или договоров в выборке).
