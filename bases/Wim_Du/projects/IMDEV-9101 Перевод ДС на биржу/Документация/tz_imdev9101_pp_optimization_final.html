IMDEV-9101 — Оптимизация проведения ПП (краткое ТЗ)

Массовое создание и проведение платежных поручений из обработки «Синхронизация НСИ» (перевод ДС на биржу, розничное ДУ). База WIM_DU.

Версия: краткая (финальная) Приоритет: P1 Дата: 13.07.2026

1. Цель и целевые метрики

Снизить время создания и проведения одного ПП в массовом режиме регламента, не меняя бизнес-результат (статусы документов, выгрузка CSV, проведение). Точка входа — внСинхронизацияНСИ.ПлатежныеПорученияРозничногоДУ → СоздатьПлатежноеПоручение.

135 → ≤95
мс на 1 ПП (создание+проведение)
~88 → ≤62
сек на 649 ПП (без удаления)
0
ошибок создания
до 10 000
ПП в день (целевая нагрузка)

База замеров: отчёт внТестППРозничногоДУ, период 01.07–13.07.2026, 649 ПП, 135,2 мс/ПП, 0 ошибок.

2. Что оптимизируем (два узких места)

# Узкое место Стоимость (на 649 ПП) Решение
P1-A Регистр ИсторияСтатусовОбъектов: ~5 запросов чтения статусов + 2 записи на каждое ПП ~68 сек В массовом режиме статус основания уже известен из отбора регламента — не перечитывать, писать статусы без предварительного чтения регистра
P1-B Синхронная регистрация выгрузки CSV (ОбъектыДляВыгрузкиВоВнешнюСистему) на каждое ПП ~20 сек Пропустить поштучную регистрацию в цикле; зарегистрировать все ПП одним пакетным вызовом после цикла
Вне задачи (P1): запрос отбора поручений (431 мс — незначимо), СоздатьПоручение / ЗаполнитьАналитикуПоДоговоруДУ (контур A), оптимизация Заполнить и шаблонов ПП (это P2). Прямые правки конфигурации WIM_DU запрещены.

3. Архитектура решения

Два артефакта поставки: расширение CFE IMDEV9101 (вся логика ускорения) и обновлённая EPF внСинхронизацияНСИ v0.69 (включает режим). Отдельный общий модуль не создаём — API размещаем в модуле менеджера Документ.ПлатежноеПоручение, область IMDEV9101_МассовоеСозданиеППРДУ.

3.1. Как это работает

  • EPF перед записью каждого ПП ставит флаги в ДополнительныеСвойства объекта (через API менеджера).
  • Расширение в обработчиках записи ПП читает флаги и идёт по «быстрому пути» (без лишних чтений статусов, с пропуском CSV).
  • EPF собирает ссылки созданных ПП в локальный массив и после цикла вызывает пакетную регистрацию CSV.
Почему ДополнительныеСвойства, а не флаг сеанса/глобальная переменная. Флаги привязаны к конкретному ПП, это стандартный приём 1С, они автоматически «умирают» после записи — не нужен ручной сброс и нет риска «залипания» при ошибке в середине цикла. Пакет CSV — обычная локальная переменная-массив в EPF, глобальное состояние не требуется.

3.2. Схема «сейчас / после»

СЕЙЧАС: EPF: СоздатьДокумент -> Заполнить -> Записать(Проведение) (ДопСвойства пустые) v CFG: 5 запросов к статусам + 2 записи статусов + 1 запись CSV — на КАЖДОЕ ПП ПОСЛЕ: EPF: МассивСозданныхПП = Новый Массив ЦИКЛ по поручениям: СоздатьДокумент -> Заполнить -> Документы.ПлатежноеПоручение.УстановитьФлагиМассовогоСоздания(...) -> Записать(Проведение) v CFE: 0 лишних чтений статусов, CSV пропущен (флаг на объекте) -> МассивСозданныхПП.Добавить(СсылкаПП) Документы.ПлатежноеПоручение.ЗарегистрироватьВыгрузкуCSVПакетом(МассивСозданныхПП)

4.1. Условия быстрого пути (нужны ВСЕ одновременно)

  1. ДополнительныеСвойства.МассовоеСозданиеППРозничногоДУ = Истина
  2. ЭтоНовый() — создаётся новое ПП
  3. ТипЗнч(ДокументОснование) = Тип("ДокументСсылка.Поручение")
  4. ДокументОснование.ВидОперации = ВидыОперацийПоручение.Перевод

Иначе (форма, ручное создание, другое основание) — полностью старая логика.

5. Логика ДО и ПОСЛЕ (главное — не сломать результат)

Суть оптимизации. Мы не отменяем бизнес-действия — мы убираем их дублирование. Текущий код написан под единичное интерактивное создание, где контекст неизвестен, поэтому он каждый раз перечитывает то, что в массовом режиме уже известно заранее. В массовом режиме статус основания = Новый, ПП новый, вид операции = Перевод — эти факты приходят из отбора регламента, повторное чтение из БД ничего не меняет. Конечное состояние базы после доработки идентично.

5.1. Таблица «действие → ДО → ПОСЛЕ → результат»

5.2. Ключевая мысль: убрать повтор, а не действие

СЕЙЧАС (дублирование): на каждое ПП: прочитать статус основания -> прочитать статус ПП -> перед записью в регистр снова прочитать регистр (x2) -> синхронно записать выгрузку CSV (одни и те же данные читаются по многу раз, хотя они уже известны) ПОСЛЕ (то же самое, но один раз): контекст известен заранее (флаги) -> записать статусы напрямую -> CSV собрать в массив и записать пакетом после цикла (лишних чтений нет; количество и содержание записей в БД не меняется)

5.3. Инварианты — что обязано остаться прежним

ИнвариантКак проверяем
Поручение-основание переходит в статус СформированоПлатежноеПоручение Сверка регистра статусов до/после на 20 документах + SQL
ПП получает статус КОплате и проводится Проверка проведённости и статуса созданных ПП
Число записей в ИсторияСтатусовОбъектов совпадает Счётчик записей регистра на одинаковом наборе поручений
Все созданные ПП зарегистрированы к выгрузке CSV (ровно один раз) Сверка количества с ОбъектыДляВыгрузкиВоВнешнюСистему, контроль отсутствия дублей
Интерактивное/единичное создание ПП работает как раньше Ручной регресс в форме (флаги не выставляются — старый путь)
На что обратить внимание при реализации (чтобы не «сломать»):
  • Пакет CSV в той же транзакции/серверном вызове. Регистрацию выгрузки завершаем до возврата из ПлатежныеПорученияРозничногоДУ — иначе CSV-регламент может стартовать раньше.
  • Ошибка в середине цикла. Флаги живут только на одном объекте; уже созданные ПП нужно зарегистрировать для CSV даже при обрыве (регистрация пакетом по фактически созданным ссылкам).
  • Коллизия дат в регистре статусов при пакетной записи — сохранить инкремент даты, как в текущем СохранитьТекущийСтатусОбъекта.
  • Только целевой сценарий. Быстрый путь включается лишь при всех условиях из п. 4.1; любой другой случай идёт по старой логике без изменений.
