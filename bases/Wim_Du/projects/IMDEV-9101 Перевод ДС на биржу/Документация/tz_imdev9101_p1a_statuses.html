IMDEV-9101 — ТЗ P1-A: оптимизация статусов при создании ПП

Только P1-A: убрать дублирующие чтения ИсторияСтатусовОбъектов при массовом создании ПП. Логика включения режима — во внешней обработке; в расширении — минимум кода (только то, что нельзя сделать из EPF).

Scope: только статусы CFE: минимальный Основное — EPF 13.07.2026

1. Цель

Снизить время проведения нового ПП в массовом режиме РДУ за счёт устранения лишних чтений регистра статусов — без отмены бизнес-записей статусов. Максимально вынести изменения во внешнюю обработку внСинхронизацияНСИ, чтобы Avancore потом перенёс в базовую конфигурацию минимальный объём из расширения.

3. Проблема (почему дорого)

При СоздатьПлатежноеПоручение → Записать(Проведение) на каждое новое ПП срабатывает цепочка в модуле объекта ПлатежноеПоручение.

ДО (1 успешное ПП РДУ): ПередЗаписью [Q1] ПолучитьАктуальныйСтатус(ПП) — пусто (документ новый) [Q2] ПолучитьАктуальныйСтатус(Поручение) — проверка TM-3447 (= Новый) ПриЗаписи (КОплате <> пусто) ИзменитьСтатусДокОснования...(ПП, КОплате) [Q3] ПолучитьАктуальныйСтатус(Поручение) — дубль Q2 СохранитьТекущийСтатус(Поручение, ...) [Q4] ПолучитьСтатусОбъектаНаДату(Поручение) — только ради Периода [W1] Записать статус Поручения СохранитьТекущийСтатус(ПП, КОплате) [Q5] ПолучитьСтатусОбъектаНаДату(ПП) — только ради Периода [W2] Записать статус ПП ИТОГО: 5 чтений + 2 записи

Что обязано остаться:

  • Поручение: Новый → СформированоПлатежноеПоручение
  • ПП: пусто → КОплате

4. Принцип доработки

Не отменяем действия — убираем дублирование чтений. EPF передаёт контекст флагами; CFE в обработчиках записи использует этот контекст и пишет те же 2 статуса напрямую через МенеджерЗаписи регистра, без вызова ПолучитьАктуальныйСтатус / СохранитьТекущийСтатусОбъекта (которые сами делают лишние чтения).

Отбор ПлатежныеПорученияРозничногоДУ не фильтрует по статусу поручения; флаг статуса основания передаёт EPF. Без флагов — полный старый путь (форма, ручное создание).

8. Тестовый отчёт внТестППРозничногоДУ — два режима и сравнение

Источник: Тестирование/erf_test_pp_rdu_erf/внТестППРозничногоДУ.xml (модуль объекта + форма). Нужен не просто «зеркальный» прогон, а сравнительный бенчмарк на одном и том же наборе поручений.

8.1. Два режима создания ПП

РежимКак работаетСмысл
A. Как было
(без доп. свойств)		 В СоздатьПлатежноеПоручение флаги не ставятся. CFE идёт по старому пути (5 чтений + 2 записи статусов) Baseline — поведение до оптимизации
B. Как стало
(с доп. свойствами)		 Перед Записать(Проведение) ставятся МассовоеСозданиеППРозничногоДУ и СтатусОснованияИзвестен. При подключённом CFE — быстрый путь (0 чтений + 2 записи) Оптимизированный контур P1-A

8.2. Требования к прогону

  • Один запуск отчёта прогоняет оба режима подряд на одном и том же списке поручений (один отбор, одна дата расчёта, один лимит количества).
  • Порядок: сначала режим A («как было»), затем режим B («как стало») — либо наоборот, но фиксированный и документированный на форме.
  • Перед каждым режимом — одинаковая подготовка (как сейчас в тесте производительности: удаление ранее созданных ПП по отобранным поручениям, если включено пересоздание).
  • Замеряется по каждому режиму отдельно: время блока создания (без учёта удаления в сравнении «бой»), число ПП, число ошибок, мс/ПП, общее время создания.
  • После каждого режима — снятие фактических статусов из ИсторияСтатусовОбъектов по созданным ПП и их поручениям-основаниям (см. п. 8.4).
  • После двух прогонов — блок сравнения времени и блок сравнения статусов (А vs B) в табличном документе и в сообщениях.

8.3. Что показать в отчёте (сравнение времени)

ПоказательРежим AРежим BДельта

Относительный выигрыш — — (T_A − T_B) / T_A × 100%

8.4. Сравнение статусов «было / стало» (обязательно)

Цель: доказать, что оптимизация не меняет бизнес-результат — те же статусы, что и в режиме без флагов.

Что снимать после каждого режима (по всем успешно созданным ПП):

ОбъектОжидаемый актуальный статусИсточник
Документ.Поручение (основание) СформированоПлатежноеПоручение ИсторияСтатусовОбъектов (срез последних)
Документ.ПлатежноеПоручение КОплате ИсторияСтатусовОбъектов (срез последних)

Как сравнивать A и B:

  • По каждому поручению из отбора: статус основания после A = статус основания после B.
  • По каждому созданному ПП: статус ПП после A = статус ПП после B (сопоставление по ДокументОснование, т.к. ссылки ПП разные в двух прогонах).
  • Оба режима должны совпасть с инвариантами выше (не только «A = B», но и «правильные значения»).
  • В отчёте — сводка: сколько строк совпало / сколько расхождений; при расхождениях — детальная таблица (Поручение, СтатусОснования_A, СтатусОснования_B, СтатусПП_A, СтатусПП_B).
  • Приёмка P1-A: 0 расхождений по статусам при 0 ошибок создания.
Практическая схема: после режима A сохранить таблицу значений {Поручение, СтатусОснования, СтатусПП}; после режима B — такую же; сверить по ключу Поручение. Удаление ПП между режимами статусы поручений вернёт/сбросит по старой логике отмены — поэтому снимок статусов делать сразу после создания в каждом режиме, до удаления под следующий прогон.
UI: на форме отчёта — переключатель/флаг, например СравнительныйПрогонP1A (по умолчанию включён для замера). Либо всегда двойной прогон в режиме теста производительности. Текущий реквизит РежимТестаПроизводительности сохраняется; внутри него добавляется логика двух проходов + сверка статусов.

8.5. Схема прогона

СформироватьНаСервере (сравнительный режим): 1. Отбор поручений (один раз) 2. РЕЖИМ A «как было» - удаление ПП (если пересоздание) - цикл: СоздатьПлатежноеПоручение БЕЗ доп. свойств - замер T_A, ошибок, мс/ПП - снимок статусов_A (Поручение + ПП) <- до удаления к режиму B 3. Если CFE не подключено, режим B по времени будет близок к A (флаги есть, но быстрого пути нет) — это само по себе показывает, что выигрыш даёт расширение, а не «магия» флагов. 9. Приёмка — что должен показать тестовый отчёт

Единственный источник для решения «принято / не принято» по P1-A — сравнительный прогон внТестППРозничногоДУ на одном наборе поручений (режимы A «как было» и B «как стало», CFE подключено). Ниже — что именно отчёт обязан вывести, чтобы было видно: 1) регресса нет и 2) скорость выросла.

9.1. Нет регресса (бизнес-результат не сломан)

Отчёт считается успешным по регрессу, если одновременно видно:

Что показывает отчётКритерий «ОК»
Число успешно созданных ПП в режиме A и в режиме B Одинаковое число; оба > 0
Число ошибок создания в A и в B 0 и 0
Сводка сравнения статусов A vs B Расхождений = 0 (по всем поручениям из отбора)
Ожидаемые статусы после создания (и в A, и в B) Поручение = СформированоПлатежноеПоручение; ПП = КОплате
Таблица расхождений статусов (если есть) Пустая / не выводится; иначе — FAIL
Вывод без регресса: «Создано одинаково, ошибок нет, статусы A = B и совпадают с инвариантами» — оптимизация не отменила и не исказила статусы.

9.2. Скорость увеличена (выигрыш по времени)

Отчёт считается успешным по скорости, если одновременно видно:

Что показывает отчётКритерий «ОК»
Общее время создания, мс — режим A (без флагов) Baseline T_A
Общее время создания, мс — режим B (с флагами + CFE) T_B < T_A
Дельта общего времени T_A − T_B Положительная (экономия мс на весь прогон)
Среднее мс/ПП в A и в B мс/ПП_B < мс/ПП_A; ориентир экономии ~30–40 мс/ПП
Относительный выигрыш, % (T_A − T_B) / T_A × 100% > 0; явное число в отчёте
Вывод по скорости: «Режим B быстрее режима A на X мс (Y мс/ПП, Z%)» — при тех же статусах и том же числе документов. В сравнении «бой» смотреть время создания, без блока тестового удаления.

9.3. Итоговый вердикт на первой странице отчёта

В шапке / блоке итогов отчёт должен вывести однозначные строки (пример формулировок):

РЕГРЕСС:   OK — ПП A=B, ошибок 0/0, расхождений статусов 0
СКОРОСТЬ:  OK — создание B быстрее A на .... мс (.... мс/ПП, ....%)
ВЕРДИКТ:   ПРИНЯТО  /  НЕ ПРИНЯТО

ПРИНЯТО — только если оба блока OK. Если статусы разошлись или T_B ≥ T_A — НЕ ПРИНЯТО, даже если «кажется быстрее».

9.4. Дополнительно (не заменяет отчёт)

  • Ручное создание ПП в форме — без флагов, старый путь, регресс UI.
