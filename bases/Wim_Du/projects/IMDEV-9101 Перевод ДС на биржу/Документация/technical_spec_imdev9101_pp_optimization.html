ТЗ: IMDEV-9101 — оптимизация массового создания ПП розничного ДУ (P1)

Техническое задание на доработку производительности этапа ПлатежныеПорученияРозничногоДУ / СоздатьПлатежноеПоручение. База: WIM_DU. Версия EPF: 0.68 -> 0.69.

Jira: IMDEV-9101 Приоритет: P1 Дата ТЗ: 13.07.2026 Baseline: 135 мс/ПП Цель: 70-95 мс/ПП

Краткий ответ: расширение и обработка

Да, нужно расширение конфигурации (CFE).
Основная логика P1 затрагивает объекты метаданных WIM_DU, которые нельзя менять «в лоб» в типовой/боевой поставке: Документ.ПлатежноеПоручение, РегистрСведений.ИсторияСтатусовОбъектов, ОбщийМодуль.ОбработкаСобытийВыгрузкаCSVВоВнешнюСистему.
Да, обработку внСинхронизацияНСИ (EPF) тоже нужно доработать — минимально.
Расширение не может изменить код внешней обработки. EPF — единственная точка вызова СоздатьПлатежноеПоручение в регламенте. Без EPF расширение не узнает, что идёт массовое создание ПП розничного ДУ, и оптимизация не включится.

1. Основание и цель

Основание: замеры отчета внТестППРозничногоДУ (649 ПП, 13.07.2026): 135,2 мс/ПП на создание, ~88 сек без удаления. Узкие места: регистр статусов (~68 сек) и CSV-регистрация (~20 сек на PFF).

Цель: снизить время создания 1 ПП до 70-95 мс в массовом режиме регламента без изменения бизнес-результата (статусы документов, выгрузка CSV, проведение ПП).

Целевая нагрузка: до 10 000 ПП/день; вместимость одного прохода регламента (120 сек) — с ~888 до ~1 200-1 600 ПП.

1.1. Scope (входит в задачу)

  • P1-A: оптимизация цепочки ИсторияСтатусовОбъектов при массовом создании ПП
  • P1-B: отложенная/пакетная регистрация ОбъектыДляВыгрузкиВоВнешнюСистему
  • Минимальные правки EPF для активации массового режима
  • Зеркальные правки ERF для регрессионных замеров

1.2. Out of scope (не входит)

  • Оптимизация СоздатьПоручение / ЗаполнитьАналитикуПоДоговоруДУ (контур A)
  • Оптимизация запроса отбора поручений (431 мс — незначимо)
  • Оптимизация Заполнить / шаблонов ПП (P2, отдельная задача)
  • Изменение логики синхронизации с ДО, кроме точек вызова СоздатьПлатежноеПоручение

2.4. Словарь флагов

Флаги — это не реквизиты метаданных и не константы. Это временные значения в коллекции ДополнительныеСвойства объекта документа ПлатежноеПоручение. EPF выставляет их перед Записать(Проведение), расширение читает внутри обработчиков записи. В базу не сохраняются, живут только на время одной записи.

2.4.2. Пакет CSV: без «флага сеанса»

Отказ от идеи «ПакетАктивен» в общем модуле. Отдельный глобальный флаг сеанса не нужен и плохо объясняется: непонятно, кто его сбрасывает при ошибке в середине цикла.

Как делаем вместо этого (рекомендуется):

  • EPF в ПлатежныеПорученияРозничногоДУ держит локальный МассивСозданныхПП = Новый Массив — обычная переменная процедуры.
  • На каждое успешное создание: МассивСозданныхПП.Добавить(СсылкаПП).
  • После цикла: Документы.ПлатежноеПоручение.ЗарегистрироватьВыгрузкуCSVПакетом(МассивСозданныхПП) — экспорт из модуля менеджера ПП (расширение).

Пока идёт цикл, на каждом ПП стоит только флаг ПропуститьРегистрациюВыгрузкиCSV в ДополнительныеСвойства — подписка CSV молчит. В конце EPF один раз регистрирует все ссылки.

2.4.3. Что уже есть в WIM_DU для «глобальных» данных (и почему не используем)

В конфигурации есть механизмы хранения служебного состояния на время сеанса. Для P1 они не требуются, но полезно понимать контекст:

2.4.4. Условия активации быстрого пути (все одновременно)

Расширение переключается на оптимизированную логику только если выполняются все условия:

  1. ДополнительныеСвойства.МассовоеСозданиеППРозничногоДУ = Истина
  2. ЭтоНовый() — создаётся новое платежное поручение
  3. ТипЗнч(ДокументОснование) = ДокументСсылка.Поручение
  4. ДокументОснование.ВидОперации = Перевод

Если хотя бы одно условие не выполнено — полностью старая логика (форма, ручное создание, другие основания).

2.4.9. Почему не параметр сеанса и не глобальная переменная

Способ Недостаток
Параметр сеанса Сложнее гарантировать сброс; может повлиять на посторонний код в том же сеансе

4. Требования к EPF внСинхронизацияНСИ

EPF дорабатывается минимально: не переносить бизнес-логику статусов в EPF. EPF только включает режим и собирает ссылки для пакетной CSV-регистрации.

Для единичного создания ПП при новом договоре:

  • Флаги в СоздатьПлатежноеПоручение уже сработают автоматически
  • CSV: после создания одного ПП — ЗарегистрироватьВыгрузкуCSVПакетом с массивом из одной ссылки (или пропустить вызов, если расширение при единичном ПП не откладывает CSV)
