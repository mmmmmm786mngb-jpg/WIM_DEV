1.3. Что в тексте запроса лишнее по скорости (логику не трогаем)

  1. Соединение с НачислениеЗадолженности при виде Перевод - в ветке ГДЕ для Перевода не используется, таблица читается вхолостую.
  2. Столбец НачислениеЗадолженности.Ссылка во ВТ - в третий пакет не идет.
  3. ЛЕВОЕ СОЕДИНЕНИЕ со всеми поступлениями по ПлановаяПозиция, затем ЕСТЬ NULL. Тот же смысл «нет проведенного поступления» дешевле записать как НЕ Ссылка В (подзапрос). В подзапросе тот же отбор, что сейчас: только Проведен, без новых условий.
  4. Торговые коды по договору без счета ДС в ПО - для Перевода условие счета уже есть в ГДЕ, его нужно перенести в ПО, чтобы не соединять лишние коды.
  5. Один текст с ВЫБОР по виду операции - те же две ветки, но двумя текстами оптимизатору проще. Поля ВЫБОР в списке выборки для каждого вида раскрыть в константы этой ветки (для Перевода сразу Поручение.ДоговорКонтрагента и т.д.).
Дубли строк соединений Лишние соединения могут размножить одну ссылку поручения в ВТ. Это не отдельное бизнес-правило, а цена текущего текста. После переноса условий в ПО и отказа от ненужных таблиц уникальный набор поручений должен совпасть с текущим. Оператор РАЗЛИЧНЫЕ не добавлять: он менял бы состав, если два торговых кода дают две строки при одном счете ДС - сейчас так и будет.

1.5. Что оптимизировать вокруг запроса (код процедуры, не текст запроса)

Заполнение ТЧ Цикл Выборка.Следующий() + Добавить() + ЗаполнитьЗначенияСвойств ТЧ.Загрузить(РезультатЗапроса.Выгрузить()). Имена колонок уже совпадают с реквизитами ТЧ.
ОбщегоНазначенияДУ.ДобавитьВЛогОтладки Вызов перед Выполнить(). При включенном логе отладки модуль ДУ может выполнить запрос еще раз. Оставить вызов, но не добавлять второй ручной Выполнить() «для лога». На нагрузочном прогоне лог отладки выключить.
Индекс CF на ПлановаяПозиция DontIndex Не блокер EPF. Отдельное согласование с типовой. В 9202 в обработке достаточно НЕ Ссылка В (подзапрос по Проведен).

1.6. Что в запросе трогать нельзя

  • Новые отборы: комментарий, период, пометка удаления, проведение поручения, проведение начисления.
  • Пул, вид операции, статус Новый через срез регистра.
  • Для Перевода: источник = счет ДС торгового кода, приемник на ЕРС.
  • Пропуск поручений, по которым есть проведенное поступление по плановой позиции (только признак Проведен, как сейчас).
  • Для ВводВДУ: правило флага НДФЛ и контрагента НДФЛ; соединение торговых кодов только по договору.
  • Состав колонок ТЧ.

2. Раздел 2. Диспетчер чанков в СоздатьПоступленияДС

После исправленной начитки узкое место - цикл СоздатьПоступленияДС: на каждую строку ТЧ вызывается Поступление() (создание, УстановитьНовыйНомер, проверка заполнения, Записать(Проведение) с БУ+ВУ+УУ). До ~20 000 отдельных проведений в одном серверном вызове.

Задумка раздела 2 Не плодить 20 000 фоновых заданий и не копировать пул IMDEV-9096. Взять скользящее окно из IMDEV-8663: очередь порций, одновременно работает не больше N заданий, внутри задания - тот же Поступление() по строкам порции. Минимум новых методов. ПорученияПоДС остается последовательным.

2.3. Почему запуск не как в 8663 один в один

В IMDEV-8663 диспетчер делает ФоновыеЗадания.Выполнить("ОбщегоНазначения.ВыполнитьБПБезопасно", ...), а обёртка вызывает метод модуля менеджера конфигурации. Методы внешней обработки платформа в ФоновыеЗадания.Выполнить не принимает.

Для EPF в этой базе уже проверен путь IMDEV-9096:

  • ДлительныеОперации.ВыполнитьПроцедуруМодуляОбъектаОбработки + ссылка ДополнительныеОтчетыИОбработки (реквизит ДополнительнаяОбработка у нашей EPF уже есть, при пустой ссылке - поиск по ИмяОбъекта = "ПоступленияНаРасчетныйСчет_РозничноеДУ");
  • ожидание в том же серверном вызове (кнопка выписок и так ждет возврата СоздатьПоступленияДС);
  • статус задания - ДлительныеОперации.ОперацияВыполнена(Идентификатор, Ложь). Не использовать ЗаданиеВыполнено: при аварии она делает исключение и роняет весь пул.

Скользящее окно - как в 8663, транспорт запуска - как в 9096 для внешней обработки. Новый «оркестратор групп выписок» не делать.

2.5. Контракт воркера СоздатьПоступленияДСПоЧанку

  • Вход: массив структур с полями строки ТЧ (минимум те, что читает Поступление(): поручение, договор ДУ, сумма ДС, аналитические счета, контрагент, договор/счет контрагента, номер ДУ) плюс структура Настройки и скаляры объекта, которые сейчас читаются из реквизитов (ДатаПоступления, ЕРС).
  • Внутри: последовательный цикл, вызов существующего Поступление(). Вложенный диспетчер не запускать.
  • Выход в временное хранилище: массив структур ПоручениеПоДС + ПоступлениеНаРасчетныйСчет (пустая ссылка, если проведение не удалось - как сейчас).
  • Сообщения об ошибках проведения - через существующий ОбщегоНазначенияДУКлиентСервер.СообщитьОбОшибке; диспетчер после завершения чанка выводит сообщения сеанса задания в текущий сеанс.
Передача данных в фон Параметры процедуры модуля объекта уходят через инфраструктуру доп. обработок. Структуры/массивы допустимы. Не тащить в фон весь объект обработки с двумя ТЧ на 20 000 строк: только порция до 50 структур и настройки шапки.

2.6. Безопасный режим и нумерация

СведенияОВнешнейОбработке: сейчас БезопасныйРежим = Истина Поставить Ложь. Проведение поступления с БУ+ВУ+УУ в фоне в безопасном режиме внешней обработки, как правило, падает. После смены версии (например 1.05) обработку перерегистрировать в справочнике доп. обработок.
УстановитьНовыйНомер() в каждом Поступление() Оставить. Параллельные чанки могут сериализоваться на нумераторе - это ограничение платформы, не чинить отдельным механизмом в 9202. Окно N все равно ускоряет проведение (основное время не номер, а движения БУ/ВУ/УУ).
Файловая ИБ Параллельности нет. Ветка «N <= 1 / файловая» идет в текущий цикл. На WIM_DU (клиент-сервер) - окно N.

2.7. Чего не делать в разделе 2

  • Не выносить ПорученияПоДС в фон.
  • Не делать одно ФЗ на одно поручение.
  • Не менять Поступление() ради «пакетного проведения» (одна транзакция на 50) - вне минимального объема; риск отката 50 документов из-за одного.
  • Не трогать копирование строк в форму выписок после создания (это UI выписок, не эта EPF).
  • Не добавлять клиентский ПодключитьОбработчикОжидания: ждать внутри серверного СоздатьПоступленияДС.

3. Критерии приемки

Раздел 1

  • На одном и том же стенде набор ссылок поручений после начитки совпадает с v1.04 (тот же пул, ЕРС, вид операции). Допустимо: меньше технических дублей, если они шли только от соединений, которые не участвуют в ГДЕ.
  • Колонки ТЧ и заполнение Поступление() без изменений.
  • ВводВДУ: при выключенном флаге НДФЛ начисление не требуется; при включенном без начисления по контрагенту НДФЛ строка не попадает - как сейчас.
  • Замер: время ПорученияПоДС меньше, чем на той же базе до правки (ориентир - журнал замера / лог отладки выключен).

Раздел 2

  • При МаксПараллельныхЧанков = 0 или 1 результат по ссылкам в ТЧ совпадает с текущим последовательным циклом (на одной и той же начитке).
  • При N > 1 на клиент-сервере в консоли заданий видно не больше N одновременных заданий этой обработки; каждое обрабатывает до 50 документов; последнее может быть короче.
  • После возврата СоздатьПоступленияДС все чанки завершены, в ТЧ проставлены ссылки созданных поступлений (или пустая ссылка по ошибке строки, без обрыва всего пакета).
  • Кнопка «Зачисления на р/с» в выписках по-прежнему вызывает те же два экспорта, без доработки выписок.
  • Ручной путь формы EPF («Начитать» / «Создать») работает с тем же диспетчером.

4. Вне скоупа

  • Новые отборы в ПорученияПоДС: комментарий, период, пометка удаления.
  • TIBCO / макет WSDL / кнопка «Прочитать» выписок.
  • Кнопка «Разобрать отмеченные», КлиентБанк, пул МаксПараллельныхГрупп (IMDEV-9096).
  • Создание поручений (это «Оплата КЗ по клиентам РДУ»).
  • Индекс на ПлановаяПозиция в CF - отдельное согласование с типовой, не условие сдачи EPF.
  • Параллельная начитка запроса.
  • Сценарий ВводВДУ как целевой объем оптимизации (только не сломать).
