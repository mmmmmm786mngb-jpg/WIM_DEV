## 1. Выводы замера (19.08.2026)

### 1.1. Условия

- Дата операции: **17.08.2026**
- Вид операции поручения: **Перевод**
- Объем: **45** поступлений (кнопка «Создать» на форме EPF)
- Профиль: `Тестирование/Замеры_45_17082026_Было.pff`
- Пользователь / сеанс: Admin, AVC_PP_DU

### 1.2. Иерархия в замере

| Уровень | Строка EPF | Операция | Вызовов | Время |
|---------|------------|----------|---------|-------|
| Корень | цикл «Создать» | весь прогон | 45 | **~14,0 сек** |
| Узкое место | **299** | `Поступление.Записать(РежимЗаписиДокумента.Проведение)` | 45 | **~13,6 сек (~97%)** |
| Заполнение | ~261 | реквизиты документа | 45 | ~0,15 сек (~1%) |
| Проверка | ~291 | `ПроверитьЗаполнение()` | 45 | ~0,22 сек (~1,5%) |

**Среднее на один документ при проведении: ~302 мс.**

Код узкого места (без изменений в v1.04):

```bsl
// ПоступлениеНаРасчетныйСчет_РозничноеДУ, функция Поступление(), строка 299
Поступление.Записать(РежимЗаписиДокумента.Проведение);
```

### 1.3. Куда уходит время внутри проведения

Агрегация по модулям внутри 45 вызовов `Записать(Проведение)`:

| Доля | Модуль | Смысл |
|------|--------|-------|
| ~23% | `ИсторияСтатусовОбъектов` | статус поступления «Проведен», поручению «Исполнено» |
| ~23% | `ВыгрузкаДУFinance` | регистрация изменений в плане обмена |
| ~14% | `ЗначенияПараметровДоговораДУ` | чтение параметров в `ОбработкаПроведения` |
| ~10% | `ПоступлениеНаРасчетныйСчет.МодульОбъекта` | логика проведения документа |
| ~9% | `БухгалтерскийУчет` | проводки и движения |

Ускорить «внутренности» одного проведения в рамках EPF **нельзя** (это код конфигурации и подписок платформы). Ускорение достигается **параллельным выполнением N независимых проведений** в разных сеансах.

### 1.4. Что не является узким местом на замеренном объеме

- Запрос `ПорученияПоДС` — выполняется **один раз** до цикла «Создать»; на 45 документах не попадает в топ профиля.
- Заполнение реквизитов и `ПроверитьЗаполнение()` — пренебрежимо мало.

> **Примечание.** Оптимизация запроса `ПорученияПоДС` остается актуальной для кнопки «Начитать» при **тысячах** поручений в день (ориентир: снимок `Тестирование/IM9202_receipts_2026-08-11 БЫЛО`, 5052 док.). Для сценария «Создать» приоритет смещен на параллельное проведение.

## 2. Цель и границы (v2)

### 2.1. Цель

Сократить **wall-clock время** массового создания поступлений (`СоздатьПоступленияДС`) за счет параллельного вызова функции `Поступление()` в фоновых заданиях.

### 2.2. Не меняем

- Состав и логику отбора поручений (`ПорученияПоДС`) — условия v1.04 заморожены.
- Сигнатуры экспорта: `ПорученияПоДС(ВидОперации)`, `СоздатьПоступленияДС(ВидОперации)`.
- Алгоритм заполнения одного поступления в `Поступление()` (реквизиты, виды операций, проверки).
- Интеграцию с `ЗагрузкаВыписок`, TIBCO, кнопку «Разобрать отмеченные».
- Имя объекта в справочнике доп. обработок.

### 2.3. Меняем

- `СоздатьПоступленияДС` — диспетчер параллельных пачек вместо последовательного цикла (при достаточном объеме).
- Модуль объекта EPF — фоновый воркер для одной пачки поручений.
- `СведенияОВнешнейОбработке` — `БезопасныйРежим = Ложь` (как в тестовой EPF сброса).
- Форма EPF — настройки параллелизма (число потоков, размер пачки), индикация прогресса / лог.

## 3. Техническое решение

### 3.1. Единица параллелизма

**Одна строка ТЧ = один вызов `Поступление(ПоручениеПоДС, Настройки)`**, внутри которого:

1. создается и заполняется документ;
2. выполняется `Записать(Проведение)`.

Параллелить имеет смысл **только этот вызов**, обернутый диспетчером в `СоздатьПоступленияДС`.

### 3.2. Архитектура (по аналогии с тестовой EPF)

Эталон реализации: `Тестирование/test_reset_receipts_epf/внТестСбросПоступленийРДУ` (удаление поступлений, v1.09).

```
СоздатьПоступленияДС(ВидОперации)
  |
  +-- Настройки = Настройки(ВидОперации)   // один раз
  +-- ТЧ = ПорученияПоДС | ПорученияПоДСВвод
  |
  +-- Если ТЧ.Количество() <= ПорогПоследовательно
  |     -> последовательный цикл (как сейчас)
  |
  +-- Иначе
        -> ДлительныеОперации / фоновые задания
        -> N потоков, пачки по M строк
        -> воркер: СоздатьПачкуПоступленийВФоне(массив структур строк ТЧ + Настройки + контекст формы)
              для каждой строки: Поступление(...); записать ссылку в результат
```

### 3.3. Параметры по умолчанию

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| `КоличествоПотоков` | 12 | как в тестовой EPF удаления |
| `РазмерПачки` | 50 | документов на одно фоновое задание |
| `ПорогПоследовательно` | 10 | ниже порога — без накладных расходов на фон |

Значения выносить в реквизиты формы / хранилище настроек EPF.

### 3.4. Передача данных в фон

В фон передавать **сериализуемые** данные:

- массив структур с полями строки ТЧ (ссылка поручения, договор, суммы, счета и т.д.);
- структура `Настройки` (ВхНомер, СтатьяДДС, …);
- `ДатаПоступления`, `ЕРС`, `ВидОперации`.

Не передавать объект формы целиком. Результат пачки — массив `{Поручение, ПоступлениеНаРасчетныйСчет, Ошибка}`.

### 3.5. Обновление ТЧ на форме

После завершения всех пачек — одним проходом заполнить колонку `ПоступлениеНаРасчетныйСчет` в ТЧ по ключу `ПоручениеПоДС`. Ошибки по строкам — в лог / колонку «Комментарий» (если есть) или сообщения пользователю.

### 3.6. Регистрация в доп. обработках

Обязательна регистрация EPF в `Справочник.ДополнительныеОтчетыИОбработки` с совпадением `ИмяОбъекта = ПоступленияНаРасчетныйСчет_РозничноеДУ` — иначе `ДлительныеОперации.ВыполнитьПроцедуруМодуляОбъектаОбработки` недоступен.

### 3.7. Риски и ограничения

| Риск | Митигация |
|------|-----------|
| Блокировки при проведении | Поручения независимы (1 поступление на 1 поручение); мониторинг на прогоне 5000+ |
| `УстановитьНовыйНомер()` в параллели | Нумерация в разных сеансах; при коллизиях — повтор / лог |
| Рост нагрузки на СУБД | Ограничить `КоличествоПотоков` настройкой; старт с 8–12 |
| Безопасный режим | Отключить для EPF в `СведенияОВнешнейОбработке` |
| Регресс данных | JSON-снимки тестовой EPF до/после |

## 4. Раздел «ПорученияПоДС» (пониженный приоритет)

Оптимизация запроса начитки **не отменяется**, но выносится во **вторую очередь**:

- выполнять после внедрения параллельного «Создать»;
- отдельный замер кнопки «Начитать» на дате с большим объемом (11.08.2026, ~5000 поручений);
- критерий: время `ПорученияПоДС` меньше baseline при том же результате ТЧ.

Логика отбора — без изменений (как в v1.04 и тестовой EPF сброса).

## 5. Критерии приемки

### 5.1. Функциональность

- [ ] После «Начитать» + «Создать» состав поступлений совпадает с baseline (JSON-снимок тестовой EPF, ключ `ДоговорДУКод + ПоручениеНомер + ПоручениеДата`).
- [ ] Статус поручений после создания — **Исполнено** (как сейчас).
- [ ] Поступления **проведены**, реквизиты совпадают с эталонным снимком (сумма, счета, назначение, ЕРС, вид операции).
- [ ] Экспортные вызовы из `ЗагрузкаВыписок` работают без изменения вызывающего кода.

### 5.2. Производительность

Baseline «Было» (45 док., 17.08.2026, последовательно):

- ~14 сек на «Создать» (~302 мс/док).

Целевые ориентиры после параллели (12 потоков, та же база, тот же день):

- [ ] Wall-clock «Создать» для 45 док.: **не более 5 сек** (ориентир ~3× ускорение).
- [ ] На объеме **> 500** док.: режим «Параллельно» включается автоматически; в логе указаны потоки и размер пачки.
- [ ] Замер «Стало»: файл `Тестирование/Замеры_<N>_<дата>_Стало.pff`; строка 299 EPF — сравнение общего времени корня.

### 5.3. Надежность

- [ ] При ошибке проведения одного документа остальные пачки завершаются; ошибки видны в логе (до 20 первых).
- [ ] Повторный «Создать» не дублирует поступления (проверка `ПоступлениеНаРасчетныйСчет = ПустаяСсылка()` сохранена).

## 7. Вне скоупа v2

- Изменение `ОбработкаПроведения` документа `ПоступлениеНаРасчетныйСчет` в конфигурации.
- Отключение подписок (`ВыгрузкаДУFinance`, статусы) ради скорости.
- Параллельное проведение из регламентного задания TIBCO (отдельная задача, если потребуется).
- Физическое удаление поступлений (достаточно пометки для тестового цикла).
