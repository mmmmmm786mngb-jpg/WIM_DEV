Цель

Формирование отчёта 0420431 занимает около 4 часов. Задача — сократить время за счёт распараллеливания вычислений: расчёт разделов выполняется в фоновых заданиях модуля длительных операций, разбивкой по пачкам договоров ДУ, с последующей склейкой результатов в итоговый документ.

Технология

  • Фоновые задания запускаются штатным механизмом БСП: ДополнительныеОтчетыИОбработки.ВыполнитьКомандуОбработкиПоПараметрам через ФоновыеЗадания.Выполнить(...). Это работает, так как обработка зарегистрирована в справочнике «Дополнительные отчёты и обработки».
  • Для воркера добавлена служебная команда РассчитатьПачкуРазделов9005 (вызов серверного метода, без оповещения).
  • Воркер считает свою пачку на временном документе-контейнере (СоздатьДокумент(), без записи в ИБ) и возвращает выгрузки табличных частей (ТаблицаЗначений) через ВременноеХранилище.
  • Существующие процедуры заполнения разделов (ЗаполнитьРаздел_2_3, _4, _5, _6, _7, ЗаполнитьРазделРеестрЦБ) не менялись — воркер вызывает их как есть.

Раздел 1 (1.1/1.2/1.3) считается агрегатами по всем договорам, поэтому остаётся в основном сеансе и не распараллеливается. Разделы 2–7 и реестр ЦБ формируются по договорам, поэтому пачкуются. Точка фильтрации одна — корневая ВТ ВТ_Договоры, через неё funnel-ом сужаются все нижестоящие временные таблицы.

КонецФункции

По умолчанию возвращается 1 — это прежнее последовательное поведение, поэтому пересобранный .epf безопасен для прома. Для теста параллельного режима поменяйте число (рекомендуется по числу свободных ядер/потоков сервера, например 4–8) и пересоберите обработку.

Важно проверить перед включением на проме (A/B на РЕГР)

  • Сравнить выгрузку отчёта в последовательном и параллельном режимах на РЕГР — итоговые разделы 2–7 и реестр ЦБ должны совпадать построчно (раздел 1 считается одинаково).
  • Проверить доступность внешних соединений с МО из фоновых сеансов (под пользователем регл. заданий).
  • Подобрать число потоков по нагрузке сервера; учесть, что каждый воркер держит своё соединение с МО.

Ограничение 100 000 строк (раздел 4) — отдельная задача

Распараллеливание не снимает лимит 99 999 строк табличной части (см. смежную задачу IMAPPS-37477): при склейке строки всё равно попадают в единый Раздел4. Это решается отдельно (дополнительная ТЧ Раздел4ч2 либо платформенный лимит). В рамках IMDEV-9005 поведение по лимиту не изменилось — регресса нет.
