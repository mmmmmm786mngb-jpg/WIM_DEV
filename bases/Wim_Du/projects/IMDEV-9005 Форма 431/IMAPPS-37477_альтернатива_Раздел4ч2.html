⚠️ 1. Текущая проблема

🐞 Ошибка при запуске обработки (01/Jun/26)
{ВнешняяОбработка.внЗаполнениеРеглОтчетаПоДоговорамДУ_0420431_71.МодульОбъекта(111)}
:ОбъектНазначения.Записать();

по причине:
Число строк табличной части объекта превышает максимально допустимое -
'Регл. отчет "(XBRL7.1) (0420431)".Раздел4'

Что произошло

В мае/июне 2026 г. количество строк раздела 4 отчёта 0420431 превысило 99 999 — максимальное число строк в одной табличной части документа 1С:Предприятие 8.3.

ПараметрЗначение
ДокументРО_XBRL7_1_0420431_СведенияОДеятельностиПоУправлениюЦБ_7119У
Проблемная ТЧРаздел4 (ценные бумаги по клиентам)

📄 2. Текущее решение — два документа

Принятое решение: формировать два отдельных документа в 1С, каждый покрывает свою половину клиентов, затем объединять их в Ортиконе.

Схема работы

1
Создать два пакета в Ортиконе: 431-1 и 431-2 Обработка -1: клиенты-физики (фильтр Клиент В (&ТЗсписокКлиентов)
Обработка -2: все остальные (фильтр Клиент НЕ В (&ТЗсписокКлиентов)
2
Создать промежуточный пакет «431 объединённый» В Ортиконе объединить пакеты 431-1 и 431-2
3
Итоговый пакет 409+414+431 Перелить данные из объединённого пакета в итоговый
4
Ручная обработка расхождений в Ортиконе Раздел 1.3 — агрегация (простое слияние даёт дубли строк)
Реестр ЦБ (459) — дедупликация по ключу ИдентификаторЦБ

Проблемы текущего решения

РазделПроблема при объединении в ОртиконеСложность
Разделы 2–6 Простое слияние строк — клиенты не пересекаются, работает корректно Нет проблем
Раздел 7 После слияния нужен повторный Свернуть по измерениям Средняя
Раздел 1.3 Суммарные показатели по стратегиям — нужна агрегация, не concat. При простом слиянии Ортикон «склеивает» строки с одинаковыми ключами, получаются дубли с разными суммами Высокая
Реестр 459 Одна ценная бумага встречается в обоих отчётах — нужна дедупликация по ИдентификаторЦБ Высокая

Юля: «сильно разошлись два раздела 431 раздел 1.3 и 459, потому что при объединении ортикон слепил два отчета вместе не сгруппировав их»

Итого в Ортиконе создаётся 5 объектов вместо одного: пакет 431-1, пакет 431-2, промежуточный объединённый, итоговый, плюс ручные шаги агрегации.

💡 3. Альтернатива — табличная часть Раздел4_2

Идея

Добавить в метаданные документа вторую табличную часть Раздел4_2 с теми же реквизитами, что у Раздел4. При заполнении, когда основная ТЧ достигает лимита, строки пишутся в Раздел4_2. При выгрузке в XML обе ТЧ объединяются в один тег <Раздел4> — XSD-схема не меняется.

Ключевое свойство: в XML-файле (.xtdd), который уходит в Ортикон, по-прежнему один <Раздел4> с неограниченным количеством строк. Лимит 99 999 — это только ограничение хранения в базе 1С, в XDTO/XML его нет.

Схема работы

1
Заполнение: обработка пишет строки через helper-функцию Пока Раздел4.Количество() < 99999 — пишет в Раздел4, иначе — в Раздел4_2
2
Запись документа Обычная запись одного документа, обе ТЧ сохраняются в БД
3
Выгрузка: модуль объекта объединяет обе ТЧ в XDTO Цикл по Раздел4, затем цикл по Раздел4_2 (со смещением НомерСтроки)
Оба цикла добавляют СтрокаРаздел4 в один XDTO-объект
4
Один XML-файл (.xtdd) — один документ в Ортиконе Все строки раздела 4 в одном теге, разделы 1.3 и 459 не затронуты

Принцип нумерации строк при merge

В ТЧ Раздел4_2 нумерация строк начинается снова с 1. В XML нужна сквозная нумерация. При выгрузке второй ТЧ к реквизиту НомерСтроки добавляется смещение равное количеству строк в Раздел4 (обычно 99 999). Пример: строка 1 из Раздел4_2 → НомерСтроки = 100000.

// Новая вспомогательная процедура (добавить в #Область СлужебныеПроцедурыИФункции)
// Описание: Добавляет строки табличной части Раздел4 (или Раздел4_2) в XDTO-объект
// Параметры:
//   Таблица          - ОбъектXDTO - целевой XDTO-объект Раздел4
//   ТипТаблицы       - ТипXDTO   - тип строки (СтрокаРаздел4)
//   СтрокиТЧ         - КоллекцияСтрок - строки ТЧ документа
//   СмещениеНомера   - Число - прибавляется к НомерСтроки (0 для основной, 99999 для второй)
Процедура ДобавитьСтрокиРаздела4ВXDTO(Таблица, ТипТаблицы, СтрокиТЧ, СмещениеНомера)

    ТабЧастиДокумента = Метаданные.Документы
        .РО_XBRL7_1_0420431_СведенияОДеятельностиПоУправлениюЦБ_7119У.ТабличныеЧасти;

    Для каждого СтрокаТабЧасти Из СтрокиТЧ Цикл

        СтрокаТаблицы  = Фабрика.Создать(ТипТаблицы);
        СтрокаСвойства = СтрокаТаблицы.Свойства();

        // Сквозная нумерация: строка 1 из второй ТЧ → НомерСтроки = 100000
        СтрокаТаблицы.НомерСтроки = ПривестиЗначениеДляВыгрузки(
            СтрокаТабЧасти.НомерСтроки + СмещениеНомера);

        Для каждого ТекРеквизит Из ТабЧастиДокумента.Раздел4.Реквизиты Цикл

            Если СтрокаСвойства.Получить(ТекРеквизит.Имя) <> Неопределено Тогда
                СтрокаТаблицы[ТекРеквизит.Имя] = ПривестиЗначениеДляВыгрузки(
                    СтрокаТабЧасти[ТекРеквизит.Имя]);
            КонецЕсли;

        КонецЦикла;

        Таблица.СтрокаРаздел4.Добавить(СтрокаТаблицы);

    КонецЦикла;

🎯 7. Вывод и рекомендация

ВопросОтвет
Технически реализуемо? Да — XSD не меняется, Ортикон не меняется
Сложно ли доработать код? Умеренно — ~3 локальных изменения, helper-функции
Требует смены режима совместимости? Нет
Устраняет проблемы Ортикона (1.3, 459)? Полностью
Масштабируется при дальнейшем росте? Да — добавить Раздел4_3 аналогично

Рекомендация: Вариант с Раздел4_2 является более устойчивым долгосрочным решением. Он убирает весь дополнительный ручной труд в Ортиконе (агрегация 1.3, дедупликация 459, 5-шаговый процесс) и исключает риск неправильного объединения половинок. Трудозатраты на разработку (~2–3 дня) окупаются уже в первый же отчётный период.

Если решение нужно прямо сейчас (текущий отчётный период), то текущий вариант с двумя документами работает — его можно использовать сейчас, а доработку Раздел4_2 запланировать на следующий спринт как технический долг.
