IMDEV-9005 v1.20 — Оптимизации заполнения регламентированного отчета 0420431

Введение и цель работ

Заполнение формы 0420431 (таксономия 7.1, по договорам ДУ) — длительная операция. По результатам профилирования (Тесты_замеры_9005.docx, локальная база WIM_DU, период февраль 2026) основное время уходило не на SQL-запросы базы ДУ, а на:

  • многократные COM-вызовы расчета TWR во внешней базе МО;
  • линейный поиск НайтиСтроки в больших таблицах значений.

В версии 1.20 реализованы две независимые оптимизации, каждая закрывает отдельный «горячий» участок профиля. Бизнес-логика и итоговые данные отчета сохранены; изменен только способ получения данных.

Теория

Проблема

Процедура СформироватьВТ_ДанныеПоСтратегиям для каждого COM-соединения с МО и для каждой стратегии вызывала ВТБ_РасчетДоходностиСервер.TWR с группировкой "MANDATE" и отбором по ТекущаяСтрока.Стратегия. При десятках стратегий это давало десятки полных пересчетов TWR через COM.

Почему нельзя просто MANDATE + Неопределено

Режим Группировка = "MANDATE" при Стратегия = Неопределено считает доходность сводно по всему мандату (все стратегии вместе). Это дает другие значения, чем per-strategy расчет.

Решение: MANDATE_STRATEGY

В отчете МО VTBAM_MWR_TWR режим "MANDATE_STRATEGY" считает TWR отдельно для каждой пары (мандат, нормализованная стратегия). Ключ результата:

Разделитель = КодМандата + "_" + КодСтратегии

Нормализация стратегии (подъем к родителю) совпадает с логикой запроса ДУ к МО. Каждый «общий» мандат имеет ровно одну нормализованную стратегию (мандаты с несколькими стратегиями уходят в ветку IS-001), поэтому batch-вызов эквивалентен N отдельным per-strategy вызовам.

Исключение IS-001

Для индивидуальных стратегий (ИдентификаторСтратегии = "IS-001") в запросе МО поле Стратегия = "". Сохранен оригинальный вызов TWR(..., "MANDATE") со Стратегия = ТекущаяСтрока.Стратегия — один вызов на всю группу IS-001.

Практика (версия 1.20)

Процедура: СформироватьВТ_ДанныеПоСтратегиям, строки ~747–867.

Алгоритм (на каждое соединение МО):
1. Запрос к МО -> ДанныеПоСтратегиям (добавлена колонка КодМандата)
2. Предцикл: собрать МассивМандатовОбщих (без IS-001, с дедупликацией по КодМандата)
3. Один вызов: TWR(..., МассивМандатовОбщих, Неопределено, "MANDATE_STRATEGY")
4. Построить ИндексДоходностиОбщих (локальное Соответствие, ключ = строка Разделитель)
5. Цикл по стратегиям: общие -> индекс; IS-001 -> отдельный TWR + НайтиСтроки по мандату 
// Предрасчет (один раз на соединение)

2 Оптимизация НайтиСтроки в разделе 1.2

Теория

Проблема

При заполнении Раздел1_Подраздел1_2 для каждой строки агрегата выполнялись два линейных поиска в таблице СведенияПоДоговорам:

  • СведенияПоДоговорам.НайтиСтроки(Отбор) — 10 полей отбора;
  • СведенияПоДоговорамЗагруженные.НайтиСтроки(Отбор) — проверка «группа уже обработана».

Сложность: O(N x M) — число строк отчета умножается на число договоров во временной таблице.

Решение: индекс + кэш

Классический прием «построить индекс один раз, читать много раз»:

  • ИндексСтрокПоГруппе — Соответствие «составной ключ -> Массив строк ТЗ»;
  • ОбработанныеГруппы — Соответствие для O(1) проверки «уже считали»;
  • ключ формирует КлючГруппыРаздел1_2() из 10 полей (нормализация через XMLСтрока).

Итоговая сложность: O(N + M). Логика подсчета договоров (заключен / прекращен / на конец периода) не изменена.

Практика (версия 1.20)

Процедура: ЗаполнитьРаздел_1, строки ~2500–2611.

Алгоритм:
1. Выгрузить СведенияПоДоговорам из ВТ
2. Один проход -> ИндексСтрокПоГруппе
3. В цикле по ДанныеРаздела_1_2:
  - Строки = ИндексСтрокПоГруппе.Получить(КлючГруппы)
  - СтрокиУжеЗагружены = ОбработанныеГруппы.Получить(КлючГруппы) <> Неопределено
4. Подсчет количеств договоров — без изменений 
// Построение индекса (один проход)
КлючГруппы = КлючГруппыРаздел1_2(
    СтрокаДоговора.КвалификацияИнвестора,
    СтрокаДоговора.КодПоОКАТОиОКСМ, ...);
СтрокиГруппы = ИндексСтрокПоГруппе.Получить(КлючГруппы);
// ... Добавить(СтрокаДоговора)

// В цикле раздела 1.2
Строки = ИндексСтрокПоГруппе.Получить(КлючГруппы);
СтрокиУжеЗагружены = ОбработанныеГруппы.Получить(КлючГруппы) <> Неопределено;

Сравнение двух оптимизаций

Опт. 1 — МО / TWR

  • Узкое место: 63% профиля
  • Тип: сокращение COM-вызовов
  • Механизм МО: MANDATE_STRATEGY
  • Индекс: по строковому Разделитель
  • Риск: эквивалентность при 2-уровневой иерархии стратегий

Опт. 2 — Раздел 1.2

  • Узкое место: ~18% профиля
  • Тип: индексация в памяти ДУ
  • Механизм: Соответствие + КлючГруппыРаздел1_2
  • Индекс: 10-полевой составной ключ
  • Риск: минимальный (логика подсчета не менялась)

Выводы

  1. Обе оптимизации выбраны по измеримым долям времени в профиле, а не произвольно.
  2. Опт. 1 (TWR + MANDATE_STRATEGY) устраняет главный узкий участок (~63%) с сохранением per-strategy точности за счет правильного режима группировки МО.
  3. Опт. 2 (индекс раздела 1.2) снимает еще ~18% за счет замены O(N x M) на O(N + M).
