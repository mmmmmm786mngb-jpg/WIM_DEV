Введение

Задача IMDEV-9005 — ускорить заполнение регламентированного отчета 0420431 по договорам ДУ без изменения результата отчета.

Итоговая разработка сфокусирована на устранении узких мест НайтиСтроки, выявленных профилировщиком на среде т-1:

  • ДУ две точечные доработки внешней обработки;
  • МО исправление индекса таблицы значений MV в РасчетTWR.

Замеры до/после и регрессия: imdev-9005_measurements_before_after.html

Выполненная работа — база ДУ

ДУ-1 Стр. 801 — индекс доходности по мандату

Проблема: после каждого из 64 вызовов TWR для каждого мандата стратегии выполнялся ДанныеДоходности.НайтиСтроки — 25 729 полных переборов таблицы, 2 355 сек.

Решение: один проход по результату TWR, построение COM-Соответствие (ключ — ссылка мандата из МО), далее O(1) получение строк.

// БЫЛО (стр. 801):
Отбор = Соединение.NewObject("Структура");
Отбор.Вставить("Разделитель", ТекСтрока.Мандат);
СтрокиДоходности = ДанныеДоходности.НайтиСтроки(Отбор);

// СТАЛО:
ДоходностьПоМандатам = Соединение.NewObject("Соответствие");
Для Каждого СтрокаДоходности Из ДанныеДоходности Цикл
    Мандат = СтрокаДоходности.Разделитель;
    СтрокиМандата = ДоходностьПоМандатам.Получить(Мандат);
    Если СтрокиМандата = Неопределено Тогда
        СтрокиМандата = Соединение.NewObject("Массив");
        ДоходностьПоМандатам.Вставить(Мандат, СтрокиМандата);
    КонецЕсли;
    СтрокиМандата.Добавить(СтрокаДоходности);
КонецЦикла;
// ...
СтрокиДоходности = ДоходностьПоМандатам.Получить(ТекСтрока.Мандат);

Важно: для COM-объектов из МО используется Соединение.NewObject("Соответствие"), не локальное Новый Соответствие — иначе ключи-ссылки не сопоставляются.

Результат замера: вместо стр. 801 (2 355 сек) — стр. 781 ДоходностьПоМандатам.Получить (~34 сек).

ДУ-2 Стр. 2470/2471 — раздел 1.2, индекс по группе договоров

Проблема: для каждой строки раздела 1.2 — два НайтиСтроки по СведенияПоДоговорам (44 932 вызова, 491 сек суммарно).

Решение: предварительный проход — построение ИндексСтрокПоГруппе (ключ из 10 полей группировки) + ОбработанныеГруппы вместо повторного поиска «уже загруженных».

// БЫЛО (стр. 2470-2471):
Отбор = Новый Структура(...);  // 10 полей группы
Строки = СведенияПоДоговорам.НайтиСтроки(Отбор);
СтрокиУжеЗагружены = СведенияПоДоговорамЗагруженные.НайтиСтроки(Отбор).Количество();

// СТАЛО:
ИндексСтрокПоГруппе = Новый Соответствие;  // один проход при загрузке
ОбработанныеГруппы = Новый Соответствие;   // кэш обработанных ключей
КлючГруппы = КлючГруппыРаздел1_2(...);
Строки = ИндексСтрокПоГруппе.Получить(КлючГруппы);
СтрокиУжеЗагружены = ОбработанныеГруппы.Получить(КлючГруппы) <> Неопределено;

Результат замера: ЗаполнитьРаздел_1 — 510 сек → 51 сек (-90%).

Выполненная работа — база МО

МО-1 Стр. 2275 — исправление индекса таблицы MV

Проблема: в Отчет.VTBAM_MWR_TWR.РасчетTWR цикл по разделителям вызывает:

СтрокиРазделителя = MV.НайтиСтроки(ПараметрыПоискаСтрок);
// ПараметрыПоискаСтрок = Новый Структура("Разделитель", ТекРазделитель.Ключ)

14 869 вызовов, 1 333 сек, 90,87% времени РасчетTWR.

Корневая причина: индекс таблицы MV был объявлен по двум полям, а поиск — только по одному полю Разделитель. Платформа не использовала индекс эффективно.

ВариантКодЭффект
БЫЛО MV.Индексы.Добавить("Разделитель, Период"); НайтиСтроки по одному полю — 1 333 сек
СТАЛО MV.Индексы.Добавить("Разделитель"); Индекс совпадает с полем поиска — ускорение TWR

Исправление минимальное: одна строка в конфигурации МО. Логика РасчетTWR не переписывалась.

Выводы

  1. Финальная разработка — три точечных исправления узких мест НайтиСтроки без смены бизнес-логики.
  2. В ДУ: COM-Соответствие для доходности (стр. 801) и локальный индекс групп раздела 1.2 (стр. 2470/2471) — убрали ~2 800 сек линейных поисков.
  3. В МО: одна строка — индекс MV по полю Разделитель вместо "Разделитель, Период" — устранила 90,9% времени РасчетTWR.
  4. Совместный эффект: ускорение заполнения 0420431 с ~1 ч 54 мин до ~20 мин на стене (~8,6x по чистому времени).
  5. Регрессия данных пройдена — документы 000000016 и 000000017 идентичны.
