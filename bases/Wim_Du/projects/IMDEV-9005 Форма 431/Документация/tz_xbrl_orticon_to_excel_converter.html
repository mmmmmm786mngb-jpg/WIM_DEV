Техническое задание: внешняя обработка-конвертер XBRL (ОРТИКОН) в Excel

Проект: IMDEV-9005 Форма 431  |  База: Wim_Du  |  Версия ТЗ: 1.0  |  Дата: 15.07.2026  |  Заказчик: пользователи ДУ (АО ВИМ Инвестиции)

Цель: создать внешнюю обработку 1С, которая принимает файл XBRL instance, сформированный модулем ОРТИКОН, и преобразует его в multi-sheet книгу Excel по сути совпадающую с результатом штатного Excel-конвертера (эталон прилагается). Затем оптимизировать производительность (штатный конвертер ЦБ/ОРТИКОН на больших файлах занимает более часа).

1. Основание и проблема

Отчётность профучастника (пакет НСО ПУРЦБ) выгружается из ОРТИКОН в формат XBRL instance (.xbrl / .zip). Для анализа и сверки пользователям нужен удобный Excel.

Штатный путь (конвертер Банка России / table-view ОРТИКОН) на реальном объёме (~60+ МБ instance, десятки тысяч контекстов, ~90+ тыс. фактов) занимает более одного часа, что неприемлемо в операционной работе.

Требуется собственная обработка-конвертер в контуре 1С (Wim_Du), ориентированная на тот же результат по составу листов и данных, с последующим ускорением.

Принцип разработки (зафиксирован): сначала добиться результата по сути как эталонный Excel, затем ускорять и улучшать. Нельзя на первом этапе жертвовать группировками/полнотой ради скорости.

3.2. Что обязан разобрать парсер

  • link:schemaRef (entry point) - в TOC;
  • xbrli:context: entity, period (instant / duration), scenario (explicitMember + typedMember);
  • факты (элементы с contextRef, опционально unitRef, decimals);
  • пространства имён показателей: purcb-dic, nfo-dic и др.;
  • измерения dim-int / члены mem-int.

Парсинг - потоковый (ЧтениеXML), без загрузки всего DOM в память целиком.

4. Выходные данные (эталон желаемого результата)

Эталонный Excel (тот же XBRL, прогнанный штатным конвертером):

bases/Wim_Du/projects/IMDEV-9005 Форма 431/ОРТИКОН/
0420431_409_январь_2026_конвертер.xlsx

Это образец состава листов, группировок, смысла колонок/пивотов и данных, который должны получить пользователи после конвертации нашей обработкой.

4.1. Структура эталона (суть)

  • Лист TOC: entry point, период, identifier, список таблиц пакета.
  • ~40 рабочих листов по таблицам отчётности (ОКУД 0420409, 0420414, 0420431, 0420458, 0420459 + сопроводительные).
  • Имена ярлыков Excel ограничены 31 символом, стиль: 0420431 Раздел 4 Сведения о п_1, суффиксы _1, _2 при коллизиях.
  • Группировки: раздел/подраздел; разделение брокерской деятельности и деятельности по УЦБ; тип имущества и др. разрезы scenario.
  • Часть листов - «открытая ось + показатели» (например стратегии 1.1, счета 409, реестр 459, портфель ЦБ разд.4).
  • Часть листов - широкие пивоты (например подразделы 1.2 / 1.3 с десятками/сотнями колонок).
  • Русские подписи показателей и членов измерений в шапках.
  • Служебный _dropDownSheet эталона для нашей обработки не обязателен.

4.2. Динамичность набора листов

Набор вкладок не фиксируется «всегда 43 листа». Он зависит от фактических данных в конкретном XBRL (какие формы/разрезы заполнены). Эталон показывает ожидаемый результат на данном sample; алгоритм должен быть общим для того же entry point / пакета.
XBRL instance (Orticon) | v Парсинг contexts + facts | v Группировка по правилам эталона (signature + ключевые члены scenario) | v XLSX: TOC + листы разделов (имена и суть группировок как у конвертера)

5. Объём и порядок работ

Этап 1 Изучение + рабочий конвертер «как эталон»
  1. Детальный разбор структуры sample XBRL (contexts, facts, оси, OKUD).
  2. Детальный разбор эталонного XLSX (TOC, каждый тип листа, пивоты, заголовки, объёмы строк).
  3. Маппинг: блок XBRL -> лист эталона; оси в строки / в колонки; показатели.
  4. Реализация обработки внВыгрузкаXBRLОртиконВXLSX.
  5. Сверка результата на sample с эталоном (листы, объёмы, выборочные значения).
Этап 2 Ускорение и улучшения (после приёмки этапа 1)
  • профилирование парсинга и записи XLSX;
  • оптимизация записи больших листов (по опыту внВыгрузка0420431ВXLSX);
  • при необходимости - дополнительные режимы (плоский без пивотов, упрощённый);
  • уточнение словарей русских подписей / поддержка соседних дат таксономии.

Целевой ориентир этапа 2: минуты, а не час+, при сохранении полезного результата этапа 1.

6. Функциональные требования

6.1. Обязательные (этап 1)

IDТребование
FR-01 Обработка принимает файл .xbrl или .zip с instance ОРТИКОН.
FR-02 Формирует один файл .xlsx (multi-sheet) с выбором пути сохранения пользователем.
FR-03 Формирует лист TOC с метаданными пакета и перечнем выгруженных таблиц.
FR-04 Группирует данные по листам в той же сути, что эталон (разделы/подразделы ОКУД, брокер/ДУ, иные разрезы эталона).
FR-05 Имена листов - в стиле эталона (ОКУД + краткое описание), длина не более 31 символа, суффиксы _N при коллизиях.
FR-06 Набор листов динамический: пустые (отсутствующие в instance) блоки не создавать или создавать только при явно включённой опции (по умолчанию - не создавать).
FR-07 Для таблиц эталона с пивотом - сохранить суть пивота (какие разрезы в строках, какие в колонках; те же показатели), на сколько позволяет разбор instance без полной таксономии ЦБ.
FR-08 Числовые значения выгружать как числа Excel (не текст с запятой), где тип однозначно определяется.
FR-09 Показывать прогресс выполнения (БСП ДлительныеОперации или эквивалент).
FR-10 Регистрация через БСП: СведенияОВнешнейОбработке, БезопасныйРежим = Ложь.
FR-11 При неизвестном наборе осей - не терять данные: fallback-лист (техническое имя) + запись в статус/лог.

6.2. Желательные / этап 2

IDТребование
FR-20 Опциональный режим «плоский» (без широких пивотов) для максимальной скорости сверки.
FR-21 Опциональный режим «по signature XBRL» (лист = уникальный набор осей) для отладки.
FR-22 Максимально близкие к эталону русские многоуровневые шапки (если потребуется label/table linkbase).
FR-23 Замер и вывод времени конвертации в статусе формы.

8. Ограничения и допущения

  • Полный движок table-view ЦБ с онлайн-загрузкой таксономии не является обязательным способом реализации (именно он даёт многочасовую обработку).
  • Допускается маппинг раскладок листов/пивотов, снятый с эталона + instance, с последующим обобщением.
  • Pixel-perfect совпадение merged-ячеек и всех уровней шапки эталона на этапе 1 желательно, но не блокирует приёмку, если сохранены: набор листов по сути, группировки, объёмы строк и значения.
  • Обработка не заменяет выгрузку документа 0420431 из 1С (внВыгрузка0420431ВXLSX) и не заменяет XTDD.
  • Поддержка других entry point / годов таксономии - по отдельному расширению ТЗ (базовый scope: текущий пакет sample).

9. Критерии приёмки

9.1. Этап 1 - конвертер «как эталон»

  1. На sample XBRL обработка формирует XLSX без критических ошибок.
  2. Есть лист TOC и рабочие листы по заполненным разделам пакета.
  3. На крупных блоках порядок величины строк согласуется с эталоном (ориентиры sample: счета 0420409 ~4 тыс., стратегии ~53, портфель ЦБ 431 разд.4 ДУ ~17 тыс., реестр 459 ~542).
  4. Выборочная сверка значений (стратегия / счёт / ISIN / сумма StoimOcz) совпадает с эталоном с учётом формата числа/даты.
  5. Имена листов узнаваемы и соответствуют стилю эталона (не произвольные Блок_1 для известных таблиц sample).
  6. Пользователь может запустить конвертацию из дополнительных обработок (или согласованного сценария открытия EPF) и сохранить файл.

9.2. Этап 2 - ускорение

  1. Зафиксировано время «до/после» на том же sample.
  2. Время существенно меньше штатного конвертера ЦБ при сохранении критериев этапа 1 (либо отдельный быстрый режим явно подписан и не ломает режим «как эталон»).
