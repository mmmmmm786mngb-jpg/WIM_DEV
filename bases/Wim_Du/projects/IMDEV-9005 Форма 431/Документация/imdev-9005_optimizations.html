IMDEV-9005 — Оптимизации заполнения регламентного отчета 0420431

Обработка: внЗаполнениеРеглОтчетаПоДоговорамДУ_0420431_71  |  Версия: 1.10  |  База: Srvr="localhost";Ref="WIM_DU"  |  Маркировка изменений: IMDEV-9005 ++ / --

Введение

Заполнение формы 0420431 (таксономия 7.1, по договорам ДУ) — длительная операция. По результатам профилирования (файл Тесты_замеры_9005.docx) основное время уходило не на SQL-запросы базы ДУ, а на многократные обращения к базе МО и на линейный поиск в таблицах значений (НайтиСтроки).

Реализованы три независимые оптимизации, каждая закрывает отдельный «горячий» участок профиля.

Три вида оптимизаций

1 Оптимизировано обращение к базе МО

Было: для каждого внешнего соединения с МО и для каждой стратегии отдельный вызов ВТБ_РасчетДоходностиСервер.TWR; затем в цикле — ДанныеДоходности.НайтиСтроки(Отбор) по мандату.

Стало:

  • Один раз собирается МассивВсехМандатов по всем строкам ДанныеПоСтратегиям.
  • Один вызов TWR(..., МассивВсехМандатов, ..., "MANDATE", ...) на соединение.
  • Индекс ДоходностьПоМандатам (Соответствие мандат -> массив строк) вместо НайтиСтроки в цикле.

Маркеры в коде: строки ~768–870, комментарии IMDEV-9005.

// IMDEV-9005 ++ один вызов TWR на все мандаты
// IMDEV-9005 ++ индекс строк TWR по мандату (Соответствие вместо НайтиСтроки)
СтрокиДоходности = ДоходностьПоМандатам.Получить(ТекСтрока.Мандат);

2 Оптимизированы НайтиСтроки для раздела 1.2

Было: для каждой строки агрегата раздела 1.2 — два линейных поиска в таблице значений (СведенияПоДоговорам.НайтиСтроки и поиск в кэше СведенияПоДоговорамЗагруженные).

Стало:

  • Перед циклом — один проход по СведенияПоДоговорам, построение ИндексСтрокПоГруппе (Соответствие).
  • Ключ группы — функция КлючГруппыРаздел1_2() (10 полей отбора, нормализация через XMLСтрока).
  • Кэш обработанных групп — ОбработанныеГруппы (Соответствие) вместо второй таблицы с НайтиСтроки.

Сложность: O(N x M) -> O(N + M).

Маркеры в коде: строки ~2499–2677.

3 Параллельное вычисление разделов 2–7 и реестра ЦБ

Было: после раздела 1 все разделы 2–7 и реестр ЦБ считаются последовательно в одном сеансе.

Стало:

  • Раздел 1 — всегда в основном сеансе (агрегаты по всем договорам).
  • Договоры делятся на N пачек; каждая пачка — отдельное фоновое задание БСП (РассчитатьПачкуРазделов9005).
  • Воркер: свой МВТ с фильтром пачки, расчет разделов 2–7 + реестр, результат через ВременноеХранилище.
  • Основной сеанс склеивает табличные части (СклеитьРезультатыПачек9005).

Число потоков: ПолучитьКоличествоПотоковЗаполнения9005() (константа в модуле, по умолчанию 1 = последовательный режим).

Подробнее: IMDEV-9005_parallel_zapolnenie.html в корне проекта.

Технология (кратко)

  • COM / внешнее соединение с МO: расчет доходности через ВТБ_РасчетДоходностиСервер.TWR во внешнем сеансе МO.
  • Индексация в памяти: Соответствие + Массив вместо ТаблицаЗначений.НайтиСтроки.
  • Фоновые задания БСП: ФоновыеЗадания.Выполнить + команда РассчитатьПачкуРазделов9005.
  • Сборка EPF: платформа 8.3.27, база localhost/WIM_DU, исходники в Обраб/.

Выводы

  1. Три оптимизации выбраны по измеримым долям времени в профиле, а не «наугад».
  2. Оптимизация МO (TWR + индекс) снимает ~60% нагрузки исходного профиля.
  3. Индекс для раздела 1.2 снимает еще ~18% (два НайтиСтроки на каждую строку отчета).
  4. Параллельный режим ускоряет оставшуюся часть (разделы 2–7) пропорционально числу потоков, при наличии ресурсов сервера и лицензий.
  5. Все изменения изолированы маркерами IMDEV-9005 ++ / -- для простого ревью и переноса.
