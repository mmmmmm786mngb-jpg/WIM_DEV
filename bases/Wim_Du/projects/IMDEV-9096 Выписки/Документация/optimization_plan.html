1 Запрос 1: ДоговорДУПоСчету

ФункцияДоговорДУПоСчету(НомерСчета)
Строка SQL1286 — Результат = Запрос.Выполнить();
Вызовыстр. 2061 (на выписку), стр. 2202 (ERS fallback); всего 255 раз
Замер100,26 с — 30,66%
Суть запросаUNION: АналитическиеСчета + БанковскиеСчета по НомерСчета, сортировка ДоговорДУ УБЫВ

Проблема

Один и тот же тяжелый UNION выполняется для каждой выписки и повторно в ERS-fallback на тот же номер счета.

План доработки

  1. В начале ПрочитатьОбъекты собрать массив уникальных НомерСчета из ответа сервиса.
  2. Один пакетный запрос: ВЫБРАТЬ НомерСчета, ДоговорДУ ИЗ ... ГДЕ НомерСчета В (&СписокСчетов) (аналог текущей логики UNION).
  3. Заполнить КэшДоговоровПоСчету = Новый Соответствие (ключ — нормализованный номер счета).
  4. ДоговорДУПоСчету — сначала lookup в кэше; SQL только при промахе (редкий счет вне отбора).
  5. Сохранить текущее правило «более 1 договора — пустая ссылка».

Критерий приемки

Количество вызовов Запрос.Выполнить на стр. 1286 снижается с 255 до 1 (+ редкие промахи). Повторный замер «Прочитать» 1 день: доля стр. 1286 < 5%, экономия ~90 с.

2 Запрос 2: ЕРС_ДоговорДУ_ПоСчетуИСчетуДепо

ФункцияЕРС_ДоговорДУ_ПоСчетуИСчетуДепо(НомерСчета, НазначениеПлатежа) — определена со стр. 1582
Строка SQL1624 — Результат = Запрос.Выполнить();
Цикл сопоставления1650–1689 — Пока Выборка.Следующий() (No.DU, ACC, № , N , KUP/PROC)
Вызовстр. 2173 в цепочке ERS; 118 раз (по числу ЕРС-платежей)
Замер (замерОтладчика_было.docx)SQL стр. 1624: 73,33 с — 22,43% при 118 вызовах
Суть запросаJOIN СчетаДепо с подзапросом по АС/БанковскиеСчета для &НомерСчета; зависит только от НомерСчета (+ константа &ПустойДоговорДУ)
Уточнение по замеру: в замерОтладчика_было.docx для этой функции зафиксирована только строка SQL 1624 (22,43%). Функционального итога «119,83 с / 36,64%» в этом замере нет — цифра ранее попала в план ошибочно. Если нужен вклад всей функции (SQL + цикл 1650–1689) — снять отдельным замером.

Проблема

На каждый ЕРС-платеж — полный JOIN, хотя результат SQL зависит только от НомерСчета (параметры запроса — НомерСчета и константа ПустойДоговорДУ); по назначению платежа различается лишь сопоставление в цикле 1С (строки 1650–1689).

План доработки

  1. Разделить функцию: ПолучитьДанныеДепоПоСчету(НомерСчета) — только SQL (возврат ТаблицаЗначений с колонками ДоговорДУ, СчетДепо) и НайтиДоговорВДанныхДепо(ДанныеДепо, НазначениеПлатежа) — текущая логика сопоставления (1С).
  2. Кэш КэшДепоПоСчету = Соответствие(НомерСчета -> ТаблицаЗначений): SQL выполняется один раз на уникальный НомерСчета за проход ПрочитатьОбъекты (паттерн как в OPT-02).
  3. Логику сопоставления в цикле (No.DU, ACC/, ACC, «№ », « N », KUP/PROC, IMAPPS-31545) оставить без изменения бизнес-правил — меняется только источник Выборки (из кэша, не из нового Запрос.Выполнить).
  4. Сохранить guard перед вызовом (стр. 2167–2174): функция вызывается только если назначение не содержит «СОГЛАСНО ПОРУЧЕНИЯ N», «{VO99090}», «Заявлению на перевод N ».
Примечание: данные ЕРС_ДоговорДУ_Отбор_ПоСчетуИНазначению (шаг 1.4) — это отдельный запрос без JOIN СчетаДепо, для депо-эвристики он не подходит. Кэш депо должен быть собственным.

Критерий приемки

Вызовов SQL на стр. 1624 — не более числа уникальных ЕРС-счетов (десятки, не сотни). Результаты сопоставления договоров идентичны исходным на контрольной выписке.

3 Запрос 3: ЕРС_ДоговорДУ_ПоПлатежномуПоручению

ФункцияЕРС_ДоговорДУ_ПоПлатежномуПоручению(БанковскийСчет, НазначениеПлатежа, Номер, Дата) — определена со стр. 1697
Строка SQL1725 — Результат = Запрос.Выполнить();
Вызовстр. 2164; 118 раз. Ключ — БанковскийСчет (ссылка, не номер) + Дата
Замер (замерОтладчика_было.docx)SQL стр. 1725: 60,02 с — 18,36% при 118 вызовах + цикл Пока Выборка.Следующий в 1С
Суть запросаВсе ПлатежноеПоручение в окне [Дата−5; Дата+1] дней (строка 1719) по счету; совпадение номера ищется в цикле 1С

Проблема

Широкая выборка ПП на каждый платеж; фильтр по номеру документа — в цикле 1С после выгрузки всех строк окна. Дополнительно: НАЧАЛОПЕРИОДА(ПлатежноеПоручение.Дата, ДЕНЬ) в условии (стр. 1719) — функция над полем, что мешает использованию индекса по дате.

План доработки

  1. Кэш по ключу (БанковскийСчет, НачалоДня(Дата)) — один SQL на пару счет+день. Результат SQL зависит только от счета и окна даты, поэтому переиспользуется для всех платежей того же счета и дня.
  2. Заменить НАЧАЛОПЕРИОДА(ПП.Дата, ДЕНЬ) МЕЖДУ ... на диапазон по сырому полю: ПП.Дата >= &Начало И ПП.Дата < &Конец, где Начало = НачалоДня(Дата) − 5 дн, Конец = НачалоДня(Дата) + 2 дн (эквивалент окна [−5; +1] по дням, но с использованием индекса).
  3. Поиск нужного ПП — в 1С по предзагруженной из кэша таблице, без повторного Запрос.Выполнить.
  4. Осторожно с фильтром по номеру в SQL: сопоставление в коде (стр. 1730) — это НомерПП = ВРег(Номер) ИЛИ Найти(назначение, НомерПП) > 0 (номер ПП как подстрока в назначении). Поэтому нельзя просто добавить Номер = &Номер — потеряются совпадения по подстроке. Допустимо лишь сузить выборку списком всех номеров платежей выписки, но проще оставить фильтрацию в памяти.
  5. Сужение окна [−5; +1] (например, до [−1; +1]) — только по согласованию с аналитиком, в этой задаче не трогаем.
Побочный эффект кэша: сообщение «не удалось определить валюту» (стр. 1739) при кэшировании будет выводиться один раз на (счет, день), а не на каждый платеж — это улучшение, не регрессия.

Критерий приемки

Вызовов SQL на стр. 1725 — по числу уникальных (счет, день), не по числу платежей. Определённые договоры совпадают с исходными на контрольной выписке.

4 Процедура с циклом: ЕРС_ДоговорДУ_ПоСчетуИНазначению

ФункцияЕРС_ДоговорДУ_ПоСчетуИНазначению(Данные, НомерСчета, НазначениеПлатежа) — определена со стр. 1347
Циклстр. 1355 — Для Каждого Выборка Из Данные Цикл
Тело цикластр. 1356, 1359 — СтрНайти(ГдеИскать, "Ф" + Выборка.Префикс + "ОТ"/"OT") > 0 (с конкатенацией строки на каждой итерации)
Итерации (замер)2 962 950 (стр. 1355); по 2 962 832 на каждую ветку СтрНайти
Замер (замерОтладчика_было.docx)СтрНайти: 9,68 с (2,96%) + 8,79 с (2,69%) = 18,5 с / 5,65%; сам цикл стр. 1355: 6,46 с (1,58%). Итого ~24,9 с / ~7,2%
КонтекстДанные — результат ЕРС_ДоговорДУ_Отбор_ПоСчетуИНазначению (1 SQL на ЕРС-выписку): ТаблицаЗначений с колонками ДоговорДУ, Префикс (нормализованный)

Проблема

Алгоритм O(платежи × договоры_счета): для каждого платежа перебираются все префиксы договоров счета, на каждой итерации строится новая строка "Ф" + Префикс + "ОТ" и выполняется СтрНайти по назначению.

Важно про принцип: прямое Соответствие с ключом "Ф"+Префикс+"ОТ" само по себе не решает задачу — из строки платежа префикс заранее неизвестен, поэтому сделать один lookup нельзя. Проверка СтрНайти(назначение, "Ф"+Префикс+"ОТ") — это поиск подстроки, где переменная часть (префикс) находится внутри назначения. Правильный подход — сначала извлечь из назначения токены вида Ф…ОТ / Ф…OT, затем искать их в карте префиксов.

План доработки (исправленный принцип)

  1. Один раз на выписку (по Данные) построить КартаПрефиксов = Соответствие(Префикс -> ДоговорДУ). Кэшировать по НомерСчета (для выписки Данные не меняются).
  2. Нормализовать ГдеИскать один раз (как сейчас: ВРег, замена F→Ф, удаление пробелов и дефисов).
  3. Из ГдеИскать извлечь кандидатов-префиксы: для каждого вхождения "Ф" найти ближайшее последующее "ОТ" (рус.) или "OT" (лат.); подстрока между ними — кандидат. Это в точности повторяет семантику СтрНайти("Ф"+Префикс+"ОТ"), но за один проход по строке.
  4. Каждого кандидата искать в КартаПрефиксов за O(1); первое совпадение — возврат ДоговорДУ. Цикл Для Каждого Выборка убрать.
  5. Сложность на платеж: было O(число_договоров × длина_назначения) с конкатенациями, станет O(длина_назначения).
// Было: O(договоры) на каждый платеж, с конкатенацией строки в цикле
Для Каждого Выборка Из Данные Цикл
    Если СтрНайти(ГдеИскать, "Ф" + Выборка.Префикс + "ОТ") > 0 Тогда Возврат Выборка.ДоговорДУ;
    ИначеЕсли СтрНайти(ГдеИскать, "Ф" + Выборка.Префикс + "OT") > 0 Тогда Возврат Выборка.ДоговорДУ;
    КонецЕсли;
КонецЦикла;

// Стало: карта строится один раз на выписку, на платеж — извлечение токенов + O(1) lookup
КартаПрефиксов = ПостроитьКартуПрефиксовЕРС(Данные);            // Префикс -> ДоговорДУ (1 раз на выписку/счёт)
Для Каждого Кандидат Из ИзвлечьПрефиксыИзНазначения(ГдеИскать) Цикл  // токены между "Ф" и "ОТ"/"OT"
    Договор = КартаПрефиксов.Получить(Кандидат);
    Если Договор <> Неопределено Тогда Возврат Договор; КонецЕсли;
КонецЦикла;
Проверка эквивалентности: при перекрывающихся токенах (например, несколько Ф…ОТ в одной строке) поведение должно совпасть с исходным перебором префиксов — обязательно сверить результат на контрольной выписке перед заменой.

Критерий приемки

Строки 1355-1359 не фигурируют в топ замера (нет многомиллионных итераций). Время ЕРС_ПоСчетуИНазначению < 1 с на весь сценарий; определённые договоры совпадают с исходными.

Блок 2. Кнопка «Разобрать отмеченные» — параллельность (IMDEV-9096)
Базовая линия (замер): 12 выписок за 09.06.2026, синхронный цикл ~383 с. Узкие места внутри КлиентБанк (правила, проведение) остаются; блок 2 сокращает стеновое время ожидания пользователя за счет параллельных фоновых групп.

Цель и подход

Вместо последовательного цикла «1 выписка = 1 полный КлиентБанк» — сгруппировать отмеченные выписки по (БанковскийСчет, ДоговорДУ) и обрабатывать до N групп параллельно в фоновых заданиях БСП. Внутри группы — последовательно (сохранить ПослеЗагрузкиВыписки).
