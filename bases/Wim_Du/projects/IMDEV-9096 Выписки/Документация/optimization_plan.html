1 Запрос 1: ДоговорДУПоСчету

ФункцияДоговорДУПоСчету(НомерСчета)
Строка SQL1286 — Результат = Запрос.Выполнить();
Вызовыстр. 2061 (на выписку), стр. 2202 (ERS fallback); всего 255 раз
Замер100,26 с — 30,66%
Суть запросаUNION: АналитическиеСчета + БанковскиеСчета по НомерСчета, сортировка ДоговорДУ УБЫВ

Проблема

Один и тот же тяжелый UNION выполняется для каждой выписки и повторно в ERS-fallback на тот же номер счета.

План доработки

  1. В начале ПрочитатьОбъекты собрать массив уникальных НомерСчета из ответа сервиса.
  2. Один пакетный запрос: ВЫБРАТЬ НомерСчета, ДоговорДУ ИЗ ... ГДЕ НомерСчета В (&СписокСчетов) (аналог текущей логики UNION).
  3. Заполнить КэшДоговоровПоСчету = Новый Соответствие (ключ — нормализованный номер счета).
  4. ДоговорДУПоСчету — сначала lookup в кэше; SQL только при промахе (редкий счет вне отбора).
  5. Сохранить текущее правило «более 1 договора — пустая ссылка».

Критерий приемки

Количество вызовов Запрос.Выполнить на стр. 1286 снижается с 255 до 1 (+ редкие промахи). Повторный замер «Прочитать» 1 день: доля стр. 1286 < 5%, экономия ~90 с.

2 Запрос 2: ЕРС_ДоговорДУ_ПоСчетуИСчетуДепо

ФункцияЕРС_ДоговорДУ_ПоСчетуИСчетуДепо(НомерСчета, НазначениеПлатежа)
Строка SQL1624 — Результат = Запрос.Выполнить();
Вызовстр. 2173 в цепочке ERS; 118 раз (по числу ЕРС-платежей)
ЗамерSQL: 73,33 с — 22,43%; вызов функции: 119,83 с — 36,64% (с циклом по выборке)
Суть запросаJOIN СчетаДепо с подзапросом по АС/БанковскиеСчета для &НомерСчета

Проблема

На каждый ЕРС-платеж — полный JOIN, хотя для одного НомерСчета результат запроса одинаков; различается только сопоставление с назначением платежа в цикле 1С.

План доработки

  1. Разделить функцию: ПолучитьДанныеДепоПоСчету(НомерСчета) (SQL) + НайтиДоговорВДанныхДепо(Данные, НазначениеПлатежа) (1С).
  2. Кэш Соответствие(НомерСчета -> ТаблицаЗначений) — SQL один раз на счет за проход ПрочитатьОбъекты.
  3. Данные ЕРС_ДоговорДУ_Отбор_ПоСчетуИНазначению (уже есть на выписку) использовать для раннего выхода до вызова депо-эвристики.
  4. Оставить существующую логику сопоставления в цикле (No.DU, ACC, KUP/PROC и т.д.) без изменения бизнес-правил.

Критерий приемки

Вызовов SQL на стр. 1624 — не более числа уникальных ЕРС-счетов (десятки, не сотни). Доля ЕРС_ПоСчетуИСчетуДепо в замере < 10%.

3 Запрос 3: ЕРС_ДоговорДУ_ПоПлатежномуПоручению

ФункцияЕРС_ДоговорДУ_ПоПлатежномуПоручению(БанковскийСчет, НазначениеПлатежа, Номер, Дата)
Строка SQL1725 — Результат = Запрос.Выполнить();
Вызовстр. 2164; 118 раз
Замер60,02 с — 18,36% (SQL) + цикл Пока Выборка.Следующий в 1С
Суть запросаВсе ПлатежноеПоручение за период ±5 дней по счету; номер ищется в коде

Проблема

Широкая выборка ПП на каждый платеж; фильтр по номеру документа — в цикле 1С после выгрузки всех строк периода.

План доработки

  1. Кэш по ключу (БанковскийСчет, НачалоДня(Дата)) — один SQL на пару счет+день выписки.
  2. В SQL добавить условие по номеру (или по списку номеров платежей выписки, если пакетировать по выписке).
  3. Заменить НАЧАЛОПЕРИОДА(...) МЕЖДУ ... ±5 дней на диапазон Дата >= &Начало И Дата <= &Конец (индекс по дате).
  4. Сузить окно с ±5 до ±1 дня, если бизнес допускает (согласовать с аналитиком).
  5. Поиск в 1С — по предзагруженной таблице в памяти, не повторный Запрос.Выполнить.

Критерий приемки

Вызовов SQL на стр. 1725 — по числу уникальных (счет, день), не по числу платежей. Экономия ~50 с на сценарии 1 день / 118 платежей.

4 Процедура с циклом: ЕРС_ДоговорДУ_ПоСчетуИНазначению

ФункцияЕРС_ДоговорДУ_ПоСчетуИНазначению(Данные, НомерСчета, НазначениеПлатежа)
Циклстр. 1355 — Для Каждого Выборка Из Данные Цикл
Тело цикластр. 1356, 1359 — СтрНайти(ГдеИскать, "Ф" + Префикс + "ОТ"/"OT")
Итерации~2 962 950 на каждую ветку СтрНайти
Замер~18,5 с (~5,7%) + нагрузка на CPU
КонтекстДанные — результат ЕРС_ДоговорДУ_Отбор_ПоСчетуИНазначению (1 SQL на ЕРС-выписку, ~25k договоров в таблице)

Проблема

Алгоритм O(платежи x договоры_ЕРС): для каждого платежа перебираются все префиксы договоров счета с конкатенацией строк в СтрНайти.

План доработки

  1. Нормализовать ГдеИскать один раз (уже есть: ВРег, замена F/пробелов/дефисов).
  2. При загрузке Данные (в ЕРС_ДоговорДУ_Отбор_ПоСчетуИНазначению или при первом обращении) построить Соответствие: ключ "Ф" + Префикс + "ОТ" и "Ф" + Префикс + "OT" -> ДоговорДУ.
  3. Альтернатива: извлечь из ГдеИскать токен вида Ф\d+ОТ регексом/разбором и lookup за O(1).
  4. Убрать цикл Для Каждого Выборка — заменить на 1-2 поиска по индексу.
  5. Кэшировать индекс префиксов на уровне НомерСчета (данные Данные не меняются в рамках выписки).
// Было: O(N) на платеж
Для Каждого Выборка Из Данные Цикл
    Если СтрНайти(ГдеИскать, "Ф" + Выборка.Префикс + "ОТ") > 0 Тогда ...

// Стало: O(1) lookup
ИндексПрефиксов = ПолучитьИндексПрефиксовЕРС(Данные); // один раз на выписку
ДоговорДУ = НайтиДоговорПоНазначениюЕРС(ГдеИскать, ИндексПрефиксов);

Критерий приемки

Строки 1355-1359 не фигурируют в топ-20 замера (0 многомillionных итераций). Время ЕРС_ПоСчетуИНазначению < 1 с на весь сценарий.

Блок 2. Кнопка «Разобрать отмеченные» — параллельность (IMDEV-9096)
Базовая линия (замер): 12 выписок за 09.06.2026, синхронный цикл ~383 с. Узкие места внутри КлиентБанк (правила, проведение) остаются; блок 2 сокращает стеновое время ожидания пользователя за счет параллельных фоновых групп.

Цель и подход

Вместо последовательного цикла «1 выписка = 1 полный КлиентБанк» — сгруппировать отмеченные выписки по (БанковскийСчет, ДоговорДУ) и обрабатывать до N групп параллельно в фоновых заданиях БСП. Внутри группы — последовательно (сохранить ПослеЗагрузкиВыписки).

ТемаРешение
Единица параллелизма Группа выписок с одинаковыми (БанковскийСчет, ДоговорДУ)
Лимит Не более N активных фонов (МаксПараллельныхГрупп, по умолчанию 3-5)
API фона ДлительныеОперации.ВыполнитьПроцедуруМодуляОбъектаОбработки -> ЗагрузитьГруппуВыписокВФоне
Передача данных XML: УпаковатьДанныеВXML / РаспаковатьДанныеИзXML (пакет в фон, результат в хранилище)
Проверка завершения ФоновыеЗадания.НайтиПоУникальномуИдентификатору — запрещено ДлительныеОперации.ЗаданиеВыполнено (исключение при аварии)
Сообщения из фона ДлительныеОперации.СообщенияПользователю после каждой группы
Ошибка группы Не прерывает очередь; текст в ОбщийЛог и Сообщить
Fallback Нет регистрации в ДополнительныеОтчетыИОбработки — синхронный режим без изменений UX
