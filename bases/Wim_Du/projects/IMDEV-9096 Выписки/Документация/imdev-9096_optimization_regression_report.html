1. Введение

В рамках задачи IMDEV-9096 выполнена оптимизация внешней обработки внЗагрузкаВыписокДУ (загрузка банковских выписок для доверительного управления). Исходная версия при обработке периода 01-05 июня 2026 выполнялась около 23 минут. Оптимизированная версия (v5.90, ispr5) обрабатывает тот же период за 2,6 минуты при полном сохранении бизнес-данных.

В данном отчете сравниваются только две версии:

  • Оригинал - erf_Оптимизация/внЗагрузкаВыписокДУ (версия до доработок)
  • Оптимизированная (ispr5) - erf_Оптимизация_Тест1/внЗагрузкаВыписокДУ (версия 5.90)

3. Виды оптимизации (версия 5.90)

В оптимизированной версии реализованы 4 блока оптимизации, не изменяющие бизнес-логику:

OPT-02 Пакетный кэш ДоговорДУ по счетам

Было: для каждого счета в цикле - отдельный SQL-запрос (ДоговорДУПоСчету), ~255 вызовов на период.

Стало: один пакетный SQL перед циклом (ЗаполнитьКэшДоговоровДУПоСчетам), результат в Соответствие, lookup без повторных запросов.

Эффект: ~255 SQL -> 1 SQL на определение договоров.

OPT-05 Кэш платежных поручений по окну дат

Было: повторные запросы ПП для каждого платежа в окне [-5; +1] день.

Стало: ленивый кэш КэшПП с ключом (счет + день), один запрос на уникальную пару.

Эффект: исключение повторных запросов ПП в рамках одного дня/счета.

OPT-17 Ленивый кэш данных депо

Было: SQL-запрос данных депо при каждом вызове ЕРС_ДоговорДУ_ПоСчетуИСчетуДепо.

Стало: ленивый кэш КэшДепоПоСчету, один запрос на уникальный счет.

Эффект: исключение повторных запросов депо для одного счета.

OPT-18 Кэш карт префиксов ЕРС

Было: SQL + построение карты префиксов при каждом вызове ЕРС_ДоговорДУ_ПоСчетуИНазначению.

Стало: кэш КэшКартПрефиксов, одна карта на счет, поиск без SQL.

Эффект: исключение повторных запросов и построения карт для одного счета.

Дополнительно (ispr5): исправлена семантика предупреждений "не определен ДоговорДУ". Введено множество СчетаБезДоговораДУ - предупреждение только при 0 строках в БД (как Результат.Пустой() в оригинале), а не при любом пустом договоре в кэше.

6. Исправление лишних предупреждений (ispr5)

В промежуточной версии (ispr4) в логе появились 5 дополнительных счетов (76 лишних сообщений), которых не было в оригинале. Причина: при использовании кэша предупреждение выводилось при любом пустом договоре, а в оригинале - только при Результат.Пустой() (0 строк в БД).

Решение: множество СчетаБезДоговораДУ заполняется при предзагрузке кэша (только для счетов с 0 строк). В блоке ЕРС предупреждение выводится только если счет в этом множестве. Семантика полностью соответствует оригиналу.

7. Детали регрессии

7.1. Методология сравнения MXL

Сравнение выполнено скриптом compare_mxl.py с multiset-сравнением по ключу:

(Data, NomerScheta, Dogovor, BankSchet, N) + balances[]

7.2. Методология сравнения ПП

Сравнение выполнено скриптом compare_pp_business.py по ключевым полям платежа:

(Data, Nomer, Summa, Плательщик счет, Получатель счет, Naznachenie platezha)

7.3. Методология сравнения логов

Сравнение выполнено скриптом verify_ispr5_run.py:

  • Подсчет сообщений "не определен ДоговорДУ" по каждому счету
  • Сравнение уникальных счетов между оригиналом и оптимиз.
  • Проверка идентичности набора счетов и количества повторов

8. Выводы

Оптимизация успешна. На примере периода 01-05.06.2026 оптимизированная обработка (версия 5.90, ispr5) показала:
  • Ускорение в 8,9 раза (1389,7 сек -> 156,3 сек)
  • Полное сохранение бизнес-данных выписок (2287 строк, MD5 идентичен)
  • Полное сохранение платежных документов (487 ПП, 0 расхождений по ключу)
  • Идентичный набор предупреждений (32 счета, 114 сообщений ДоговорДУ)
  • Без изменений предупреждений БИК (71 сообщение)

Четыре блока оптимизации (OPT-02, OPT-05, OPT-17, OPT-18) сокращают количество SQL-запросов за счет пакетной предзагрузки и ленивых кэшей, не меняя алгоритм определения договоров и не влияя на итоговые данные.

Исправление семантики предупреждений в ispr5 (СчетаБезДоговораДУ) устранило 5 лишних счетов из лога, вернув поведение к оригиналу.
