# IMDEV-8641: постановка на разработку (бизнес + технические вставки)

**Назначение документа:** единый текст для постановки задачи разработчикам и согласования с бизнесом. Смысл изложен простым языком; имена процедур, реквизитов, примеры запросов и контракты даны буквально, как в конфигурации.

**Исходные материалы:** [ГлобальнаяЛогика](../ГлобальнаяЛогика), [ПеречеьВидовОпераций](../ПеречеьВидовОпераций), [filter_plan_regl_operations_table_integration.md](filter_plan_regl_operations_table_integration.md).

---

## 1. Для бизнеса: зачем и что получим

При массовом закрытии периода по многим портфелям система строит **план** — перечень регламентных операций по каждому портфелю на день. Сейчас дальше по цепочке обрабатываются и заведомо «пустые» для данного портфеля сценарии, что удлиняет закрытие и нагружает сервер.

**Цель доработки:** в сценарии **розница ДУ / РДУ** до фактического запуска расчётов система **автоматически** снимает признак «нужно выполнять» с части строк плана там, где по данным уже видно, что операция для конкретного портфеля не нужна.

**Важно для прозрачности:** строки плана **не удаляются** — в таблице остаётся полная картина. Меняется только признак выполнения (в технических терминах: колонка **`Выполнять`** становится «не выполнять»), как если бы пользователь вручную снял флажок, но без ручной работы.

**Перечень видов операций**, для которых такая оптимизация разрешена, ведётся **в данных**: регистр сведений **`ВидыОптимизируемыхРегламентныхОперацийДУ`** со ссылками на элементы справочника **`ВидыОперацийЗакрытияПериода`**. Сопровождение может согласованно добавлять или убирать виды **без** правки «белого списка» в коде.

**Когда оптимизация срабатывает (оба условия одновременно):**

1. В настройках заполнена константа **`ПулРозницаДУ`** (ссылка на пул «розница ДУ»).
2. В **таблице плана на этот день** все портфели относятся **только** к этому пулу: у каждого реквизит **`Справочник.Портфели.Пул`** строго равен **значению константы** **`ПулРозницаДУ`** (не путать имя константы с именем реквизита **Пул**). Если в том же плане есть «чужой» пул или пустой пул — таблицу плана **не меняем**, поведение как сейчас.

**Вне зоны задачи (на первом этапе):** однопоточный режим закрытия без кэша **`ПланРеглОперацийПоДням`** — ветка **не** дорабатывается; см. раздел «Однопоточный режим» в [filter_plan_regl_operations_table_integration.md](filter_plan_regl_operations_table_integration.md).

## 2. Для разработки: объём метаданных и настройки

| Объект | Назначение |
|--------|------------|
| **Константа** `ПулРозницаДУ` | Тип **`СправочникСсылка.Пул`** (или фактический тип пула в WIM_FIn). Значение в коде: например **`ПулРозницаДУ = Константы.ПулРозницаДУ.Получить()`**. Пустая константа — **ранний выход**, фильтр плана не вызывается. |

Запись в регистре = «этот вид участвует в оптимизации под РДУ». В коде: **`РегистрыСведений.ВидыОптимизируемыхРегламентныхОперацийДУ`**. |
| **Код** | Процедура фильтрации плана; функции **`ПолучитьДанныеОптимизацииПланаПоВидуОперации`** и **`ПолучитьПортфелиДляСохраненияВыполненияВПлане`** в модуле менеджера РС **`ВидыОптимизируемыхРегламентныхОперацийДУ`** (`InformationRegisters/.../Ext/ManagerModule.bsl`). |

## 2.1. План расширения конфигурации (CFE) для базы WIM_FIn

Доработка вносится **расширением конфигурации**, без прямого изменения типовой поставки. Целевая информационная база на этапе разработки: **`Srvr="localhost";Ref="WIM_FIN";`** (фактическое имя **`Ref`** в списке баз должно совпадать с вашей публикацией; в репозитории выгрузка конфигурации — **WIM_FIn**).

### Шаг 1. Создать расширение

1. В **Конфигураторе** или **EDT** создать новое расширение для данной ИБ (пустой каркас или по шаблону проекта).
2. Задать **префикс** имён расширения (синоним, префикс процедур перехвата) по регламенту вашей команды — единый на всё расширение IMDEV-8641.
3. Убедиться, что расширение **подключается** к серверу **`localhost`** и информационной базе с указанным **`Ref`**.

### Шаг 2. Заимствовать из основной конфигурации

Объекты заимствуются в расширение (**свойство принадлежности** «Заимствованный» / `ObjectBelonging=Adopted`), чтобы перехватывать код в точке встраивания.

| Объект метаданных | Зачем |
|-------------------|--------|
| **Обработка** **`ГрупповоеВыполнениеЗакрытияПериодов`** | Нужен **модуль объекта** (`ObjectModule.bsl`): в нём расположена процедура **`ВыполнитьМногопоточноеЗакрытиеПериодовПортфелей`**, куда вставляется вызов фильтра плана. Путь в выгрузке: `DataProcessors/ГрупповоеВыполнениеЗакрытияПериодов/Ext/ObjectModule.bsl`. |

Другие объекты (например **`РегистрыСведений.НастройкиЗакрытияПериода`**) **не заимствуются**: к ним обращаются из кода расширения по типовым именам, как в основной конфигурации.

### Шаг 3. Перехват процедуры — **`ИзменениеИКонтроль`**

1. В **заимствованном** модуле объекта **`ГрупповоеВыполнениеЗакрытияПериодов`** оформить перехват процедуры **`ВыполнитьМногопоточноеЗакрытиеПериодовПортфелей`** с вариантом встраивания **`ИзменениеИКонтроль`** (в XML-метаданных расширения — `ModificationAndControl`).
2. Скопировать тело типовой процедуры в модуль расширения и внести **точечную вставку** согласно разделу **3**: **после** получения таблицы плана вызовом **`РегистрыСведений.НастройкиЗакрытияПериода.ПланРеглОпераций(...)`** для очередного дня и **до** **`ПланРеглОперацийПоДням.Вставить(День, тПланРеглОперацийПоДням)`** — вызвать процедуру фильтрации плана из расширения (см. шаг 4), передав **`тПланРеглОперацийПоДням`** (или эквивалентную **`ТаблицаЗначений`**) и дату дня.
3. Альтернативы **`Перед`** / **`После`** для этой процедуры **не подходят**: вставка в **середину** алгоритма после расчёта плана и до помещения в соответствие — только через **`ИзменениеИКонтроль`** (или эквивалентное ручное дублирование с риском расхождения при обновлении — нежелательно).

После обновления типовой конфигурации перехват **следует пересверить**: конфликтные фрагменты в модуле расширения разрешить вручную, сохранив вставку вызова фильтра.

### Шаг 4. Новые объекты (собственные объекты расширения)

Создаются **в составе расширения**, не как заимствования.

| Объект | Назначение |
|--------|------------|
| **Константа** **`ПулРозницаДУ`** | Тип **`СправочникСсылка.Пул`**. Пустая — фильтр не вызывается (ранний выход в процедуре фильтра). |
| **Регистр сведений** **`ВидыОптимизируемыхРегламентныхОперацийДУ`** | Измерение **`ВидОперации`** (`СправочникСсылка.ВидыОперацийЗакрытияПериода`). Первичное наполнение пятью видами раздела **4**. |
| **Модуль менеджера** этого регистра | **Экспортная** процедура фильтрации плана (имя по соглашению команды, напр. **`ОтфильтроватьТаблицуПланаРеглОпераций`**) и функции **`ПолучитьДанныеОптимизацииПланаПоВидуОперации`**, **`ПолучитьПортфелиДляСохраненияВыполненияВПлане`** — см. разделы **6–8**. |

При необходимости общий модуль расширения для вспомогательной логики допускается; минимальный вариант — весь серверный код фильтра в **модуле менеджера** РС.

### Шаг 5. Подключение к базе и приёмка

1. Собрать **CFE-файл** или загрузить расширение из **EDT** в ИБ **`localhost` / `WIM_FIN`**.
2. Включить расширение, проверить отсутствие ошибок компиляции.
3. Выдать **роли** на новые объекты (константа, регистр, при необходимости запись константы) пользователям сценария закрытия; доступ к обработке **`ГрупповоеВыполнениеЗакрытияПериодов`** — не уже типового закрытия.
4. Прогон по критериям раздела **10**.

**Инструменты сценария в репозитории:** заимствование объектов и заготовка перехвата — навыки **`cfe-borrow`**, **`cfe-patch-method`** (параметр **`ModificationAndControl`** / **`ИзменениеИКонтроль`**); валидация расширения — **`cfe-validate`**.

## 3. Точка встраивания и цепочка исполнения

**Где вставить вызов фильтра (многопоточный режим):**

- Обработка **`ГрупповоеВыполнениеЗакрытияПериодов`**, модуль объекта **`ObjectModule.bsl`**.
- Процедура **`ВыполнитьМногопоточноеЗакрытиеПериодовПортфелей`**.
- **Сразу после** вызова **`РегистрыСведений.НастройкиЗакрытияПериода.ПланРеглОпераций`** для очередного дня и **до** строки вида **`ПланРеглОперацийПоДням.Вставить(День, тПланРеглОперацийПоДням)`**.

**Почему до `Вставить`:** таблица по дням попадает в **`ДопПараметры.ПланРеглОперацийПоДням`** (`Соответствие`); далее **`СформироватьРеглОперацииПоГруппе`** нарезает план и вызывает **`ФоновыеЗаданияСервер.СоздатьПланРегламентныхОперацийДУ`**. Корректировка **`Выполнять`** должна быть **до** помещения в соответствие, чтобы все потоки видели уже отфильтрованный план.

**Источник таблицы плана:** функция **`ПланРеглОпераций`** модуля менеджера **`РегистрыСведений.НастройкиЗакрытияПериода`** (`InformationRegisters/НастройкиЗакрытияПериода/Ext/ManagerModule.bsl`).

**Дальше по цепочке (для понимания приёмки):**

- **`ФоновыеЗаданияСервер.СоздатьПланРегламентныхОперацийДУ`** переносит колонку **`Выполнять`** в ТЧ **`Операции`** документа **`ПланРегламентныхОперацийДУ`** (в ТЧ тип **`Булево`**).
- **`ПолучитьСписокОперацийДляВыполнения`** (модуль объекта **`ПланРегламентныхОперацийДУ`**) не отбирает строки с **`Выполнять = Ложь`**.

## 5. Структура таблицы плана (что трогаем)

Результат **`ПланРеглОпераций`** — **`ТаблицаЗначений`**. Минимально нужны колонки:

| Колонка | Смысл | Тип / значение для отсечения |
|---------|--------|------------------------------|
| **`Выполнять`** | Выполнять ли в рамках плана | **`Число`**: **0** или **1** (в запросе — `МАКСИМУМ` по 0/1). Для «не выполнять» в коде: **`СтрокаПлана.Выполнять = 0`**. |
| **`Портфель`** | Портфель | **`СправочникСсылка.Портфели`** |
| **`ВидОперации`** | Вид операции закрытия | **`СправочникСсылка.ВидыОперацийЗакрытияПериода`** |
| **`ВремяРеглОпераций`** | Время группы | **`Дата`** |
| **`Родитель`** | Группа в иерархии видов | Ссылка или **`Неопределено`** |

Поведение при **`Выполнять = Неопределено`** в строке плана — зафиксировать при реализации (в свод шага 2 обычно не включают неоднозначные строки или трактуют отдельно).

## 6. Алгоритм фильтра (логика шагов 1–3)

**Шаг 1.** Если **`НЕ ЗначениеЗаполнено(ПулРозницаДУ)`** — **выход** без изменений таблицы.

Иначе проверка: **все** уникальные **`Портфель`** из таблицы плана при соединении с **`Справочник.Портфели`** имеют **`Пул`** равным **значению константы** **`ПулРозницаДУ`**. Если найден хотя бы один портфель с другим или пустым пулом — **выход** без изменений.

**Шаг 2.** Свод: **`ВЫБРАТЬ РАЗЛИЧНЫЕ ВидОперации`** из строк, где **`Выполнять <> 0`**.

**Шаг 3.** Для каждого **`ВидОперации`** из свода:

1. Собрать **`МассивПортфелей`** — уникальные **`Портфель`**, где **`ВидОперации`** совпадает и **`Выполнять <> 0`**.
2. Вызвать **`ПолучитьДанныеОптимизацииПланаПоВидуОперации`** с параметрами **`ВидОперации`**, **`День`**, **`МассивПортфелей`**.
3. Если ответ — флаг **`Ложь`** (вида нет в **`ВидыОптимизируемыхРегламентныхОперацийДУ`**) — **строки этого вида не менять**.
4. Если ответ — **`Истина`** и второй ключ — **`Массив`** портфелей «оставить выполнение»: для всех строк плана с этим **`ВидОперации`**, чей **`Портфель`** **не** в массиве, установить **`Выполнять = 0`**. Если массив **пустой** — обнулить **`Выполнять`** у **всех** строк плана с этим видом (где до правки было **`Выполнять <> 0`**).

**`ПолучитьПортфелиДляСохраненияВыполненияВПлане` (п. 3.2):** по **`МассивПортфелей`**, **`День`**, **`ВидОперации`** ветвление **`Если` / `ИначеЕсли`** по **пяти** видам из раздела 4 (ссылки на элементы справочника); в каждой ветке — **свои** специализированные запросы (тексты — отдельной проработкой, те же источники данных, что типовая процедура закрытия для этого вида). Возврат ветки — **`Массив`** портфелей, для которых операцию **оставляем** (подмножество входа или пустой). Ветка **`Иначе`** (вид не совпал ни с одной из пяти ссылок в коде): возврат **того же** **`МассивПортфелей`**, что на входе — **все** эти портфели остаются с **`Выполнять`** без изменений. Подробно — [filter_plan_regl_operations_table_integration.md](filter_plan_regl_operations_table_integration.md), п. 3.2.

Блок-схема в Mermaid: [filter_plan_regl_operations_table_integration.md](filter_plan_regl_operations_table_integration.md).

## 7. Пример много-пакетного запроса (иллюстрация шагов 1–2)

Ниже **не** финальный производственный текст, а **шаблон** для согласования подхода: табличный параметр **`&ТаблицаПлана`**, параметр **`&ПулРозницаДУ`**. Имена временных таблиц (`ВТ_План`, `ВТ_ПортфелиПлана`, …) можно заменить на принятые в модуле.

```bsl
// Иллюстрация: первый пакет кладет план во ВТ, второй проверяет пул,
// третий готовит свод видов при Выполнять <> 0.
ТекстЗапроса =
"ВЫБРАТЬ
    ТаблицаПлана.Портфель КАК Портфель,
    ТаблицаПлана.ВидОперации КАК ВидОперации,
    ТаблицаПлана.Выполнять КАК Выполнять
ПОМЕСТИТЬ ВТ_План
ИЗ
    &ТаблицаПлана КАК ТаблицаПлана
;

////////////////////////////////////////////////////////////////////////////////
ВЫБРАТЬ РАЗЛИЧНЫЕ
    ВТ_План.Портфель КАК Портфель
ПОМЕСТИТЬ ВТ_ПортфелиПлана
ИЗ
    ВТ_План КАК ВТ_План
;

////////////////////////////////////////////////////////////////////////////////
ВЫБРАТЬ ПЕРВЫЕ 1
    ИСТИНА КАК ЕстьНарушениеПула
ИЗ
    ВТ_ПортфелиПлана КАК ВТ_ПортфелиПлана
        ВНУТРЕННЕЕ СОЕДИНЕНИЕ Справочник.Портфели КАК Портфели
        ПО ВТ_ПортфелиПлана.Портфель = Портфели.Ссылка
ГДЕ
    Портфели.Пул <> &ПулРозницаДУ
    ИЛИ Портфели.Пул = ЗНАЧЕНИЕ(Справочник.Пул.ПустаяСсылка)
;

////////////////////////////////////////////////////////////////////////////////
ВЫБРАТЬ РАЗЛИЧНЫЕ
    ВТ_План.ВидОперации КАК ВидОперации
ПОМЕСТИТЬ ВТ_ВидыКОбработке
ИЗ
    ВТ_План КАК ВТ_План
ГДЕ
    ВТ_План.Выполнять <> 0
";
```

**Замечание по метаданным:** в выгрузке **WIM_FIn** справочник пулов в метаданных — **`Пул`** (в запросах: **`Справочник.Пул`**, пустая ссылка — **`ЗНАЧЕНИЕ(Справочник.Пул.ПустаяСсылка)`**; в типах — **`СправочникСсылка.Пул`**). Имя объекта совпадает с `Catalogs/Пул` в дереве конфигурации.

**Замечание по логике:** если третий пакет вернул строку (**`ЕстьНарушениеПула`**), дальнейшие пакеты для фильтра **не выполнять**, исходную **`ТаблицаЗначений`** плана не менять. Если нарушения нет, четвёртый пакет (или отдельный запрос) выгружает **`ВТ_ВидыКОбработке`** для цикла шага 3 в коде. На практике проверку «все портфели из пула» иногда делают сравнением **`КОЛИЧЕСТВО(РАЗЛИЧНЫЕ Портфель)`** до и после соединения с **`Пул = &ПулРозницаДУ`** — эквивалентно по смыслу.

## 8. Контракт функций модуля менеджера РС ВидыОптимизируемыхРегламентныхОперацийДУ (п. 3.1 и 3.2)

**`ПолучитьДанныеОптимизацииПланаПоВидуОперации` — вход:** **`ВидОперации`**, **`День`**, **`МассивПортфелей`**.

**Выход (структура):**

- Вид **не** в **`ВидыОптимизируемыхРегламентныхОперацийДУ`**: один ключ — признак **`Ложь`** (второй ключ не используется).
- Вид **в** **`ВидыОптимизируемыхРегламентныхОперацийДУ`**: после вызова **`ПолучитьПортфелиДляСохраненияВыполненияВПлане`** — признак **`Истина`** + **`Массив`** портфелей для **сохранения** **`Выполнять = 1`** (остальным строкам с этим видом в плане — **0**).

**`ПолучитьПортфелиДляСохраненияВыполненияВПлане`:** вход **`МассивПортфелей`**, **`День`**, **`ВидОперации`**; выход только **`Массив`** портфелей (без таблицы значений с колонкой **`Портфель`**). Ветвление **`Если` / `ИначеЕсли`** по **пяти** видам (раздел 4); **`Иначе`** — возврат **того же** **`МассивПортфелей`**, что на входе (все остаются с **`Выполнять`**). Ветки можно вынести во вспомогательные функции модуля менеджера с тем же контрактом.

---

## 9. Производительность

- Не обходить десятки тысяч портфелей в цикле с чтением реквизитов по одному.
- Ранний выход при пустой **`ПулРозницаДУ`** без тяжёлых пакетов.
- Шаг 1 и 2 — пакетные запросы; шаг 3 — цикл **по видам** (их мало), внутри **`ПолучитьПортфелиДляСохраненияВыполненияВПлане`** — запросы с параметром-массивом портфелей.

## 10. Критерии приёмки (минимум)

1. При незаполненной **`ПулРозницаДУ`** или смешанных пулах в таблице плана за день **`Выполнять`** у всех строк совпадает с исходом **`ПланРеглОпераций`**.
2. При заполненной **`ПулРозницаДУ`** и однородном пуле для видов **не** из **`ВидыОптимизируемыхРегламентныхОперацийДУ`** строки плана по этим видам **не меняются**.
3. Для вида **из** **`ВидыОптимизируемыхРегламентныхОперацийДУ`**: строки с портфелями, не попавшими в «массив оставить» (**`ПолучитьПортфелиДляСохраненияВыполненияВПлане`**), получают **`Выполнять = 0`**; остальные строки этого вида остаются с **1**.
4. Документ **`ПланРегламентныхОперацийДУ`** после **`СоздатьПланРегламентныхОперацийДУ`** содержит в ТЧ **`Операции`** согласованные **`Выполнять`**; операции с **`Ложь`** не попадают в исполнение через **`ПолучитьСписокОперацийДляВыполнения`**.
5. Регистр **`ВидыОптимизируемыхРегламентныхОперацийДУ`** заполнен согласованно с пятью видами раздела 4 (ссылки на элементы справочника в базе).
