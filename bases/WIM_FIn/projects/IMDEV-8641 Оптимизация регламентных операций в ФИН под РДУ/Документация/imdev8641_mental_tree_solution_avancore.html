Оптимизация регламентного закрытия периода: цель, дерево решения и основные идеи

Ускорить массовое закрытие периода по портфелям РДУ за счет того, что заведомо лишние регламентные операции не доходят до исполнения: до запуска типовой цепочки по портфелю заранее снимается признак выполнения в плане на день (строки плана не удаляются), а при отсутствии выполняемых операций по группе не создаются пустые планы. Изменения доставляются как расширение, без правок состава типовой конфигурации.
Главное 1
Фильтрация выполняется сразу по всему списку портфелей, а не по одному портфелю.
Главное 2
У лишних операций снимается только признак Выполнять, строки плана сохраняются.
Главное 3
Если по группе нет исполняемых строк, новый документ плана не создается.

1) Текущий процесс и целевое изменение

Как сейчас (типовая методика)

  • Сначала строится общий план на день по списку портфелей: ПланРеглОпераций.
  • План кладется в ПланРеглОперацийПоДням.
  • Дальше типовая цепочка закрытия идет по каждому портфелю отдельно: для портфеля выбирается срез плана, затем по группам формируется и исполняется ПланРегламентныхОперацийДУ.
  • Выполняются строки, где Выполнять = Истина. При этом для каждой такой операции типовая цепочка выполняет не только саму регламентную операцию, но и связанные с ней запросы к данным (проверки, выборки, подготовка контекста), что на больших объемах накапливается по числу портфелей и строк плана.
  • На больших объемах это превращается в много повторяющихся проходов "портфель за портфелем" (и внутри - по группам операций).

Как будет после оптимизации

  • Между построением плана и вставкой в кэш запускается фильтр сразу по всем портфелям из списка закрытия: один общий план на день обрабатывается целиком, без предварительного разбиения «портфель за портфелем» на этом этапе.
  • Отбор «нужен ли расчет этого вида по портфелю» выполняется в модуле менеджера регистра ВидыОптимизируемыхРегламентныхОперацийДУ запросами к тем же источникам данных, что и у соответствующей типовой регламентной операции (регистры бухгалтерии и накопления, справочники, документы). В тексте запроса оставляют минимально достаточный фрагмент из той же логики: он должен однозначно дать ответ «расчет по портфелю возможен в принципе», не воспроизводя полный набор проверок типовой процедуры. Запросы выполняются пакетно по массиву портфелей из плана; у портфелей вне найденного подмножества в строках плана снимается Выполнять.
  • Если по группе после фильтра нет исполняемых строк, новый пустой план не создается.
  • Основная логика типового исполнения остается неизменной.

2) Дерево принятия решения

Шаг 0. Проверка сценария и свод исполняемых строк плана
Что делаем?
Получаем план на день из НастройкиЗакрытияПериода.ПланРеглОпераций. Проверяем константу ПулРозницаДУ и однородность пула у портфелей плана; если условия не выполнены - сразу выход, план не меняется. Иначе берем только строки с Выполнять = 1 и только виды операций из регистра оптимизации.
Для чего? Чтобы либо не трогать типовой план при неверном сценарии или неоднородном пуле, либо получить сжатый перечень строк для дальнейшего ускорения: видно, что потенциально нужно и с каким признаком Выполнять операции стартуют в типовой цепочке, при этом в работу попадают только целевой сценарий "розница ДУ" с однородным пулом, без лишних видов и без строк с уже снятым выполнением.
Шаг 1. Отбор портфелей по виду операции
Что делаем?
Собираем массив портфелей из плана по текущему виду и вызываем ПолучитьПортфелиДляСохраненияВыполненияВПлане.
Для чего? Чтобы по минимальным запросам к тем же данным, что и у типовой операции, оставить в плане только портфели, по которым расчет данного вида в принципе возможен; остальным по этому виду признак выполнения потом снимают пакетно.
Шаг 2. Пакетное снятие признака выполнения в плане
Что делаем?
Одним пакетным запросом ставим Выполнять = 0 строкам текущего вида, чей портфель не вошел в список "оставить".
Для чего? Чтобы до запуска типовой цепочки убрать из исполнения заведомо лишние строки плана, не удаляя сами строки и не меняя состав типовой конфигурации.
Шаг 3. Запись плана в кэш дня и передача в типовую цепочку
Что делаем?
Возвращаем обновленный план в ПланРеглОперацийПоДням, дальше работает типовой процесс.
Для чего? Чтобы все потоки и последующие шаги закрытия видели уже отфильтрованный план: меньше операций дойдет до исполнения и связанных запросов, при этом механизм закрытия остается типовым.
Шаг 4. Пропуск группы без исполняемых строк и без документа плана
Что делаем?
Если при формировании по группе нет существующего плана и количество строк с Выполнять = 1 равно нулю, группа пропускается.
Итог: не создается пустой документ плана.
Для чего? Чтобы не создавать новый пустой ПланРегламентныхОперацийДУ и не запускать связанный проход, если по срезу плана выполнять нечего и документа плана еще не было.

3) Ключевые принципы оптимизации

  • Исполнение без удаления строк плана: таблица плана остается полной для прозрачности и совместимости, меняется только признак Выполнять.
  • Состав оптимизируемых видов задается данными: перечень видов операций, на которые распространяется ускорение, хранится в регистре ВидыОптимизируемыхРегламентныхОперацийДУ.
  • Пакетные запросы по всему набору портфелей: один запрос сразу по массиву портфелей обычно быстрее, чем много отдельных запросов, каждый из которых обрабатывает один портфель.
  • Сразу завершать при несоответствии сценарию: если условия не соответствуют сценарию "розница ДУ", ресурсоемкая часть доработки (фильтрация и корректировка плана) не выполняется.
  • Не создавать пустые планы по группе: если по группе нет строк с Выполнять = 1, новый документ плана не формируется.
Формальный критерий "лишняя операция": после фильтрации по виду операции и портфелю строка остается с Выполнять = 0; если в группе не осталось строк с Выполнять = 1, группа не запускается.
