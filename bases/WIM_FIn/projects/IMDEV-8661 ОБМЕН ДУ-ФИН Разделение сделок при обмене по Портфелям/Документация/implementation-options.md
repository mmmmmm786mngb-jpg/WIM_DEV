# IMDEV-8661 - Варианты реализации двухволнового обмена

## 1. Исходная идея

Целевой сценарий из `Текстовый документ.txt`:

1. Волна 1: `6` потоков по `СделкиTn` и `1` общий поток без `СделкиTn`.
2. Волна 2: `6` потоков по `Документ.Сделка` и `1` общий поток без `СделкиTn`.

Ожидаемый эффект:

- уменьшение времени за счет исключения очень длинного общего пакета;
- снижение риска пересечений при параллельной загрузке по одинаковым GUID.

## 2. Вариант A - минимальные изменения (низкий риск)

### Идея

- Не ломать текущий конвейер `СделкиTn`.
- Добавить вторую волну после полного завершения первой.
- Вторую волну реализовать отдельными флагами: `ЭтоПакетСделка`, `ПулСделка`.

### Что менять

- `EPF/.../Ext/ObjectModule.bsl`:
  - расширить структуру параметров;
  - добавить второй проход оркестрации;
  - добавить функцию выборки `Документ.Сделка` по портфелям.
- `VTB_ОбщийМодуль`:
  - принять новые параметры;
  - в `ПолучениеДанныеXMLПоПравиламКонвертации` добавить ветку для правила `Сделка`.

### Плюсы

- минимальное влияние на существующий поток `СделкиTn`;
- понятный rollback;
- можно включать через feature-флаг.

### Минусы

- два прохода увеличивают число фоновых заданий;
- потребуется аккуратная синхронизация рассылки и завершающих операций.

## 3. Вариант B - матричная оркестрация волн (рекомендуемый)

### Идея

- Выделить единый механизм "волна обмена":
  - `СделкиTn`;
  - `Сделка`.
- Для каждой волны явная матрица:
  - общий поток исключает целевой тяжелый тип;
  - пакетные потоки включают только целевой тип.

### Что менять

- В EPF сделать универсальную процедуру `ВыполнитьВолнуОбмена(ТипВолны)`.
- В `VTB_ОбщийМодуль`:
  - искать правила по паре `Имя + ОбъектВыборки`;
  - централизовать логику отбора по пулу.
- Добавить единый протокол статуса волны: старт, завершение, ошибки.

### Плюсы

- прозрачная логика и проще сопровождать;
- легче расширить на третий тип "тяжелых" объектов;
- меньше ручных условий в коде.

### Минусы

- больше объем рефакторинга по сравнению с вариантом A;
- выше требования к регрессионному тестированию.

## 4. Вариант C - разделение только на уровне правил (не рекомендуется)

### Идея

- Попытаться разрулить проблему только через `Template.txt` (правила выгрузки), без расширения параметров и оркестрации.

### Плюсы

- меньше изменений в BSL-коде.

### Минусы

- логика становится неявной и хрупкой;
- сложно гарантировать порядок волн и корректное ожидание завершения;
- высокий риск регрессий при обновлении макета правил.

## 5. Важное уточнение по требованиям

- Во второй волне есть семантическая неоднозначность:
  - вариант 1: общий поток исключает только `СделкиTn`;
  - вариант 2: общий поток исключает и `СделкиTn`, и `Документ.Сделка`.
- Для устранения дублей и конфликтов по GUID безопаснее вариант 2.
- Если нужно строго оставить только исключение `СделкиTn`, это стоит зафиксировать отдельным бизнес-решением.

## 6. Рекомендуемый путь внедрения

1. Внедрять вариант B с возможностью быстрого отката к текущему режиму.
2. Запускать волну 2 только после полного завершения всех задач волны 1.
3. Рассылку и "финальные операции после обмена" выполнять только в последнем потоке второй волны.
4. Добавить диагностику в ЖР:
   - номер волны;
   - номер потока;
   - количество объектов в пуле;
   - текст ошибки из фонового задания.

## 7. Критерии приемки

- Нет ошибок `PRIMARY KEY` при параллельной загрузке `СделкаTn`.
- Средняя длительность полного обмена не хуже текущей, целевой результат - лучше текущей.
- Результат загрузки идентичен текущему по составу объектов и снятию регистрации изменений.
- При падении любого потока второй волны обмен завершается с корректной диагностикой и без "тихих" успехов.
