1. Введение и постановка задачи

Между двумя базами «Аванкор» идёт регулярный обмен данными:

  • Аванкор-ДУ (PROD_AVC_DU) — учёт доверительного управления, источник операций.
  • Аванкор-ФИН (PROD_AVC_FIN20 / AVC_FIN20) — финансовая учётная система, приёмник.

Из описания задачи (JIRA IMDEV-8643, отчёт E.Shved / L.Reshetnikova):

«При перепроведении операций за период в Аванкор-ДУ, в систему Аванкор-ФИН обменом загружаются повторно эти же операции. В результате в Аванкор-ФИН ранее загруженные сделки распроводятся, что приводит к необходимости повторного запуска сессии «групповое закрытие периода». … Просим разработать механизм, который позволит выполнять перепроведение в Аванкор-ДУ без нарушения корректности данных и повторных действий в Аванкор-ФИН.»

Сопроводительное письмо уточняет деловой эффект: сделки в ФИН меняют статус «исполнены» → «не исполнены», команда финансового департамента вынуждена повторно выполнять работу согласно daily, что срывает сроки сдачи отчётности.

Уточнение по объёму анализа

В задании указано расширение VTB_NDFL_Exchange. По факту это отдельное расширение для обмена НДФЛ (документы «Начисление НДФЛ по портфелю/УК», план обмена «ОбменНДФЛ»), оно не управляет проведением сделок. Механизм, который распроводит сделки, целиком находится в расширении src\cfe\VTB_ExchangeDU — на нём и сфокусирован анализ.

2. Описание проблемы (по материалам пользователя)

Пример по договору ДУ 5609 «ООО СК НСГ». Последовательность из файла СК НСГ распроведение.docx:

2.1. Исходное (корректное) состояние в ФИН

На 08.06.2026 сделки проведены и сверены с первичными отчётами. Признак сделки в журнале — лист с галочкой (документ проведён, бизнес-процесс исполнен).

2.2. Перепроведение в ДУ → повторная загрузка в ФИН

08.06.2026 в конце дня в базе PROD_AVC_DU было выполнено перепроведение операций за июнь по этому клиенту. После этого обмен повторно загрузил сделки в ФИН, т.к. программа обнаружила, что в них «было изменение».

2.3. Результат — сделки распроведены

После повторной загрузки сделки в ФИН сменили статус на «неисполненные». Признак сделки изменился на лист с галочкой и часиками (документ требует перепроведения / не исполнен). Данные в ОСВ изменились (сравните «Сальдо на конец периода»).

Ключевая цитата пользователя (суть бага с точки зрения бизнеса)

«Решение ставить дату запрета редактирования на Т-1 не вариант. Как только открываешь период, чтоб внести уточнение по субконто или ещё какой-нибудь аналитики, обмен моментом загружает в открытый период данные из DU, и необходимо вновь всё перепроводить и сверять в ФИН. … В некоторых случаях необходимо пометить на удаление все бизнес-процессы и перепроводить заново, т.к. не списываются комиссии. По времени это может занимать 20–40 минут — один торговый день.»

2.4. Дата запрета изменения данных установлена — но не помогает

Пользователи установили даты запрета изменения данных по портфелям (раздел «Портфель», по каждому договору ДУ). Из второго файла Распроведение бизнес-процессов в FIN20.docx:

«В системе PROD_AVC_FIN20 в портфеле с установкой даты запрета изменения данных на 07.06.2026 по состоянию на 16.06.2026 распровелись сделки от 01.06.2026. Это происходит, когда в системе PROD_AVC_DU перепроводят и трогают прошедшие и завершённые бизнес-процессы текущей датой.»

На последнем скриншоте видно, что бизнес-процесс «Сделка T+n» по портфелю ДУ 9775 содержит цепочку документов (Открытие плановой позиции, Валютирование, Оплата комиссии брокера, Перерегистрация ц/б и т.д.). Именно перезапуск шагов этого БП и распроводит/перепроводит документы-сделки в ФИН.

3. Архитектура обмена ДУ → ФИН (технология)

Обмен реализован как веб-сервис на стороне ФИН + универсальный обмен данными XML + расширение VTB_ExchangeDU с собственными регистрами-«очередями» и пост-обработкой.

3.1. Точка входа — веб-сервис

Файл: VTB_ExchangeDU\WebServices\NDFL\Ext\Module.bsl, функция upload_data (переопределена через &Вместо, IMDEV-3254). ДУ присылает XML-порцию данных, ФИН её загружает:

// Веб-сервис, принимающий данные из ДУ (упрощённо)
Если Не ПривилегированныйРежим() Тогда
    УстановитьПривилегированныйРежим(Истина);
КонецЕсли;

ДатыЗапретаИзмененияСлужебный.ПропуститьПроверкуЗапретаИзменения();  // <-- см. раздел 5

ОбработкаXML = Обработки.УниверсальныйОбменДаннымиXML.Создать();
ЗаполнитьЗначенияСвойств(ОбработкаXML, СтруктураПараметров,
    "ИмяФайлаОбмена, ЗагружатьДанныеВРежимеОбмена,
    ЗаписыватьВИнформационнуюБазуТолькоИзмененныеОбъекты, ...");
ОбработкаXML.РежимОбмена = "Загрузка";
ОбработкаXML.ВыполнитьЗагрузку();

3.2. Регистры-«очереди» в расширении

В ходе загрузки правила обмена раскладывают изменившиеся объекты по регистрам сведений (каждая запись = «что сделать с объектом после загрузки»):

Регистр сведенийНазначение (операция после обмена)
ExchDU_СписокДокументовДляПроведенияпровести документ
ExchDU_СписокДокументовДляОтменыПроведенияотменить проведение / пометить на удаление
ExchDU_СписокНепроведенныхДокументовзаписать без проведения
ExchDU_СписокДокументовДляУдаленияпометить на удаление
ExchDU_СписокНовыхБП / …НовыхБПдляСтартазаписать и стартовать новый бизнес-процесс
ExchDU_СписокИзмененныхБП / …ИзмененныхБПдляСтартаотменить шаги БП и перезапустить их
ExchDU_СписокЗавершенныхБП / …НовыхЗавершенныхБПпровести и завершить БП
ExchDU_СписокБПНаУдаление / …НовыхБПНаУдалениепометить БП на удаление

3.3. Запуск пост-обработки

После загрузки порций запускается обработка ExchDU_ЗапускОперацийПослеОбмена (доп. обработка БСП «Обработки объектов после загрузки из DU», v3.00). Она читает все регистры-очереди, формирует единую таблицу операций и выполняет их фоново, с разбивкой по портфелям (см. ExchDU_ОбработкаОбъектовПослеЗагрузки.ВыполнениеОперацийСДокументамиБП).

ДУ: перепроведение операций за период (в т.ч. закрытый), «трогаются» завершённые БП текущей датой.
Обмен выгружает из ДУ изменившиеся объекты (сделки, бизнес-процессы, документы цепочки).
ФИН, веб-сервис upload_data: привилегированный режим + отключение проверки даты запрета.
Универсальный обмен XML грузит «только изменённые объекты», правила раскладывают их по регистрам-очередям.
Пост-обработка читает очереди и выполняет ОтменаПроведения / перезапуск шагов БП.
Сделки в ФИН становятся «не исполнены» (значок с часиками), ОСВ «плывёт» → нужно групповое закрытие периода заново.

4. Механизм пост-обработки (детально, с кодом)

Все процедуры-исполнители находятся в общем модуле VTB_ExchangeDU\CommonModules\ExchDU_ОбработкаОбъектовПослеЗагрузки\Ext\Module.bsl. Диспетчеризация — по имени операции: Выполнить("Выполнение_" + ИмяОперации + "(СтрокаДанные)").

4.1. Прямая отмена проведения документа

Срабатывает для записей очереди ExchDU_СписокДокументовДляОтменыПроведения:

Процедура Выполнение_ДокументДляОтменыПроведения(СтрокаДанные)
    ДокументСсылка = СтрокаДанные.ОбъектДляОперации;
    Попытка
        ДокументОбъект = ДокументСсылка.ПолучитьОбъект();
        Если ДокументСсылка.ПометкаУдаления Тогда
            ДокументОбъект.УстановитьПометкуУдаления(Истина);
        Иначе
            ДокументОбъект.Записать(РежимЗаписиДокумента.ОтменаПроведения);  // <-- РАСПРОВЕДЕНИЕ
        КонецЕсли;
    Исключение
        ... // "Не удалось отменить проведение документа"
    КонецПопытки;
КонецПроцедуры

4.2. Перезапуск шагов изменённого бизнес-процесса (главный источник распроведения)

Срабатывает для очередей ExchDU_СписокИзмененныхБП и ExchDU_СписокИзмененныхБПдляСтарта. Логика: отменить все шаги БП → затем заново выполнить шаги (Старт, Открытие плановой позиции, Оплаты комиссий, Валютирование, Оформление сделки …):

Процедура Выполнение_ИзменениеБППослеЗагрузки(СтрокаДанные)
    БПСсылка = СтрокаДанные.ОбъектДляОперации;
    ...
    Если БПСсылка.Стартован Тогда
        БизнесПроцессы[ТипБП].ОтменитьШагиБизнесПроцессаАвтоматически(БПСсылка);  // распроводит ВСЮ цепочку сделки
    КонецЕсли;
    Если Не БПОбъект.ПометкаУдаления И Не Ошибки Тогда
        БизнесПроцессы[ТипБП].ВыполнитьШагБизнесПроцессаАвтоматически(БПСсылка, "Старт");
        БизнесПроцессы[ТипБП].ВыполнитьШагБизнесПроцессаАвтоматически(БПСсылка, "ОткрытиеПлановойПозиции");
        ... // повторное проведение шагов и документов
    КонецЕсли;
КонецПроцедуры

Метод ОтменитьШагиБизнесПроцессаАвтоматически отменяет проведение всех документов бизнес-процесса (Открытие плановой позиции, Перерегистрация ц/б, Оплата комиссий, Валютирование и т.д.). Именно поэтому «сделка» переходит в статус «не исполнена» и появляется значок с часиками, даже если экономическое содержание сделки не менялось.

4.3. Прочие операции с документами

ПроцедураЧто делает с объектом в ФИН
Выполнение_ПроведениеДокументовПослеЗагрузкиснимает пометку удаления и проводит/перепроводит документ
Выполнение_ЗаписьНепроведенныхДокументовПослеЗагрузкизаписывает документ без проведения (статус «записан, не проведён»)
Выполнение_СтартИзмененныхБППослеЗагрузкиотменяет шаги и заново проходит пройденные шаги БП (IMDEV-4941, по полю ПройденныеШаги)
Выполнение_ЗавершениеБППослеЗакрытияпроводит и завершает БП целиком
Выполнение_УдалениеБППослеЗагрузкипомечает БП на удаление, сбрасывает Стартован/Завершён

Все процедуры выполняют запись через ПолучитьОбъект().Записать(...) в привилегированном режиме фонового задания — то есть проверка даты запрета на этом этапе тоже фактически не работает (контекст уже привилегированный, объект пишется напрямую).

5. Корень проблемы: почему сделки распроводятся в закрытом периоде

Проблема — результат сочетания трёх факторов:

Фактор 1. Обмен принудительно отключает дату запрета изменения данных

В веб-сервисе upload_data явно вызывается:

ДатыЗапретаИзмененияСлужебный.ПропуститьПроверкуЗапретаИзменения();

Плюс весь обмен идёт в привилегированном режиме. Поэтому «дата запрета изменения данных», которую финансисты ставят по портфелям, не препятствует загрузке и перезаписи объектов в уже закрытом периоде. Именно это пользователь и наблюдает: «обмен моментом загружает в открытый/закрытый период данные из DU».

Фактор 2. Загрузка «только изменённых объектов» + перепроведение в ДУ

Обмен настроен с флагом ЗаписыватьВИнформационнуюБазуТолькоИзмененныеОбъекты. Когда в ДУ выполняют перепроведение/«трогают» завершённые бизнес-процессы текущей датой, у объектов ДУ меняется состав движений/реквизитов (пусть даже технически), и обмен считает их «изменёнными» → выгружает в ФИН. В логе обмена такие БП помечаются статусом «Изменён» (красным).

Фактор 3. Реакция пост-обработки = распроведение + перезапуск

Для «изменённого» БП пост-обработка вызывает ОтменитьШагиБизнесПроцессаАвтоматически и затем заново выполняет шаги. Для отдельных документов — Записать(РежимЗаписиДокумента.ОтменаПроведения). В результате ранее проведённые и сверенные сделки в ФИН становятся непроведёнными, и требуется повторное «групповое закрытие периода».

Итоговая цепочка причинно-следственной связи

Перепроведение в ДУ (даже без изменения сути) → объект помечается «изменён» → обмен грузит его в ФИН с отключённой проверкой даты запрета → пост-обработка отменяет шаги БП/проводки → сделки «не исполнены», ОСВ изменилась → ручное перепроведение и сверка (20–40 мин на торговый день).

Важно: текущая логика нигде не сравнивает дату объекта с датой запрета/закрытия периода перед тем, как распровести его. Решение о распроведении принимается только по факту «объект изменился в ДУ», без учёта того, что период в ФИН уже закрыт и сверен.

6. Что хочет пользователь

  • Главное: перепроведение операций в ДУ не должно распроводить и менять статус уже загруженных, проведённых и сверенных сделок в ФИН в закрытом (сверенном) периоде.
  • Не должно требоваться повторного «группового закрытия периода» и ручной пересверки из-за технического перепроведения в ДУ.
  • При этом значимые изменения (комиссии по сделке, расчёты и т.п.) должны иметь управляемый, предсказуемый путь попадания в ФИН — а не лавину распроведений по всему портфелю.
  • Механизм «дата запрета на Т-1» в текущем виде их не устраивает: обмен его игнорирует, а при открытии периода для точечной правки аналитики обмен тут же затягивает данные из ДУ.

Формулировка цели (из JIRA): «разработать механизм, который позволит выполнять перепроведение в Аванкор-ДУ без нарушения корректности данных и повторных действий в Аванкор-ФИН».

7. Варианты решения

Вариант A (рекомендуемый). Учитывать дату запрета/закрытия периода в пост-обработке

Сделать «дату запрета изменения данных» (по портфелю) барьером для распроведения. Перед выполнением операций ДокументДляОтменыПроведения, ИзменениеБППослеЗагрузки, СтартИзмененныхБППослеЗагрузки и т.п. проверять дату объекта/портфеля:

// Псевдокод фильтра в начале процедуры-исполнителя
ДатаЗапрета = ДатыЗапретаИзмененияДанных.ДатаЗапрета(
                  Новый Структура("Портфель", Портфель), "Портфель");
Если ЗначениеЗаполнено(ДатаЗапрета) И ДатаОбъекта <= ДатаЗапрета Тогда
    // период закрыт: НЕ распроводим, объект - в отчёт/очередь "к ручному разбору"
    УстановкаСтатусаОбработкиОбъекта(СтрокаДанные, Ложь, "Пропущено: закрытый период");
    Возврат;
КонецЕсли;
ПлюсыМинусы / риски
Минимальная, локальная доработка в одном расширении; не трогает правила обмена ДУ. Использует уже привычный финансистам инструмент — «дата запрета». Нужно определить «источник правды» даты (подсистема «Даты запрета изменения» по портфелям). Объекты закрытого периода в ФИН перестанут авто-обновляться — изменения из ДУ туда не попадут до открытия периода (это и есть желаемое поведение, но требует регламента «что делать с такими изменениями»).

Вариант B. Не выгружать из ДУ объекты закрытого периода (фильтр на источнике)

На стороне ДУ в правилах обмена / регистрации изменений исключать объекты, дата которых попадает в закрытый в ФИН период (или старше согласованного «горизонта» T-N).

ПлюсыМинусы / риски
Снимает нагрузку и трафик обмена в принципе — лишние объекты вообще не передаются. Доработка в базе ДУ (вне данного расширения ФИН); ФИН должен сообщать ДУ актуальную «дату закрытия» по портфелям; риск рассинхронизации границ периода между базами.

Вариант C. Анализ значимости изменений (диф по экономическим реквизитам)

Перед постановкой БП/документа в очередь «изменённых» сравнивать ключевые поля (сумма, количество, актив, контрагент, комиссия) с уже загруженным объектом в ФИН. Если значимые поля не изменились — не распроводить (максимум — тихо обновить служебные реквизиты).

ПлюсыМинусы / риски
Точечно отсекает «пустые» перепроведения, при этом реальные изменения комиссий/расчётов проходят. Самая трудоёмкая логика; нужно согласовать перечень «значимых» полей по каждому виду сделки/БП; выше риск ошибок и сложнее сопровождать.

Рекомендация

В качестве базового решения — Вариант A (барьер по дате запрета в пост-обработке расширения VTB_ExchangeDU): он прямо отвечает на жалобу «дата запрета не работает», локален и управляем. При необходимости пропускать значимые изменения комиссий/расчётов внутри закрытого периода — дополнить его элементами Варианта C (диф по узкому списку полей) или регламентом контролируемого «открытия окна» для точечных правок.

Перед реализацией требуется согласовать с заказчиком: (1) источник «даты закрытия» (подсистема дат запрета по портфелям), (2) что делать с изменениями ДУ, пришедшими в закрытый период — складывать в отчёт/очередь на ручной разбор или отклонять, (3) перечень «значимых» реквизитов, если выбираем гибридный путь.

8. Выводы

  • Распроведение сделок в ФИН вызывает пост-обработка обмена ДУ → ФИН в расширении VTB_ExchangeDU, а не НДФЛ-обмен.
  • Технически распроведение делают: ОтменитьШагиБизнесПроцессаАвтоматически (для «изменённых» БП) и Записать(РежимЗаписиДокумента.ОтменаПроведения) (для документов из очереди отмены проведения).
  • Корень — сочетание: (1) обмен отключает проверку даты запрета (ПропуститьПроверкуЗапретаИзменения + привилегированный режим), (2) грузит «только изменённые объекты» при перепроведении в ДУ, (3) пост-обработка безусловно распроводит/перезапускает, не глядя на закрытый период.
  • «Дата запрета изменения данных» не помогает, потому что обмен её осознанно обходит.
  • Пользователю нужно, чтобы перепроведение в ДУ не ломало закрытый и сверенный период в ФИН; рекомендуемый путь — сделать дату запрета реальным барьером в пост-обработке (Вариант A), при необходимости — с учётом значимости изменений (Вариант C).
