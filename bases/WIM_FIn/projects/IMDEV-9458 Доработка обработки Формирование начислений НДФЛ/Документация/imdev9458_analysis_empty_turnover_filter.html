IMDEV-9458. Не создавать НДФЛ по клиентам без оборотов

Технический анализ для разработки. Постановка: выгрузка Jira IMDEV-9458.doc. Продолжение IMDEV-7330.

Суть. На форму обработки ФормированиеНачисленийНДФЛ добавить флажок: не создавать начисление, если у пары клиент + УК нет оборотов по счетам доходов. Умолчание списка: 90.01, 91.01, 91.03 (префикс раскрывает субсчета, 91.02 не входит). При Заполнить строка остается, только если по портфелям этой пары есть оборот. Без флага поведение как сейчас. Старые пустые документы не удалять.
База. WIM_FIn, обработка ФормированиеНачисленийНДФЛ, документ НачислениеНДФЛПоПортфелю (ТЧ Общие обороты).
Расширение (план). IMDEV9458_EmptyTurnover. Типовую конфигурацию не менять.

Содержание: A. Хранение списка счетов (A.3 постановка, A.4 сравнение с колонкой «Это счет доходов», A.5 умолчание 90.01 / 91.01 / 91.03). B. Точка встройки и варианты 0-4. C. Запрос оборотов. D. Расширение и перехваты. E. Риски, тесты, открытые вопросы.

A. Хранение списка счетов

A.1. Что уже есть в типовой

Документ НачислениеНДФЛПоПортфелю, функция ОбщиеОбороты, параметр запроса собирается так:

Запрос.УстановитьПараметр("СчетаУчета", ПланыСчетов.Хозрасчетный.СчетаПоСтроке(
    "68.01, 90.01, 90.02, 91.01.02, 91.01.09, 91.02.02, 91.02.03, 91.02.04, 91.02.05, 91.02.06, 91.02.10, 91.02.11, 91.03, 91.04, 91.02.08"));

Функция ПланыСчетов.Хозрасчетный.СчетаПоСтроке режет строку по запятой и переводу строки и отбирает счета, у которых ПОДСТРОКА(Код, 1, длина_фрагмента) совпадает с фрагментом. То есть "90" даст все счета, код которых начинается с 90. Счета с ЗапретитьИспользоватьВПроводках = Истина по умолчанию не попадают. Это не конструкция В ИЕРАРХИИ, а префикс по коду. Дальше в запросе Общих оборотов стоит Счет В (&СчетаУчета) - тот же прием нужен фильтру (раздел C).

Счет 68.01 в расчете НДФЛ есть (налог), в фильтр доходов/расходов его брать нельзя: иначе клиент только с проводкой налога без доходов пройдет отбор.

A.5. Умолчание на форме: три кода

На форме обработки в поле счетов показывается компактная строка (префиксы 90.01 и 91.01 раскрывают субсчета):

90.01, 91.01, 91.03

Явно по листьям это: 90.01, все 91.01.xx (в том числе листья из текста Jira), 91.03. Расходы 90.02 / 91.02.* / 91.04 и налог 68.01 не входят.

Сверка на данных Вариант 2, УК АО НВМ Инвестиции, налоговый период 2026. Кандидатов Заполнить: 27 797. Отсев по листьям из текста Jira: 2 903. Отсев по строке 90.01, 91.01, 91.03: 2 903. Отличий: 0. Пары только с «лишним» 91.01.xx или только с 91.03 на этом срезе не нашлись. 91.03 в умолчании все равно оставляем: это счет доходов (выручка на 91), на форме три понятных кода.

Пять процедур заполнения пишут в ТЧ циклом ДатыДокументов.Добавить(). Вшивать оборот в каждый запрос или в каждый цикл не нужно: источники разные, тексты разъедутся. Достаточно одного места - диспетчер ЗаполнитьДатыДокументов.

Как работает Заполнить
  1. Типовой код набирает кандидатов как сейчас (вариант 0-4).
  2. Если новый флаг выключен - эти строки и есть результат, на форму как сейчас.
  3. Если флаг включен - до возврата на форму из набора убираются пары клиент+УК без оборотов по списку счетов. Один запрос на весь набор. Оператор видит уже отфильтрованную таблицу.
Это не отдельный «второй проход после заполнения» для пользователя: для него это часть кнопки Заполнить. Технически проверка стоит сразу после типового набора, а не внутри пяти запросов и не в СоздатьДокументы.

Перехваты на СоздатьДокументы и на нарезку пачек не нужны для основного сценария: снимок пачек IMDEV-7330 берется с уже заполненной формы, в ТЧ пустых пар уже нет.

Не копировать логику внутрь СписокКлиентовСЦБ: там остатки 58, другой флаг.

B.3. Зерно отсева

Клиент + УК. В Jira написано «клиент / все портфели». В обработке строка ТЧ уже пара клиент+УК, отбор по той же паре. Строка остается, только если по портфелям этой пары за период есть оборот хотя бы по одному счету из списка. У того же клиента другая УК без оборотов в таблицу не попадает.

Пример: клиент в двух УК, купон 91.01.02 только в первой. В таблице одна строка (первая УК), вторая не добавляется. Пример из Jira про 01.09 / 02.09 остается: до появления оборота пары нет, после 02.09.2026 по 91.01.02 - пара есть.

B.4. Снимок формы для параллельных пачек (IMDEV-7330)

Снимок берется с формы после Заполнить. Если отбор уже сделан в ЗаполнитьДатыДокументов, в ТЧ нет пустых пар клиент+УК. Оркестратор нарезает только то, что видно оператору. Отдельный перехват менеджера и СоздатьДокументы для этого флага не нужны.

Новые реквизиты флага и строки счетов попадут в снимок сами: СнимокОбъектаОбработки копирует все реквизиты объекта.

B.5. Порядок флагов на прогоне

  1. Заполнить (варианты 0-4), внутри 2/4 может сработать фильтр движений по НДФЛ + 68.01
  2. Новый фильтр по счетам доходов из Jira (этот проект)
  3. СоздатьДокументы: БезЦБ (остатки 58)
  4. Расчет, затем БезУдержаний

Фильтры ортогональны. Пара без доходов из списка Jira при включенном флаге не попадет в ТЧ. Пара с 90.01 и без остатка 58 отсечется БезЦБ уже на создании.

C. Быстрый запрос Хозрасчетный.Обороты

C.1. Важные факты по регистру

  • Портфель - это измерение регистра бухгалтерии Хозрасчетный, не субконто. Субконто 1..3 - аналитика счета. В виртуальной таблице условие по портфелю пишется в параметре отбора по измерениям: Портфель.Клиент В (&Клиенты).
  • Периодичность виртуальной таблицы - пустая (не Регистратор): нужна только факт оборота, не разрез документов.
  • Гранулярность результата - пара клиент + УК (РАЗЛИЧНЫЕ Портфель.Клиент, Портфель.УправляющаяКомпания).
  • Счета: массив из СчетаПоСтроке("90.01, 91.01, 91.03"). В виртуальной таблице Счет В (&СчетаОборотов) - как в Общих оборотах. Префикс уже развернут в A.1, второй раз иерархией не раскрывать. 91.02 в массив не попадет.
  • Два независимых В (&Клиенты) и В (&УправляющиеКомпании) нельзя считать зерном пары: Иванов+УК1 и Петров+УК2 дали бы еще Иванов+УК2. После оборотов обязательно соединение с временной таблицей пар из ТЧ.
