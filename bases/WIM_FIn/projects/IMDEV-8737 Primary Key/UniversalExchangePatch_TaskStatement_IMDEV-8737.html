Постановка задачи: патч универсальной обработки обмена

Задача для IMDEV-8737: стабилизировать загрузку из ДУ в ФИН в условиях параллельных потоков, чтобы обмен не падал на повторной записи одних и тех же объектов.

Основание: Тесты/ОшибкиПриОбменеИзДУ_в_ФИН.txt и текущая доработка в Расширения/FonProv/DataProcessors/УниверсальныйОбменДаннымиXML/Ext/ObjectModule.bsl (&ИзменениеИКонтроль("ЗаписатьОбъектВИБ")).

1. Что болит в продовом сценарии

Во время обмена несколько потоков одновременно пытаются записать один и тот же объект. Первый поток успевает вставить запись, второй получает ошибку SQL по первичному ключу и останавливает загрузку.

1.1 Фактические ошибки из лога

Ошибка записи объекта
ТипОбъекта             =  Сделки T+n
ОписаниеОшибки         =  Ошибка при вызове метода контекста (Записать)
...
Ошибка при попытке вставки записи с неуникальным значением ссылки.
Microsoft OLE DB Driver 19 for SQL Server: Violation of PRIMARY KEY constraint 'PK___BPr6072__AC8ED0C4AE9F975E'.
Cannot insert duplicate key in object 'dbo._BPr6072'.
The duplicate key value is (0x85a800505689c99411f13af591251ab1).
HRESULT=80040E2F ... native=2627

Такие же ошибки повторяются сериями для разных экземпляров Сделки T+n в одном запуске обмена.

2. Простыми словами о причине

  • Поток A и поток B одновременно получают одно и то же событие по объекту.
  • Оба пытаются сделать Объект.Записать() с одинаковым GUID.
  • Один поток побеждает, второй падает на PRIMARY KEY.
  • Без патча вся загрузка прерывается, хотя нужная запись уже есть в базе.
Важный момент: это не всегда "плохие данные". Часто это именно техническая гонка записи в параллельном обмене.

3. Цель доработки

Сделать запись в универсальной обработке более идемпотентной:

  • если объект уже корректно записан другим потоком - не считать это фатальной ошибкой;
  • если в базе остался неполный "каркас", а текущий объект полный - заменить каркас на полный объект;
  • сохранить стандартное поведение в конфликтных ситуациях, где нужна явная ошибка.

4. Область действия патча

Группа объектов Что делаем Зачем
БизнесПроцессОбъект.СделкиTn Обработка дубля PRIMARY KEY/UNIQUE с анализом GUID и состояния объекта в ИБ Снять падения на гонке и корректно перезаписывать каркас
СправочникОбъект.Облигации, СправочникОбъект.Акции, СправочникОбъект.ПаиПИФ При ошибке конкурентной записи (несоответствие версии или отсутствие записи) - ранний Возврат Не падать на повторной записи справочников, которые выгружаются полно и параллельно

5. Идея устранения ошибок (доступным языком)

5.1 Для Сделки T+n

  • Ловим исключение записи.
  • Понимаем, что это дубль ключа (по тексту ошибки).
  • Берем GUID из SQL-текста 0x... и находим объект в базе.
  • Если текущий объект неполный - не мешаем обмену, выходим без ошибки.
  • Если текущий объект полный, а в базе неполный каркас - удаляем каркас и повторяем запись.
  • Если оба объекта полные - это уже не техническая гонка, оставляем стандартную ошибку.

5.2 Для Акции / Облигации / ПаиПИФ

  • Проверяем тип объекта через ТипОбъекта = ТипЗнч(Объект).
  • Если это один из трех справочников и ошибка относится к конкуренции версии/записи - выходим без падения.
  • Для остальных типов и остальных ошибок работает штатная схема протоколирования и исключения.

6. Формулировка задачи для разработки

Нужно: доработать перехват ЗаписатьОбъектВИБ в расширении FonProv, чтобы исключения гонки при обмене не роняли загрузку и обрабатывались по матрице правил выше.

Нельзя: отключать общее логирование ошибок и "глотать" любые исключения без проверки типа и признаков ошибки.

7. Критерии приемки

  • Повторный обмен не падает серией ошибок Violation of PRIMARY KEY constraint по Сделки T+n в сценариях гонки.
  • Для полного объекта и каркаса в ИБ выполняется замена каркаса на полный объект.
  • Для Облигации/Акции/ПаиПИФ ошибка конкурентной записи не прерывает загрузку.
  • Для нецелевых типов поведение остается типовым: запись в протокол и исключение при отключенной отладке.
Риск: если слишком широко распознавать "безопасные" ошибки, можно скрыть реальные проблемы данных. Поэтому ветки обхода ограничены типами объектов и конкретными текстовыми маркерами ошибок.
Результат внедрения: обмен становится устойчивым к параллельной записи, при этом критичные конфликты данных не маскируются и продолжают попадать в стандартный механизм ошибок.
