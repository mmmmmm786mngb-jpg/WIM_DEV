Оптимизация2485 — ТаблицыАванса (строка ~2485)

Ниже — основные идеи оптимизации и то, как они реализованы в тексте запроса и коде из TablitsyAvansa_Function.bsl. Контекст: IMDEV-8662, документ Сделка, модуль объекта; в типовой базе узким местом профилирования был вызов ВыполнитьПакет() в ТаблицыАванса, в оптимизированном варианте итог читается через Выполнить().Выгрузить().

Замеры: measurements_table_IMDEV-8662.html.

Основные идеи оптимизации и как они реализованы

1. Убраны лишние соединения со справочником

Идея

В типовом тексте запроса к итоговому ОБЪЕДИНИТЬ шапка Документ.Сделка многократно соединялась со Справочник.ДоговорыКонтрагентов, при этом из справочника в выборку не подставлялось ни одного поля — соединение только отсекало строки с пустым договором.

Реализация

Все ВНУТРЕННЕЕ СОЕДИНЕНИЕ со Справочник.ДоговорыКонтрагентов удалены. Вместо них в первой временной таблице (в запросе она называется Реквизиты) задан явный отбор по договору:

И Реквизиты.ДоговорКонтрагента <> ЗНАЧЕНИЕ(Справочник.ДоговорыКонтрагентов.ПустаяСсылка)

Семантика «нет строк зачета, если договор не заполнен» сохраняется за счет того, что дальнейшие части пакета строятся от этой ВТ: пустая Реквизиты дает пустой итог третьей части.

2. Шапка документа читается в запросе по сути один раз

Идея

В базе в разных частях одного пакета документ Сделка фигурировал как источник полей шапки несколько раз (фактически три-четыре обращения к логике чтения шапки в одном пакете).

Реализация

Все реквизиты шапки, нужные для объединения «взаиморасчеты / НКД / доп. расходы» (контрагент, договор, счета расчетов и по авансам, валюта документа, курс и кратность, сумма, НКД), один раз помещаются во временную таблицу Реквизиты. Третья часть пакета читает шапку уже из этой ВТ, а не повторно из Документ.Сделка в каждой ветке ОБЪЕДИНИТЬ.

Способ зачета авансов в состав первой ВТ не выносится: он не участвует в построении ТаблицаДокумента. Решение «нужен ли запрос по табличной части ЗачетАвансов» принимается в коде модуля по реквизиту объекта СпособЗачетаАвансов (см. следующий пункт).

3. Разделены обязательные и условные данные

Идея

Таблица для проводок по зачету авансов из сумм документа нужна почти всегда; таблица документов аванса при зачете «по документу» — только в одном режиме. Нет смысла каждый раз выполнять четвертый запрос пакета, если режим другой (чаще всего «автоматически»).

Реализация

  • Обязательный путь: один текст запроса из трех частей (Реквизиты, ТаблицаДанныхПоДопРасходам, итоговый ОБЪЕДИНИТЬ); результат последней части — ТаблицыПроведенияАванса.Вставить("ТаблицаДокумента", Запрос.Выполнить().Выгрузить()) без ВыполнитьПакет() и без структуры НомераТаблиц.
  • Условный путь: если СпособЗачетаАвансов = Перечисления.СпособыЗачетаАвансов.ПоДокументу, выполняется отдельный объект Запрос с тем же смыслом, что и четвертая часть типового пакета (выборка из Документ.Сделка.ЗачетАвансов с соединением со шапкой и отбором по способу).
  • Иначе: отдельный запрос не выполняется; в структуру вставляется пустая ТаблицаЗначений с колонками по именам, как ожидает остальной код по ключу ТаблицаДокументыАвансов.
Если СпособЗачетаАвансов = Перечисления.СпособыЗачетаАвансов.ПоДокументу Тогда
    // отдельный Запрос: ЗачетАвансов + шапка, затем Вставить("ТаблицаДокументыАвансов", Выгрузить())
Иначе
    // Новый ТаблицаЗначений + Колонки.Добавить(...) без строк
КонецЕсли;

4. Упрощена структура пакета

Идея

Убрать лишние промежуточные сущности и поля, не влияющие на итоговые колонки ТаблицаДокумента, и сделать третью часть проще для чтения и плана выполнения.

Реализация

  • ВТ ТаблицаДанныхПоАктивам из типового пакета не используется: ее роль по смыслу выполняет ВТ Реквизиты (шапка с суммой и НКД в нужной точности).
  • ТЧ ДопРасходы материализуется во второй ВТ с минимальным набором полей (номер строки, сумма, контрагент, договор, валюта и курс комиссии — только то, что участвует в формулах третьей части).
  • Блок ОБЪЕДИНИТЬ строится от одной строки шапки в Реквизиты и строк ТЧ доп. расходов; связь «шапка — строки доп. расходов» в тексте фрагмента задается соединением Реквизиты с ТаблицаДанныхПоДопРасходам при уже отобранных по &Ссылка строках ТЧ (в реализации — ПО ИСТИНА при одной строке Реквизиты на документ).

5. Сохранена совместимость с остальным проведением

Идея

Не менять контракт для вызывающего кода: те же ключи структуры и ожидаемый смысл таблиц.

Реализация

  • Возвращаемая структура по-прежнему содержит ТаблицаДокумента и ТаблицаДокументыАвансов с прежним смыслом таблиц.
  • Поведение при пустом договоре согласовано с типовым отбором через соединение со справочником: итоговая выборка для зачета из сумм документа в этом случае пустая.

6. Удалены лишние параметры запроса

Идея

В типовой функции ТаблицыАванса часть параметров запроса устанавливалась через УстановитьПараметр, но в тексте пакета для этой функции не использовалась: лишние действия при каждом проведении и путаница при сопровождении.

Реализация

Из кода подготовки запроса убраны неиспользуемые в тексте пакета параметры:

  • ВалютаРегУчета — в типовом тексте запроса ТаблицыАванса не встречается (ни как &ВалютаРегУчета, ни иначе).
  • СчетУчетаЗатратКонтрагента — в типовой конфигурации передавался во вторую ВТ по доп. расходам для поля, которое не участвует в итоговом ОБЪЕДИНИТЬ и в формировании ТаблицаДокумента. В новой схеме вторая ВТ содержит только поля, нужные для третьей части, поэтому этот параметр не задается.

В пакете остаются параметры, которые реально читает текст запроса (в фрагменте реализации — как минимум Ссылка и СчетДопРасходов).

Для бизнеса (одним абзацем)

Мы ускоряем подготовку данных при проведении за счет более короткого запроса к СУБД и отказа от лишней работы там, где она не нужна по настройке документа. Для пользователя проводки и зачет авансов по смыслу остаются прежними; меняется внутренняя технология подготовки тех же таблиц.

Справочно про типовую базу: в исходнике ТаблицыАванса пакет из четырех частей и один вызов ВыполнитьПакет(); четвертая часть всегда выполнялась, даже когда возвращала пустой набор.
