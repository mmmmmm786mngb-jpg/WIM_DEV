1. Цель и рамки

Перевести выполнение команды формирования начислений НДФЛ в длительную операцию с параллельной обработкой табличной части ДатыДокументов: константа задаёт число окон разбиения K, после учёта отбора НомерСтрокиС/НомерСтрокиПо и упаковки по клиентам формируются непустые пачки; по каждой запускается воркер одновременно с остальными; оркестратор отслеживает статусы и прогресс в окне длительной операции (детали в п. 5).

Принятое допущение: в каждой фоновой пачке строится свой локальный кэш расчетов. Это допустимо и не требует межпоточной синхронизации кэша.

2. Что дорабатываем

2.1 Модуль формы обработки

  • Команда СоздатьДокументы переводится с синхронного вызова на серверный старт ДлительныеОперации.ВыполнитьВФоне и клиентское ожидание (см. раздел 8).
  • Добавляются обработчики результата: оповещение о завершении длительной операции, при необходимости промежуточные проверки статуса.
  • Настраиваются параметры ожидания: ВыводитьОкноОжидания = Истина, ВыводитьПрогрессВыполнения = Истина.

2.2 Константа числа пачек

В расширении заводится новая константа (целое положительное значение): целевое число параллельных пачек при разбиении ТЧ ДатыДокументов. Имя и синоним — по согласованию с администрированием; значение по умолчанию и верхняя граница валидации фиксируются в метаданных константы и в коде оркестратора.

2.3 Модуль менеджера и модуль объекта обработки (расширение NDFL_RDU)

Модуль менеджера (Ext/ManagerModule.bsl):

  • Экспортная процедура оркестратора для основной длительной операции БСП: NDFL_RDU_ОркестраторФормированияНДФЛ (см. раздел 3).
  • Экспортная процедура воркера пачки (вызывается из оркестратора через ФоновыеЗадания.Выполнить): NDFL_RDU_ВыполнитьПачкуФормированияНДФЛ.
  • Служебные процедуры и функции: разбиение ТЧ на пачки, заполнение экземпляра воркера из параметров пачки, подготовка параметров пачки, сшивка результатов (имена — в п. 3.5).

Модуль объекта (Ext/ObjectModule.bsl): существующие перехваты расчёта и кэш; при необходимости доработки параметризации кэша по номерам строк пачки — без выноса оркестратора и воркера в модуль объекта.

2.4 Без новых общих модулей

Без отдельного общего модуля: экспортные процедуры и функции, которые вызываются как ДлительныеОперации.ВыполнитьВФоне и как метод воркера для ФоновыеЗадания.Выполнить, размещаются в ManagerModule обработки ФормированиеНачисленийНДФЛ и помечаются Экспорт. Строка метода для основной ДО — Обработки.ФормированиеНачисленийНДФЛ.NDFL_RDU_ОркестраторФормированияНДФЛ (стандарт 1С: менеджер обработки, не объект).

4. Что видит пользователь

4.1 Старт

  1. Пользователь нажимает «Создать документы».
  2. Появляется стандартное окно длительной операции.

4.2 В процессе

  • Показывается общий процент.
  • В тексте прогресса выводится агрегированная строка, например: Пачка1-20%; Пачка2-25%; Пачка3-10%; ...
  • UI формы не блокируется до завершения вычислений.

4.3 Завершение

  • После завершения показывается итоговый лог формирования (единый табличный документ).
  • Если были ошибки, они отображаются в общем логе и в статусе завершения длительной операции.

5. Что происходит в системе

  1. Из текущего объекта обработки берется шапка и заполненная ТЧ ДатыДокументов.
  2. Из константы читается целевое число окон разбиения K (например 10).
  3. ТЧ ДатыДокументов до любых фоновых запусков разбивается не более чем на K непересекающихся непустых пачек: сначала учитывается пересечение с отбором НомерСтрокиС..НомерСтрокиПо (см. п. 5.1), затем геометрия окон по константе K. Алгоритм распределения должен по возможности сохранять правило: строки одного клиента не разносить по разным пачкам (упаковка клиентских групп в K контейнеров с минимизацией конфликтов по НачислениеНДФЛПоУправляющейКомпании). Пустые пересечения «окно на полной ТЧ» и пользовательского диапазона не порождают воркеров. Если после отбора клиентских групп свободных контейнеров меньше K, часть окон остаётся без строк — заданий нет.
  4. Для каждой непустой пачки формируется сериализуемая структура параметров.
  5. Оркестратор без ожидания между стартами запускает фоновое задание на каждую непустую пачку (все воркеры стартуют параллельно в пределах возможностей кластера).
  6. Каждое задание:
    • создает свой экземпляр обработки;
    • копирует шапку и выставляет НомерСтрокиС = 0, НомерСтрокиПо = 0 (см. 5.1);
    • заполняет только свою часть ТЧ и при необходимости перенумеровывает НомерСтроки;
    • выполняет СоздатьДокументы для своей пачки;
    • возвращает результат пачки через временное хранилище.
  7. Оркестратор отслеживает состояние каждого запущенного задания (готовность, ошибка, аварийное завершение), агрегирует прогресс по пачкам через СообщитьПрогресс, дожидается завершения всех воркеров и сшивает итог.
  8. Итог передается в форму, где показывается единый лог.

5.1 НомерСтрокиС, НомерСтрокиПо и границы пачек (обязательно явно реализовать)

Критично: при разбиении на пачки и подготовке воркера нужно явно учесть пересечение пользовательского диапазона НомерСтрокиС..НомерСтрокиПо с окнами пачек по константе K. В шапке объекта воркера после копирования выставить НомерСтрокиС = 0, НомерСтрокиПо = 0, чтобы не применять отбор по номеру повторно (он уже «зашит» в состав строк ТЧ воркера). Нули означают: фильтры по номеру в шапке не учитывать (см. логику NDFL_RDU_СобратьПарыКлиентУКСУчетомОтборовДокументов в модуле обработки).
Пример: в ТЧ всего 100 строк, пользователь задал НомерСтрокиС = 3, НомерСтрокиПо = 15, константа деления K = 10 (номинальные окна по 10 строк: 1–10, 11–20, …). Реально допустимы только глобальные строки 3–15 (13 строк). Тогда:
  • Пачка 1 (окно 1–10): в воркер попадают строки 3–10 (8 строк). В шапке воркера НомерСтрокиС = 0, НомерСтрокиПо = 0.
  • Пачка 2 (окно 11–20): в воркер попадают строки 11–15 (5 строк). В шапке воркера снова 0 / 0.
  • Дальнейшие окна не создаются: строки 16–100 выходят за пользовательский отбор и не должны обрабатываться в этом запуске.
Дополнительно рекомендуется в ТЧ воркера проставить у строк последовательные НомерСтроки = 1..N в порядке обхода (согласованность с типовым Прервать при превышении НомерСтрокиПо в цикле по табличной части).

Соглашения по комментариям // IMDEV-7330-П и единой области кода — в п. 3.5.1 (без дублирования текста здесь).

5.2 Воркер как N виртуальных обработок и вызов СоздатьДокументы

Такой вариант согласуется с идеей «N виртуальных обработок»: каждый воркер создаёт свой объект обработки, переносит в него полную копию шапки (структура реквизитов), заполняет только свою часть ДатыДокументов, затем вызывает СоздатьДокументы(ТабличныйДокумент), то есть тот же типовой контракт, что и при ручном запуске. Срабатывает уже существующий перехват NDFL_RDU_СоздатьДокументы: сброс и инициализация кэша по данным этой пачки, далее ПродолжитьВызов и типовой цикл. Тело перехвата не обязательно менять под параллельность, если оркестратор и форма не вызывают «полный» прогон по всей ТЧ из UI в том же сеансе.

Что остаётся снаружи воркера:

  • разбиение ТЧ на пачки по K, одномоментный старт фонов по непустым пачкам, сбор и сшивка результатов - в оркестраторе;
  • запуск длительной операции БСП и окно ожидания - в модуле формы (как в разделе про референс БСП), а не внутри перехвата СоздатьДокументы.

На что обратить внимание:

  • Форма после команды «Создать документы» не должна вызывать объектный СоздатьДокументы по всей таблице, если включён параллельный режим, иначе возможен двойной прогон. Нужна одна точка входа: либо только длительная операция и воркеры, либо только синхронный вызов (например для отладки или малого объёма).
  • У каждого воркера свой экземпляр обработки и свой сеанс - модульные переменные кэша изолированы; это совпадает с допущением «кэш в каждой пачке свой».
  • Табличный документ лога: у каждого воркера свой фрагмент; оркестратор их сшивает - это код оркестратора или сшивки, а не тело перехвата СоздатьДокументы.

Итог: не менять тело NDFL_RDU_СоздатьДокументы ради параллелизма допустимо; параллельность и имитация N обработок достигаются воркером, который подставляет урезанную ТЧ и вызывает тот же СоздатьДокументы.

7. Прогресс по пачкам

7.0 Явный прогресс внутри длительной операции

В активной реализации Wim_Du для регламентных операций (каталог РегламентныеПериоды, задача ASP-196537) прогресс передаётся через одну переиспользуемую структуру Прогресс с полями Процент и Текст; перед тяжёлым шагом вызывается ДлительныеОперации.СообщитьПрогресс(Процент, Текст), по завершении цикла — финальный вызов с Процент = 100. Этот приём имеет смысл перенести в наш оркестратор как основной канал текста для окна БСП.

7.1 Как собирать прогресс

  1. Каждый воркер периодически сообщает локальный прогресс (0..100) и текст по своей пачке.
  2. Оркестратор читает статусы всех пачек, формирует:
    • агрегированный процент (например, средний),
    • строку вида Пачка1-20%; Пачка2-25%; ....
  3. Оркестратор вызывает ДлительныеОперации.СообщитьПрогресс(...) для основного окна ожидания.

7.2 Почему через оркестратор

Стандартное окно длительной операции ориентировано на один идентификатор задания. Поэтому детализацию по N пачкам лучше агрегировать в оркестраторе и передавать единым текстом и единым процентом.

8. Референс Wim_Du и практики БСП

Ниже — проверенные в другой конфигурации приёмы (С:\1c\Cursor_1c\WORK\Wim_Du\SRC\CF, форма элемента РегламентныеПериоды и экспорт процедуры модуля менеджера СформироватьРегламентныеОперации), которые напрямую стыкуются с нашей схемой «одна длительная операция + несколько фонов внутри» без нового общего модуля.

8.1 Клиент после вызова «запуск на сервере»

  • Выполнить быструю валидацию до обращения к серверу (период, пустые списки, корректность адреса временного хранилища параметров).
  • Различать результат запуска по полю Статус: Выполняется — включить отслеживание; Ошибка — показать ПодробноеПредставлениеОшибки; Выполнено — сразу обработать результат (режим отладки, файловая ИБ без очереди фона и др.).
  • Дублировать вход в отслеживание проверкой «уже выполнено» внутри процедуры ожидания — защита от гонки и повторного вызова.

8.2 Серверный старт через ДлительныеОперации.ВыполнитьВФоне

  • Собрать ПараметрыПроцедуры только из сериализуемых данных.
  • Получить ПараметрыВыполнения = ДлительныеОперации.ПараметрыВыполненияВФоне(УникальныйИдентификатор) (идентификатор формы), задать НаименованиеФоновогоЗадания по смыслу операции для администрирования.
  • Установить ПараметрыВыполнения.КлючФоновогоЗадания = Строка(Новый УникальныйИдентификатор) или иной ключ — снижение риска дублирующего запуска при повторном нажатии.
  • ПараметрыВыполнения.ОжидатьЗавершение = 0 — не блокировать клиентский HTTP-запрос в ожидании завершения фона.
  • Выделить АдресРезультата = ПоместитьВоВременноеХранилище(Неопределено, УникальныйИдентификатор) и передать его в ПараметрыВыполнения.АдресРезультата; фоновая процедура обязана по завершении положить итог по этому адресу (успех или диагностическое сообщение).
  • Вызываемое имя метода — строка вида Обработки.ФормированиеНачисленийНДФЛ.NDFL_RDU_ОркестраторФормированияНДФЛ (экспорт модуля менеджера заимствованной обработки в расширении).
  • Обработка исключений на этапе подготовки и запуска: заполнить поля ошибки результата, при необходимости ЗаписьЖурналаРегистрации.

8.3 Клиент: ДлительныеОперацииКлиент.ОжидатьЗавершение

  • ПараметрыОжидания = ДлительныеОперацииКлиент.ПараметрыОжидания(ЭтотОбъект), включить окно и прогресс: ВыводитьОкноОжидания = Истина, ВыводитьПрогрессВыполнения = Истина, задать ТекстСообщения пользователю.
  • По аналогии с Wim_Du: опционально ПараметрыОжидания.Интервал = 0, включить блок ОповещениеПользователя после завершения (заголовок/текст уведомления ОС при свёрнутой форме — по политике проекта).
  • ПараметрыОжидания.ВыводитьСообщения = Истина — проброс сообщений пользователю из фонового сеанса, если они формируются.
  • ОписаниеОповещения на обработчик финального результата; в обработчике — чтение из временного хранилища по АдресРезультата.

8.4 Тело экспортной фоновой процедуры (оркестратор)

  • Оркестратор размещается в ManagerModule обработки (NDFL_RDU_ОркестраторФормированияНДФЛ), не в модуле объекта.
  • Инициализировать результат «по умолчанию» как неуспешный или пустой, затем при нормальном завершении заменить на успех.
  • Валидация параметров через Свойство; при ошибке — ПоместитьВоВременноеХранилище(Результат, АдресХранилищаРезультат) и Возврат.
  • Общая обёртка Попытка ... Исключение ... КонецПопытки с логированием; в блоке исключений не забыть положить осмысленную структуру результата в хранилище.
  • В конце штатного сценария гарантированно выполнить ПоместитьВоВременноеХранилище(Результат, АдресХранилищаРезультат).

8.5 Вложенная параллельность: Wim_Du и обязательная модель НДФЛ

В Wim_Du для части шагов используется мини-пул: фоновые задания накапливаются до лимита КоличествоПотоков, затем вызывается ФоновыеЗадания.ОжидатьЗавершения, после чего цикл продолжается следующей «волной». Это удобно при последовательной подаче элементов, но не является целевой схемой для НДФЛ по IMDEV-7330.

Важно для НДФЛ: константа задаёт число окон K для геометрии разбиения; после пересечения с отбором по строкам и правилом по клиентам остаются непустые пачки (их может быть меньше K). Для каждой непустой пачки создаётся отдельное фоновое задание-воркер, и все эти задания запускаются сразу (без поочерёдных волн накопления). Оркестратор в контексте одной длительной операции ведёт учёт статуса каждой пачки (ожидание, процент, ошибка, аварийное завершение), обновляет агрегированный прогресс в окне БСП и после завершения всех воркеров выполняет сшивку результата.

Справочно: при реализации на ФоновыеЗадания.Выполнить после одномоментного старта всех воркеров используется одно ожидание по полному списку заданий (например ФоновыеЗадания.ОжидатьЗавершения по массиву) плюс разбор ПолучитьСообщенияПользователю и проверка СостояниеФоновогоЗадания.ЗавершеноАварийно по каждому элементу — без искусственного дробления на волны по числу константы.

Окно длительной операции пользователя по-прежнему привязано к одному идентификатору длительной операции (оркестратор); детализация по пачкам выводится агрегированной строкой и процентом (раздел 7).

9. Ошибки, отмена, устойчивость

  • Ошибка в одной пачке: помечаем пачку как ошибочную, собираем текст ошибки, продолжаем остальные.
  • Критическая ошибка оркестратора: прерываем запуск, возвращаем статус «Ошибка» в длительную операцию.
  • Отмена пользователем: реализуем корректную остановку активных фоновых заданий и частичную сшивку лога.
  • Идемпотентность: повторный запуск не должен дублировать уже созданные документы сверх типового поведения.
Число параллельных воркеров администрируется константой; при очень большом значении возможны очереди на кластере и рост блокировок — верхнюю границу константы и мониторинг фоновых заданий согласовать с эксплуатацией. Технически пустые пачки не порождают заданий, поэтому фактическое число одновременных воркеров не превышает число непустых пачек после разбиения.

11. Последовательность внедрения

  1. Итерация 1: перевод формы на ВыполнитьВФоне, ветвление статусов и чтение результата из временного хранилища; пока один поток (без пула воркеров).
  2. Итерация 2: константа K, разбиение с п. 5.1 и п. 5, одномоментный запуск воркеров по непустым пачкам и сборка итога.
  3. Итерация 3: агрегированный прогресс по пачкам в окне ожидания (СообщитьПрогресс из оркестратора).
  4. Итерация 4: отмена, разбор сообщений пользователю после завершения набора параллельных воркеров, контроль аварийных подзадач.
  5. Итерация 5: константа числа пачек в метаданных, валидация диапазона, нагрузочные замеры и согласование с эксплуатацией.
Ожидаемый эффект: ускорение массового расчета при сохранении текущей бизнес-логики, без ввода нового общего модуля и с прозрачным для пользователя интерфейсом длительной операции.
