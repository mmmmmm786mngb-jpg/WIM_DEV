Краткий вывод

Основные точки нагрузки — две, суммарно ~38,2% общего времени:

  • Строка 1 (22,13%) — ОбщиеОбороты = Запрос.Выполнить().Выгрузить(); в модуле объекта документа НачислениеНДФЛПоПортфелю (строка 7 544): запрос вызывается отдельно на каждый портфель текущего клиента.
  • Строка 2 (16,10%) — Пакет = Запрос.ВыполнитьПакет(); в модуле менеджера документа НачислениеНДФЛПоУправляющейКомпании (строка 3 069): запрос вызывается отдельно на каждую пару (Клиент, Дата), фактически дублируется по разным документам начислений одного клиента.

В первую очередь — проблема ТаблицаПродаж (смурфинг/chatty I/O): ранее выполнялось много мелких повторных обращений к регистру продаж по спискам регистраторов (N+1-подобный сценарий), из-за чего росло общее время расчёта. В расширении NDFL_RDU это уже решено перехватом ТаблицаПродаж: список регистраторов помещается во временную таблицу с индексацией, далее используется соединение с регистром. Это снижает количество повторных обращений и стабилизирует план выполнения.

Во вторую очередь — запрет записи пустых документов УК: в перехвате СоздатьНачислениеНДФЛПоУК после РассчитатьНДФЛ() добавлена проверка: если табличные части Начисления, Удержания и ИнвестиционныйВычетПоПортфелям пустые, документ не записывается и в лог добавляется сообщение.

В третью очередь — подход «один запрос на всех клиентов сразу»: тяжёлые точки переводим с режима «запрос на портфель / пару (Клиент, Дата)» на массовый запрос по выборке, далее данные раздаются из кэша через короткое замыкание в перехватах расширения NDFL_RDU.

В четвертую очередь — параллельные расчёты: когда массовые предрасчёты готовы, основной цикл обработки ФормированиеНачисленийНДФЛ разбивается на N пачек клиентов и запускается параллельно через ДлительныеОперации.ВыполнитьПроцедуруВНесколькоПотоков. Кэши предрасчёта передаются в каждое фоновое задание срезом по клиентам пачки, чтобы внутри потока продолжало работать короткое замыкание и не было повторных тяжёлых запросов.

Прочие точки в таблице (строки 3–7) после этих двух шагов либо снимаются автоматически (потому что используют те же предрасчитанные данные), либо имеют существенно меньший вес и оптимизируются по остаточному принципу.

План оптимизации

  1. Проблема ТаблицаПродаж (смурфинг/chatty I/O) — решено в расширении. Реализация: NDFL_RDU/Documents/НачислениеНДФЛПоУправляющейКомпании/Ext/ManagerModule.bsl, перехват ТаблицаПродаж. Суть: табличный параметр регистраторов, помещение во временную таблицу, индексация и соединение с регистром вместо повторных мелких обращений.
  2. Запрет записи пустых документов УК. Реализация: NDFL_RDU/DataProcessors/ФормированиеНачисленийНДФЛ/Ext/ObjectModule.bsl, перехват СоздатьНачислениеНДФЛПоУК. Суть: после расчёта документ не записывается, если пусты Начисления, Удержания и ИнвестиционныйВычетПоПортфелям.
  3. Строка 1 (22,13%) — ОбщиеОбороты в модуле объекта документа Портфеля. Массовый предрасчёт по массиву портфелей: один пакетный запрос на всю выборку, кэш в разрезе портфеля, короткое замыкание в перехвате NDFL_RDU_ОбщиеОбороты. План: imdev7330_ndfl_mass_precalc_oborots.html.
  4. Строка 2 (16,10%) — РасходыПоНКДПоВидуОбращаемости в модуле менеджера документа УК. Массовый предрасчёт по массиву клиентов на единую дату: один пакет вместо повторных вызовов на пары (Клиент, Документ начисления), кэш в разрезе (Клиент, Дата), короткое замыкание в перехвате модуля менеджера УК. План: imdev7330_ndfl_uk_nkd_mass_precalc_byclient.html.
  5. Распараллеливание расчётов по пачкам клиентов. После того как массовые предрасчёты готовы, обработка ФормированиеНачисленийНДФЛ.СоздатьДокументы разбивает выборку на N пачек клиентов (константа НДФЛ_МаксимумПотоковПараллельногоРасчёта) и запускает их параллельно через ДлительныеОперации.ВыполнитьПроцедуруВНесколькоПотоков. Кэши предрасчёта передаются срезом по клиентам пачки в каждое фоновое задание. План: imdev7330_ndfl_parallel_calculation.html.
