1. Резюме для заказчика

Пользователь по-прежнему запускает в одной обработке «Формирование начислений НДФЛ» расчет по табличной части ДатыДокументов. При включенном режиме параллельности система делит отобранные строки на несколько пачек и обрабатывает их в отдельных фоновых заданиях с той же бизнес-логикой, что и при однопоточном запуске; по завершении результаты сшиваются: единый лог в табличном документе, при успехе — возможность применить снимок данных формы к объекту обработки. Режим отключается константой (число окон 0) или отбором по одному клиенту на форме — тогда выполняется прежний синхронный сценарий.

Зачем отдельный документ. Постановка фиксирует что должна делать система с точки зрения бизнеса и приемки, без дублирования построчного описания модулей. Детальный контракт полей, имен процедур и геометрии окон — в технической спецификации по ссылке выше.

2. Цели, метрики успеха, вне объема

2.1 Цели (Goals)

  1. Сократить время ожидания пользователя при больших объемах строк ТЧ за счет параллельного выполнения пачек в фоне (при сохранении корректности расчета).
  2. Сохранить единый пользовательский сценарий: одна команда, одно окно ожидания БСП, предсказуемый итог (лог + обновление формы при успехе).
  3. Обеспечить управляемость нагрузки на сервер через верхнюю границу числа окон и константу K.

2.2 Метрики успеха (измеримые)

МетрикаОписание
Эквивалентность результатаНа контрольной выборке итог при K=1 и при K>1 совпадает с эталоном (документы, суммы, ключевые табличные части по регламенту тестирования).
Время отклика UXФорма не блокируется полным расчетом; пользователь видит прогресс основной длительной операции.
ОтказоустойчивостьЧастичный отказ пачек отражается в итоге (ЧастичныйУспех), полный отвал — статус ошибки ДО; отмена пользователем останавливает дочерние задания.

2.3 Вне объема (Out of scope)

  • Изменение типовой конфигурации вне расширения NDFL_RDU.
  • Новый общий модуль только под эту задачу (исходное ограничение: логика в форме, менеджере и объекте обработки).
  • Ограничение числа одновременно активных пачек «волнами» (текущая реализация: подряд запуск всех дочерних ДО; см. риск нагрузки в разделе 7).
  • Оптимизация справки-расчета по портфелю (ОбщаяСправкаРасчет2021) — отдельные постановки.

3. Заинтересованные стороны и сценарии

РольИнтерес
Пользователь бэк-офисаБыстрее получить результат массового формирования; видеть прогресс; при ошибке — понятная диагностика.
Администратор ИБРегулировать агрессивность параллелизма константой; не перегружать кластер неограниченным числом окон.
Разработка / сопровождениеЕдиная постановка и отдельная техническая спецификация; расширяемость (новые предрасчеты в оркестраторе, параметры пачки).

Ключевые сценарии (User journeys)

  • SC-01 — Полный список клиентов, K>0: запуск ДО, параллельные пачки, сшивка лога, применение снимка.
  • SC-02 — Заполнен отбор «Клиент»: синхронный расчет без параллельных пачек (снижение риска состояния гонки по одному клиенту).
  • SC-03 — K=0: поведение как до внедрения (одно окно, без дочерних ДО).
  • SC-04 — Отмена в окне ДО: дочерние задания отменяются, итог «прервано», сшивка не выполняется.
  • SC-05 — Часть пачек упала: главная ДО завершена, пользователь предупрежден, частичный успех в итоге.

4. Функциональные требования

Нотация: Должно — обязательное; Желательно — усиливает сопровождение.

IDТребованиеПримечание
FR-01Должно: команда формирования на форме обработки при активном параллельном режиме запускает длительную операцию БСП с оркестратором на сервере.Перехват команды в модуле формы расширения.
FR-02Должно: перед разбиением на пачки формируется снимок реквизитов и табличных частей обработки, достаточный для воспроизведения расчета в воркере.Сериализация XDTO между сеансами.
FR-03Должно: отбор строк (в т.ч. НомерСтрокиС/По) применяется до геометрии окон; в воркере шапка с обнуленными границами номера строк, чтобы не двоить отбор.См. техспек, раздел про воркер.
FR-04Должно: при одной фактической пачке дочерние ДО не создаются; выполняется один проход СоздатьДокументы из снимка.Оптимизация на малых выборках.
FR-05Должно: для каждой пачки — отдельный экземпляр обработки, табличная часть урезана до строк пачки; результат пачки во временном хранилище по адресу, согласованному с формой.Воркер NDFL_RDU_ВыполнитьПачкуФормированияНДФЛ.
FR-06Должно: оркестратор опрашивает фоновые задания пачек по уникальному идентификатору без кэширования объекта ФоновоеЗадание между итерациями.Требование платформы.
FR-07Должно: прогресс основной ДО отражает агрегат по всем пачкам (строки, завершенные потоки, время).Локальный процент внутри пачки в текст родителя не подмешивается.
FR-08Должно: итог главной ДО для клиента — XML-строка во ВХ; клиент не десериализует тяжелый снимок на клиентской стороне.Тонкий клиент, п. 4.4 техспека.
FR-09Должно: сшивка итогового лога касается только табличных документов пачек; таблицы сообщений пачек в общую сшивку логов не входят.Контракт сшивки.
FR-10Желательно: новые массовые предрасчеты (оборота, НКД и др.) выполняются в оркестраторе один раз на полный снимок и передаются в параметры пачки, а не дублируются в каждом воркере.Правило эволюции; см. imdev7330_parallel_ndfl_dev_prompt.html.

5. Нефункциональные требования и ограничения

КлассТребование
ПроизводительностьВерхняя граница эффективного K в коде (например 50) совместно с константой; геометрия окон за линейное время по числу отобранных строк.
НадежностьИсключение в воркере не рушит платформенный контур без записи диагностики в результат пачки; оркестратор классифицирует «упавшие» пачки.
СопровождениеОбласти кода с префиксом IMDEV7330_ПараллельноеФормированиеНДФЛ_*; комментарии с маркером IMDEV-7330.
СовместимостьПри K=0 или отборе по клиенту — поведение идентично типовому сценарию формы (регрессионные тесты).

6. Критерии приемки (Acceptance)

IDУсловие (Given / When / Then)
AC-01Дано пустой отбор строк после фильтров, когда пользователь запускает формирование, тогда оркестратор завершает без дочерних ДО, итог во ВХ, без исключения.
AC-02Дано K>0 и строк больше одной пачки, когда расчет завершен, тогда сшитый табличный документ показан пользователю, снимок при успехе применен на сервере.
AC-03Дано K=0, когда запуск формирования, тогда не создаются вложенные ДО пачек, результат совпадает с эталоном однопоточного прогона.
AC-04Дано заполнен Объект.Клиент, когда команда формирования, тогда выполняется синхронный серверный вызов без параллельного оркестратора.
AC-05Дано пользователь отменил главную ДО при активных пачках, когда отмена обработана, тогда дочерние задания остановлены, сшивка не выполняется.
AC-06Дано часть пачек завершилась с ЕстьОшибка, когда оркестратор собрал результаты, тогда ЧастичныйУспех в итоге, главная ДО в статусе выполнено, пользователь видит предупреждение.

7. Риски и смягчение

РискВлияниеСмягчение
Пиковая нагрузка на сервер при большом K и больших пачкахКонкуренция за CPU/IOКонстанта + жесткий cap в коде; нагрузочное тестирование; регламент значения K на продуктиве.
Расхождение порядка строк при изменении алгоритма сбора индексовДругая геометрия оконФиксировать контракт: порядок ИндексыСтрок = обход ТЧ в снимке; регрессионные тесты.
Дублирование тяжелых запросов в каждом воркере при новых фичахПараллелизм не ускоряетПравило FR-10; ревью постановки при добавлении предрасчетов.

8. Глоссарий и артефакты

ТерминОпределение
KЧисло окон разбиения: константа NDFL_RDU_ЧислоПараллельныхПачекФормированияНДФЛ (0 — режим «как раньше»).
СнимокСериализуемая структура данных обработки для оркестратора и воркера.
ОркестраторСерверная процедура главной ДО: отбор, разбиение, запуск пачек, ожидание, сшивка, запись итога.
ВоркерЭкспортная процедура модуля объекта обработки, выполняемая в дочерней ДО для одной пачки.
ПачкаМножество номеров строк ТЧ ДатыДокументов, обрабатываемых одним воркером после возможного слияния по клиенту.

Схема потока (кратко)

Форма --(ДО БСП)--> Оркестратор (менеджер)
  |-- отбор индексов, разбиение на пачки (K, cap, слияние по клиенту)
  |-- 1 пачка: один объект, СоздатьДокументы, итог XML во ВХ
  `-- N пачек: N вложенных ДО -> Воркер (объект) -> ВХ результата пачки
        -> ожидание + прогресс -> сшивка ТабличныйДокумент -> итог XML во ВХ
Форма <--(оповещение)-- разбор итога на сервере, применение снимка, показ лога
