Почему это узкое место. Запрос в РасходыПоНКДПоВидуОбращаемости фильтрует данные только по клиенту (Портфель.Клиент = &Клиент) и периоду (НачалоГода(Дата) … КонецДня(Дата)). При этом он вызывается на каждое начисление по портфелю клиента и ещё раз — на начисление по УК того же клиента. То есть для одной пары (Клиент, Дата) один и тот же тяжёлый пакетный запрос исполняется несколько раз подряд с идентичными параметрами и идентичным результатом.

1. Цель и идея

Сейчас РасходыПоНКДПоВидуОбращаемости в Документ.НачислениеНДФЛПоУправляющейКомпании.МодульМенеджера выполняется один пакетный запрос (4 временные таблицы, агрегации ПоПартиям / ПоРегистраторам) для каждой связки (Клиент, Дата), причём:

  • В типовой конфигурации функция вызывалась дважды в ИнвестиционныйВычетУКД(Клиент, Дата) — по обращающимся и необращающимся видам ЦБ, после чего таблицы сливались.
  • В расширении NDFL_RDU уже сделано: перехват &Вместо("ИнвестиционныйВычетУКД") собирает один объединённый массив видов и вызывает РасходыПоНКДПоВидуОбращаемости один раз на пару (Клиент, Дата) вместо двух.
  • Тем не менее ИнвестиционныйВычетУКД(Клиент, Дата) (а значит и РасходыПоНКДПоВидуОбращаемости) повторно вызывается из:
    • Документ.НачислениеНДФЛПоПортфелю.МодульМенеджера.НачисленияПоПортфелям (через Документы.НачислениеНДФЛПоУправляющейКомпании.РезультатРасчетаИнвестиционногоВычета) — на каждом расчёте начисления по портфелю клиента;
    • Документ.НачислениеНДФЛПоУправляющейКомпании.МодульОбъекта — на расчёте начисления УК того же клиента.

Запрос на 3069 параметризуется по одному &Клиент и периоду НачалоГода(Дата) … КонецДня(Дата). Для одной и той же пары (Клиент, Дата) результат одинаков в любом числе вызовов в рамках одного сеанса формирования. Замер дал 194 вызова — то есть запрос выполняется кратно числу пар (Клиент, ДокументНачисления, Дата) в выборке.

Идея оптимизации: один раз перед основным циклом ФормированиеНачисленийНДФЛ.СоздатьДокументы собрать массив уникальных пар (Клиент, Дата), выполнить один массовый пакетный запрос (с Портфель.Клиент В (&МассивКлиентов) и группировкой по полю Клиент), разложить результат в кэш (Клиент, Дата) → (ПоПартиям, ПоРегистраторам), а затем в реальных циклах по портфелям и УК передавать кэш в РассчитатьНДФЛ. В перехвате &Вместо("РасходыПоНКДПоВидуОбращаемости") модуля менеджера УК делать короткое замыкание: при наличии кэша по (Клиент, Дата) и заданному набору видов обращаемости возвращать готовую структуру до выполнения тяжёлого пакета.

Архитектурно это тот же приём, что в плане imdev7330_ndfl_mass_precalc_oborots.html (массовый ОбщиеОбороты по массиву портфелей), но применённый к точке «Клиент × Дата» в модуле менеджера документа УК. Контракты обоих планов согласованы и могут быть реализованы независимо или одной волной.

2.4. Что из этого следует

Для массового предрасчёта нужно:

  1. Добавить новый текст запроса (или модификацию существующего) с фильтром Портфель.Клиент В (&Клиенты) и проброской Клиент во все ВТ и финальные группировки.
  2. Завести экспортный метод модуля менеджера УК NDFL_RDU_ПолучитьРасходыПоНКДПоКлиентам, который вернёт кэш по уникальным парам (Клиент, Дата).
  3. Перехватить &Вместо("РасходыПоНКДПоВидуОбращаемости") в модуле менеджера УК и сделать короткое замыкание по кэшу.
  4. Добавить перехват &Вместо("РассчитатьНДФЛ") в документе УК — для приёма опциональной структуры с кэшем.
  5. Дополнить ФормированиеНачисленийНДФЛ.СоздатьДокументы сбором массива пар (Клиент, Дата) и вызовом нового метода предрасчёта.

3. Контракты нового API

Сохраняем тот же стиль, что и в плане по ОбщиеОбороты: два независимых публичных контракта расширения, без перегруженной семантики имени «Рассчитать».

  • Контракт A — подготовка кэша: новый экспортный метод модуля менеджера документа УК NDFL_RDU_ПолучитьРасходыПоНКДПоКлиентам(МассивПарКлиентДата). Вызывается обработкой один раз перед основным циклом.
  • Контракт B — приём готового кэша: в перехвате &Вместо("РассчитатьНДФЛ") документа УК добавляется опциональный параметр ПараметрыРасчетаВнешн, в который обработка кладёт кэш по текущему клиенту и дате.

Имя Тип Назначение
МассивПарКлиентДата (вход) Массив структур ("Клиент, Дата") Уникальный набор пар, по которым нужно посчитать расходы НКД. Дубли допустимы (внутренне свернутся в ВТ).

Текущая логика NDFL_RDU_ИнвестиционныйВычетУКД зовёт функцию с объединённым массивом видов (обращающиеся + необращающиеся), плюс есть прямые вызовы из модуля объекта документа Портфеля только по обращающимся или только по необращающимся. Чтобы кэш покрывал все сценарии, метод предрасчёта не фильтрует по ВидыОбращаемости на стороне SQL — финальная группировка по партиям/регистраторам делается без фильтра, фильтрация по видам выполняется уже на 1С при коротком замыкании в перехвате (см. п. 4.4). Это гарантирует, что один и тот же кэш обслуживает все три набора видов.

Где вызывается

  • Один раз в ФормированиеНачисленийНДФЛ.СоздатьДокументы до основного цикла — рядом с вызовом NDFL_RDU_ПолучитьОбщиеОборотыПоПортфелям.
  • Возвращаемая структура целиком сохраняется в защёлку модуля менеджера через NDFL_RDU_УстановитьВнешнийКэшНКДРасходов, а в РассчитатьНДФЛ обработка передаёт срез по текущему клиенту/дате (через ПараметрыРасчетаВнешн.КэшНКДРасходов).

            Продолжить;
        ИначеЕсли НомерСтрокиПо <> 0 И СтрокаДокументов.НомерСтроки > НомерСтрокиПо Тогда
            Прервать;
        КонецЕсли;
    КонецЕсли;

    Если НеСоздаватьДокументыПоКлиентамБезЦБ
        И КлиентыСЦБ.Найти(СтрокаДокументов.Клиент) = Неопределено Тогда
        Продолжить;
    КонецЕсли;

    Ключ = Строка(СтрокаДокументов.Клиент.УникальныйИдентификатор())
        + "|" + Формат(СтрокаДокументов.Дата, "ДФ=yyyyMMdd");
    Если УникПарКД.Получить(Ключ) = Неопределено Тогда
        Пара = Новый Структура("Клиент, Дата",
            СтрокаДокументов.Клиент, КонецДня(СтрокаДокументов.Дата));
        МассивПарКлиентДата.Добавить(Пара);
        УникПарКД.Вставить(Ключ, Истина);
    КонецЕсли;

КонецЦикла;
Если уже реализован пункт 4.1 из плана по оборотам, объединить два сбора в один цикл — это сэкономит проход по ДатыДокументов.

5. Сценарии и обратная совместимость

Сценарий A. Один документ, форма «Рассчитать»

Пользователь открыл НачислениеНДФЛПоУправляющейКомпании и нажал «Рассчитать НДФЛ».
поведение РассчитатьНДФЛ() вызывается без параметров → защёлка кэша остаётся Неопределено → перехват РасходыПоНКДПоВидуОбращаемости идёт по ПродолжитьВызов(). Поведение не меняется.

Сценарий B. Обработка с одним клиентом и одной датой

поведение Кэш всё равно собирается, но содержит одну пару. Запрос отрабатывает на одном клиенте — это «нулевой» выигрыш от группировки, но плюс предрасчёта остаётся (один пакет вместо трёх повторных по тем же параметрам). Чтобы не штрафовать совсем малую выборку, добавляем порог ПорогМассовогоПредрасчёта (значение по умолчанию — 5 пар, согласовать с планом по оборотам).

Сценарий C. Большая выборка (продакшн)

главный сценарий Сотни клиентов, сотни документов. Один пакет на дату, в кэше — все клиенты этой даты. Дальше короткое замыкание O(1) на каждое РасходыПоНКДПоВидуОбращаемости. Главный выигрыш по времени.

Сценарий D. Внешние вызовы РассчитатьНДФЛ() (обмен и пр.)

поведение Вызов без параметров → защёлка остаётся пустой → старый путь. Гарантия обратной совместимости: новая логика срабатывает только при явной передаче внешнего кэша из обработки.

6. План тестирования

№ Что проверяем Как Ожидаемый результат
1 Идентичность сумм НКД/УКД до и после оптимизации. Два запуска обработки на тестовой базе за один период: с СтруктураКэшНКД = Неопределено и с включённым массовым предрасчётом. Сверка по табличной части «Расшифровка инвестиционного вычета» документа УК. Нулевая разница в суммах и составе строк.
2 Сценарий A (форма документа). Открыть документ УК на тестовой базе, нажать «Рассчитать НДФЛ». Поведение и результат не отличаются от типового.
3 Контракт NDFL_RDU_ПолучитьРасходыПоНКДПоКлиентам. Юнит-тест: 3 клиента × 1 дата; 3 клиента × 2 даты. Сверить результат с тремя одиночными вызовами типовой РасходыПоНКДПоВидуОбращаемости. Совпадение строк по числу и суммам, корректное разложение по (Клиент, Дата).
4 Фильтрация по видам обращаемости. Из готового кэша получить три варианта: только обращающиеся, только необращающиеся, объединение — и сравнить с типовыми вызовами. Совпадение наборов строк.
5 Изоляция защёлки кэша. Параллельно запустить два сеанса обработки (фон + интерактив). При живой защёлке через повторное использование на сеанс кэши не пересекаются. Каждый сеанс работает в своём кэше; гонок нет.
6 Производительность. Замер общего времени СоздатьДокументы и числа выполнений ОбщегоНазначенияДУ.ДобавитьВЛогОтладки(..., "НачислениеНДФЛПоУправляющейКомпании.РасходыПоНКДПоВидуОбращаемости") до и после оптимизации. Снижение общего времени; число попаданий в логе сократилось до количества уникальных (Клиент, Дата); точка Документ.НачислениеНДФЛПоУправляющейКомпании.МодульМенеджера, 3069 покинула топ замера.
7 Граничные условия. Пустая выборка ДатыДокументов; один клиент без портфелей; смешанные даты в одной обработке. Обработка не падает; идёт по старому пути; кэш не используется.

7. Риски, ограничения, открытые вопросы

  • Память кэша. Расходы НКД для большой выборки клиентов могут давать заметный объём строк. Решение: формировать кэш помесячно или по клиенту в случае превышения порога; альтернатива — выгружать ПоПартиям и ПоРегистраторам только в момент короткого замыкания (lazy load).
  • Согласованность периода. Типовая РасходыПоНКДПоВидуОбращаемости использует НачалоГода(Дата) и КонецДня(Дата). Это однозначно вычисляется по дате документа, поэтому ключ Дата в кэше = КонецДня(Дата). Дата документа Портфеля и Дата документа УК на одном дне совпадают (см. цепочку через СтрокаДокументов.Дата). Если в обработке появятся разные даты в одной строке выборки — поведение должно остаться корректным за счёт ключа в кэше.
  • Виды обращаемости. В перечислении есть значения вне пары обращающиеся / необращающиеся (например, СделкаРЕПО). Они намеренно не включены в NDFL_RDU_ИнвестиционныйВычетУКД; в нашем массовом запросе фильтр ВидыОбращаемости снимается на стороне SQL, а на 1С при коротком замыкании применяется тот же массив видов, который пришёл в перехват. Поведение остаётся идентичным типовому.
  • Расширение VTB_NDFL_Exchange. В нём нет перехвата РасходыПоНКДПоВидуОбращаемости (только модули обмена), конфликта по &Вместо не будет. Тем не менее перед внедрением — формальная проверка Расширения/VTB_NDFL_Exchange/Documents/НачислениеНДФЛПоУправляющейКомпании/Ext/ObjectModule.bsl на отсутствие соприкосновений.
  • Защёлка vs модульная переменная. В модуле менеджера нет Перем. Использование хранения в ПараметрыСеанса.ОбщиеЗначения даёт нужную область видимости. Ключевое требование - явная очистка кэша в перехвате РассчитатьНДФЛ в блоках «после вызова» и «Исключение».
  • Срез по ЗначенияПараметровПортфеля внутри запроса привязан к КонецПериода = КонецДня(Дата). На массиве клиентов это всё ещё один срез на дату (через виртуальную таблицу), поэтому SQL получает один проход — как и в типовом варианте.

8. Выводы и порядок реализации

  1. Шаг 1 (документ УК, модуль менеджера, NDFL_RDU). Добавить функции NDFL_RDU_КлючКэшаНКД, NDFL_RDU_РазложитьПарыПоДате, NDFL_RDU_СтрокиПоКлиенту, NDFL_RDU_РасходыПоНКДПоКлиентамИДате (текст массового запроса), NDFL_RDU_ПолучитьРасходыПоНКДПоКлиентам. Юнит-тестировать на 3 клиентах.
  2. Шаг 2 (документ УК, модуль менеджера, NDFL_RDU). Перехват &Вместо("РасходыПоНКДПоВидуОбращаемости") с коротким замыканием + методы установки/получения внешнего кэша через защёлку (повторное использование на сеанс). Прогон сценария A (форма документа): результат идентичен типовому.
  3. Шаг 3 (документ УК, модуль объекта, NDFL_RDU). Перехват &Вместо("РассчитатьНДФЛ") с приёмом ПараметрыРасчетаВнешн и пробросом СтруктураКэшНКД в защёлку.
  4. Шаг 4 (обработка ФормированиеНачисленийНДФЛ). Сбор МассивПарКлиентДата, вызов NDFL_RDU_ПолучитьРасходыПоНКДПоКлиентам, проброс СтруктураКэшНКД в СоздатьНачислениеНДФЛПоУК.

Главное преимущество. Архитектура остаётся «расширенческой» — NDFL_RDU добавляет два независимых публичных контракта:
  • Контракт A — новый экспортный метод модуля менеджера документа УК NDFL_RDU_ПолучитьРасходыПоНКДПоКлиентам (вызывает обработка для подготовки кэша);
  • Контракт B — единственный новый опциональный параметр у РассчитатьНДФЛ документа УК (обработка кладёт целостный кэш по всем клиентам и датам выборки).
Плюс защёлка NDFL_RDU_УстановитьВнешнийКэшНКДРасходов для проброса значения из перехвата РассчитатьНДФЛ в перехват РасходыПоНКДПоВидуОбращаемости модуля менеджера. Любой текущий вызов РассчитатьНДФЛ() в системе по-прежнему работает один-в-один как до доработки; оптимизация активируется только при явной передаче кэша обработкой.
