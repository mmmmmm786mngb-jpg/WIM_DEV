SBB_Broker / ACCOUNTING-10214

Варианты исправления: сумма 1000000 читается как договор

Четыре способа закрыть сегодняшний возврат. Вариант 1 ломает уже найденный договор. Рекомендация: вариант 2.
Рекомендация Делать вариант 2. Если семь цифр - это живой договор, платеж уже сегодня проводится как обычный ввод и письмо «Невыясненный платеж!» не уходит. Вариант 1 эту ветку отключает: вывод по сумме и номеру может не найтись, и тот же платеж станет невыясненным. Вариант 3 в общую функцию не выносить. Вариант 4 не закрывает повторение.

1. Что нельзя сломать

Сбой в одном месте: ОбработкаРеестровНРДAPIРКО.СформироватьВводДС сначала ищет семь цифр подряд и, найдя 1000000, не включает возврат. Функция НомерДоговораИзНазначенияПлатежа общая. Ее вызывают не только возвраты:

  • ОбработкаРеестровНРДAPIРКО.СформироватьВводДС - сегодняшний путь;
  • ОбработкаРеестровНРДAPIРКО.СуществующийВводДС - поиск уже созданного ввода по коду договора;
  • ОбработкаРеестровНРД - старая загрузка реестров;
  • ОбработкаОтветовНКЦ - код клиента из назначения ответа НКЦ.

Обычный ввод клиента по-прежнему должен находить настоящий ДОФР из семи цифр. Тесты 10214 (81.60RUB, 73.85RUB), июньский эталон (23,000,000.00) и запасной поиск номера п/п из ACCOUNTING-15493 должны остаться как есть.

2. Вариант 1. Сначала слово «Возврат» ломает найденный договор

Где: только СформироватьВводДС

Если назначение после СокрЛП начинается с «Возврат», сразу идти в ДополнитьДанныеДляЗаполненияПоВозврату. Семь цифр из этого текста как номер договора не читать. Договор, клиент, портфель и р/счет возьмутся из найденного вывода, как в июне. 

// СформироватьВводДС, вместо текущей развилки
Назначение = СокрЛП(СтрокаДанных.НазначениеПлатежа);
ЭтоВозвратДС = СтрНайти(Назначение, "Возврат") = 1;
Если ЭтоВозвратДС Тогда
    НомерДоговора = "";
    ЗаполнитьДаннымиПоУмолчанию = Истина;
    Уведомить("Получен возврат от банка получателя!");
Иначе
    НомерДоговора = РаботаСПоручениямиПовтИсп.НомерДоговораИзНазначенияПлатежа(Назначение);
    ЗаполнитьДаннымиПоУмолчанию = ПустаяСтрока(НомерДоговора);
КонецЕсли;

Плюсы

  • Совпадает с постановкой 10214: первое слово «Возврат».
  • Одна процедура, общий парсер договора не меняется. НКЦ и старые реестры не задеты.
  • Сегодняшний 1000000RUB, тесты 81.60 и июнь 23,000,000.00 попадают в одну ветку.
  • Запасной поиск п/п из 15493 начинает работать: первая группа цифр здесь 43867.

Минусы

  • Любой ввод, у которого текст начинается с «Возврат», пойдет как возврат вывода, даже если дальше в тексте есть живой номер ДОФР.
  • Если вывод по сумме и номеру п/п не найдется, документ все равно останется на невыясненных, но уже после попытки сценария возврата.
  • Пробел или другой текст перед словом «Возврат» по-прежнему не считается возвратом. Поэтому нужен СокрЛП.
Проверка веток: так делать нельзя Сейчас семь цифр важнее слова «Возврат». Если первая семерка - код существующего договора, портфель найден, договор не закрыт и имя плательщика совпало, клиент и договор записываются, для рубля ОписаниеОшибки = Неопределено, письмо о невыясненном не отправляется. Флажок «Возврат ДС» при этом не ставится: это обычный ввод. Вариант 1 эту ветку пропускает. Дальше ДополнитьДанныеДляЗаполненияПоВозврату ищет вывод по сумме и номеру п/п. Если вывода нет, клиент и договор остаются пустыми, НовыйВводДС уходит в значения по умолчанию и шлет «Невыясненный платеж!». Платеж, который раньше определялся, станет невыясненным.

Парсер берет только первую семерку. Текст «Возврат ... 1000000RUB ... договор 1003084» и сегодня не доходит до 1003084: первой находится сумма. Регрессия варианта 1 - другой случай: «Возврат ... договор 1006427», где 1006427 существует.

3. Вариант 2. Возврат, только если клиент по семи цифрам не найден рекомендую

Где: СформироватьВводДС, после НайтиПоКоду

Порядок поиска договора не менять. Если семь цифр нашлись, но контрагента с таким кодом нет и текст начинается с «Возврат», не создавать обычный невыясненный ввод, а вызвать ДополнитьДанныеДляЗаполненияПоВозврату. Сегодня 1000000 клиента не найдет, ветка возврата включится. Если в тексте возврата стоит настоящий код существующего клиента, останется обычный ввод.

Плюсы

  • Точечно закрывает сегодняшний кейс: ложный договор не существует.
  • Обычный ввод с живым ДОФР не ломается, даже если назначение начинается с «Возврат».
  • Общая функция не меняется.

Минусы

  • Если в возврате банка когда-нибудь окажется чужой или старый, но существующий код из семи цифр раньше суммы, возврат снова не включится. Флажок «Возврат ДС» не встанет.
  • Логика длиннее: развилка уже после поиска клиента, а не в начале процедуры.
  • Расходится с исходной формулировкой 10214 «первое слово Возврат решает все».

Имеет смысл, если бэк-офис подтвердит вводы, которые одновременно начинаются с «Возврат» и содержат действующий номер договора. По известным банковским шаблонам таких текстов нет.

Вставка в СформироватьВводДС сразу после Клиент = Справочники.Контрагенты.НайтиПоКоду(НомерДоговора) и до проверки банковского счета плательщика. Возврат обязателен, иначе процедура пойдет дальше и создаст второй ввод.

// Семь цифр нашлись, контрагента с этим кодом нет.
// Так бывает, когда банк пишет сумму без разделителей: "1000000RUB" читается как договор.
// Если клиент найден, блок пропускается и дальше работает прежнее заполнение ввода.
НазначениеПлатежа = СокрЛП(СтрокаДанных.НазначениеПлатежа);
Если Не ЗначениеЗаполнено(Клиент)
    И СтрНайти(НазначениеПлатежа, "Возврат") = 1 Тогда

    Уведомить("Получен возврат от банка получателя!");
    ДополнитьДанныеДляЗаполненияПоВозврату(СтрокаДанных, ДанныеДляЗаполнения);

    ОбрабатыватьПоЭтапам = Истина;
    Стр.Документ = Документы.ОперацииДС.НовыйВводДС(
        ДанныеДляЗаполнения, ЭтотОбъект, ОписаниеОшибки, ОбрабатыватьПоЭтапам).Ссылка;
    Возврат;

КонецЕсли;

4. Вариант 3. Не считать сумму номером договора только как дополнение

Где: копия строки перед вызовом парсера, не в общей функции

Перед поиском договора вырезать из назначения фрагмент суммы: «на сумму 1000000RUB», «1000000RUB», сумму с запятыми. Семь цифр, которые равны целой части СтрокаДанных.Сумма, не считать договором. Для сегодняшнего текста договор не найдется, сработает уже существующая проверка «Возврат».

Плюсы

  • Бьет прямо в дефект: 1000000 - это сумма платежа, а не ДОФР.
  • Остальной текст можно разбирать по-старому. Настоящий номер из семи цифр в другом месте строки сохранится.

Минусы

  • В общую НомерДоговораИзНазначенияПлатежа так делать нельзя: ее читают НКЦ, старый реестр НРД и поиск существующего ввода. Назначение вида «договор 1006427 RUB» может потерять договор.
  • Банки пишут сумму по-разному: 1000000RUB, 1 000 000, 23,000,000.00, 73.85RUB. Правила вырезания придется держать списком.
  • Следующая ложная семерка (номер счета, кусок даты, другой код) снова сломает возврат. Вариант 1 от формата суммы не зависит.
  • Если сумма вывода случайно совпадет с чужим номером ДОФР, этот номер будет пропущен.
Не делать это единственной правкой общей функции Если когда-нибудь фильтровать сумму, только на копии назначения внутри СформироватьВводДС. Общий модуль оставить как есть.

5. Вариант 4. Код не менять, править документ вручную не как решение

Где: уже созданная операция 260921-00076

Найти вывод по п/п 43867, вручную проставить клиенту договор, флажок «Возврат ДС» и основание. Либо пометить ввод на удаление и загрузить файл еще раз после правки данных. Так уже делали в декабре 2024, до задачи 15493: в регистре подменяли номер п/п и перегружали файл.

Плюсы

  • Сегодняшний платеж можно закрыть без выкладки.
  • Нет риска регресса обычных вводов.

Минусы

  • Следующая целая сумма без разделителей снова уйдет на невыясненные.
  • Письмо робота уже ушло. Этапы, Перевод ДС и п/п сами не соберутся, пока документ не похож на возврат 10214.
  • Ручная подмена номера в регистре - обход, не правило. Его как раз заменили задачей 15493.

6. Сравнение

Вариант Сегодняшний 1000000RUB Обычный ввод с живым ДОФР Объем правки Оценка
1. Сначала «Возврат» Возврат, договор из вывода Ломается, если текст начинается с «Возврат» и первая семерка - живой договор Одна процедура Не делать
2. Возврат, если клиент не найден Возврат, потому что клиента 1000000 нет Живой договор остается обычным вводом Одна процедура, ветка длиннее Делать
3. Вырезать сумму из текста Сработает для этого формата Риск, если править общую функцию Парсер и список форматов банков Не как основная правка
4. Вручную Только этот документ Не задевает Без кода Разово, не вместо правки

7. Что выбрать и как проверить

Выкладка: вариант 2. Сначала оставить поиск семи цифр и заполнение клиента, как сейчас. В возврат уходить только если портфель по этому коду не собрался и назначение начинается с «Возврат». Живой договор не переводить в ветку вывода.

Вариант 1 не выкладывать: он отменяет уже успешное определение договора. Вариант 3 в общую функцию не выносить. Вариант 4 годится, чтобы руками довести уже созданную 260921-00076, пока правки нет в базе.

Проверка после варианта 2
  1. Назначение как сегодня, 1000000RUB: флажок «Возврат ДС», основание = вывод п/п 43867, договор 1003084.
  2. XML 10214: 81.60RUB на действующий договор и 73.85RUB на закрытый, портфель с «_».
  3. Июньский текст 23,000,000.00 без изменений.
  4. Кейс 15493: в файле НРД один номер п/п, в назначении другой. Запасной поиск по первой группе цифр жив.
  5. Обычный ввод без слова «Возврат» в начале, с настоящим ДОФР из семи цифр: договор находится по-старому.
